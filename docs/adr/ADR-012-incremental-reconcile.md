# ADR-012: 카운터 증분 대조 — 바뀐 쌍만 짧은 주기로 대조해 C의 규모 한계를 없앤다

- 상태: **제안 — 측정 전 고정**(2026-10-18). §1~§6은 측정 전에 커밋한다. 결과·판정은 측정 뒤 §7 이후에 쓴다.
- 명세: `docs/plans/2026-10-18/adr-012-incremental-reconcile/requirement-spec.md` · 기록: 같은 폴더 `log.md`
- 선행: **ADR-009**(A+C 기본값 · `PairRepair` 복구 규칙 · S3e 효과 측정) · **ADR-011**(§6.4 — C의 규모 한계 · 측정 조건 §8)
- 후행: **ADR-013**(Kafka + 읽기 복제본 대조 — 이 ADR의 M0~M3 결과를 기준선으로 쓴다) · ADR-015(홀드 만료) · ADR-020(오픈 폭주)

## 1. 문제

ADR-009가 기본으로 켠 C(앱 안 대조)는 60초마다 **열린 회차의 쿼터 행 전체와 홀드·확정 예약 전체**를 훑는다. 한 바퀴의 일은 쌓인 행 수에 비례한다. ADR-011의 30분 S4c4200(고정 도착률 4,200건/s)에서:

- 쌍이 약 400만을 넘자 바퀴가 14~26초로 길어졌다(마지막 766만 쌍 25.4초). 그동안 DB CPU 사용률은 338~384%(한도 400%)였다.
- 후반 서버형 느린 초가 대조 끔 1개 ↔ 켬 12개였다(1회씩 — 켜고 끄기로 확정). 1초 p99 최대는 50.6 → 97.6ms였다.
- 7분 회차의 비용 판정(ADR-009 §7.7 — p99 +2.2%)은 이 증가를 보지 못했다.

ADR-015(홀드 만료)·ADR-020(오픈 폭주)처럼 행이 쌓이는 장시간·대량 측정 전에 대조 구조를 고쳐야 한다. 그대로 두면 그 측정의 꼬리에 C 바퀴가 섞인다.

## 2. 선택지 — 모델과 고른 것

### 2.1 모델

| 모델 | 바뀐 쌍을 아는 방법 | 탐지를 읽는 곳 | 원본 DB 부하 | 이 ADR |
|---|---|---|---|---|
| M0 C(지금) | 없음 — 매번 전체 훑기 | 원본 | 큼(행 수에 비례) | 기준선 |
| M1 F(별도 대조 앱, ADR-009 후보) | 없음 — 전체 훑기 | 원본 | 큼 — 앱 커넥션 풀만 분리 | 1단계 — 병목 가름 |
| M2 앱 안 증분 | ⓐ 앱 메모리 집합 · ⓑ 쿼터 행 `updated_at`(DB 트리거) · ⓒ 쿼터 행 `updated_at`(앱 문장) | 원본 | 작음(바뀐 쌍 수에 비례) | **구현·비교** |
| M3 외부 앱 증분 | `updated_at`(ⓑ·ⓒ — 메모리 집합은 다른 프로세스가 볼 수 없다) | 원본(.158 → .164) | 작음 — 앱 CPU·풀도 분리 | **구현·비교** |
| M4 Kafka + 읽기 복제본 | Kafka 메시지(CDC 또는 아웃박스) | **복제본** | 복구만 | **ADR-013**으로 나눔 |

공통: 증분은 **탐지만 새로** 한다. 어긋나 보인 쌍은 기존 `PairRepair`(쿼터 행 잠금 → 다시 세기 → 다르면 덮어씀 · 맞으면 오탐 기록)로만 고친다. **전체 훑기 안전망** = 기존 C를 1시간 주기로 남긴다 — 증분이 못 보는 어긋남(앱 밖 DB 수정 · 앱 재시작으로 잃은 집합 · 행 삭제)을 잡는다.

### 2.2 고른 것과 고르지 않은 것 (인터뷰 2026-10-18 — 원문 명세 §0)

| 질문 | 고른 것 | 고르지 않은 것 | 이유·대가 |
|---|---|---|---|
| 해결 방향 | **바뀐 쌍만 대조(증분)** + 긴 주기 안전망 | 청크 사이 쉬기(바퀴를 늘려 펴기) · 주기만 늘리기 · DB CPU 늘리기(스케일업) · 앱 분리만(F) | 쉬기·주기·스케일업은 비용이 여전히 행 수에 비례해 늦출 뿐이다. 앱 분리는 DB 부하를 옮기지 않는다 — 1단계(M1)로 확인한다 |
| 범위 | **F 측정 + 증분 구현(M0~M3)** · M4는 ADR-013 | F 측정만 · 한 ADR에 M4까지 · M4 중심 | M4는 인프라(복제본·Kafka)가 커서 결정 주기를 짧게 나눴다 |
| ADR 번호 | **012(증분)·013(Kafka·복제본)으로 끼움** — 기존 012~018 → 014~020(8차) | 019 뒤에 붙임 | 이 결정이 ADR-014(운영 중 매수 방식 전환)·015(홀드 만료)의 입력이다 |
| 바뀐 쌍을 아는 방법 | **세 가지 모두 비교** — 메모리 집합 · updated_at 트리거 · updated_at 앱 문장 | 하나만 | 메모리는 DB 비용 0이지만 앱 밖 변경·재시작에 약하다. 트리거는 앱 밖 변경도 남지만 가장 뜨거운 행에 트리거 비용. 앱 문장은 트리거 비용이 없지만 고칠 곳이 많고 앱 밖 변경을 못 본다 |
| 증분 주기 | **1초·5초 측정으로 비교** | 1초 고정 · 5초 고정 | 1초는 탐지가 빠르고, 5초는 호출이 적다 |
| 안전망 | **기존 C를 1시간 주기로** | 청크 사이 쉬기 · 안전망 없음 | 30분 측정 안에 돌지 않게 — 안전망 한 바퀴의 비용은 따로 잰다 |
| 구현 위치 | **앱 안 + 별도 폴더 외부 앱**(독립 앱 · Dockerfile · compose — .158) | 외부 앱만 · 앱 안만 | 외부 앱은 앱 CPU·풀을 나눈다. DB CPU는 그대로 .164다(DB 부하 분산은 ADR-013) |
| 측정 서버 | **.164 Linux 유지** | .9로 옮김 · .164 + .9 | ADR-011 수치와 직접 비교한다 |
| 성공 기준 | **대조 끔(noc)과 같은 꼬리** + ADR-009 효과 기준 | C 대비 절반 · 측정 뒤 정함 | §5 |
| 효과 측정(S3e) | **증분 전부 × 3 · 증분 + 안전망 합산** | 고른 기본값만 · 증분만으로 판정 · 주입을 앱 경로로 바꿈 | 주입은 DB를 직접 고친다(`lib.sh:541-543`) — 메모리 집합은 주입을 못 보고, updated_at은 D(행 삭제)를 못 본다. 탐지 경로별 시간을 따로 기록한다 |
| 기본값 | **성공 시 교체**(손잡이로 옛 방식 복귀) | 손잡이만 | §5 고르는 규칙 |
| 둘 이상 통과 | **비용 낮은 쪽, 같으면 메모리 집합** | 같으면 updated_at | 메모리 집합은 스키마·외부 의존이 없다 |
| 반복 | **×3, 단계 나눔** | ×2 · ×1 후 일부만 ×3 | 범위 판정에 3회가 필요하다(ADR-009·010 규칙) |
| 여러 앱 인스턴스 | **범위 밖**(대조는 1대에서만) | 앱 2대 | 메모리 집합은 다른 인스턴스의 변경을 못 본다 — 한계로 적는다 |
| stakes | **높음** | 중간 | 동시성·카운터 정합성·마이그레이션 V9·기본값 교체 |

## 3. 실험

모든 측정: S4c4200 · tmpfs 12g(DB 14g) · 2g + 세대형 ZGC · L4 · 측정기 두 곳 · 주 k6 v2.2.0 · 캠페인 전 k6 PC 점검 1행(ADR-011 §8). 30분 측정은 `--seed-schedules 800 --s4c-steps 60 --pg-tmpfs-size 12`. 같은 캠페인 안에서 조건 순서를 회차마다 바꾼다.

| 단계 | 셀 | 회차 | 묻는 것 |
|---|---|---|---|
| 1 | noc(A + 정리, C 끔) · M0 C · M1 F | 30분 × 3 | C 바퀴가 길어진 것이 앱 풀 대기인가 DB CPU인가 · noc 기준선 3회 |
| 2 | noc · M0 · M2ⓐ·ⓑ·ⓒ × {1초, 5초} | 30분 × 3 | 증분이 noc와 같은 꼬리인가 · 방식별 비용 |
| 2' | M3(.158) ⓑ·ⓒ 중 2단계에서 통과한 것 × {1초, 5초} | 30분 × 3 | 외부 앱이 앱 안과 같은가 · 앱 CPU 분리 효과 |
| 효과 | M2·M3 각 셀(안전망 60초) | S3e × 3 | 주입 어긋남을 끝까지 고치는가 · 탐지 경로별 시간 |

- 효과 셀은 안전망 주기를 60초(지금 C 주기)로 둔다. 1시간이면 S3e 안에 돌지 않아 메모리 집합이 판정 불가가 된다. 판정은 '증분 + 안전망 합산', 탐지 시간은 기록 출처(증분·안전망)별로 나눈다.
- '후반' = 정상 구간 15~30분(ADR-011에서 C 튐이 시작된 시점 — 약 400만 쌍).

## 4. 가설 (측정 전 고정)

| # | 가설 | 틀렸다고 판정할 관측 |
|---|------|------------------|
| R1 | C 바퀴의 꼬리는 DB CPU 때문이다 — F(자기 풀)도 후반 서버형 느린 초가 C와 범위가 겹친다 | F 3회 후반 서버형 느린 초 범위가 C보다 낮고 겹치지 않는다(→ 앱 풀 대기가 주원인) |
| R2 | 증분 대조 한 바퀴의 시간은 쌓인 행 수와 무관하다 | 증분 셀에서 정상 구간 첫 5분 대비 마지막 5분의 바퀴 시간 중앙값이 2배 이상 |
| R3 | 증분(M2·M3)의 후반 꼬리는 noc와 같다 | 후반 서버형 느린 초 또는 1초 p99 최대의 3회 범위가 noc 3회 범위와 겹치지 않는다(위로) |
| R4 | 증분 + 안전망은 ADR-009 효과 기준을 지킨다 | S3e 3회 중 하나라도 끝에 주입 쌍 cnt ≠ 실제 · 오탐 복구 > 0 · 정합성 위반 > 0 · 주입 원인 아닌 틱 실패 > 0 |
| R5 | 트리거 방식의 선점 비용은 허용선 안이다 | ⓑ의 정상 구간 선점 p99 중앙값이 noc 대비 +10% 초과(ADR-009 허용선) |
| R6 | 메모리 집합은 앱 경로 변경을, updated_at 트리거는 값 변경 주입(L1·L2·H)을 증분 경로로 잡는다 | 효과 셀에서 해당 경로 탐지가 0건(기록 출처 기준) |

## 5. 성공 기준 · 고르는 규칙 (측정 전 고정)

**성공(셀마다)**: R3 성립 + R4 성립 + 정상 구간 선점 p99 중앙값이 noc 대비 +10% 이하 + 30분 3회 모두 상태 ok(안정성 4항목 — ADR-010 §9).

**고르는 규칙(기본값)** — 성공한 셀 중에서:
1. 1초 p99 최대 · 정상 구간 선점 p99 · 정상 구간 DB CPU 평균 세 지표에서 **다른 후보보다 범위 비겹침으로 낮은 지표가 있고, 범위 비겹침으로 높은 지표가 없는 후보**를 고른다.
2. 그런 후보가 없거나 둘 이상이면(범위가 겹치면) **메모리 집합 > updated_at 앱 문장 > updated_at 트리거** 순(스키마·외부 의존이 적은 쪽) · 같은 방식 안에서는 **1초**(탐지가 빠름) · 앱 안 > 외부 앱(배포 단위가 하나 적음).
3. 성공한 셀이 없으면 기본값은 A+C 그대로 둔다. 원인을 적고 ADR-013으로 넘긴다.

기본값 교체 = A + 고른 증분(주기) + 안전망 C 1시간. 옛 방식(C 60초)은 설정 손잡이로 되돌릴 수 있게 둔다.

## 6. 받아들이는 한계 (측정 전)

1. **메모리 집합은 앱 밖 변경·앱 재시작·다른 인스턴스의 변경을 못 본다.** 안전망(1시간)이 잡을 때까지 그 쌍은 틀린 채 남는다(최대 약 1시간 + 바퀴).
2. **updated_at은 행 삭제(D 갈래 — 쿼터 행 없음)를 못 본다.** 행 없음 쌍은 안전망 또는 새 홀드의 행 없음 탐지가 잡는다(설계에서 정한다).
3. 외부 앱(M3)도 탐지 쿼리는 .164 DB에서 돈다 — DB CPU는 나뉘지 않는다(ADR-013 복제본에서 다룬다).
4. 효과 셀은 안전망 60초 — 운영 기본값(1시간)과 다르다. 운영 주기에서의 최악 탐지 시간은 측정이 아니라 계산(주기 + 바퀴)으로 적는다.
5. 여러 앱 인스턴스는 범위 밖(ADR-009 '대조는 1대에서만' 제약 유지).
6. 측정은 S4c4200 tmpfs 한 부하와 S3e뿐이다 — 디스크 부하에서의 증분 비용은 재지 않는다.
