  - **주제** — 1차 답에 사용자 제안 "이걸 이전 카운터 계열을 이번에 업데이트 형태로 바꾸는 작업으로 전환 주제를 바꾸는게 더 좋지않을까?" → 확인 질문에 **"ADR-009 → ADR-012 구성 전환만"**. 원래 질문(advisory-try/none → counter 계열 · V6 백필 · 롤링)은 **이번 범위 밖 — NEXT 후보로 남긴다**. 1차에서 고른 범위(매수 방식 전환 · 증분 스키마 운영 중 적용 · 대조 방식 C → 증분)는 이 주제 안의 '증분 스키마 운영 중 적용 + C → 증분'으로 합친다.

  - **롤링 재현** — 앱 2대 동시 기동(같은 DB · 옛 이미지 + 새 이미지 · 부하 나눔 · 중간에 옛 앱을 내림).
  - **기존 데이터 규모** — 두 규모 모두 → **측정 규모 답**: 조합 둘로 줄여 × 3회 = 24회 — 큰 규모(30분 S4c급 수백만 쌍)는 S4c(초당 4,200 선점 — 인덱스 생성·마이그레이션의 쓰기 차단 · 다운타임 · 꼬리), 작은 규모는 S3e(어긋남 주입 흐름 — 전환 구간 정합·복구). 선택지 4 × 2조합 × 3회.
  - **전환 중 부하** — S3e + S4c 둘 다(위 조합).
  - **앱 배치** — .164에 둘 다(DB와 같은 서버).
  - **브랜치** — `feat/adr-012-incremental-reconcile` 끝에서 `feat/adr-013-config-cutover`를 만든다(PR #11 병합 뒤 main 대상 PR).

## 1. 목표·대상 (필수)

seat-reservation-lab에서, **ADR-009 구성(main 93dd610a — counter-upsert-precheck + A + C 60초 전체 대조 · `updated_at` 없음)으로 운영 중인 서비스에 기존 데이터가 쌓인 상태에서 ADR-012 구성(V9 트리거 `updated_at` + V10 + 앱 안 증분 1초 + 안전망 + split)으로 롤링 배포 전환하는 절차** 5가지(①~④ + ⑤ = ④ 적용판 + ② 소유 — 재합의 2026-10-23)를 앱 2대 혼재 측정(S4c 1,200초 큰 규모 · S3e 작은 규모 × 3회 = 30회)으로 비교하고, 고르는 기준(정합 > 다운타임 > 단계 수)으로 기본 전환 절차 하나를 정해 `docs/adr/ADR-013-*.md`(제목·문제·선택지 갱신 · 결과 · 결정)에 기록하면 끝. 필요한 코드(운영 중 적용판 마이그레이션·그림자 모드 손잡이·하네스 전환 오케스트레이션)는 이 브랜치에서 구현한다.

## 2. 경계·불변식 (필수)

- **기존 마이그레이션 파일 무변경**: V1~V10(기본·선택 위치 전부) 내용·버전 그대로 — 이미 적용된 DB의 Flyway 체크섬이 깨지지 않는다. 운영 중 적용판은 별도 위치·버전·절차.
- **새 손잡이를 지정하지 않으면 ADR-012 기본값 동작·렌더가 그대로다**(명세 ADR-012 §10 K1~K10 회귀 없음 — 기존 테스트 green). 하네스의 과거 조건(ADR-001~012)도 실효값 그대로.
- **카운터 정합**: 어느 전환 절차든 전환이 끝난 뒤 끝 불일치 0(대조가 고침)이어야 '완료' — 전환 구간 중 한도 초과·부당 거절은 **측정 대상**(숨기지 않는다 · 쌍 단위 기록).
- **옛 앱 = 93dd610a 이미지 그대로**(코드 무변경 — 실제 운영 중인 옛 버전 흉내). 새 앱이 V9·V10을 적용한 DB에서 옛 앱이 계속 돈다는 것이 load-bearing 가정 1.
- **대조는 한 프로세스에서만**(ADR-009 제약): 혼재 구간에 옛 C와 새 증분·안전망이 동시에 돌면 그 사실과 영향을 기록한다(절차마다 누가 대조를 쥐는지 설계에서 고정).
- **거부된 기동은 스키마를 바꾸지 않는다**(ADR-012 RC-1·RC-8 범위 그대로).
- 측정 전 고정: 가설·성공 기준·고르는 규칙은 측정 전에 ADR에 커밋(ADR-012 방식).
