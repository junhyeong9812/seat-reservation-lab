# 01. Seat Reservation Lab

## 결정 기록 (ADR)

> **현재 진행: ADR-005** 1인 매수 제한(1인 2매) — 사용자 단위 직렬화. 기본 선점 방식은 ADR-003 결정(3b) 위에서.

| ADR | 결정 (2026-10-06 확정) | 이유 | 문서 |
|-----|----------------------|------|------|
| **ADR-003** 같은 좌석 동시 선점 — 락 방식 | **3b `pessimistic-nowait`**(`SELECT … FOR NO KEY UPDATE NOWAIT`)를 선점 기본 방식으로 한다. 이미 잠긴 좌석은 기다리지 않고 바로 409 | 기다리는 동안 사용자가 다른 좌석을 고를 기회를 잃으면 안 된다는 것이 우선이다(즉시 실패형). 즉시 실패형은 3b와 7 `redis-nx` 둘인데, redis-nx는 Redis 운영, Redis↔DB 부분 실패(키만 남는 경우 — 미측정), 홀드 TTL 동안 남는 키 관리가 따른다. 그래서 **아직 Redis는 쓰지 않고** DB만으로 끝나는 3b를 고른다. 대가: 이긴 쪽이 롤백하거나(1인 2매 초과 등) 만료 배치·확정이 좌석 행 락을 쥔 동안 들어온 요청도 409 — 사용자가 다시 눌러야 한다 | [ADR-003](docs/adr/ADR-003-same-seat-contention.md) §8 |
| **ADR-004** 임계 구역 길이와 락 보유 시간 | **느린 작업(외부 호출)은 좌석 판정 뒤에 둔다.** 진 쪽이 느린 작업을 하지 않게, 기다리는 동안 커넥션을 쥐지 않게 한다. 느린 작업을 트랜잭션 밖으로 빼는 것(선점 커밋 → 외부 호출 → 실패 시 보상)은 ADR-007·008에서 판정 | 지연 20ms에서 즉시 실패형(3b·7)과 커넥션 밖 대기형(1a·8)만 경합 영향 최저점(K=100)을 지켰다. 진 쪽도 지연을 다 쓰는 방식(2·5·4)은 최저점보다 약 35~42% 낮았다 | [ADR-004](docs/adr/ADR-004-critical-section-hold-time.md) §6 |

3. 좌석을 선점해놓고 결제 없이 떠났다면?
4. 오픈 정각에 20만 명이 동시에 들어왔다면?
5. 화면엔 빈자리였는데 누르니 이미 팔렸다면?
6. 결제는 성공했는데 그 사이 선점이 만료됐다면?
7. 테스트가 끝났을 때 좌석 상태는 정말 정확한가?

## Architecture

```
Client
  ↓
Queue Server (Redis Sorted Set)
  ↓ 입장 토큰 (초당 N명)
Reservation API
 ├── Seat Map Query ── Cache
 └── Seat Hold ─────── Redis SET NX EX / DB Lock
        ↓
      Hold Expiry ── 만료 시 좌석 반환
        ↓
Payment (→ 02. Payment Consistency Lab)
  ↓
Reservation Confirm

Verification Batch → Seat state consistency check
```
