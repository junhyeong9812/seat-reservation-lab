## 1. 문제

> 주제의 일반형(사용자 2026-10-23): **트래픽을 받기 위해 기능·구조를 더할 때, 운영 중인 데이터와 스키마를 어떻게 안전하게 전환하나** — 이 ADR은 ADR-012의 대조 구성 전환을 사례로 그 질문(운영 중 스키마 변경의 락 · 옛·새 버전 혼재 중 정합 · 작업 소유권(대조) 넘김 · 되돌리기 경로)에 답한다. 결정 절에 사례 결론과 함께 일반화한 전환 원칙을 적는다.

ADR-012가 기본값을 바꿨다 — 옛 구성(main 93dd610a: counter-upsert-precheck + A(만료 감소) + C(앱 안 60초 전체 대조) · 쿼터 행에 `updated_at` 없음)에서 새 구성(V9: `user_hold_quota.updated_at` 열·인덱스·트리거 + V10 기록 테이블 + 앱 안 증분 대조 1초 + 안전망 + split 탐지)으로. 이미 데이터가 쌓인 운영 DB에서 이 전환을 하면:

1. **스키마 적용이 쓰기를 막는다**: V9의 `CREATE INDEX`는 쿼터 테이블 쓰기를 인덱스가 다 만들어질 때까지 막는다(ADR-012 §7-13 ①). 행이 수백만이면 그동안 선점이 멈춘다. `ADD COLUMN … DEFAULT now()`는 빠른 기본값이라 행을 다시 쓰지 않는다(PostgreSQL 11+ — 설계에서 확인).
2. **롤링 배포 동안 옛 앱과 새 앱이 섞여 돈다**: 옛 앱은 C를 돌리고 `updated_at`을 모른다. 새 앱은 증분·안전망을 돌린다. 대조가 두 프로세스에서 겹치거나(ADR-009 '대조는 한 곳에서만' 제약), 옛 앱의 쓰기를 증분이 못 보는 구간이 생길 수 있다(V9 트리거가 있으면 옛 앱 쓰기도 `updated_at`을 남긴다 — ⓑ 방식을 고른 이유).
3. **되돌리기가 어렵다**: V9·V10이 적용된 DB는 위치를 빼는 것만으로 옛 구성으로 못 돌아간다(ADR-012 명세 §10 K3 — method=trigger 표시만으로 C 복귀).

> 정정(2026-10-23 — 설계 §4.5): 1-1의 '쓰기를 막는다'는 부족하다 — Flyway V9는 트랜잭션 하나라 `ALTER TABLE`의 `ACCESS EXCLUSIVE`를 인덱스 생성이 끝날 때까지 쥔다 → **읽기까지** 막는다.

### 4.1 기존 데이터 만들기

**사실**(실코드): S4c(초당 4,200 선점 고부하 — `s4-throughput.js:60-62`)는 요청마다 좌석 = 반복 번호 + 1 · 사용자 = 400000 + 반복 번호라 **쌍마다 홀드 1건 · cnt 1**이다. 회차 = ⌈좌석 ÷ 1만⌉. 시드(`LoadtestDataService.reset`)는 회차 ≤ 1,000(회차당 1만 석) · 회차 `starts_at` 2026-12-31(열린 회차). S3e(어긋남 주입 효과 측정 부하)는 회차 1개 · 좌석 1만 · 입장 20만 명(사용자마다 세션 1번)이다.

| 규모 | 고른 것 | 고르지 않은 것 | 이유 |
|---|---|---|---|
| 큰 규모(S4c) | **SQL 대량 시드(회차마다 새 DB)** — 옛 앱의 `/internal/reset`(회차 1,000 · 1만 석) 뒤 하네스가 psql로 회차 501~999에 쿼터 행 + 홀드 + 좌석 `HELD`를 쌍마다 1건씩(약 499만 쌍 — 사용자 = 20,000,000 + i, cnt 1, `held_at` = 시드 시각, `expires_at` = 시드 시각 + 3시간) 넣고 `VACUUM ANALYZE`. k6 S4c는 그대로 회차 1~500(1,200초 — 약 492만 요청)을 쓴다. 회차 1,000은 한도 탐침 전용 | (가) 옛 앱으로 S4c 30분을 미리 돌리기(회차마다) · (나) 한 번 쌓아 DB 파일을 보관 → 회차마다 복원 | (가) 회차마다 30분 + 전환 회차 → 12회에 약 6시간이 더 든다. (나) 보관한 홀드의 `expires_at`이 복원 시각보다 과거가 되면 회차 첫 만료 틱이 수백만 건을 지운다(교란) — 시각을 옮기려면 홀드 테이블 전체를 다시 쓴다. SQL 시드는 정합 검사가 결정적이다(기대 = 쌍마다 cnt 1 = 실제 1 · 시드 직후 끝 불일치 0을 SQL로 확인). 물리 모양(삽입 순서 = PK 순 · 쿼터 행 INSERT만)은 S4c 실제 흐름과 같다 — 다른 점(좌석 행 갱신 dead tuple · autovacuum 이력)은 `VACUUM ANALYZE`로 줄이고, **보정 1회**(옛 앱 S4c 30분으로 쌓은 DB 대 SQL 시드 DB의 테이블·인덱스 크기 · C 한 바퀴 시간 · V9 `CREATE INDEX` 시간)를 측정 전에 log에 남긴다 |
| 작은 규모(S3e) | **회차 안에서 옛 앱이 쌓는다**(사전 시드 없음 — 단독(옛) 구간 360초 동안 S3e 흐름 그대로) | SQL 시드 · 사전 부하 | S3e의 쌍은 수만 개라 V9 비용은 작다 — 이 조합의 질문은 '섞인 구간에 생긴 어긋남을 누가 언제 고치나'(정합·복구)다. 실제 흐름(선점·확정·이탈·만료)이 만든 데이터 위에서 바꾸는 것이 가장 현실적이고 비용이 없다 |

- 전환 시각의 쌍 수(큰 규모): 시드 499만 + 단독(옛) 300초 약 113만 ≈ **약 610만 쌍**(ADR-011에서 C 바퀴가 길어진 400만 쌍을 넘는다). 회차 끝 약 990만 쌍 — tmpfs(DB를 메모리에 둔 측정 조건) 크기는 ADR-012의 12g로 모자랄 수 있다 `[구현 검증]`.
- 미리 쌓은 홀드는 회차 안에 만료되지 않는다(3시간) — 큰 규모는 ADR-011·012 S4c처럼 측정 중 만료가 없다(만료 경로의 섞임은 S3e가 본다 · TTL(홀드 유효 시간) 5분).

- **시드 조건(설계 선검증 DS-16)**: 큰 규모의 시드 쌍과 S4c 쌍은 모두 **열린 회차 100%**(회차 `starts_at` 2026-12-31) · **cnt 1** · **확정 예약 없음** · 측정 중 만료 없음이다. 결과 해석 주의 — ① C 바퀴·안전망·증분의 열린 회차 걸러내기가 쿼터 행 전부를 대상으로 남긴다(마감 회차 제외 0 — 마감 회차가 섞인 운영 DB는 바퀴가 더 짧을 수 있다) ② 확정 예약이 없어 탐지 쿼리의 예약 쪽 비용이 운영보다 작다 ③ 한도(2)에 닿은 쌍이 없어 주 부하에는 한도 판정이 없다(§4.7.1 탐침이 필요한 이유) ④ 기존 행의 `updated_at`이 모두 같은 값 m이다(§4.11). 결과를 운영 규모로 옮길 때 이 네 가지를 붙인다.
- **보정 1회의 허용 범위(설계 선검증 DS-12)**: 위 보정의 두 시간 비(SQL 시드 DB ÷ 옛 앱 S4c 30분 DB) — C 한 바퀴 시간 비 · V9 `CREATE INDEX` 시간 비 — 가 **둘 다 [0.8, 1.25]** 안이면 SQL 시드를 그대로 쓴다. 밖이면 **측정하지 않는다**: ① 원인(테이블·인덱스 크기 · dead tuple · 물리 순서)을 log에 남기고 시드를 고쳐(좌석 행 갱신 재현 · 삽입 순서 등) 다시 시드한 뒤 보정을 1회 다시 한다(재시드 1회) ② 두 번째도 밖이면 측정하지 않고 **task 05(하네스 구현)로 되돌린다** — 시드 방식을 다시 설계한다((가) 옛 앱 S4c 사전 부하로 바꾸기 포함). 범위 밖의 비를 '해석에 붙여 진행'하는 길은 두지 않는다 — 측정 뒤가 아니라 측정 전에 정해야 하는 판단이라 사용자 결정 칸을 없앤다(§5 리뷰 S5-6). 테이블·인덱스 크기는 기록만 한다(문턱 없음). 보정 결과·판정은 측정 전 log 1행.

**넘김 조건 — 소유 공백 길이가 아니라 '옛 C 마지막 완료 바퀴 시작 ≥ 새 앱 첫 하한'(설계 선검증 DS-2)**: 초안의 '소유 공백 < 60초면 공백 동안의 변경이 첫 창 안에 든다'는 필요조건이 아니다 — 옛 C가 마지막으로 **끝낸** 바퀴가 언제 시작했는지가 빠져 있다. 옛 C 바퀴는 회차·쌍 순서로 훑으므로(93dd610a `CounterReconciler.runOnce` — `started_at` = 바퀴 시작 앱 시각) 바퀴 시작 S 앞에 생긴 어긋남은 그 바퀴가 본다. S 뒤의 변경은 그 바퀴가 이미 지나친 쌍이면 보지 못한다(옛 앱을 내리면 다음 바퀴가 없다). 새 앱 증분은 첫 하한 L* 뒤의 변경만 본다. 그래서 빈틈이 없으려면 **S ≥ L***이다:
- S = 옛 앱 `counter_reconcile_run` source `reconcile-app` 마지막 행(옛 앱을 내리기 전에 끝난 바퀴)의 `started_at` · L* = 새 앱 `counter_inc_gap` kind `restart` 행의 `to_at`(첫 하한), 단 §4.11의 m이 그보다 뒤면 m(V9 앞의 변경은 표시가 없어 증분이 못 본다 — ①). 두 시각은 같은 .164 시계다(앱 `Clock` 대 DB `now()` — 시계 차는 기록만).
- 못 넘긴 구간 [S, L*)의 길이(`owner-uncovered-s` — 0이면 넘김 성립)를 회차마다 기록하고, 그 구간에 쓰기가 있었는지(①은 옛 앱 내림 뒤 쓰기 없음 — [S, 옛 앱 내림)만 쓰기 구간)를 함께 남긴다. 무음 금지 — 회차 사유가 아니라 판정 자료다(S4c는 C 한 바퀴가 길어 ②·⑤에서 넘기지 못할 수 있다 — 그것이 재는 대상이다).
- **못 넘긴 몫은 안전망 전체 커서만 본다**(초안의 '최근 2시간 창'은 틀렸다): 안전망 최근 창은 기동 때 최대 id부터 시작하고(`SafetyNetReconciler.kt:178-186` · 첫 실행 `:271-276`), 최근 창 하한 B = id_at(T − 2시간)은 맞는 표본이 없으면 0이다(`:426-428`) — 새 앱이 뜬 뒤 2시간 동안은 늘 표본이 모자라 B = 0이고, 0은 커서보다 작아 최근 창을 **뒤로 넓히지 않는다**(건너뜀도 없다 — `sample_short`만 남는다). 그러니 기동 전에 만들어진 홀드·예약 id의 쌍(공백 동안 그림자 앱이 쓴 쌍 포함)은 전체 커서가 그 회차·쌍에 닿을 때까지 아무도 보지 않는다. 그 시간은 전체 커서 한 바퀴 시간(S4c 약 610만 쌍 — 회차 안에 못 닿을 수 있다)에 달렸다 — 못 넘긴 구간의 탐침·주입 쌍은 첫 복구 출처·시각으로 이를 드러낸다(§4.7.1).

**새 코드가 필요한 곳**: 없음(그림자 모드 자체는 — §4.4 N8 · §4.11 DS-1은 따로). 하네스가 슬롯별 `SPRING_APPLICATION_JSON`을 렌더한다(§4.6).

### 4.4 ④ 운영 중 적용판 — 쓰기를 막지 않는 V9와 Flyway 이력

**외부 근거**(PostgreSQL 16 · Flyway 11.7.2 — 이 저장소의 Flyway 버전은 Gradle 캐시 `org.flywaydb/flyway-core/11.7.2`로 확인):
- `ADD COLUMN … DEFAULT <비휘발>`: 기본값을 문장 시각에 한 번 계산해 카탈로그에 두고 **테이블을 다시 쓰지 않는다**(문서 예시가 바로 `DEFAULT now()`). 락은 `ALTER TABLE` 기본 `ACCESS EXCLUSIVE`(읽기·쓰기 모두와 충돌 — 순간이지만 앞 트랜잭션을 기다리는 동안 뒤 요청이 줄을 선다).
- `CREATE INDEX`(보통): `SHARE` — 쓰기(`ROW EXCLUSIVE`)를 막고 읽기는 허용. **`CONCURRENTLY`**: `SHARE UPDATE EXCLUSIVE` — 쓰기를 막지 않는다 · 트랜잭션 블록 안에서 못 돈다 · 표를 두 번 훑고 그 사이 기존 트랜잭션을 기다린다 · 실패하면 **INVALID 인덱스**가 남는다(질의에는 안 쓰이지만 갱신 비용은 든다 — 지우고 다시 하라).
- `CREATE TRIGGER`: `SHARE ROW EXCLUSIVE` — 쓰기와 충돌(순간).
- 락은 트랜잭션 끝까지 쥔다. → **지금 V9를 Flyway가 트랜잭션 하나로 돌리면**(Flyway 기본 = 스크립트마다 트랜잭션 하나) `ALTER TABLE`의 `ACCESS EXCLUSIVE`를 인덱스를 다 만들 때까지 쥔다 — **쓰기뿐 아니라 쿼터 행 읽기(precheck 조회 · C 탐지)까지 멈춘다**. §1-1의 '쓰기를 막는다'보다 넓다(열린 질문 1).
- Flyway: 스크립트별 설정 파일(`V…sql.conf`의 `executeInTransaction=false` — 커뮤니티판) · `skipExecutingMigrations`(실행 없이 이력만 기록 — 7.0 출시 글은 Teams 기능으로 소개, 지금 설정 문서에는 판 표시가 없다 · 11.7.2 jar의 `DbMigrate`에 이 설정 처리 문자열은 있고 판 확인 예외 참조는 보이지 않는다 → **판에서 실제로 되는지는 `[구현 검증]`**) · `baselineOnMigrate`는 **이력 테이블이 없는** 비어 있지 않은 스키마에만 적용된다(이 DB는 이력 V1~V7이 있다).

- **거부된 기동 불변식(ADR-012 RC-1·RC-8)과의 관계**: 적용판은 앱 기동이 아니라서 그 불변식의 대상이 아니다 — 대신 적용판 자체의 규칙 '**동치 확인 전에는 기록하지 않는다**'를 둔다. 단계 1~3만 하고 기록하지 않은 DB에 새 앱을 띄우면 Flyway가 V9를 다시 실행하려다 `ADD COLUMN`에서 실패하고 V9 트랜잭션이 롤백된다 — 스키마는 그대로(거부된 기동이 스키마를 바꾸지 않는다는 결과는 성립), 메시지만 Flyway의 SQL 오류다(열린 질문 6).
- **새 코드(최소 · 제안 — 이 건 + §4.11 DS-1 수정)**: `IncrementalSchemaCheck.readSchema`(`IncrementalSchemaCheck.kt:82-84`)의 인덱스 확인이 `pg_indexes` 이름만 본다 — CONCURRENTLY 실패로 남은 **INVALID 인덱스도 '있음'**으로 통과하고, 증분 창 조회가 매초 쿼터 테이블을 순차로 읽게 된다. 인덱스 확인에 `indisvalid AND indisready`를 더해 INVALID면 기동 실패(메시지: 지우고 다시 만들라). 정상 경로(Flyway V9)에서는 INVALID가 생기지 않으므로 K1~K10 동작은 같다 — blind 테스트 1개(INVALID 인덱스 DB → 거부 · 스키마 무변경)를 더한다.
  - **마이그레이션 앞 예측이 기존 INVALID를 덮지 않게(설계 선검증 DS-3)**: 위 확인을 `readSchema`에만 더하면 거부가 마이그레이션 **뒤**로 밀린다 — 마이그레이션 앞 게이트(`HoldStrategyMigrationGate` — `HoldStrategyStartupCheck.kt:53-58` — 예측 `:54-56` 뒤 `flyway.migrate()`)는 `afterLocations`로 내다본 스키마를 판정하는데 `afterLocations`가 `updatedAtIndex = updatedAtIndex || v9Trigger || v9Stmt`(`IncrementalSchemaCheck.kt:68-69`)로 '위치가 있으면 인덱스 있음'을 덮어 INVALID가 통과하고, 그 뒤 Flyway가 V10을 적용한 다음에야 `run`의 검사가 거부한다(거부된 기동이 스키마를 바꾼다 — RC-8 범위 위반). 그래서 `Schema`에 **인덱스 유효 여부를 따로 둔다**(`updatedAtIndexValid` — 인덱스가 없으면 뜻 없음). 규칙: DB에 인덱스가 **이미 있으면** 유효 여부는 DB 값 그대로(Flyway V9는 이미 있는 인덱스를 다시 만들지 못한다 — 위치가 덮지 않는다) · 없고 V9 위치가 닿으면 '유효'로 본다. `checkSchema`는 trigger·stmt 방식에서 `열 ∧ 인덱스 ∧ 유효`를 요구한다(메시지에 INVALID 인덱스 이름 · 지우고 다시 만드는 문장). → 게이트가 `migrate` 앞에서 거부한다.
  - **테스트 DB 상태 고정**(blind 테스트 입력): V1~V7 적용 + V9 객체(열·함수·트리거·인덱스) + **V9 이력 기록(success)** + **V10 미적용** + 인덱스 INVALID(`pg_index.indisvalid = false` — 테스트 superuser의 카탈로그 직접 갱신이 결정적이라 1순위 · CONCURRENTLY 취소로 만든 INVALID 재현은 스모크 1회). 기대: 기본 위치 새 앱 기동 거부(메시지에 인덱스 이름) · 그 뒤 V10 테이블 3개 없음 · Flyway 이력에 V10 행 없음 · 카탈로그 무변경. 같은 DB에서 인덱스를 지우고 다시 만들면 기동(V10만 적용).

**④의 되돌리기**: 기록 전이면 단계 역순(`DROP INDEX CONCURRENTLY` · `DROP TRIGGER` · `DROP FUNCTION` · `ALTER TABLE … DROP COLUMN` — 마지막은 순간 `ACCESS EXCLUSIVE`) — 옛 앱은 어느 단계에서도 그대로 돈다(task 02 가정 1). 기록 뒤에는 ③과 같다(아래 §4.7.4).

### 4.5 ①·③(·②)에서 Flyway가 트랜잭션 안에서 V9를 돌릴 때 — 재는 법

- 영향 예상(위 근거): 새 앱 Flyway가 `ALTER TABLE`에서 옛 앱의 열린 쿼터 트랜잭션을 기다리는 동안 뒤의 모든 쿼터 접근이 줄을 서고, 잡은 뒤에는 인덱스 생성이 끝날 때까지 쿼터 행 읽기·쓰기가 모두 멈춘다. 옛 앱의 선점은 쿼터 행에 닿으므로(precheck 조회 → upsert) **선점 전체가 멈추고** Hikari(앱 DB 커넥션 풀) 대기 → 요청 시한으로 번질 수 있다. 인덱스 대상 값은 기존 행 전부가 같은 `updated_at`(열 추가 시각)이다 — 생성 시간은 행 수(약 610만)에 비례 `[구현 검증]`.
- **재는 것**:
  1. **정지 초**(k6 주 부하 1초 구간 — 201이 0인 초)의 개수와 가장 긴 연속 길이 · 201 < 계획 도착률의 50%인 초(구간별 · §4.7.3).
  2. **락 대기 표본(새 — 촘촘한 표본)**: 전환 창 [T1 − 10초, 새 앱 lb 편입 + 30초](④는 적용판 시작 − 10초 ~ 끝 + 30초도) 동안 0.2초마다 `pg_stat_activity`(`wait_event_type = 'Lock'`인 세션 수 · `application_name` · `pg_blocking_pids(pid)` · `now() − query_start` 최대 · 문장 앞 60자)와 `pg_locks`(관계 = `user_hold_quota` · `granted` 별 모드 · 대기 수) → `timeline-migration-locks.jsonl`. 지금 0.5초 표본(`timeline-locks.jsonl` — lib.sh `db_sampler`)은 그대로 둔다.
  3. **마이그레이션 단계 시간**: Flyway 이력의 `execution_time`(V9 · V10) + 새 앱 로그의 Flyway 시작·끝 줄 시각 + 앱 기동 → health UP 시각. ④는 적용판 단계별 벽시계·재시도 횟수·`lock_timeout` 걸린 수 → `pre-apply.json`.
  4. 구간별 5xx · 502(lb) · 요청 시한 수 · 앱별 Hikari 대기(지금 표본 그대로 — 앱별로).
- 같은 측정을 ①에도 한다 — ①은 부하가 없을 때 V9를 돌리므로 락 대기는 0이고, 대신 중단 = 내리기 + V9·V10 + 기동이 정지 초로 보인다(S4c — S3e 중단은 가용성 탐침으로 · §4.7.3)(설계 선검증 DS-6).
- **추가 스모크 — 부하 중 옛 앱 + V9 적용(task 05 측정 앞 · 설계 선검증 DS-13)**: task 02 가정 스모크는 부하 없는 옛 앱만 봤다. 30회 전에 1회씩 두 경로를 본다 — (가) 옛 앱 S4c 부하(짧게 — 120초) 중 새 앱 기동으로 Flyway V9를 트랜잭션 안에서 적용(③ 경로) (나) 같은 부하 중 운영 중 적용판(④ 경로). 보는 것: 옛 앱이 표에 열이 더해진 뒤에도 오류 없이 도는가 — 서버 쪽 준비문(prepared statement)·캐시된 계획 무효화(PostgreSQL 오류 `cached plan must not change result type` — 열 추가로 결과 모양이 바뀐 `SELECT *`류 준비문) · 옛 앱 5xx · 옛 앱 로그 ERROR 줄 수 · 그 동안 선점 201률. 통과 = 그 오류 0 · 5xx는 V9 락 대기로 설명되는 것뿐(시각이 §4.5-2 표본의 대기 구간 안). 오류가 나오면 숨기지 않는다 — 그 자체가 절차 비교의 판정 자료(어느 경로에서 나는가)이므로 log에 남기고, 30회 측정이 그 오류로 회차 판정이 흔들리는지(회차 사유로 둘지) 측정 전에 정한다(task 04).

### 4.7 지표와 판정 자료

#### 4.7.1 한도 판정 — 결정적으로 세기

**사실**: 두 주 부하 모두 사용자마다 선점이 1건이다(S4c 반복마다 새 사용자 · S3 세션마다 새 사용자 — `s3-full-flow.js:55`). 한도(2)에 닿는 요청이 주 부하에 없으므로, 주 부하만으로는 한도 초과·부당 거절이 **생길 수가 없다** — '0건'이 판정 자료가 되지 못한다(그린 위장).

**고른 것 = 한도 탐침**(하네스 전용 회차 1개 — S4c는 회차 1,000 · S3e는 시드 회차를 2로 늘려 회차 2. 좌석·사용자를 탐침만 쓰므로 그 쌍의 실제 값을 하네스가 정확히 안다):

| 종류 | 순서(사용자 u는 탐침마다 새로) | 맞는 답 | 틀린 답 = 판정 자료 |
|---|---|---|---|
| H(카운터 > 실제) | 선점 1(201) → SQL `cnt = cnt + 1`(cnt 2 · 실제 1) → d초 뒤 선점 2 | 201 | 409 `HOLD_LIMIT_EXCEEDED` = **부당 거절** |
| L(카운터 < 실제) | 선점 1(201) → SQL `cnt = cnt − 1`(cnt 0 · 실제 1) → d초 뒤 선점 2 → 선점 3 | 선점 2 = 201 · 선점 3 = 409 `HOLD_LIMIT_EXCEEDED` | 선점 3 = 201(실제 3 > 2) = **한도 초과** |

- d ∈ {1, 5, 30, 75}초(증분 1초 · C 60초 + 바퀴를 가르는 값) × 종류 2 = 구간마다 8탐침, 구간 시작 + 30초부터. 구간은 단독(옛) · 전환 · 단독(새)(①의 중단 구간에는 탐침이 실패로 남는다 — '중단'으로 분류).
- **탐침 일정과 구간 분류(§5 리뷰 S5-11)**: 탐침 일정은 **계획 시각 기준**이다 — 다섯 절차가 같은 계획 칸(단독(옛) 칸 30초~ · 전환 칸 T1 + 30초~ · 단독(새) 칸 T2 + 30초~)에 같은 시각으로 탐침을 보낸다(실제 사건이 늦어도 일정을 옮기지 않는다). 탐침이 어느 구간에 드는지는 **실제 사건 시각**으로 정한다: 단독(옛) = [0, T1 첫 사건) · 전환 = [T1 첫 사건, 마지막 전환 사건(옛·그림자 앱 내림) 끝) · 단독(새) = 그 뒤 ~ k6 끝. **①만 다르다** — 중단 = [T1 첫 사건(옛 앱 lb 빼기), 새 앱 lb 편입) · 단독(새) = [새 앱 lb 편입, k6 끝). ①의 전환 칸 탐침 중 lb 편입 뒤에 주입된 것은 단독(새)로 센다. 주입·판정이 서로 다른 구간에 걸치면 경계 탐침(아래 DS-10)이다. 주입 SQL은 주입 시각(DB 시계 `clock_timestamp()`)을 `probe.jsonl`에 남기고, 응답 코드·시각을 함께 남긴다.
- **판정 요청 직후 스냅숏(설계 선검증 DS-5)**: 판정 요청(H의 선점 2 · L의 선점 2·3)의 응답을 받은 **바로 뒤** 하네스 세션(`seatlab-harness`)이 그 쌍의 `cnt`와 실제(그 쌍의 홀드 수 + 확정 예약 수 — 끝 검사 `v_counter_mismatch`와 같은 정의)를 한 문장으로 읽어 `probe.jsonl`에 남긴다(DB 시각 포함). 같은 문장이 그 쌍의 홀드 행 목록(id · `held_at`)도 읽는다 — `probe-nondeterministic` 원인 분류(§5.3)의 입력이다(§5 리뷰 S5-10). 맞음·틀림은 응답 코드 대 하네스가 아는 실제로 판정하고, 스냅숏은 ⓐ 탐침의 결정성(N10 — 스냅숏 실제 = 그 탐침의 201 누계) ⓑ 그 순간 카운터가 이미 고쳐졌는지(`cnt` = 실제)를 남긴다. 초안의 '끝에 대조'는 S3e에서 성립하지 않는다 — 탐침 홀드도 TTL 5분에 만료되어 끝 검사 때 홀드 수 ≠ 201 수다.
- **이름표 — 주입·판정 시각과 그 사이 소유 변경(설계 선검증 DS-10)**: 탐침마다 `inject_at`(주입 SQL의 DB `clock_timestamp()`) · `decide_sent_at`·`decide_done_at`(판정 요청 보낸·받은 PC 시각 → 시계 차로 서버 시각) · `owner_at_inject`·`owner_at_decide`(사건 기록으로 정한 그 시각의 대조 소유 구간) · `owner_changed`(= [`inject_at`, `decide_done_at`] 안에 lb 넣기·빼기 · 앱 내림·기동 · 새 앱 첫 증분 틱 · 옛 앱 마지막 C 바퀴 끝 중 하나라도 있음). **`owner_changed` 탐침은 경계 탐침**으로 따로 센다 — 구간별 집계에 넣지 않고 '경계 탐침' 표(절차 · 부하 · 넘어간 사건 · 종류 · d · 맞음/틀림)로 낸다(d = 75초 탐침이 구간 끝에 걸리는 것 등).
- 결과 = (절차, 부하, 구간, 대조 소유, 종류, d)별 맞음·틀림 수(경계 탐침 제외 — 위) + 그 쌍의 첫 복구(`counter_drift_log` repaired · 출처 · 시각 − 주입 시각).
- 고르지 않은 것: 주 부하만으로 DB 상태(실제 > max) 세기(위 사실 — 생길 수 없다) · k6 원시 기록으로 '409 시점의 실제 값'을 사후에 다시 만들기(만료·확정이 섞인 S3 흐름에서 실제 값을 시각별로 복원할 기록이 없다) · 앱에 판정 기록 추가(옛 앱은 코드 무변경).
- 탐침 쌍은 끝 검사와 따로 센다(§5 리뷰 S5-1 — 정정): 초안의 '끝 검사의 탐침 쌍 수 = 탐침의 한도 초과 결과 수'는 S3e에서 성립하지 않는다 — 탐침 홀드도 TTL(홀드 유효 시간) 5분에 만료되어 끝 검사 때 실제 3인 쌍이 남지 않는다(`run.sh` `ttl_s_of` base = 300 · S3 셀은 TTL + 유예를 기다린 뒤 끝 검사). 그래서 ⓐ **탐침 대조는 판정 요청 직후 스냅숏 기준**이다(위 DS-5 스냅숏 재사용 — N10과 같은 행): 탐침마다 마지막 판정 요청(L의 선점 3) 직후 스냅숏의 실제 > max(2)인 탐침 수 = 탐침의 '한도 초과' 결과 수(두 부하 공통). ⓑ **끝 검사의 한도 초과는 주 부하 쌍만** 센다 — `v_over_limit_users`에서 탐침 회차(S4c 회차 1,000 · S3e 회차 2)를 뺀 수 = 0. ⓒ S4c는 탐침 홀드가 회차 안에 만료되지 않으므로(S4c 앱 TTL 60분 — `config_of` s4) 끝 검사의 탐침 회차 한도 초과 쌍 수 = 탐침 '한도 초과' 결과 수도 함께 본다(보조 대조 — 지금 정의 유지).

**주 부하의 정합**(탐침 밖):
- S3e 주입 쌍: 지금 effect.json 그대로(쌍마다 첫 복구 출처·시각 · 끝 상태) + 주입 시각의 **대조 소유 구간** 이름표.
- **주입 밖 쌍의 복구**(`counter_drift_log` repaired · 주입·탐침 쌍 제외): 섞임이 스스로 어긋남을 만들었다는 증거다 — 출처·시각·구간별 수(기대 0 — 가설은 task 04).
- 같은 쌍을 두 출처가 본 경우(③·④): 늦은 쪽의 `false_positive` 기록 수(출처 쌍별).

#### 4.7.2 끝 불일치

- 수렴 창 뒤 `/internal/consistency`(마지막 새 앱): `v_counter_mismatch` · `v_over_limit_users`(탐침 분리) · 주입 쌍 끝 상태(`end_pairs`) · `updated_at` NULL 0 · 트리거 존재·활성 · 인덱스 `indisvalid` · V9·V10 이력 행(체크섬 · 설치 순번) → `end-check.json`. 큰 규모는 끝 검사 쿼리 하나에 수 분이 걸릴 수 있다(ADR-011 E3 — 시한 600초 그대로).
- 전환 경계 표본(작은 규모만): T2 직후 1회 끝 불일치 수(옛 앱이 내려간 순간 남은 어긋남 — 새 앱이 넘겨받는 양).
- **해석 — S4c 끝 불일치는 약한 자료(설계 선검증 DS-15 · task 04 고르는 규칙의 입력)**: S4c 주 부하는 어긋남을 스스로 만들지 않고(쌍마다 홀드 1건 · 만료·확정 없음 — §4.1 시드 조건) 시드도 불일치 0으로 시작하므로, S4c 끝 불일치 0은 '대조가 고쳤다'가 아니라 '고칠 것이 없었다'일 수 있다. **정합 판정 자료는 S4c 한도 탐침 · S3e 주입·탐침**(§4.7.1)이다. 끝 불일치 0은 '완료' 조건(명세 §2 카운터 정합)으로만 쓰고, 절차 사이 정합 순위에는 쓰지 않는다.

#### 4.7.3 선점 멈춤 · 꼬리

- 구간별(단독(옛) · 전환 · 단독(새) · 수렴): 정지 초 수 · 가장 긴 연속 정지 · 201 < 계획 도착률 50%인 초 · 선점 p99 · 1초 p99(99번째 백분위 응답 시간) 최대 · 서버형 느린 초(ADR-012 tail.py 정의 — 최대 응답 > 50ms이고 서버 쪽 대기가 원인인 초) · 5xx · 502 · 요청 시한. 구간 경계는 사건 기록의 실제 시각.
- **정지 초는 완료 시각 기준이다(설계 선검증 DS-6)**: 정의는 `wall.py`와 같다(k6 CSV `http_req_duration` 행 시각 = 응답 완료 시각 — `wall.py:11`). 막힌 요청은 풀릴 때 한꺼번에 완료되거나 요청 시한(코드 0)으로 늦게 완료되므로, 완료 시각 기준 정지 구간은 '아무것도 끝나지 않은 초'다 — 요청을 보낸 시각 기준(완료 − 지연 · 코드 0 행 제외 — `wall.py` 시작 초 정의)의 정지 구간도 함께 내고, 두 길이가 다르면 둘 다 적는다.
- **정지 초(201이 0인 초)는 S4c 지표다(DS-6)**: S3e 주 부하는 전환과 무관하게 201이 0이 된다 — 약 350초부터 이탈 홀드가 만료되는 약 610초까지 빈 좌석이 없다(`k6/ADR-009/scenarios/s3-full-flow.js:66` 주석 — 스모크 실측) → S3e 전환 구간(360~540초)과 겹친다. S4c는 요청마다 새 좌석이라(`s4-throughput.js:60-62`) 좌석 소진이 없다.
- **S3e 다운타임 = 가용성 탐침(DS-6)**: 탐침 회차(회차 2)의 **전용 좌석 범위**(한도 탐침과 겹치지 않게 — 좌석 5,001~10,000) · **전용 사용자**(요청마다 새 사용자 — 한도에 닿지 않는다)로 **일정 도착률 선점**(초당 2건 `[구현 검증]` · 별도 k6 프로세스 `constant-arrival-rate` · lb 경유 · k6 시작부터 끝까지)을 보낸다 → 요청마다 보낸 시각 · 완료 시각 · 코드 · 지연을 `avail-probe.jsonl`에, 구간별 **보낸 요청 수 · 응답 수 · 실패 수**(코드 0 · 5xx · 502 · 요청 시한)를 `avail-probe.json`에. S3e 다운타임 = 보낸 시각 기준 가장 긴 연속 실패 구간(+ 완료 시각 기준) · 실패 수. 초당 2건 × 약 1,030초 ≈ 2,060석이라 전용 범위 안에서 다시 쓰지 않는다. S4c에도 같은 탐침(회차 1,000의 전용 범위)을 띄워 정지 초와 맞대 본다(보조).
- 중단 시간(①): 첫 정지 초 ~ 201이 계획의 50%로 돌아온 첫 초(S4c) · 가용성 탐침의 연속 실패 구간(S3e — S4c도 함께)(DS-6).
- 대조 비용: 구간별 C 바퀴(`reconcile-app`) 시간 · 증분 틱 · 안전망 실행 DB 시간(ADR-012 기록 그대로) · ③·④의 겹친 구간 DB CPU(docker stats).

### 4.11 ADR-012 기본값 결함 수정 — 증분 첫 창과 후보 상한 (설계 선검증 DS-1)

**결함**(실코드): V9의 `ALTER TABLE user_hold_quota ADD COLUMN updated_at timestamptz NOT NULL DEFAULT now()`(트리거판 `V9__quota_updated_at_trigger.sql:3-4` · 문장판도 같은 문장)는 기존 행을 다시 쓰지 않고 값 하나(그 트랜잭션의 `now()`)를 카탈로그에 둔다 — **기존 행 전부가 같은 값 m을 갖는다**. ⓑⓒ 증분의 첫 하한은 기동 DB 시각 − `start-lookback` 60초(`IncrementalReconciler.kt:388-393`)이고 후보 조회에 상한이 없다(`:454` `updated_at >= ?` · `:141-147` 받은 쌍 전부를 한 틱에서 정렬·회차별 청크 탐지). 그래서 **V9 직후 60초 안에 뜬 증분 앱**(①·③의 새 앱 — 자기 Flyway가 V9를 막 적용했다 · ADR-012 K1을 기존 데이터 DB에 처음 배포하는 경우 전부)은 첫 틱이 기존 행 전부(S4c 전환 시각 약 610만 쌍)를 후보로 읽어 한 틱에 정렬·탐지한다 — 틱 시간·힙·DB 부하가 기존 데이터 크기에 비례한다. 기존 행은 'V9 뒤에 바뀐 쌍'이 아니므로 증분이 읽을 몫도 아니다(ADR-012 §2.3 재합의 행 — 보장 = 첫 하한 뒤에 시작한 트랜잭션의 변경). ②(T2 새 앱 — V9는 300초 전)·④·⑤(적용판 90초 — T1 기동보다 60초 넘게 앞)는 m이 첫 창 밖이라 이 결함을 밟지 않는다(§4.2 교란).

**① 첫 창에서 기존 행을 빼는 규칙 — 'V9 적용 시각'의 출처**

| 후보 | 출처 | 판단 |
|---|---|---|
| **(가) m = 카탈로그의 빠른 기본값** | `pg_attribute.attmissingval`(`user_hold_quota.updated_at` · `atthasmissing = true`일 때) — '행이 만들어진 뒤 비휘발 DEFAULT로 열을 더했을 때 그 행에 없는 열 대신 쓰는 값'([PostgreSQL 16 pg_attribute](https://www.postgresql.org/docs/16/catalog-pg-attribute.html) · [ALTER TABLE 주의 — 빠른 기본값](https://www.postgresql.org/docs/16/sql-altertable.html#SQL-ALTERTABLE-NOTES)) | **고른다** — 기존 행이 실제로 갖는 값 그 자체다. Flyway V9(트리거판·문장판)와 운영 중 적용판 단계 1이 같은 문장이라 출처가 하나다 · Flyway 이력과 무관(이력 없는 DB · 기록 방법 ①② 어느 쪽이든) · `timestamptz`라 시간대 변환이 없다 |
| (나) `flyway_schema_history` V9 행 `installed_on` | Flyway 이력 표 | 기각 — ⓐ 열이 시간대 없는 `timestamp`라 기록 세션 시간대에 묶인다 ⓑ m과 같은지가 이력 행을 V9와 같은 트랜잭션에 쓰는지에 달렸다(같으면 m과 같은 값 · 아니면 커밋 뒤 시각) ⓒ **운영 중 적용판은 이력 기록(단계 4)이 열 추가(단계 1)보다 수 분 늦다** — 'installed_on 뒤'를 하한으로 두면 그 사이 트리거가 남긴 옛 앱 쓰기 표시가 빠진다(트리거를 먼저 세운 뜻 — §4.4 순서 — 이 사라진다) ⓓ 이력 없이 객체만 있는 DB에서 출처가 없다 |
| (다) 적용판이 남기는 별도 시각 기록(새 표·주석) | 적용판 | 기각 — Flyway V9 경로에는 없어 출처가 둘이 되고, 새 표는 스키마 변경이다. 적용판은 m을 `pre-apply.json`에 **기록만** 한다(감사용 — 판정은 카탈로그 값) |

- **규칙**: 창 하한 L이 m 이하인 틱(첫 틱 · V9 뒤 `max-overlap` 안에서 하한이 m 앞으로 물러난 틱)은 후보 조회를 m 앞뒤 **두 인덱스 범위**로 나눠 `updated_at = m`인 행을 읽지 않는다 — 범위 A `L ≤ updated_at < m` · 범위 B `updated_at > m`. L > m이면 지금 문장 그대로(범위 하나). `updated_at <> m` 조건 하나로 쓰지 않는다 — 인덱스 범위 조건이 아니라 걸러내기라 m 묶음(기존 행 전부)을 인덱스·힙에서 다 훑는다(`[구현 검증]` §4.9-17).
- **왜 '하한 = max(기동 − start-lookback, V9 적용 시각)'(엄격한 하한)이 아닌가**: V9 트랜잭션보다 **먼저 시작해** V9의 `ACCESS EXCLUSIVE`를 기다린 뒤 쿼터 행을 고친 트랜잭션은 트리거 값 = 자기 시작 시각 < m이다(트리거 값 = 쓴 트랜잭션의 `now()` — ADR-012 §4.2.3). 그 시작이 기동 − 60초 뒤면 ADR-012 보장 안의 변경인데, 엄격한 하한은 이것을 빼서 ADR-012 보장을 좁힌다. **값이 m인 행만 빼면** 기존 행만 빠진다 — m과 같은 값을 쓰는 것은 V9 트랜잭션 자신뿐이고 V9는 행을 쓰지 않는다(다른 트랜잭션의 시작 시각이 마이크로초까지 m과 같을 가능성은 무시할 만하다 — 생기면 그 쌍은 안전망 몫). 사용자 결정('첫 하한 ≥ V9 적용 시각')의 뜻 — 기존 행을 첫 창에서 뺀다 — 을 보장을 좁히지 않는 꼴로 옮긴 것이다(메인 확인 필요 — 보고의 열린 질문).
- **읽는 때**: 증분 기동(`UpdatedAtCandidates.start` — 첫 하한과 같은 때)에 1회 읽어 메모리에 둔다. 그 뒤 표가 다시 쓰여 카탈로그 값이 사라져도 행에는 m이 물리로 남으므로 기억한 m으로 계속 뺀다.
- **출처가 없을 때**: `atthasmissing = false`(표를 다시 쓴 뒤 — `VACUUM FULL`·`CLUSTER`·표 재작성 `ALTER`는 빠른 기본값을 행에 써 넣고 카탈로그 값을 지운다 · 빈 표에 V9를 적용했을 때도 값이 없을 수 있다 — `[구현 검증]` §4.9-16) → 제외 없이 지금 문장 그대로 + 기동 WARN 1행 + `restart` 행 `detail`에 'm 없음'. 이때 기존 행이 첫 창 안에 드는 경우(재작성이 기동 60초 안 — 드묾)는 ②의 상한이 틱 하나의 비용을 묶는다.
- **기동 기록**: `restart` 행(`counter_inc_gap` — 스키마 무변경)의 `to_at` = 첫 하한(그대로) · `detail`에 m(또는 'm 없음')을 더한다(VARCHAR(200) 안).
- 방식별: ⓒ(문장)도 V9 문장판이 같은 `ADD COLUMN … DEFAULT now()`라 같은 규칙 — 앱 문장이 쓰는 `updated_at = now()`는 m과 다르다. ⓐ(메모리 집합)는 창이 없어 무관하다. 외부 대조 앱(Flyway 끔)도 같은 core 코드라 같은 규칙.

**② 후보 조회 상한 — 키셋 페이지(나눠 읽기)**

- 문장 2를 `… AND (updated_at, schedule_id, user_id) > (?, ?, ?) ORDER BY updated_at, schedule_id, user_id LIMIT ?`로 바꾼다(키셋 — 인덱스 `idx_user_hold_quota_updated_at` 순서 · 같은 `updated_at` 묶음 안은 PK 열 순서). 틱 안에서 쌍을 다시 정렬하므로(`IncrementalReconciler.kt:141`) 탐지·복구 순서는 지금과 같다.
- **새 손잡이** `seat.hold.counter-drift.reconcile.incremental.page-size`(틱 한 번이 읽는 후보 행 상한 · 기본 100,000 `[구현 검증]` §4.9-18 — 정상 운영에서는 걸리지 않는 값으로 고정). 한 틱 = 페이지 1개(①로 범위가 둘이면 A를 먼저 읽고, A가 상한보다 적으면 같은 틱에서 남은 몫만큼 B를 잇는다 — 행 수 합이 상한). 기동 검사는 양수만 본다(K1~K10 조합 규칙 무관).
- **이월과 하한 전진**(ADR-012 §4.2.3 '유실 없음' 근거가 깨지지 않게):
  - **페이지가 찼다**(덜 읽음): 하한 L을 **옮기지 않고** 키셋 위치 p(마지막 행 키)를 메모리에 두어 다음 틱이 p 뒤부터 잇는다. 그 틱의 문장 1이 낸 다음 하한 후보 `next_k`(지금 식 — `max(min(t, o) − 1초, t − max-overlap − 1초)` · `h > 0`이면 보수 하한)는 버리지 않고 **최솟값**으로 들고 간다(`pending = min(pending, next_k)`).
  - **페이지가 덜 찼다**(다 읽음): `L = max(min(pending, next_k), t₀ − max-overlap − 1초)` · p · pending · t₀를 비운다. **t₀ = 이 이어 읽기를 시작한 틱의 문장 1 시각**(이어 읽기가 없으면 t₀ = t — 지금 규칙과 같다)(재점검 NF-1 — 초안의 `t − max-overlap`(다 읽은 시각 기준)은 이어 읽기가 길면 그 사이 시작·커밋한 짧은 트랜잭션(≤ max-overlap)의 시작 시각을 창 밖으로 밀어 보장을 깼다).
  - 근거: 이어 읽는 동안 커밋한 트랜잭션 X의 표시(= X 시작 시각)가 p보다 앞이면 키셋은 X를 지나쳤다. X가 어느 틱 k의 문장 1 때 열려 있었다면 `o_k ≤ X 시작`이라 `next_k ≤ X 시작 − 1초`이고, 문장 1들 사이에서 시작해 커밋했다면 X 시작 > `t_k` ≥ `next_k`다. 어느 쪽이든 다 읽은 뒤 하한 ≤ X 시작이라 다음 창이 X를 다시 읽는다 — 지금 규칙의 '문장 1을 먼저 보낸다'를 틱 여러 개로 늘린 것이다.
  - **겹침 상한**: 하한은 `t₀ − max-overlap − 1초` 앞으로 가지 않는다 — pending이 그보다 앞이면(t₀ 앞에 시작해 오래 열린 트랜잭션 · 길이 > max-overlap) 잘리고 지금과 같은 `window_clamped` 행·지표·WARN(보장 밖 · 안전망 몫 — 무음 아님). t₀ 뒤에 시작한 트랜잭션은 길이와 무관하게 표시 ≥ t₀ > 잘린 하한이라 다음 창이 다시 읽는다 — 트랜잭션 ≤ max-overlap 조건부 보장이 이어 읽기 길이와 무관하게 유지된다(NF-1). 대가: 이어 읽기가 길수록 다음 창이 t₀ − 60초부터 다시 읽는다(수렴은 아래 — 이어 읽기 한 번마다 t₀가 앞으로 가므로 하한은 늘 전진한다).
  - **수렴**: 다 읽은 뒤 다시 읽는 양 ≈ 이어 읽기 동안 생긴 변경량이다. 페이지 상한 × 틱 빈도 > 쿼터 변경률(S4c 4,200건/s 대 100,000건/틱)이면 몇 틱 안에 정상 창으로 돌아온다. 이어 읽기가 `max-overlap` 넘게 이어지면 WARN.
  - **실패**: 문장 2가 실패하면 L · p · pending을 그대로 둔다(다음 틱이 같은 페이지를 다시 읽는다 — 지금 규칙 그대로). **재시작**: p · pending은 메모리 — 재시작하면 사라지고 새 첫 하한(①)부터 읽는다(지금 재시작 규칙 · `restart` 행 그대로).
- 새 지표: `…incremental.page_full`(찬 페이지 수 — 카운터) · `…incremental.carry_ticks`(이어 읽기 한 번이 이어진 틱 수 — 끝날 때 분포). 틱 기록 `pairs_scanned`는 그대로 그 틱 후보 수. 지표는 처음 쓸 때 등록(ADR-012 §4.2.6 등록 시점 규칙).

**③ 빠지는 몫 = 안전망 몫**: 첫 창에서 빠지는 것은 값이 m인 행 — V9 앞에 마지막으로 바뀐 기존 쌍(표시가 없다) — 이다. 이 쌍들의 어긋남(전환 전부터 있던 것 · V9 앞 옛 앱 쓰기가 만든 것)은 **증분 보장 밖 = 안전망 몫**이다(ADR-012 §2.3 재합의 행 '첫 하한 앞의 변경은 안전망 몫'과 같은 자리 · 혼재 구간(③·④)에서는 그동안 옛 C도 본다). 안전망이 그 쌍에 닿는 경로는 **전체 커서뿐**이다(최근 창은 기동 때 최대 id부터 — `SafetyNetReconciler.kt:178-186` · §4.3 DS-2). 수정 전에는 첫 틱이 기존 행을 다 읽어 '우연한 전체 대조'가 됐다 — 수정 뒤 기존 쌍의 어긋남을 잡는 시간은 안전망 전체 바퀴 시간이 된다. 이 차이는 숨기지 않는다: 탐침·주입 쌍의 첫 복구 출처·시각(§4.7.1)과 N4 못 넘긴 구간으로 드러난다.

**④ 새 지표(모든 절차 · 새 앱마다 — 판정 자료)**: 첫 틱 후보 수(첫 `inc-*` 행 `pairs_scanned`) · 첫 틱 시간(같은 행 `finished_at − started_at` · 지표 `…incremental.tick` 최대) · **힙 최대**(기동 → 첫 틱 끝 + 60초 동안 — GC 로그 `/dev/shm/gc.log`의 수집 전 힙 최대 + `jvm.memory.used{area=heap}` 10초 표본 최대 — H4가 내리기 직전에 받는다) · m과 첫 하한(`restart` 행) · `page_full` · 이어 읽기 틱 수. 기대: 다섯 절차 모두 첫 틱 후보 수 = 기동 − 60초 뒤 바뀐 쌍 수(≪ 기존 쌍 수) — 절차 사이 크기가 기존 데이터에 비례하지 않음으로 '첫 틱 전체 훑기' 교란이 없어졌음을 확인한다(측정 전 고정).

### 5.4 성공 기준 (절차마다)

**성공** = P9(전환 뒤 정합) 성립 + P10(안정성 — 6회 ok) 성립 + 다운타임 지표 D1·D2(§5.5)가 유효 3회 모두 계산됨 + 캠페인 유효 조건(P7 · P8) 성립. **판정 불가인 성공·유효 가설이 하나라도 있으면 그 절차는 성공으로 세지 않는다**(ADR-012 §6 방식). 설명 가설(P1~P6 · P11 · P12)의 성립·반증·판정 불가는 성공에 쓰지 않는다.

| 정합 | **전환이 만든 손해 0**(아래 비교식 — P9 (자)) · 단독(새) 탐침(d ≥ 30초) 틀림 0 · 소유 공백 탐침 미복구 0 · S3e 주입 쌍 끝 100% 복구 · J3 대상 주입 쌍 첫 복구 기록 100% · 끝 불일치 0 · 오탐 복구 0 · 주 부하 한도 초과 0 · 스키마 끝 상태 맞음(P9 (가)~(차)) | J1~J3(§5.5 1단) — 단독(옛) 대비 초과 틀림 · 복구 시간으로 순위 |

- 결과 표에 '무중단' 이름표를 단다: 유효 3회 모두 D1 = 0 이고 D2 = 0인 절차(기록 — 성공·순위와 무관).
- ADR-010 §9 안정성 4항목 중 ③(에러·코드 0)은 전환 회차에 그대로 쓰지 않는다 — 중단·락 대기 오류는 다운타임 자료다. 그 대신 단독(옛) 기준 창의 오류 0을 회차 유효 조건으로 둔다(§5.3). ④(메모리 추세)는 앱 생애가 300~900초로 짧아 기록만 한다.

**규칙**(성공한 절차만 후보 — §5.4):
0. 후보가 0개면 규칙 4 · 1개면 그것을 고른다.
1. **정합 단**: 후보 X는, 다른 후보 Y가 J1~J3 중 하나 이상에서 X보다 범위 비겹침으로 낮고 어느 J에서도 범위 비겹침으로 높지 않으면 **빠진다**. 남은 후보가 1개면 고른다. 빠지는 관계가 돌고 돌아 아무도 남지 않으면 **순환에 든 후보만 남긴다**(§5 리뷰 S5-12 — 'Y가 X를 뺀다'를 Y → X 화살표로 둔 그래프에서 화살표 순환 위에 있는 후보만 남기고, 순환 밖에서 빠지기만 한 후보는 뺀다 · 남은 후보끼리는 이 단의 동률로 다음 단에 넘긴다. 초안의 '아무도 빼지 않는다'는 순환 밖에서 분명히 빠진 후보까지 되살렸다). 두 후보 사이 순환은 생기지 않는다(X가 Y를 빼려면 어떤 J에서 낮아야 하고, 그러면 Y는 그 J에서 X보다 높아 X를 뺄 수 없다) — 순환은 셋 이상에서 범위 비교가 이행적이지 않을 때만 생긴다.
2. **다운타임 단**: 남은 후보에 같은 규칙을 먼저 멈춤(D1·D2), 다음 꼬리(D3)로 차례로 적용한다 — 각 차례 뒤 1개면 고른다. 멈춤을 꼬리보다 앞에 두는 이유: 명세 원문 순서('선점 멈춤 시간·꼬리')이고, 멈춤은 요청이 끝나지 않거나 실패하는 것이라 느려짐보다 크다.
3. **단계 수 단**: 남은 후보 중 K가 가장 작은 것을 고른다 — K와 그 동률 처리가 모두 고정값이라 이 단에서 늘 하나로 정해진다(①·③ 동률은 되돌리기 추가 중단으로 ③).
4. **아무것도 성공하지 못하면**(또는 P7·P8로 캠페인이 무효면): 기본 전환 절차를 **고르지 않는다** — §7 결정 = '고르지 않음' + 절차별 실패 항목(P9 어느 항목 · P10 어느 회차 · 판정 불가 사유) + 원인 후보. 실패 모양을 보고 새 절차·수정을 고르는 것은 측정 뒤 결정임을 밝히고 사용자가 정하며 NEXT 후보로 남긴다. ADR-012 기본값(새 DB 기본 구성)은 이 결과로 바꾸지 않는다 — 이 ADR은 기존 데이터 DB의 전환 절차만 정한다.

- **동률**: 한 단에서 아무도 빠지지 않으면(모든 범위가 겹치거나 0 [0–0]끼리) 그 단은 동률이고 다음 단으로 넘어간다. 마지막 단(K)은 동률이 없다.
- **왜 비율(J1·J2)인가**: 절차마다 판정 탐침 수가 다르다 — ①의 전환 탐침은 '중단'으로 빠지고 ②·⑤는 T2 뒤 그림자 앱 내림 사건에 걸린 경계 탐침이 생긴다. 수로 세면 탐침이 많이 남은 절차가 불리하다. **왜 같은 회차 단독(옛)을 빼나**(S5-2): 옛 C 바퀴 위상·길이가 회차마다 달라 단독(옛) 틀림 비율이 회차마다 흔들린다 — 같은 회차의 기준을 빼면 그 흔들림이 절차 비교에서 빠지고, 값이 사용자 결정의 뜻('전환이 단독(옛)에 더한 틀림')과 같아진다.
- **왜 d = 1초를 빼나**: 두 구성 모두의 약속 밖이다(옛 C 60초 · 새 증분 '주기 + 10초' — ADR-012 R4) · ADR-012 §8.6 ⓑ 1초의 DB 직접 주입 복구 최대가 1.0초 = d라 맞음·틀림이 우연에 가깝다(기록만 — P6 · P8의 d = 1은 옛 C 단독이라 쓴다).
- **왜 J3에서 행 삭제(D)와 270초 차례를 빼나**: D는 모든 절차에서 안전망·만료 복구 몫(ADR-012 §8.6 — 21~40초)이라 최대값을 덮어 절차 차이를 가린다. 270초 차례는 단독(옛)이라 다섯 절차가 같은 구성이다. 둘 다 성공 기준(P9 (나) 끝 100% 복구)에는 든다.
- **정합 자료**: S4c 탐침(J1) + S3e 탐침(J2) + S3e 주입(J3 — DS-15). S4c 끝 불일치는 쓰지 않는다(§5.4).
- **소유 공백(N4 — `owner-uncovered-s`)은 강제도 순위 지표도 아니고 기록이다(P5 — 판정 자료로는 결과 해석에만 쓴다)**. 근거 ① 결과가 따로 잰다 — 소유 공백이 실제로 안 고쳐진 어긋남을 냈다면 P9 (아)(못 넘긴 구간 [S, L*)에 주입된 탐침 — **경계 탐침 포함** — 의 수렴 창 끝 미복구)·(다)(끝 불일치)·(나)(주입 쌍 복구)에 나타난다. 원인 지표를 결과 지표 옆에 한 번 더 세면 같은 손해를 두 번 센다. (§5 리뷰 S5-3 — 정정: 초안은 'J1·J2·J3에 이미 나타난다'고 했지만, 공백을 넘나드는 탐침은 거의 모두 `owner_changed` 경계 탐침이라 J1·J2 비율에서 빠지고 J3은 S3e 450·630초 주입만 본다 — 공백의 손해가 판정 밖에 남았다. 그래서 P9 (아)를 실패 기준에 더했다.) ② 값이 절차 설계로 정해진다 — ①은 늘 > 0 · ③④는 늘 0(P5 예측)이라 순위에 쓰면 측정이 아니라 설계가 고른다 ③ S4c 주 부하는 스스로 어긋남을 만들지 않아(§4.1) 공백이 있어도 손해가 없을 수 있다 — 공백 길이만으로 정합 손해를 말할 수 없다. 대신 P9 반증 쌍이 [S, L*) 안에 있으면 결과 문서에 원인을 '소유 공백'으로 적는다(무음 금지).
- 원인 귀속 비교(§4.2 참고 표)는 고르는 근거로 쓰지 않는다(DS-7).

### 5.6 받아들이는 한계 (측정 전)

1. **시드 조건(DS-16 — §4.1)**: 큰 규모의 시드·S4c 쌍은 열린 회차 100% · cnt 1 · 확정 예약 없음 · 측정 중 만료 없음 · 기존 행의 `updated_at`이 모두 m. 운영 DB(마감 회차가 섞임 · 확정 예약 있음)에서는 C 바퀴·안전망 전체 커서가 더 짧고 탐지 쿼리 예약 쪽 비용은 더 크다. 한도에 닿은 쌍이 없어 주 부하에는 한도 판정이 없다(탐침이 대신한다).
2. **단일 서버**: .164 한 대에 DB · 앱 2대 · lb · 탐침이 함께 돈다 — 앱 사이·앱↔DB 네트워크 지연이 없고, 혼재 구간에만 앱 자원이 두 배라 CPU 경합이 운영과 다를 수 있다(§4.10 #3).
3. **옛 앱 1대 · 새 앱 1대**: 운영의 N대 롤링(혼재 비율이 단계마다 바뀜 · 옛 앱 여러 대 중 C를 쥔 1대가 언제 내려가는가)을 재현하지 않는다. 소유 공백(N4)·겹침(③④)은 1번씩만 생긴다.
4. **시각표 고정**: T1·T2(S4c 300·600초 · S3e 360·540초)와 혼재 길이가 다섯 절차에 같다 — ②·⑤ 전환 구간의 '옛 C 몫' 틀림(J1·J2)은 혼재 길이에 비례하고, 운영에서 혼재를 줄이면 줄어든다. 옛 C 마지막 바퀴 위상은 회차마다 우연이라 N4가 생길지는 3회로 다 보지 못한다.
5. **탐침 해상도**: 구간마다 8탐침(d ≥ 5초는 6) · 3회 — 틀림 비율의 격자가 1/6이다. 드문 틀림(< 5%)은 0으로 보일 수 있다. 전환 손해 비교(P9 (자) — 3회 모두의 T > 3회 모든 O)는 이 격자에서 **큰 손해만** 잡는다(예: O [0.33–0.5]이면 T가 3회 모두 ≥ 0.67이어야 반증) — 작은 손해는 J1·J2 순위로만 드러난다. 경계 탐침을 빼면 남은 탐침의 d 구성이 O와 T 사이에 달라질 수 있다(전환 칸 끝의 d = 75초가 경계로 빠지기 쉽다) — 비율에 그 치우침이 섞인다(d별 판정 수를 결과 표에 함께 낸다)(§5 리뷰 S5-2).
6. **다운타임 해상도**: S4c 정지 초는 1초 격자 · 완료 시각 기준 — 1초보다 짧은 멈춤과 '느려졌지만 끝난' 요청은 정지 초가 아니다(꼬리 D3 · 지연으로만 보인다). S3e 가용성 탐침은 0.5초 간격 · **실패만** 센다 — 요청 시한 안에 풀린 차단은 실패가 아니다(지연은 `avail-probe.jsonl`에 기록).
7. **수렴 창 < 안전망 전체 바퀴**: 못 넘긴 구간 [S, L*)의 몫은 안전망 전체 커서만 본다(§4.3). 끝 검사 전 수렴 창(S4c 180초 · S3e 322초)과 T2 뒤 시간 안에 전체 커서가 그 쌍에 닿지 못하면 끝 불일치로 나타나 그 절차가 실패한다 — 운영(언젠가 고쳐짐)보다 엄격한 쪽이다. 전체 커서 한 바퀴 시간은 S4c 990만 쌍 끝에서 ADR-012 2단계(30분에 3바퀴 — §8.5)보다 길 수 있고, 탐침 회차(1,000)가 커서 순서의 어디에 있느냐에도 달렸다.
8. **S4c 끝 불일치는 약한 자료**(DS-15) — 문턱으로만 쓴다.
9. **보정 1회 · SQL 시드**: 물리 모양(좌석 행 갱신 dead tuple · autovacuum 이력)이 실제 흐름과 다르다 — 보정 비가 [0.8, 1.25] 안이어도 운영 규모로 옮길 때 ±25%의 해석 주의가 남는다.
10. **주입·탐침은 흉내다**: SQL로 카운터를 틀어 만든 어긋남이고 실제 버그의 모양을 다 담지 않는다(ADR-012 §7-5). 앱 경로 주입(AH·AL·AE)은 옛 앱에 없어 쓰지 않는다.
11. **되돌리기 경로는 재지 않는다**(§4.7.4 표 고정) — 단계 수 단의 동률 처리에만 쓴다.
12. **원인 귀속은 참고뿐**(DS-7): 절차 사이 차이가 어느 요소(V9 적용 방식 · 대조 소유 · 앱 기동 횟수)에서 왔는지는 판정하지 않는다.
13. **고정값 중 일부는 보수적 선택**(§5.1): 보정 상한 25% · N6b 여유 1초 · 탐침 초당 2건 · P7의 1.5배 · health 시한 300초 · 가용성 탐침 요청 시한 5초 · VU 20(§5 리뷰 S5-8) · 최소 판정 탐침 수(§5.4 — 계획의 절반 · N만 1)(§5 리뷰 S5-4) — 측정 뒤 바꾸지 않는다.
14. **tmpfs**(DB를 메모리에 둔 측정 조건): 디스크 DB에서 V9 `CREATE INDEX`·CONCURRENTLY 시간과 정지 초는 더 길 수 있다(ADR-009 §7 디스크 벽 선례).

### 5.7 §5 수정 뒤 메인 판단 (2026-10-23 — S5 수정 워커 열린 질문)

4. `probe-nondeterministic` ⓑ는 서버 시각 정합에 기댄다 → 회차마다 시계 차를 재서 기록한다(ADR-012 하네스 clock-offset 방식).
5. 하네스 결함으로 '그 부하 15회 재실행' → **사용자 확인 뒤** 실행한다(P7 경우와 같다).
6. P12 문턱 ≥ 2 → 설명 가설이라 그대로 둔다.

C 바퀴·안전망 전체 커서·증분의 열린 회차 걸러내기가 쿼터 행 전부를 대상으로 남겼다 — 마감 회차가 섞인 운영 DB에서는 C 바퀴·전체 커서가 더 짧다. S4c 주 부하는 어긋남을 스스로 만들지 않아 S4c 끝 불일치 0은 '고칠 것이 없었다'일 수 있다(DS-15 — 정합 자료는 탐침·주입).
2. **V9 인덱스가 1초 미만이라 ①③의 Flyway 쓰기 차단이 작았다 — 그래서 ④⑤의 이점이 드러나지 않았다**: V9의 `ADD COLUMN … DEFAULT now()`는 기존 행 전부에 같은 값 m을 준다(끝 검사 `m_rows` — ①②③ 612.1만~615.0만 · ④⑤ 525.3만). 그 열 위 트랜잭션 안 `CREATE INDEX`를 포함한 V9 전체가 S4c에서 780–853ms였고(보정 DB 769만 행 `CREATE INDEX` 0.94초 — 시작 조건), ②③에서 업무 세션이 마이그레이션 세션에 막힌 최대가 0.65–0.79초(V9 시간과 같은 급 — §1 정정 '트랜잭션 끝까지 `ACCESS EXCLUSIVE`'와 맞다)였다. 이 크기는 1초 격자의 정지 초(D1)·가용성 탐침 실패(D2 — 요청 시한 5초)에 잡히지 않고, D3도 ③ [55–95] 대 ④ [46–108]로 갈리지 않았다 → 다운타임 단 동률 → K가 ③을 골랐다. '같은 값이라 빠르다'는 인과는 이번에 따로 대조하지 않았다(값이 다른 열의 인덱스 시간을 재지 않음 — 가설). 다만 기존 행 전부가 m을 갖는 것은 시드의 성질이 아니라 **V9 문장 자체의 성질**이라 운영 DB에서도 같다. 운영에서 ③의 차단이 커질 수 있는 조건(측정 밖): 디스크 DB(tmpfs 측정 — §5.6-14) · 훨씬 큰 표 · **V9 앞에 오래 열린 트랜잭션**(`ALTER TABLE`이 그 뒤에서 `ACCESS EXCLUSIVE`를 기다리는 동안 뒤의 모든 쿼터 접근이 줄을 선다 — 이번 부하에는 긴 트랜잭션이 없었고, Flyway V9에는 ④ 1·2단계의 `lock_timeout` 2초 + 재시도가 없다).
3. **차가운 JVM 504 구간(§5.8-3b ⓒ — 절차의 성질로 그대로 둠)**: 예열 안 된 새 JVM이 **혼자** 전체 부하를 받으면 S4c에서 약 40~60초 동안 504가 난다 — ① 새 앱 lb 편입(323.8초) 뒤 약 345~395초에 12,224–15,315건(lb `proxy_connect_timeout` 5초) · ②⑤ T2 새 앱 편입(약 627초)과 그림자 앱 내림(약 629초) 뒤 약 630~690초에 11,468–14,962건(② rep3는 합 18,509 중 4,252가 T1 그림자 앱 B1 몫(337~354초 — lb upstream별) · T2 뒤 몫 14,257) (결과 리뷰 RD-2). ③④는 새 앱이 T1부터 300초 동안 옛 앱과 부하를 나눠 받으며 데워진 뒤 T2에 혼자가 되어 **5xx 0**이다(단 절반 부하 투입도 S4c ②③④⑤ 12번 중 1번 — ② rep3 그림자 앱 — 은 504를 냈다 · §7.3 · 결과 리뷰 RD-2)(대신 전환 구간 서버형 느린 초 46~108 · 1초 p99 최대 5.3~15.7초 — 차가운 JVM이 절반 부하를 받는 몫). 이 504는 D1(201이 0인 초)·D2(S3e)에 거의 잡히지 않고 D3와 ① 전환 칸 탐침 실패(회차마다 4~5개)로 보인다.
4. **lb 아티팩트(§5.8-3b ⓐ)**: lb reload마다 옛 작업자가 닫는 keepalive 연결 위 요청이 코드 0으로 끝난다 — reload 4번인 ②⑤가 S4c [476–1,291]건으로 가장 많고(① [15–41] · ③ [126–409] · ④ [115–300]), 정의대로 D1·D2·실패 수에서 뺐다. 실제 운영 lb(연결을 서서히 비움)에서는 생기지 않을 몫이라 절차 비교에 넣지 않았다 — 이 규칙이 없었다면 ②⑤의 D2가 불리해졌을 것이다(S3e는 [33–48]로 차이가 작다).
5. **②⑤ J3 약 50초 = 옛 C 소유의 값**: S3e 450초 주입(전환 구간)의 H·L2 쌍을 ②⑤는 옛 C가 50.7–51.1초 뒤에 고쳤고(출처 `reconcile-app`), 630초 주입(단독(새))은 새 증분이 0.4–0.5초에 고쳤다. ①③④의 450초 주입은 새 증분이 0.2–0.6초에 고쳤다(rep1 기준). 즉 J3의 차이는 '전환 구간에 대조를 누가 쥐는가'(②⑤ = 옛 C — 설계상 N2)를 그대로 잰 것이고, ②⑤가 그림자 기간을 줄이면 줄어든다(§5.6-4 시각표 고정).
6. **환경 정지 덩어리(원인 미확인)**: S4c 31회(무효 1 포함) 중 9회에 같은 모양 — 약 11~13초 연속 정지 + 약 6초 쉼 + 2~3초 정지 — 이 절차와 무관한 시각에 생겼다(① rep1 515초 · ① rep2 1,072초 · ② rep1 851초 · ② rep3 294.8초(T1 앞 단독(옛)) · ③ rep1 1,188초 · ③ rep2 402초 · ④ rep2 410초 · ⑤ rep2 743초 · 무효 ③ rep2 attempt1 72.6초(옛 앱 하나뿐)). S3e 가용성 탐침에도 약 9초 동안 17~20건 연속 실패 덩어리가 6회(① rep1 · ③ rep2 · ⑤ rep3는 단독(옛) 안). ① rep1 덩어리 동안 새 앱 지표 표본(중앙 간격 1.2초)이 13.5초 비었고 DB 표본(중앙 간격 0.57초)은 정상이었으며 GC 멈춤은 0이었다 — 앱 쪽 응답 정지로 보이지만 원인은 확인하지 못했다. 절차와 무관하게 무작위로 떨어져 ②③④⑤ D1·D2 범위의 위 끝(13~19)을 만들었고, 다운타임 단이 갈리지 않은 원인의 일부다.
7. **소유 공백 몫은 안전망 전체 커서뿐 — 이번에는 손해로 보이지 않았다**: ① S4c 31.5–33.5초(201 64,837–71,630건) · ② 30.6–32.8초(126,004–138,592건) · ⑤ 18.9–27.7초(79,799–117,598건)의 변경 쌍은 옛 C 마지막 완료 바퀴도 새 증분도 보지 않는다(§4.3 DS-2). 그 구간에 든 탐침·주입이 0이라 P9 (아)는 비어 있는 성립이고, S4c 쌍은 스스로 어긋나지 않아 끝 불일치 0이었다 — 운영(어긋남이 실제로 생김)에서는 전체 커서가 그 쌍에 닿을 때까지 고쳐지지 않는다.
8. **값 m을 가진 '비기존' 행(N11 명시한 예외의 실제 크기)**: 끝 검사 `m_rows_post_v9`(값이 m인데 홀드가 모두 m 뒤에 생긴 쌍)가 ②③ S4c 18–22(② rep3 0) · ④⑤ S4c 2–4 · ① 0 · S3e 0이었다. 추정(원인 미검증): V9 트랜잭션 시작(m = 그 트랜잭션의 `now()`) 뒤 `ALTER TABLE`이 락을 얻기 전에 커밋한 쓰기 — 그 행은 열을 더할 때 이미 있어 값 m을 받지만 홀드 시각은 m 뒤다(업무 대기 표본이 없던 ② rep3와 부하 없는 ①이 0인 것과 맞다). NF-2(시작 시각이 m과 마이크로초까지 같을 때)보다 넓은 예외이고, 증분이 읽지 않는 안전망 몫이다 — 이번 30회에서 끝 불일치·탐침 틀림은 만들지 않았다.
9. **단일 서버 · 옛 1대 · 새 1대(§5.6-2·3)**: .164 한 대에 DB · 앱 2대 · lb · 탐침 · 혼재 구간에만 앱 자원 두 배. 운영의 N대 롤링(혼재 비율이 단계마다 바뀜 · 옛 앱 중 C를 쥔 1대가 언제 내려가는가)과 겹침·소유 공백이 여러 번 생기는 경우는 재지 않았다.
10. **시각표 고정 · 탐침 해상도(§5.6-4·5)**: T1·T2가 다섯 절차에 같고 옛 앱이 회차마다 같은 시각에 떠서 C 위상이 거의 고정이다(P6 재해석 · 단독(옛) O 비율이 S4c 0.333 · S3e 0.667로 회차마다 같음). 칸마다 6탐침(d ≥ 5초) × 3회 — 드문 틀림은 0으로 보일 수 있다.

**되돌리기 경로**(§4.7.4 표 — 측정하지 않고 고정한 경로): T2 전 = 새 앱을 lb에서 빼고 내린다(중단 없음 — 이미 떠 있던 옛 앱은 새 스키마에서 오류 없이 돈다: ②~⑤ 24회 `cached plan` 오류 0 · 새 스키마 뒤 옛 앱 ERROR 0 · 결과 리뷰 RD-5) · T2 뒤 = 옛 이미지를 다시 올리고 새 앱을 내리거나(새 스키마 위 옛 앱 재기동은 미측정 설계 경로 — 결과 리뷰 RD-5), 새 앱을 K3(C · method=trigger · 위치 유지)로 · 트리거·인덱스·V10 테이블은 남는다 — 지우려면 앞으로 가는 새 마이그레이션(ADR-012 §7-13 ③).

**주의**:
- ③의 쓰기 차단 = 트랜잭션 안 V9 시간이다(이번 0.8초). V9가 길어질 DB(디스크 · 훨씬 큰 표 · 쿼터 표 앞의 긴 트랜잭션)에서는 같은 크기 사본에서 V9 시간·락 대기를 먼저 재고, 길면 ④(적용판 — `lock_timeout` 2초 + 재시도 · CONCURRENTLY)를 쓴다 — 이 전환 조건은 측정하지 않은 **가설**이다(§6.6-2).
- 옛 앱을 내리기 전에 새 앱이 부하 일부로 데워져 있어야 한다 — 차가운 JVM이 혼자 전체 부하를 받으면 약 40~60초 504(①②⑤ — §6.6-3).
- 되돌리기(T2 뒤)도 같다: 다시 올린 옛 앱을 일부 부하로 데운 뒤 새 앱을 내린다 — 차가운 옛 JVM이 혼자 전체 부하를 받는 경우는 측정 밖이다 (결과 리뷰 RD-9).
- 혼재 구간의 겹침은 1번(옛 1 · 새 1)만 쟀다. N대 롤링에서는 옛 C를 쥔 인스턴스와 새 앱 여러 대가 겹치는 시간이 길어질 수 있다(측정 밖).
- 값 m을 가진 비기존 행(§6.6-8)과 기존 쌍의 어긋남은 증분이 아니라 안전망 전체 커서 몫이다 — 전환 직후 기존 쌍의 어긋남 복구는 안전망 전체 바퀴 시간에 달린다(§4.11 ③).

### 7.4 받아들이는 한계

1. **다운타임 단은 이번 조건에서 갈리지 않았다** — ③ 대 ④는 단계 수 하나로 정해졌다. V9가 0.8초인 조건(tmpfs · 빠른 기본값 한 값 · 긴 트랜잭션 없음)을 벗어나면 ④가 나을 수 있다(§6.6-2 · §7.1 주의 — 측정하지 않은 전환 조건).
2. **환경 정지 덩어리**(§6.6-6 — 원인 미확인)가 다섯 절차에 무작위로 들어가 D1·D2 범위를 넓혔다 — ②③④⑤의 0이 아닌 D1·D2는 환경 정지 덩어리로 보이고(원인 미확인 — 전환 구간 안의 ③ rep2·④ rep2 포함) '전환이 만든 정지는 ①의 중단뿐'이라는 해석은 사건 시각·모양 대조에 기댄다 (결과 리뷰 RD-6).
3. **설명 가설 P1·P6·P11·P12 반증 · P2 판정 불가**(§6.4) — 성공·고르기에는 쓰지 않았고, P1·P6·P11은 측정 뒤 재해석을 따로 달았다.
4. **소유 공백 몫·값 m 비기존 행**(§6.6-7·8)은 이번 부하에서 손해로 나타나지 않았을 뿐 안전망 전체 커서 몫이다.
5. §5.6의 측정 전 한계(시드 조건 · 단일 서버 · 옛 1 · 새 1 · 시각표 고정 · 탐침·다운타임 해상도 · 수렴 창 · 주입은 흉내 · 되돌리기 미측정 · 원인 귀속은 참고 · 보수적 고정값 · tmpfs)는 그대로다.
