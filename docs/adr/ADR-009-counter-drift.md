## 1. 문제

ADR-008에서 매수 제어 기본값이 counter-upsert-precheck(카운터 = 쿼터 행 `user_hold_quota.cnt`)가 됐다. 정상 경로에서는 카운터가 실제 값(`seat_hold` 행 + CONFIRMED 예약)과 어긋나지 않는다(ADR-008 13회 불일치 0). 그러나 **어긋났을 때 막을 장치가 없다**(ADR-008 §6 ①, R1):

| 어긋남 | 결과 (지금 코드) |
|---|---|
| 쿼터 행 없음 | 만료 배치의 감소 `check(updated == 1)` 실패 → **만료 틱 전체 롤백, 매 틱 반복 → 모든 회차 만료 정지**(좌석이 HELD로 남음) |
| cnt < 감소 수 | `CHECK (cnt >= 0)` 위반 → 같은 전역 정지 |
| cnt가 실제보다 조금 작음 | 감소는 성공, **조용히 한도 초과 허용** |
| cnt가 실제보다 큼 | 감소는 성공, **조용히 정상 사용자 거절** |

어긋남이 생기는 경로: 전환 전제(옛 버전 쓰기 정지) 위반 · DB 직접 수정 · 앞으로의 버그.

함께 다루는 것 (ADR-008이 넘김 + 설계 중 발견):

- **판매 마감 미정의**: 회차 `starts_at`은 저장만 되고 어디서도 검사하지 않는다(ADR-000 설계 누락 — 사용자 확인 2026-10-12). 공연이 시작된 뒤에도 선점이 된다.
- **쿼터 행 정리**: 만료로 쿼터 행이 지워지지 않아 계속 쌓인다.
- **기동 시 검사**: 쿼터 테이블이 없는 DB에서 쿼터를 쓰는 방식으로 뜨면 기동은 되고 요청 때 500이 난다.

질문: **어긋남을 막거나, 생겨도 전역 정지 없이 찾아 고치는 방법 중 무엇이 가장 싸고 확실한가? 그 비용은 부하 처리량을 얼마나 깎는가?**

## 2. 선택지 (명세 §1 · 사용자 결정 2026-10-12)

| 후보 | 하는 일 | 막는 것 | 못 막는 것·비용 |
|---|---|---|---|
| **A** 쌍 단위 견딤 (`counter-drift.expiry-repair`) | 만료 배치의 감소를 가드 감소(`cnt >= n`)로 바꾸고, 실패한 (회차, 사용자) 쌍만 그 자리에서 실제 값으로 다시 세어 덮어쓴다. 나머지 쌍은 정상 만료 | 전역 만료 정지(행 없음·음수) | 조금 작음·큼(감소가 성공하므로 안 보임) |
| **B** DB 트리거 (`limit-strategy: counter-trigger`, `db/migration-trigger` V8) | 홀드·예약 행이 바뀔 때 DB가 같은 트랜잭션에서 cnt를 고친다. 한도 판정은 앱. 트리거는 엄격(행 없음·음수 → 오류), 마감 회차는 기여 쪽별로 건너뜀 | 앱 경로·옛 버전 쓰기의 어긋남(원천 차단) | DB 직접 cnt 조작. 모든 쓰기에 비용 · 확정↔만료 교착(만료가 쿼터 행 선잠금으로 회피) |
| **C** DB 안 청크 대조 (`counter-drift.reconcile`) | 앱 안 전용 스케줄러가 60초마다 열린 회차를 두 갈래로 훑는다: ① 쿼터 행을 키 순서로 읽고 쌍마다 실제 값 탐색 ② 쿼터 행이 없는 쌍은 홀드·예약 쪽에서 찾기. 어긋난 쌍은 잠근 뒤 다시 세어 자동 복구, 맞으면 오탐으로 기록 | 네 갈래 전부(탐지까지 최대 한 주기) | 앱 풀·DB 읽기 비용 |
| **F** 별도 대조 앱 (`reconciler` 프로필) | C와 같은 일을 별도 컨테이너(같은 jar, 포트 8102)에서 | C와 같음 | DB 읽기 비용은 C와 같음, 앱 CPU 간섭만 다름(가정) |

조합 규칙(기동 검사 — 사용자 결정): C·F를 켜면 A 필수(마감 회차는 대조에서 빠지므로 남은 홀드의 감소 실패는 A가 맡음) — 단 B는 예외(트리거가 마감 회차를 건너뛰어 정지 경로가 없음). B + A는 거부. B + 판매 마감 끔은 거부(한도 우회).

함께 넣는 것:

- **판매 마감**: `now(앱 Clock) >= starts_at`이면 선점 거절 `SCHEDULE_CLOSED`(409). 판정 순서 마감 → 좌석 → 매수. 확정은 막지 않는다. 회차 행 `FOR SHARE`로 정리 ①과 직렬화. 끄는 키 `sales-close.enabled`.
- **쿼터 행 정리 2방식**: ① `schedule` — 마감 뒤 회차 행 `FOR UPDATE` → 홀드 0 재확인 → 회차 쿼터 행 전체 삭제 ② `zero` — cnt = 0 행 삭제.
- **판정기 v2**: `v_counter_mismatch`는 열린 회차만 센다(마감 회차는 카운터를 쓰지 않음 — 사용자 결정).
- **기동 검사**: 쿼터 테이블을 쓰는 방식 전부 + 위 조합 규칙.

## 5. 판정 기준 (명세 §5 — 사용자 기본 안 2026-10-12)

1. 주입한 어긋남에서 **만료 전역 정지 0** (B·B+C는 주입 → 복구 구간의 행 없음·작음 원인 틱 실패를 B의 결과로 기록 — 사용자 결정 'B 엄격'의 결과)
2. 주입한 쌍 **100% 탐지·복구**(조용한 누락 0) + 주입 안 한 쌍의 **오탐 복구 0**
3. **비용**: S4c4200 처리량·선점 p99·디스크 벽 시작 시각, S2 p99, S3-a20 선점당 WAL을 대조군과 비교. **허용선은 측정을 본 뒤 사용자와 함께 정한다.**
4. 판매 마감 `FOR SHARE`: 마감 끔 대비 처리량 또는 p99가 10% 이상 나쁘거나 벽이 앞당겨지면 잠금 방식을 다시 정한다(§11 R1 — 2026-10-13 사용자: 고정 도착률 셀에서 처리량만으로는 둔감하므로 p99·벽 시각 추가).

**고정 도착률 셀의 처리량 한계**: S4c4200은 디스크에서는 ADR-007 벽(약 2,900건/s)에 묶이고, tmpfs에서는 도착률(4,200건/s)과 같아진다. 그래서 처리량만으로는 비용이 보이지 않을 수 있다 — 비용 판정은 p99·벽 시작 시각·선점당 WAL을 함께 본다.

- tmpfs 4조건 1회차의 정상 구간(60초 이후)에서 최대 응답 > 50ms인 초는 조건마다 8~9개 — **전부 Full GC 시각(±1초)과 일치**한다(±1초 창 × 8회 ≈ 정상 구간의 7%라 우연 일치는 무시할 수준). 그 초의 최대 응답 149~296ms. 한계: 조건마다 1회차만 대조했고(나머지 회차는 `gc.json` Full GC 수 8로만 확인), '나쁜 초 → Full GC' 방향만 셌으며(Full GC마다 멈춤이 났는지는 세지 않음), 정지 시간은 Full 단계 ms다(대조 스크립트 — 작업 폴더 밖 임시 스크립트, 결과는 `log.md`). 조건 사이 차이 없음(Full GC 수 8 · GC 정지 합 약 6.4초 · 최대 101~106ms) — 후보의 비용이 아니다.

## 8. 결정 (2026-10-14 사용자 결정 · 2026-10-15 비용 재측정으로 확정)

**매수 카운터는 그대로 쓰고, 어긋나도 스스로 복구되게 A(만료 배치 쌍 단위 견딤) + C(앱 안 대조)를 기본으로 켠다. 쿼터 행 정리는 ① 마감 후 회차 단위를 기본으로. 판매 마감(공연 시작 시각에 선점 거절)은 기본으로 켠다. B(DB 트리거)·F(별도 대조 앱)는 기본이 아니다(선택지로 유지).** — 코드에 적용했고, 대조 비용 재측정(§7.7)에서 허용선 안(tmpfs 선점 p99 — 대조군 대비 +1.0%, A 대비 +2.2% · 처리량 0%)이라 **확정한다**.

- 비용 허용선(사용자): tmpfs 기준 선점 p99·처리량이 대조군 대비 10% 이내. **B(DB 트리거)는 초과**(p99 7.5배 — 유효한 비교). A·C·F는 안(대조군 대비 p99: A −1.1%, A+C +1.0%, A+F −0.5% · A 대비: A+C +2.2%, A+F +0.7% — §7.7). A+C의 +2.2%는 작지만 회차 범위가 A와 겹치지 않는 실제 비용이다(3.90–3.98 대 3.84–3.87ms). 판매 마감은 '10% 악화 관측 없음(디스크 참고 — 해상도 밖) + 판정 0.08~0.13ms'를 근거로 둔다. S2·S3-a20은 참고(명세 §5 ③).
- **왜 A + C인가**: A만으로는 조용한 어긋남(L2·H — 한도 초과 허용·부당 거절)이 남는다(H2). C를 더하면 네 갈래 모두 100%·오탐 0(H3 — 가벼운 부하에서). A는 C가 마감 회차를 대조하지 않는 동안 남은 홀드의 감소 실패를 맡는다(조합 규칙).
- **왜 F가 아닌가**: 비용으로는 F가 C보다 나쁘지 않다 — 본측정의 'F 디스크 p99 +55%·벽 −48초'는 재측정에서 재현되지 않았다(교란·잡음). 오히려 디스크(참고)에서는 C가 방향상 더 나빴다(p99 +11.1%·가장 나쁜 구간 +22.0% 대 F −1.3%·+2.8%, 성공 RPS는 A+F가 A보다 범위가 겹치지 않게 높다) — C의 긴 바퀴(최대 94초 대 F 4초 — C는 앱 풀에 묶인다)가 앱 풀을 쥐어 p99에 기여했을 수 있다. 그래도 기본은 C로 둔다: 배포 단위가 하나 늘지 않고, 판정 기준(tmpfs)에서 비용·효과(§7.1)가 같다. 과부하 구간에서 나빠지는 것이 탐지 시각과 디스크 꼬리 지연 정도라는 것은 추론이다(부하 중 주입은 재지 않음 — §8.1; D·L1 전역 정지는 A가 따로 막는다). **여러 인스턴스로 운영하거나 과부하 구간의 탐지 지연이 문제가 되면 F로 바꾼다**(아래 '여러 인스턴스').
- **왜 B가 아닌가**: 원천 차단의 장점보다 비용이 크다(H6). 엄격성 때문에 어긋남이 있으면 복구 전까지 만료가 멈추고, 확정도 실패한다(확정 실패는 코드에서 끌어낸 추론 — 측정 안 함). 운영 중 전환(ADR-014)에서 비엄격 변형으로 다시 본다.
- **적용(명세 §12, 2026-10-14)**: 기본값 3개 변경(설정·코드 — `counter-drift.expiry-repair`·`reconcile.enabled` 켬, `cleanup.mode: schedule`) · `reconciler` 프로필은 A·정리 끔 · ADR-001~009 하네스와 옛 기본값을 가정한 테스트에 '끔' 명시(렌더 58변형 실효 차이 0) · 기본값 테스트(한 사이클 통합 테스트 포함) · 전체 508/0/0 · 서버 스모크(기본값 S2·S3e, control S2 회귀) 모두 ok · 코드 듀얼 리뷰 + 타깃 재점검 신규 0. 커밋 8e4c92e3·9b0ca984·a601bba5·46f5b04d·2fd9695e·8ed82d72·cc56ef65.
- **운영 제약 — 여러 인스턴스**: 대조(C)와 정리 ①은 앱 인스턴스마다 돈다(인스턴스 사이 단일 실행 장치 없음 — 정리의 `@Synchronized`는 JVM 안에서만). N대면 60초마다 대조 부하가 N배, 같은 쌍의 기록이 중복된다(정합은 회차 행 FOR UPDATE 직렬화로 유지). 측정·허용선은 1대 기준이다. 여러 대로 운영하면 대조·정리는 1대(또는 F)에서만 켠다.
- **운영 제약 — 기록 테이블**: 기본 켬이면 `counter_reconcile_run`이 60초마다 1행(하루 약 1,440행) 쌓인다. 보존·정리 정책은 아직 없다(NEXT).
- **F와 C를 함께 켜지 않는다**: 업무 앱에 `external-reconciler=true`면 C(`reconcile.enabled`)를 꺼야 한다 — 기동 검사가 거부한다.
- 기본값에서 새로 기동 실패하는 조합(안내 메시지 있음): 카운터 계열이 아닌 매수 방식(none·quota·advisory 등)은 A·C·정리를 꺼야 하고, counter-trigger는 A를, counter(ADR-005)·판매 마감 끔은 정리를 꺼야 한다.
