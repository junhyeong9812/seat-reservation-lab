# ADR-002: 같은 좌석 동시 선점 (Q1)

- 상태: 가설 (Hypothesis) — 미측정
- 대응 질문: Q1 "같은 좌석을 1,000명이 동시에 눌렀다면?"
- 선행: ADR-000, ADR-001(판정 기준)

## 문제

기준선의 선점은 `좌석 조회 → AVAILABLE인지 앱에서 비교 → HELD 저장`이다(check-then-act). 두 요청이 모두 `AVAILABLE`을 읽은 뒤 각자 저장할 수 있다.

## 가설

- 1,000명 동시 요청 시 성공 응답이 2건 이상 나오고, 한 좌석에 홀드 행이 여러 개 생긴다.
- JPA dirty checking은 마지막 쓰기가 이기므로 좌석 상태는 `HELD` 하나로 보이지만 소유자는 여럿이다 — 좌석 테이블만 봐서는 깨짐이 안 보인다.

## 재현 시나리오

- k6: 좌석 1개, 1,000 VU 동시 선점 / 핫스팟(앞 20% 구역에 70%) / 균등 분산

## 선택지 후보

| # | 방식 | 무엇으로 1명만 이기게 하나 | 비고 |
|---|------|--------------------------|------|
| 0 | 락 없음 (기준선) | — | 대조군 |
| 1 | 앱 내 락 (`synchronized`) | JVM 모니터 | 대조군 — 인스턴스 2대면 깨짐 |
| 2 | 조건부 UPDATE | `UPDATE … SET status='HELD' WHERE id=? AND status='AVAILABLE'` 영향 행 수 | DB 원자 연산 |
| 3 | 비관락 `FOR UPDATE` | 좌석 행 배타 락 후 비교·저장 | 변형: `NOWAIT`(진 사람 즉시 실패) |
| 4 | 낙관락 `@Version` | 버전 불일치 시 실패, 재시도 없음 | 좌석은 한 명만 가지면 되므로 재시도 불필요 |
| 5 | 유니크 제약 | `seat_hold(seat_id)` 유니크 + 중복 키 예외 | 만료 행 정리와 충돌 |
| 6 | PG advisory lock (좌석 키) | `pg_advisory_xact_lock(seat_id)` | 행과 무관한 락 |
| 7 | Redis `SET NX EX` | 홀드 자체를 Redis 키로 | 홀드 원천이 DB 밖으로 — Redis↔DB 부분 실패 |
| 8 | Redis 분산락 (Redisson 등) | Redis 뮤텍스 안에서 DB 로직 | 락 만료와 트랜잭션 경계 어긋남 |

## 비교 축
