## 0. 요구사항 원문 (인터뷰 기록)

- 원문(2026-10-10): "디스크 원인 먼저 확인하고 결정하자"
- 배경:
  - ADR-007 본측정에서 S4·S4c4200·S4c2000 81회 모두 DB 컨테이너 누적 블록 쓰기 약 8.3~9.5GB 지점에서 쓰기 속도가 반감됐다(약 38 → 16MB/s).
  - 같은 순간 LWLock:WALWrite가 0.3 → 4.5로 뛰었고, 붕괴·스파이크가 이 지점에서 시작했다.
  - 이 현상은 방식·PG 설정과 무관했다.
  - 원인 후보 C5: 저장장치·호스트 쓰기 지연(미검증).
- Q/A:
  - **확인 방법(복수 선택)**:
    - 회차 재측정 + iostat
    - fio 단독 재현
    - DB를 메모리(tmpfs)에서 재측정
    - 쉬는 시간 바꿔 보기 — **넷 다 채택**
  - **재측정 범위**: 최소 셀. S4 계단 · 고정 4,200/s × none·counter-upsert·precheck × 기본 설정 × 2회 = 12회. tmpfs 조건 12회 추가.
  - **기록 위치**: ADR-007에 이어서 기록한다. §7에 본측정 결과, §7 후속에 디스크 확인, §8 결정까지 ADR-007 안에서 끝낸다.
- 서버 사전 확인(읽기 전용, 2026-10-10):
  - DB 볼륨 디스크: `nvme1n1` Samsung SSD 980 500GB(DRAM 없는 NVMe) → LVM `ubuntu-vg/ubuntu-lv` `/`(98G, 여유 51G). 마운트 `rw,relatime`, 온라인 discard 없음.
  - `fstrim.timer` 주 1회. 마지막 2026-10-05 00:04 UTC, 다음 **2026-10-12 01:21 UTC(= 10:21 KST)**.
  - vm.dirty_ratio 20 · dirty_background_ratio 10 · dirty_expire 30초. RAM 31GB.
  - `iostat` 있음(sudo 불필요). `fio` 없음. **sudo는 비밀번호 필요** → fstrim·smartctl·nvme-cli·apt 설치 불가.
  - 다른 NVMe `nvme0n1`(FireCuda 510)은 Windows 파티션이라 쓰지 않는다. 지금 실행 중인 컨테이너 0개.
  - 회차마다 `compose down -v`로 DB 볼륨을 지우고 새로 만든다(`lib.sh:76`). 즉 매 회차 새 파일에 약 12GB를 쓰고 지운다.

## 2. 경계·불변식 (필수)

- 앱 코드(`src/**`)·매수 방식 동작·응답 계약·앱 기본값은 바꾸지 않는다. 이번 작업은 측정 하네스와 문서만 다룬다.
- 기존 preset(default·nockpt·buf512)과 기존 셀의 동작·산출물 형식은 그대로다.
  - 새 지표는 새 파일로만 더한다(`timeline-iostat.jsonl`·`timeline-mem.jsonl` 등).
  - 본측정 캠페인 `20261009-adr007-ea8b85cc` 결과 폴더는 읽기만 한다.
- 새 preset `tmpfs`는 PG 데이터 디렉터리를 tmpfs 볼륨에 둔다.
  - PG 설정(체크포인트·WAL·버퍼)은 default와 같다.
  - **DB 컨테이너 메모리 한도만 올린다**(2g → tmpfs 크기 + 2g). 이 차이는 결과에 교란 변수로 명시한다.
- 측정 비교는 같은 캠페인 안에서 한다. 디스크 조건과 tmpfs 조건을 번갈아 배치해 시간 효과를 줄인다.
- **2026-10-12 10:21 KST 정기 fstrim 전에 본 재측정을 끝낸다.** fstrim 전후가 섞이면 장치 상태가 바뀐다. fstrim 뒤 1회 관찰은 자연 실험 후보로 선택 사항이며, 하게 되면 사용자 확인 후 진행한다.
- 호스트 샘플러는 측정을 방해하지 않게 1초 주기 읽기(`/proc/diskstats`·`/proc/meminfo`·`iostat`)만 한다. 받는 쪽은 bash 줄 읽기 루프를 쓴다(mawk 버퍼링 재발 금지 — ADR-007 리뷰 A11).
- fio 시험 파일은 `~/labs/seat-reservation-lab/fio-tmp/` 아래에만 만들고, 시험이 끝나면 그 경로만 지운다.

## 5. 검증 방법 (필수)

- 하네스:
  - 기존 오프라인 확인(dry-run·판정식·ADR-006 재산출 동일)이 그대로 통과해야 한다.
  - 새 샘플러는 스모크 1회로 실증한다. k6 구간 1초 표본이 빠짐 없이 들어오고 서버 사본과 일치하는지 본다.
  - tmpfs 스모크 1회로 확인한다: `SHOW data_directory` 위치가 tmpfs인지(`df`/`findmnt` in container), 그리고 메모리 한도 안에서 S4 계단을 끝까지 도는지.
- fio:
  - 초당 쓰기량·쓰기 지연 로그(1초 평균)로 판정한다.
  - 누적 쓰기량 축에서 꺾이는 지점이 있는지, 즉시 재실행·휴식 후 재실행에서 그 지점이 어떻게 움직이는지 본다.
- 판정(C5):
  - **확인**: 아래 넷이 모두 성립하면 C5를 확인으로 본다.
    - (a) 재측정 회차에서 쓰기 반감 시각에 호스트 `nvme1n1` w_await 또는 flush 시간이 함께 뛴다.
    - (b) fio 단독으로도 비슷한 누적량에서 꺾인다.
    - (c) tmpfs 조건에서 그 반감·붕괴가 사라지거나 계단 상한 밖으로 밀린다.
    - (d) 휴식 길이가 꺾이는 지점을 움직인다(선택 신호 — 없어도 a~c로 판정).
  - **반증**: tmpfs에서도 같은 지점에서 무너지면 C5는 반증이다. 원인을 앱·PG 쪽에서 다시 찾는다.
- 회차 판정: 모든 회차 status ok. 새 사유는 아래 둘이다.
  - `host-sampler-thin`: k6 구간 1초 표본 < 90%
  - `tmpfs-not-applied`
- 리뷰: 하네스 변경은 중간 stakes이므로 듀얼 1패스(Opus 워커 ∥ codex → 종합 → 감사 → post-fix 재점검 1회)를 거친다. ADR 문서도 듀얼 1패스.

## 8. load-bearing 가정 (1~2개)

1. **sudo 없이 호스트 `/proc/diskstats`를 1초로 읽어 nvme1n1의 쓰기 지연·flush 시간을 볼 수 있다.** 착수 직후 스모크로 실증한다. 열 수는 커널 버전으로 확인한다.
2. **PG 데이터(+WAL)가 S4 계단 1회 동안 tmpfs 6GB 안에 들어간다.** 세 가지를 근거로 본다.
   - max_wal_size 1GB라 WAL이 재활용된다.
   - 데이터는 홀드 약 40~70만 행 + 쿼터 행이다.
   - 스모크에서 회차 끝 `pg_database_size`와 `pg_wal` 크기를 확인한다.
   - 넘치면 tmpfs 크기를 조정하고, 사용자에게 보고한다.
