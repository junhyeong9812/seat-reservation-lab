## 1. 목표·대상 (필수)

`seat-reservation-lab`의 **선점(hold) 경로**에 락 방식 11종(아래 표)을 전략으로 넣고, ADR-002가 정한 기준선(일반 인덱스 + 풀 10) 위에서 같은 캠페인으로 실측해 **7개 기준별 비교와 선택 근거**를 `docs/adr/ADR-003-same-seat-contention.md`에 기록하면 끝.

| # | 방식(전략 키) | 1명만 이기게 하는 수단 | 비고 |
|---|------|------|------|
| 0 | `none` | — | 대조군(기준선 그대로) |
| 1a | `jvm-lock` | 좌석별 JVM 락을 **트랜잭션 밖**에서(커밋까지 포함) | 단일 인스턴스에서만 유효 |
| 1b | `jvm-lock-in-tx` | 같은 락을 `@Transactional` **안**에서 — 커밋 전 해제 | 함정 재현용 변형 |
| 2 | `conditional-update` | `UPDATE … SET status='HELD' WHERE id=? AND status='AVAILABLE'` 영향 행 수 | DB 원자 연산 |
| 3a | `pessimistic` | `SELECT … FOR UPDATE`(좌석 행) 후 기존 로직 | 대기형 |
| 3b | `pessimistic-nowait` | `FOR UPDATE NOWAIT` — 진 쪽 즉시 실패(409) | |
| 4 | `optimistic` | `@Version` 불일치 시 실패(409), 재시도 없음 | 좌석 테이블 버전 열 필요 |
| 5 | `unique` | `seat_hold(seat_id)` 유니크 + 중복 키 → 409 | 유니크 인덱스 필요 |
| 6 | `advisory` | `pg_advisory_xact_lock(seat_id)` | 대기형 |
| 7 | `redis-nx` | Redis `SET seat:{id} NX EX <TTL>` 성공한 요청만 DB 홀드 저장 — **Redis는 관문, DB가 원천** | Redis 성공·DB 실패 부분 실패 |
| 8 | `redis-lock` | Redis 분산락(Redisson) 안에서 DB 로직 — 락 해제는 커밋 뒤 | 대기형 |

## 2. 경계·불변식 (필수)

- **비교 대상은 선점 경로의 같은 좌석 경합만**이다. 확정(confirm)·만료(expire) 경로는 바꾸지 않는다 — 확정 원자성은 ADR-006, 만료는 ADR-005. 1인 2매(S2·`HoldLimitPolicy`)는 ADR-004.
- **도메인 규칙은 그대로**: 선점 가능 판정(`assertHoldable`)·상태 전이·응답 계약(201 / 409 `SEAT_NOT_AVAILABLE` / 404)은 모든 전략에서 같다. 락 방식이 진 쪽을 409로 돌려줄 때 에러 코드는 기존 `SEAT_NOT_AVAILABLE`.
- **기본 전략 = `none`**(기준선 동작 불변) — 설정 없이 띄우면 ADR-002와 같은 앱이다. 기존 테스트 전부 green.
- **DB가 원천**: 정합성 판정은 ADR-001 판정기(DB 사실)로만 한다. Redis 상태는 판정에 쓰지 않는다.
- **스키마 변경은 전략에 필요한 것만, 다른 전략의 동작을 바꾸지 않게**: `product_seat.version`(낙관락) 열 추가는 다른 전략에 무해해야 하고, `seat_hold(seat_id)` 유니크는 `unique` 전략에서만 적용(설정 전환 — ADR-002의 `flyway.target` 방식과 같은 원리).
- **측정 조건은 ADR-002 기준선과 같게**: 같은 서버·k6 PC·시나리오·시드·예열·타임아웃(30s)·Tomcat 설정·인덱스(V2)·풀 10. 달라지는 변수는 전략(과 대기형 락의 풀 20)뿐. 다른 것이 바뀌면 명시.
- **판정·근거 보존 규칙은 ADR-001·002 그대로**: DB 사실 기준 판정, 응답-DB 대조, 회차별 원시 결과 보존, 표는 스크립트 산출, 미측정은 "미측정". 요청별 원시 CSV는 커밋하지 않고 sha256 + 요약만(ADR-002 결정 승계).
- **비교는 같은 캠페인 안에서만**(ADR-002 §7.4 — 조건 간 드리프트). 대조군 `none`도 이 캠페인에서 다시 잰다.

## 5. 검증 방법 (필수)

- **전략 단위 테스트(Testcontainers PostgreSQL + Redis)**: 전략마다 같은 좌석 동시 선점 N개 → `none`·`jvm-lock-in-tx`는 중복 허용(실패해야 정상 — 판정기가 잡음), 나머지는 성공 정확히 1 · 진 쪽 409 · 판정기 위반 0. `jvm-lock`은 단일 인스턴스 조건에서.
- 기본 전략이 `none`이고 기존 테스트 전부 green
- 스키마: 버전 열·유니크 전환 테스트(유니크는 `unique` 전략에서만 존재)
- 하네스 스모크: 전략 전환이 회차 결과에 기록·대조(`strategy-mismatch` — ADR-002의 pool/index 대조와 같은 방식) · 앱 2대(nginx) S1 1회 · Redis 기동 · S4 확장 계단 1회(k6 PC가 확장 단계의 도착률을 낼 수 있는지 — 가정 2) · 단절 회차 판정이 인위적 공백에서 동작
- 본측정: 계획(`plan.json`) 대비 누락 0, 실패·단절 회차 명시 후 그 회차만 재측정
- ADR-003 표는 원시 결과에서 스크립트로 재산출

## 8. load-bearing 가정 (1~2개)

1. **전략 하나를 기동 설정으로 고르는 구조가 선점 경로만 바꾸고 기준선 동작을 보존한다** — `none`에서 기존 테스트 green + ADR-002 c01과 같은 S1(성공 ≤ 10) 스모크로 착수 직후 실증.
2. **k6 PC가 확장 계단(6,487 위, 예: 9,731·14,597건/s)의 도착률을 낼 수 있다** — 못 내면 확장 단계가 "목표 미달"로만 남는다. 스모크 1회로 실증, 안 되면 사용자 보고(계단 상한을 다시 정함).

## 9. 설계

### 9.1 전략 구조

- `HoldStrategy` 인터페이스 + 구현 11개, `seat.hold.strategy` 설정(기본 `none`)으로 하나를 빈으로 선택. 선점 유스케이스는 전략에 위임하고, 전략이 락 획득·트랜잭션 경계·진 쪽 처리(409)를 책임진다.
- 트랜잭션 경계가 전략마다 다르다(1a·8은 락이 트랜잭션을 감싸야 함) — 유스케이스의 `@Transactional`을 전략 안으로 옮긴다(TransactionTemplate).
- 요청 파라미터 전환은 하지 않는다(사용자 결정 — 회차마다 한 방식).

### 9.2 측정 매트릭스 (풀 10, 인덱스 V2, 배경 0)

| 대상 | 시나리오 | 단계 | 회차 |
|------|---------|------|------|
| 전략 11개 | S1 · S4(확장 계단) | L2 · L4 | 5 |
| 전략 11개 | S3 원본 × 이탈 0/20/50 | L4 | 5 |
| 대기형 3개(`pessimistic`·`advisory`·`redis-lock`) | 풀 20 — S1 · S4 | L2 · L4 | 5 |
| 전략 11개 | 앱 2대(nginx, L4를 2+2로 나눔) — S1 | L4 | 5 |

→ 약 70시간(추정 — 전략당 S1·S4 약 1.7h + S3 L4 약 4.3h = 6h × 11 + 풀 20 약 5h + 앱 2대 약 1h, 인터뷰 때 63h에서 S4 계단 확장분 반영). S2는 ADR-004.

### 9.3 판정 기준 (ADR에 기준별로 결론·근거·편향·다음 ADR 입력)

| 기준 | 지표 |

| ① 정합성 | 판정기 위반 전부 0, S1 성공 정확히 1 — 전 회차 |

| ④ 자원 점유 | 한계 단계의 앱·DB CPU, Hikari 대기(pending), DB 락 대기 수, 진 쪽 응답 시간 |

### 9.4 하네스 (`k6/ADR-003/` — ADR-002 하네스 복사 + 보강)

- 조건 축 `--strategy`, `--apps 1|2`(nginx), 결과에 적용 전략 기록·대조
- S4 계단 확장(`STEPS` 16 — 약 2만 건/s, 가정 2로 확정)
- 배포 SSH 재시도(백오프·상한), **단절 회차 판정**: 측정 중 서버 지표 수집 공백 > 30s면 status에 `path-gap` → 캠페인 끝에 그 회차만 재측정
- 락 대기 지표: 부하 중 Hikari pending(actuator)·`pg_locks` 대기 수·`pg_stat_activity` wait_event 표본 → 타임라인
- 공정성: S1 요청 시작 시각 태그 → 승자 도착 순위 산출(요약기)
- 실행: 별도 systemd 유닛 + `Restart=on-failure`(ADR-002 운영 대책 승계) + 스크립트 동결 + `--resume`. 로그아웃 정지는 사용자 linger 설정 전까지 위험으로 남는다.
