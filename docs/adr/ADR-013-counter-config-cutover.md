## 1. 문제

ADR-012가 기본값을 바꿨다 — 옛 구성(main 93dd610a: counter-upsert-precheck + A(만료 감소) + C(앱 안 60초 전체 대조) · 쿼터 행에 `updated_at` 없음)에서 새 구성(V9: `user_hold_quota.updated_at` 열·인덱스·트리거 + V10 기록 테이블 + 앱 안 증분 대조 1초 + 안전망 + split 탐지)으로. 이미 데이터가 쌓인 운영 DB에서 이 전환을 하면:

1. **스키마 적용이 쓰기를 막는다**: V9의 `CREATE INDEX`는 쿼터 테이블 쓰기를 인덱스가 다 만들어질 때까지 막는다(ADR-012 §7-13 ①). 행이 수백만이면 그동안 선점이 멈춘다. `ADD COLUMN … DEFAULT now()`는 빠른 기본값이라 행을 다시 쓰지 않는다(PostgreSQL 11+ — 설계에서 확인).
2. **롤링 배포 동안 옛 앱과 새 앱이 섞여 돈다**: 옛 앱은 C를 돌리고 `updated_at`을 모른다. 새 앱은 증분·안전망을 돌린다. 대조가 두 프로세스에서 겹치거나(ADR-009 '대조는 한 곳에서만' 제약), 옛 앱의 쓰기를 증분이 못 보는 구간이 생길 수 있다(V9 트리거가 있으면 옛 앱 쓰기도 `updated_at`을 남긴다 — ⓑ 방식을 고른 이유).
3. **되돌리기가 어렵다**: V9·V10이 적용된 DB는 위치를 빼는 것만으로 옛 구성으로 못 돌아간다(ADR-012 명세 §10 K3 — method=trigger 표시만으로 C 복귀).

> 정정(2026-10-23 — 설계 §4.5): 1-1의 '쓰기를 막는다'는 부족하다 — Flyway V9는 트랜잭션 하나라 `ALTER TABLE`의 `ACCESS EXCLUSIVE`를 인덱스 생성이 끝날 때까지 쥔다 → **읽기까지** 막는다.

### 4.1 기존 데이터 만들기

**사실**(실코드): S4c(초당 4,200 선점 고부하 — `s4-throughput.js:60-62`)는 요청마다 좌석 = 반복 번호 + 1 · 사용자 = 400000 + 반복 번호라 **쌍마다 홀드 1건 · cnt 1**이다. 회차 = ⌈좌석 ÷ 1만⌉. 시드(`LoadtestDataService.reset`)는 회차 ≤ 1,000(회차당 1만 석) · 회차 `starts_at` 2026-12-31(열린 회차). S3e(어긋남 주입 효과 측정 부하)는 회차 1개 · 좌석 1만 · 입장 20만 명(사용자마다 세션 1번)이다.

| 규모 | 고른 것 | 고르지 않은 것 | 이유 |
|---|---|---|---|
| 큰 규모(S4c) | **SQL 대량 시드(회차마다 새 DB)** — 옛 앱의 `/internal/reset`(회차 1,000 · 1만 석) 뒤 하네스가 psql로 회차 501~999에 쿼터 행 + 홀드 + 좌석 `HELD`를 쌍마다 1건씩(약 499만 쌍 — 사용자 = 20,000,000 + i, cnt 1, `held_at` = 시드 시각, `expires_at` = 시드 시각 + 3시간) 넣고 `VACUUM ANALYZE`. k6 S4c는 그대로 회차 1~500(1,200초 — 약 492만 요청)을 쓴다. 회차 1,000은 한도 탐침 전용 | (가) 옛 앱으로 S4c 30분을 미리 돌리기(회차마다) · (나) 한 번 쌓아 DB 파일을 보관 → 회차마다 복원 | (가) 회차마다 30분 + 전환 회차 → 12회에 약 6시간이 더 든다. (나) 보관한 홀드의 `expires_at`이 복원 시각보다 과거가 되면 회차 첫 만료 틱이 수백만 건을 지운다(교란) — 시각을 옮기려면 홀드 테이블 전체를 다시 쓴다. SQL 시드는 정합 검사가 결정적이다(기대 = 쌍마다 cnt 1 = 실제 1 · 시드 직후 끝 불일치 0을 SQL로 확인). 물리 모양(삽입 순서 = PK 순 · 쿼터 행 INSERT만)은 S4c 실제 흐름과 같다 — 다른 점(좌석 행 갱신 dead tuple · autovacuum 이력)은 `VACUUM ANALYZE`로 줄이고, **보정 1회**(옛 앱 S4c 30분으로 쌓은 DB 대 SQL 시드 DB의 테이블·인덱스 크기 · C 한 바퀴 시간 · V9 `CREATE INDEX` 시간)를 측정 전에 log에 남긴다 |
| 작은 규모(S3e) | **회차 안에서 옛 앱이 쌓는다**(사전 시드 없음 — 단독(옛) 구간 360초 동안 S3e 흐름 그대로) | SQL 시드 · 사전 부하 | S3e의 쌍은 수만 개라 V9 비용은 작다 — 이 조합의 질문은 '섞인 구간에 생긴 어긋남을 누가 언제 고치나'(정합·복구)다. 실제 흐름(선점·확정·이탈·만료)이 만든 데이터 위에서 바꾸는 것이 가장 현실적이고 비용이 없다 |

- 전환 시각의 쌍 수(큰 규모): 시드 499만 + 단독(옛) 300초 약 113만 ≈ **약 610만 쌍**(ADR-011에서 C 바퀴가 길어진 400만 쌍을 넘는다). 회차 끝 약 990만 쌍 — tmpfs(DB를 메모리에 둔 측정 조건) 크기는 ADR-012의 12g로 모자랄 수 있다 `[구현 검증]`.
- 미리 쌓은 홀드는 회차 안에 만료되지 않는다(3시간) — 큰 규모는 ADR-011·012 S4c처럼 측정 중 만료가 없다(만료 경로의 섞임은 S3e가 본다 · TTL(홀드 유효 시간) 5분).
- 시드 확인(record-level · 명세 §5 데이터 특칙): 쿼터 행 수 = 홀드 수 = 시드 쌍 수 · `HELD` 좌석 수 · 표본 100쌍 cnt = 실제 · 전체 끝 불일치 쿼리 0(시드 직후 1회 — 부하 전이라 비용 무관) → `seed-check.json`. 하나라도 어긋나면 회차를 시작하지 않는다(`seed-mismatch`).

### 4.2 절차 ①~④ — 단계와 시각표

**공통**: 회차마다 새 DB(V1~V7 — 옛 스키마). 처음 뜨는 앱은 **슬롯 A = 옛 앱**(옛 설정 그대로: A·C 60초·정리 ①·one-shot · 위치 `classpath:db/migration`) 하나다. 시드·초기화(`/internal/reset`)는 옛 앱이 한다 — DB에 V10이 아직 없어 옛 초기화가 `counter_app_inject`를 못 비우는 문제(task 02 스모크)는 생기지 않는다. 앱은 모두 nginx(lb) 뒤에 있고, k6·탐침은 lb만 부른다(옛 앱 단독 구간도 lb 경유 — 구간 사이 비교를 같은 경로로).

- 만료 A·정리 ①은 혼재 구간에 두 앱 모두에서 돈다(ADR-003 앱 2대와 같은 상태). 만료는 JPA 엔티티 삭제라 같은 홀드를 두 앱이 동시에 지우면 한쪽 틱이 롤백된다 — 이중 감소는 없다(`ExpireHoldsService.kt:28-49` 틱 하나 = 트랜잭션 하나). 틱 실패 수(`seat.hold.expiry.tick{outcome=failed}` — 옛 앱에도 있다)를 앱별로 기록한다.

### 4.4 ④ 운영 중 적용판 — 쓰기를 막지 않는 V9와 Flyway 이력

**외부 근거**(PostgreSQL 16 · Flyway 11.7.2 — 이 저장소의 Flyway 버전은 Gradle 캐시 `org.flywaydb/flyway-core/11.7.2`로 확인):
- `ADD COLUMN … DEFAULT <비휘발>`: 기본값을 문장 시각에 한 번 계산해 카탈로그에 두고 **테이블을 다시 쓰지 않는다**(문서 예시가 바로 `DEFAULT now()`). 락은 `ALTER TABLE` 기본 `ACCESS EXCLUSIVE`(읽기·쓰기 모두와 충돌 — 순간이지만 앞 트랜잭션을 기다리는 동안 뒤 요청이 줄을 선다).
- `CREATE INDEX`(보통): `SHARE` — 쓰기(`ROW EXCLUSIVE`)를 막고 읽기는 허용. **`CONCURRENTLY`**: `SHARE UPDATE EXCLUSIVE` — 쓰기를 막지 않는다 · 트랜잭션 블록 안에서 못 돈다 · 표를 두 번 훑고 그 사이 기존 트랜잭션을 기다린다 · 실패하면 **INVALID 인덱스**가 남는다(질의에는 안 쓰이지만 갱신 비용은 든다 — 지우고 다시 하라).
- `CREATE TRIGGER`: `SHARE ROW EXCLUSIVE` — 쓰기와 충돌(순간).
- 락은 트랜잭션 끝까지 쥔다. → **지금 V9를 Flyway가 트랜잭션 하나로 돌리면**(Flyway 기본 = 스크립트마다 트랜잭션 하나) `ALTER TABLE`의 `ACCESS EXCLUSIVE`를 인덱스를 다 만들 때까지 쥔다 — **쓰기뿐 아니라 쿼터 행 읽기(precheck 조회 · C 탐지)까지 멈춘다**. §1-1의 '쓰기를 막는다'보다 넓다(열린 질문 1).
- Flyway: 스크립트별 설정 파일(`V…sql.conf`의 `executeInTransaction=false` — 커뮤니티판) · `skipExecutingMigrations`(실행 없이 이력만 기록 — 7.0 출시 글은 Teams 기능으로 소개, 지금 설정 문서에는 판 표시가 없다 · 11.7.2 jar의 `DbMigrate`에 이 설정 처리 문자열은 있고 판 확인 예외 참조는 보이지 않는다 → **판에서 실제로 되는지는 `[구현 검증]`**) · `baselineOnMigrate`는 **이력 테이블이 없는** 비어 있지 않은 스키마에만 적용된다(이 DB는 이력 V1~V7이 있다).

**후보 비교**:

| 후보 | 방법 | V9 파일 · 체크섬 | 쓰기 차단 | 판단 |
|---|---|---|---|---|
| **(가) 사전 SQL + V9를 '적용됨'으로 기록** | Flyway 밖에서 V9와 같은 객체를 단계별로 만든다(CONCURRENTLY) → V9 이력 1행을 V9 파일과 같은 체크섬·설명·스크립트 이름으로 기록 → 새 앱 Flyway는 검증 통과 후 V10만 적용 | 무변경 · 이력 체크섬 = 파일 체크섬 | 없음(순간 락 2번 — `lock_timeout` + 재시도) | **고른다** |
| (나) 다른 위치의 다른 판(같은 버전 V9 · `executeInTransaction=false` · CONCURRENTLY) | 운영 DB만 그 위치를 쓴다 | 그 DB의 V9 체크섬이 기본 V9와 달라 **기본 위치 앱(K1)이 영원히 검증 실패** — 그 DB에는 늘 다른 위치를 줘야 한다(설정이 DB 이력에 묶임) · 기동 검사의 위치 예측(`afterLocations`)이 모르는 위치 | 없음(단, 새 앱 기동 중 인덱스 생성 — health 시한) | 기각 |

**고른 것 (가)의 단계**(위치: Flyway 위치가 아닌 별도 폴더 `ops/online-v9/` — 클래스패스에 넣지 않는다. 열린 질문 5):

| 단계 | 문장 | 락 · 실패 처리 |
|---|---|---|

| 1 열 | `SET lock_timeout = '2s'`; V9와 같은 `ALTER TABLE user_hold_quota ADD COLUMN updated_at timestamptz NOT NULL DEFAULT now()` | `ACCESS EXCLUSIVE` 순간. 시한에 걸리면 1초 쉬고 다시(최대 30번) — 줄 서는 시간을 2초로 묶는다 |
| 2 함수·트리거 | V9와 같은 `CREATE FUNCTION trg_quota_touch()` · `CREATE TRIGGER user_hold_quota_touch BEFORE UPDATE … FOR EACH ROW` (한 트랜잭션 · `lock_timeout 2s`) | `SHARE ROW EXCLUSIVE` 순간 · 같은 재시도 |

| 4 동치 확인 + 기록 | 카탈로그(열 정의·기본값 · `pg_get_indexdef` · `pg_get_functiondef` · `pg_get_triggerdef` · `tgenabled`)를 **같은 SHA 새 앱으로 V9를 적용한 빈 DB**의 값과 비교 → 같으면 V9 이력 기록 | 다르면 기록하지 않는다 |

- **순서 = 열 → 트리거 → 인덱스**: 트리거가 인덱스보다 먼저 서야 옛 앱 쓰기가 일찍부터 `updated_at`을 남긴다(인덱스는 증분의 속도, 트리거는 증분의 탐지 범위). 트리거를 먼저 만들 수는 없다(함수가 열을 쓴다). 열 ~ 트리거 사이 짧은 틈의 쿼터 변경은 `updated_at` = 열 추가 시각으로 남는다 — 그때 대조는 옛 C가 쥐고 있고, 새 앱이 뜬 뒤에는 안전망 몫이다(§4.8 N5).
- **기록 방법**: ① Flyway CLI(같은 11.7.2 · 공식 이미지)로 `migrate -target=9 -skipExecutingMigrations=true -locations=<V9 파일만 든 폴더>`(Flyway가 이력 행 모양·체크섬을 스스로 만든다) — **이것이 판에서 동작하면 이것을 쓴다**. ② 안 되면(판 제한 — task 05 첫 스모크로 판정, 규칙은 지금 고정): 같은 SHA 새 앱으로 V1~V10을 적용한 빈 DB의 V9 이력 행(`version · description · type · script · checksum`)을 읽어 `installed_rank` = 다음 번호 · `success = true`로 넣는다(Flyway 내부 표 직접 쓰기 — Flyway 버전에 묶인다는 한계를 기록).
- 기록 뒤 새 앱 기동: Flyway 검증(`validateOnMigrate`) — V9 체크섬 같음 → V10만 적용(새 테이블 3개 — 쿼터 테이블 락 없음). 기동 전 예측(`HoldStrategyMigrationGate` — `HoldStrategyStartupCheck.kt:44-58`)은 '위치가 있으면 객체가 있다'로 보므로(`IncrementalSchemaCheck.kt:62-72`) 실제와 같다.
- **거부된 기동 불변식(ADR-012 RC-1·RC-8)과의 관계**: 적용판은 앱 기동이 아니라서 그 불변식의 대상이 아니다 — 대신 적용판 자체의 규칙 '**동치 확인 전에는 기록하지 않는다**'를 둔다. 단계 1~3만 하고 기록하지 않은 DB에 새 앱을 띄우면 Flyway가 V9를 다시 실행하려다 `ADD COLUMN`에서 실패하고 V9 트랜잭션이 롤백된다 — 스키마는 그대로(거부된 기동이 스키마를 바꾸지 않는다는 결과는 성립), 메시지만 Flyway의 SQL 오류다(열린 질문 6).
- **새 코드 1건(최소 · 제안)**: `IncrementalSchemaCheck.readSchema`(`IncrementalSchemaCheck.kt:82-84`)의 인덱스 확인이 `pg_indexes` 이름만 본다 — CONCURRENTLY 실패로 남은 **INVALID 인덱스도 '있음'**으로 통과하고, 증분 창 조회가 매초 쿼터 테이블을 순차로 읽게 된다. 인덱스 확인에 `indisvalid AND indisready`를 더해 INVALID면 기동 실패(메시지: 지우고 다시 만들라). 정상 경로(Flyway V9)에서는 INVALID가 생기지 않으므로 K1~K10 동작은 같다 — blind 테스트 1개(INVALID 인덱스 DB → 거부 · 스키마 무변경)를 더한다.

**④의 되돌리기**: 기록 전이면 단계 역순(`DROP INDEX CONCURRENTLY` · `DROP TRIGGER` · `DROP FUNCTION` · `ALTER TABLE … DROP COLUMN` — 마지막은 순간 `ACCESS EXCLUSIVE`) — 옛 앱은 어느 단계에서도 그대로 돈다(task 02 가정 1). 기록 뒤에는 ③과 같다(아래 §4.7.4).

### 4.5 ①·③(·②)에서 Flyway가 트랜잭션 안에서 V9를 돌릴 때 — 재는 법

- 영향 예상(위 근거): 새 앱 Flyway가 `ALTER TABLE`에서 옛 앱의 열린 쿼터 트랜잭션을 기다리는 동안 뒤의 모든 쿼터 접근이 줄을 서고, 잡은 뒤에는 인덱스 생성이 끝날 때까지 쿼터 행 읽기·쓰기가 모두 멈춘다. 옛 앱의 선점은 쿼터 행에 닿으므로(precheck 조회 → upsert) **선점 전체가 멈추고** Hikari(앱 DB 커넥션 풀) 대기 → 요청 시한으로 번질 수 있다. 인덱스 대상 값은 기존 행 전부가 같은 `updated_at`(열 추가 시각)이다 — 생성 시간은 행 수(약 610만)에 비례 `[구현 검증]`.
- **재는 것**:
  1. **정지 초**(k6 주 부하 1초 구간 — 201이 0인 초)의 개수와 가장 긴 연속 길이 · 201 < 계획 도착률의 50%인 초(구간별 · §4.7.3).
  2. **락 대기 표본(새 — 촘촘한 표본)**: 전환 창 [T1 − 10초, 새 앱 lb 편입 + 30초](④는 적용판 시작 − 10초 ~ 끝 + 30초도) 동안 0.2초마다 `pg_stat_activity`(`wait_event_type = 'Lock'`인 세션 수 · `application_name` · `pg_blocking_pids(pid)` · `now() − query_start` 최대 · 문장 앞 60자)와 `pg_locks`(관계 = `user_hold_quota` · `granted` 별 모드 · 대기 수) → `timeline-migration-locks.jsonl`. 지금 0.5초 표본(`timeline-locks.jsonl` — lib.sh `db_sampler`)은 그대로 둔다.
  3. **마이그레이션 단계 시간**: Flyway 이력의 `execution_time`(V9 · V10) + 새 앱 로그의 Flyway 시작·끝 줄 시각 + 앱 기동 → health UP 시각. ④는 적용판 단계별 벽시계·재시도 횟수·`lock_timeout` 걸린 수 → `pre-apply.json`.
  4. 구간별 5xx · 502(lb) · 요청 시한 수 · 앱별 Hikari 대기(지금 표본 그대로 — 앱별로).
- 같은 측정을 ①에도 한다 — ①은 부하가 없을 때 V9를 돌리므로 락 대기는 0이고, 대신 중단 = 내리기 + V9·V10 + 기동이 정지 초로 보인다.

### 4.7 지표와 판정 자료

#### 4.7.1 한도 판정 — 결정적으로 세기

**사실**: 두 주 부하 모두 사용자마다 선점이 1건이다(S4c 반복마다 새 사용자 · S3 세션마다 새 사용자 — `s3-full-flow.js:55`). 한도(2)에 닿는 요청이 주 부하에 없으므로, 주 부하만으로는 한도 초과·부당 거절이 **생길 수가 없다** — '0건'이 판정 자료가 되지 못한다(그린 위장).

**고른 것 = 한도 탐침**(하네스 전용 회차 1개 — S4c는 회차 1,000 · S3e는 시드 회차를 2로 늘려 회차 2. 좌석·사용자를 탐침만 쓰므로 그 쌍의 실제 값을 하네스가 정확히 안다):

| 종류 | 순서(사용자 u는 탐침마다 새로) | 맞는 답 | 틀린 답 = 판정 자료 |
|---|---|---|---|
| H(카운터 > 실제) | 선점 1(201) → SQL `cnt = cnt + 1`(cnt 2 · 실제 1) → d초 뒤 선점 2 | 201 | 409 `HOLD_LIMIT_EXCEEDED` = **부당 거절** |
| L(카운터 < 실제) | 선점 1(201) → SQL `cnt = cnt − 1`(cnt 0 · 실제 1) → d초 뒤 선점 2 → 선점 3 | 선점 2 = 201 · 선점 3 = 409 `HOLD_LIMIT_EXCEEDED` | 선점 3 = 201(실제 3 > 2) = **한도 초과** |

- d ∈ {1, 5, 30, 75}초(증분 1초 · C 60초 + 바퀴를 가르는 값) × 종류 2 = 구간마다 8탐침, 구간 시작 + 30초부터. 구간은 단독(옛) · 전환 · 단독(새)(①의 중단 구간에는 탐침이 실패로 남는다 — '중단'으로 분류). 주입 SQL은 주입 시각(DB 시계 `clock_timestamp()`)을 `probe.jsonl`에 남기고, 응답 코드·시각을 함께 남긴다.
- 결과 = (절차, 부하, 구간, 대조 소유, 종류, d)별 맞음·틀림 수 + 그 쌍의 첫 복구(`counter_drift_log` repaired · 출처 · 시각 − 주입 시각).
- 고르지 않은 것: 주 부하만으로 DB 상태(실제 > max) 세기(위 사실 — 생길 수 없다) · k6 원시 기록으로 '409 시점의 실제 값'을 사후에 다시 만들기(만료·확정이 섞인 S3 흐름에서 실제 값을 시각별로 복원할 기록이 없다) · 앱에 판정 기록 추가(옛 앱은 코드 무변경).
- 탐침 쌍은 끝 검사에서 따로 센다: 한도 초과 탐침이 만든 실제 3인 쌍은 `v_over_limit_users`에 잡힌다 → **주 부하 회차의 한도 초과(실제 > max) = 0**과 **탐침 쌍 수 = 탐침의 '한도 초과' 결과 수**를 따로 낸다.

**주 부하의 정합**(탐침 밖):
- S3e 주입 쌍: 지금 effect.json 그대로(쌍마다 첫 복구 출처·시각 · 끝 상태) + 주입 시각의 **대조 소유 구간** 이름표.
- **주입 밖 쌍의 복구**(`counter_drift_log` repaired · 주입·탐침 쌍 제외): 섞임이 스스로 어긋남을 만들었다는 증거다 — 출처·시각·구간별 수(기대 0 — 가설은 task 04).
- 같은 쌍을 두 출처가 본 경우(③·④): 늦은 쪽의 `false_positive` 기록 수(출처 쌍별).

#### 4.7.2 끝 불일치

- 수렴 창 뒤 `/internal/consistency`(마지막 새 앱): `v_counter_mismatch` · `v_over_limit_users`(탐침 분리) · 주입 쌍 끝 상태(`end_pairs`) · `updated_at` NULL 0 · 트리거 존재·활성 · 인덱스 `indisvalid` · V9·V10 이력 행(체크섬 · 설치 순번) → `end-check.json`. 큰 규모는 끝 검사 쿼리 하나에 수 분이 걸릴 수 있다(ADR-011 E3 — 시한 600초 그대로).

#### 4.7.3 선점 멈춤 · 꼬리

- 구간별(단독(옛) · 전환 · 단독(새) · 수렴): 정지 초 수 · 가장 긴 연속 정지 · 201 < 계획 도착률 50%인 초 · 선점 p99 · 1초 p99(99번째 백분위 응답 시간) 최대 · 서버형 느린 초(ADR-012 tail.py 정의 — 최대 응답 > 50ms이고 서버 쪽 대기가 원인인 초) · 5xx · 502 · 요청 시한. 구간 경계는 사건 기록의 실제 시각.
