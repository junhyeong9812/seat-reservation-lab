## 0. 요구사항 원문 (인터뷰 기록)

- 원문: "지금 추가 시험" — 남은 질문 '반감이 디스크 단독 원인인지'를 fstrim(2026-10-12 10:21 KST) 전에 fio로 더 본다.
- Q/A (2026-10-11):
  - 재현할 쓰기 패턴 = **WAL 흉내 + 매번 fsync**(8KB 쓰기마다 fdatasync, DB 회차의 초당 flush 약 2,000회에 맞춤 + data 버퍼 쓰기를 함께 넣어 총량 약 28MB/s).
  - 크기 = **패턴당 8GB, 2회**.
  - 결정 시점 = **추가 시험 뒤 결정**(advisory-try → counter-upsert-precheck 전환 여부를 ADR-007 §8에 한 번에).
- 메인이 실측에서 확인한 사실(명세 근거):
  - 이전 fio의 wal job도 이미 매 쓰기 fdatasync였다. 그러나 **파일 끝에 덧붙이는 쓰기**(fallocate=none, 파일이 자람)라 sync 평균 2.44ms(p50 1.09ms · p90 4.11ms), 호스트 flush 408회/s에 그쳤다(fio-1 `fio.json` sync.lat_ns · `timeline-host.jsonl`의 fio 구간 — wal job 408 IOPS와 일치. 처음 쓴 389회/s는 앞뒤 대기 구간이 섞인 창이었다).
  - DB 회차 반감 전: nvme1n1 flush 1,750~2,055회/s · flush 평균 0.41~0.49ms · 쓰기 23~28MB/s(`20261010-dc-b943a3f0/WDROP.md`). PG WAL은 **미리 만든(0으로 채운) 16MB 세그먼트를 덮어쓴다** — 파일 크기가 안 바뀌어 fdatasync가 메타데이터 저널 커밋을 덜 부른다.
  - 그래서 이전 fio는 "fsync가 드물다"가 아니라 **"fsync 1번이 느린 다른 패턴"**이었다. 이번 시험의 핵심 변경은 **WAL 파일을 미리 채워 두고 덮어쓰기**다.

## 1. 목표·대상 (필수)

`seat-reservation-lab/k6/ADR-007/scripts/fio-disk.sh`에 PG WAL에 가까운 패턴을 고르는 옵션을 더하고, 서버(.164) nvme1n1에서 fio 단독으로 2회(각 약 8GB) 돌려, DB 회차처럼 **누적 약 3.5GB 근처에서 쓰기 반감·flush 지연 상승이 나는지** 판정한다. 결과는 C5 판정 (b)의 재판정으로 ADR-007 §7.2에 들어간다.

- 패턴(기본값 아님 — 새 옵션으로만):
  - wal: 크기 1GB 파일을 **fio 시작 전에 채워 두고**(PG max_wal_size 1GB의 재활용 흉내) 그 안을 8KB 순차 **덮어쓰기** + 매 쓰기 fdatasync, 속도 제한 16MB/s(≈ 2,000회/s). 파일 끝에 닿으면 처음부터 다시(time_based).
  - data: 기존과 같은 버퍼 순차 쓰기 8KB, 속도 12MB/s, fsync 4096쓰기마다.
  - 길이: 총 쓰기 ≈ 8GB가 되게 시간으로 끝낸다(28MB/s × 약 290초 → runtime 300초). 채우기(1GB)는 측정 구간과 분리해 기록한다.
- 실행: fio-sync-1 → (간격만 기록) → fio-sync-2. 각 실행 앞뒤 호스트 표본은 기존과 같다.

## 2. 경계·불변식 (필수)

- 이전 명세(`2026-10-10/adr-007-disk-cause` §2)의 서버 경계를 그대로 따른다: `~/labs/seat-reservation-lab` · compose project seatlab · 시험 파일은 `fio-tmp/` 아래만 · sudo 없음 · nvme0n1 손대지 않음 · 다른 컨테이너·이미지·볼륨 손대지 않음.
- **fstrim(2026-10-12 10:21 KST) 전에 끝낸다.**
- 기존 동작 보존: fio-disk.sh를 새 옵션 없이 부르면 job 파일·meta가 지금과 바이트 동일. campaign.sh main·disk-cause·disk-rest dry-run 출력 동일.
- 바이트 검증 유지: 계획 대비 job별 쓴 바이트가 모자라면 사유를 붙인다(시간 끝 방식이라 기준 = 속도 × 시간 × 0.95). **단 pgwal의 wal job 부족은 실패가 아니라 관찰값**(meta에 wal_ok=false·비율 기록, status 유지) — 찾는 현상(디스크가 느려져 wal을 덜 씀) 자체이기 때문이다(2026-10-11 사용자 재합의 "관찰값으로 기록"). data 부족·채우기 실패·fio 오류는 그대로 실패.
- fio 동안 DB를 띄우지 않는다(단독 조건).

## 5. 검증 방법 (필수)

- 오프라인: 새 옵션 dry-run의 job 파일 확인 · 옵션 없는 dry-run이 HEAD와 바이트 동일 · campaign.sh 세 세트 dry-run 동일 · 인자 검증(잘못된 값 rc=2).
- 라이브 스모크 1회(짧게 60초): 호스트 flush ≈ 2,000회/s · flush 평균이 DB 반감 전과 같은 자릿수(≈ 0.4~0.5ms)인지 — 가정 1.
- 본시험 2회: status ok · 바이트 검증 통과 · 서버 fio-tmp 비움.
- 판정:
  - **(b) 성립**: 두 회 모두 호스트 반감(wdrop) 또는 flush 평균·w_await가 DB 반감 때처럼 뛰는 지점이 누적 약 3~5GB에 있다 — 분석은 전체 쓰기 속도뿐 아니라 **호스트 flush/s에도 같은 반감 규칙**을 적용하고(data 버퍼 쓰기가 총량을 받쳐 총량 반감이 안 보일 수 있다 — 리뷰 rv10), 2회차는 첫 30초 flush 평균·w_await를 1회차 시작 기준값과 비교한다(이미 느린 상태로 시작했는지). flush 평균·w_await의 **지속 상승**(첫 3칸 중앙값의 2배를 연속 2칸)도 꺾임 신호로 본다. 이미 느린 상태로 시작한 회차는 판정 불가로 둔다. **(b) 불성립**은 그 회차의 기준선(첫 30초)이 PG 같을 때(flush ≈ 2,000회/s·평균 ≈ 0.4~0.5ms)만 인정한다(리뷰 rv10 감사) → C5 "디스크(이 패턴에서의 SSD 동작)" 확인.
  - **(b) 불성립**: 8GB 동안 꺾이지 않는다 → 디스크 단독 원인은 기각하고, 원인을 "PG가 이 디스크 위에서 만드는 무언가"(세그먼트 생성·체크포인트 쓰기·볼륨 새로 만들기 등)로 좁혀 NEXT 후보로 남긴다.
- 리뷰: 하네스 변경 = 중간 → 듀얼 1패스(Opus 워커 ∥ codex → 종합 → 감사 → post-fix 재점검 1회).
