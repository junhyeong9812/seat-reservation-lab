   129	### 설계-3 선택지 넷 — 데이터 모델 · 문장 순서 · 잠금 · 배치 · 카운터 · 에러 · 교착 · 되돌리기
   130	
   131	**공통 규칙**(네 선택지 모두):
   132	
   133	- **범위**: A(sweep) + 기본 조합의 확정 경로 + **A 만료 배치의 최소 수정(A′ — §3.6 · 사용자 재합의 2026-11-04)**. 선점 · 정리 ① · B·C·D 경로는 바꾸지 않는다(③의 트리거와 ④의 새 API만 예외 — 각 절). 손잡이 기본값(`current`)은 지금 JPA 확정 · JPA 배치 그대로다(§설계-5 — 측정의 기준선 칸이 바뀌지 않게 · '기존 동작 보존').
   134	- **시각**: 만료 비교는 `:now`(앱 Clock — 설계-0). DB `now()`를 쓰지 않는다 — A 배치가 앱 Clock으로 만료를 고르고(ExpireHoldsService.kt:39) 기존 테스트가 `MutableClock`으로 만료를 만든다(ConfirmReservationServiceTest.kt:26·66 — ADR-014 §설계-2.1 Q1과 같은 이유). 초안 예시의 `expires_at > now()`(§선택지 후보)는 `expires_at > :now`로 바꾼다.
   135	- **에러 계약 · 순서(지금 A와 같다)**: 404 HOLD_NOT_FOUND → 403 HOLD_NOT_OWNED → 409 HOLD_EXPIRED → 409 SEAT_NOT_HELD(ProductSeat.kt:59-73 · ErrorCode.kt:7-10 · ApiExceptionHandler.kt:46-55). 경합에서 진 확정은 이 넷 중 하나로 끝나야 한다 — 5xx 금지(N4). 문장 영향 행이 0이면 잠금 없는 **진단 문장**으로 코드를 고른다(판정은 영향 행 수가 하고, 진단은 코드만 고른다 — 진단 순간 값이 또 바뀌어도 결과(거부)는 같다).
   136	- **구현 형태(권장)**: 새 선택지는 JDBC 문장으로 쓴다(`LazyConfirmProcess`와 같은 방식 — LazyConfirmProcess.kt:36-71). JPA 애그리거트(`ProductSeat.confirm`)는 메모리 판정 + 전체 열 UPDATE라 조건부 문장을 담을 수 없다. `current` 경로(JPA 확정 · JPA 배치)의 SQL · 판정 · 순서는 건드리지 않는다 — 더하는 것은 유니크 위반 매핑(§설계-4)과 관측 지표 `converted_after_expiry{clock=app}`(아래) 둘뿐이다.
   137	- **카운터 · 대조**: 확정은 쿼터 행을 잡지도 쓰지도 않는다(지금과 같다 — 홀드 −1 · 예약 +1이 같은 트랜잭션이라 cnt = 홀드 행 + 확정이 어느 스냅숏에서도 성립). 커밋 뒤 등록 `changes.changed`는 지금 자리 그대로(ConfirmReservationService.kt:60 · LazyConfirmProcess.kt:69). counter-trigger 등 다른 매수 방식은 기동 거부(§설계-5)라 `beforeConfirm`을 부를 일이 없다. 대조 실제 값 정의(V6__backfill_user_hold_quota.sql:2-3 · LoadtestDataService.kt:190-203)는 바꾸지 않는다.
   138	- **최후 방어선 위반**: 예약 INSERT가 §설계-4의 인덱스에 걸리면(23505 · 인덱스 이름 일치) 409 SEAT_NOT_HELD + ERROR 로그 + 지표 `seat.confirm.unique_violation` — 다른 무결성 오류는 그대로 올린다(DbLockHoldStrategies.kt:104-111과 같은 방식 · 무음 변환 금지). **A 확정만**(`current` 포함 · 새 모드 넷). B·C·D 확정(LazyConfirmProcess.kt:61-67)의 23505는 매핑하지 않고 500으로 둔다 — 무음이 아니고(5xx로 드러남), B·C·D는 K2 좌석 잠금(LazyConfirmProcess.kt:44)이 같은 좌석 확정을 직렬화해 두 번째가 409 SEAT_NOT_HELD로 먼저 끝나므로 23505는 '가드가 뚫렸다'는 뜻일 때만 난다(§인터뷰 범위 'B·C·D는 ADR-014 최소 가드 그대로' — 받아들인 한계).
   139	- **만료 뒤 전환된 성공(관측만 — 판정은 바꾸지 않는다)**: 만료 판정 시각은 `:now`(요청 시작 · 앱 Clock — §인터뷰 사용자 답)를 그대로 둔다. 대신 성공한 확정 중 **전환 시각이 그 홀드의 `expires_at` 뒤**인 것을 따로 센다 — 지표 `seat.confirm.converted_after_expiry{clock}`:
   140	  - `clock=db`: 홀드를 지우는 전환 문장이 `RETURNING …, clock_timestamp() > expires_at AS late`로 같이 돌려준다(① C1 · ④ C1 · ③ O2 · ② P4 — `clock_timestamp()` = 그 문장을 실행한 DB 시각 · 트랜잭션 시작 시각인 `now()`가 아니다). 새 모드만.
   141	  - `clock=app`: 커밋 뒤(`TransactionSynchronization.afterCommit`) 앱 `clock.instant() > expires_at`. 모든 A 모드(`current` 포함 — `current`는 `ProductSeat.confirm` 앞에 찾은 홀드의 `expiresAt`(SeatHold.kt:20)을 들고 있다가 커밋 뒤 비교 · SQL은 바꾸지 않는다).
   142	  - 기대: 0이 아닐 수 있다(만료 직전 시작 · 지연 주입 — 설계상 허용되는 성공). 이것은 '이중 결과'가 아니라 **`:now` 규칙이 허용한 창의 크기**다 — 측정에서 모드별 분포(건수 · `전환 시각 − expires_at` 최대)를 남긴다. 두 시계 차는 `[구현 검증]` #12.
   143	- **잠금 순서(A 전체)**: 기다리는 잠금은 **쿼터 행 → 홀드 행 → 좌석 행** 순(새 모드의 배치 A′가 이 순서 — §3.6. 정정 15-02: `current`의 JPA 배치는 쿼터 → 좌석 → 홀드지만 Q15로 새 확정 모드와 짝지어지지 않는다). 확정은 쿼터 행을 잡지 않으므로 **홀드 행 → 좌석 행 → (예약 INSERT FK 검사: 회차 · 좌석 `FOR KEY SHARE`)**. 선점의 좌석 잠금은 NOWAIT라 기다리지 않는다. 초안 §함께 검증할 경합의 '사용자(advisory) → 좌석 → 홀드'는 기본 조합(쿼터 행 — advisory 아님)과 A′ 배치 순서(홀드 → 좌석)에 맞지 않는다 — 새 모드 확정이 좌석을 먼저 잡으면 A′ 배치와 교착한다(§3.2 · 열린 질문 Q2).
   144	
   145	#### 3.1 ① 조건부 문장 — 전환 문장의 WHERE가 곧 확인 (`seat.confirm.mode=conditional`)
   146	
   147	- 데이터 모델: 변경 없음.
   148	
   149	```sql
   150	-- C1 홀드 소비 = 확인(내 것 · 만료 전) — 조건이 모두 홀드 행 자신의 열이라 EPQ가 전부 다시 본다(하위 질의 없음)
   151	DELETE FROM seat_hold WHERE id = :hold AND user_id = :u AND expires_at > :now
   152	RETURNING seat_id, schedule_id, clock_timestamp() > expires_at AS late;   -- late → converted_after_expiry{clock=db}
   153	--   0행 → C1d 진단(잠금 없음): SELECT user_id, expires_at FROM seat_hold WHERE id = :hold
   154	--         없음 → 404 · 남의 것 → 403 · expires_at <= :now → 409 HOLD_EXPIRED
   155	--         '내 것 · 활성'(설계상 생기지 않는다) → ERROR 로그 + 지표 seat.confirm.unexpected + 409 HOLD_EXPIRED(무음 아님)
   156	-- C2 좌석 전환 = 확인(HELD) — 0행 → 409 SEAT_NOT_HELD(C1 롤백)
   157	UPDATE product_seat SET status = 'RESERVED' WHERE id = :seat AND status = 'HELD';
   158	-- C3 예약(created_at = :now — 지금과 같다) — 23505(§설계-4 인덱스) → 409 SEAT_NOT_HELD + 지표
   159	INSERT INTO reservation (schedule_id, seat_id, user_id, payment_uid, status, created_at)
   160	VALUES (:s, :seat, :u, :paymentUid, 'CONFIRMED', :now) RETURNING id;
   161	```
   162	
   163	- 잠금 순서: 홀드 행(C1) → 좌석 행(C2) → FK 검사(C3). C1을 C2보다 먼저 두는 이유: ⓐ 배치와 같은 순서(교착 없음) ⓑ 에러 순서 HOLD_EXPIRED → SEAT_NOT_HELD를 문장 순서가 그대로 만든다.
   164	- 왜 충분한가(A 불변식 ② 'HELD ⇔ 홀드 정확히 1개' 위 — ADR-000 §2.1): 기본 조합 A에서 좌석이 다시 선점되려면 먼저 배치가 그 좌석의 홀드(내 것)를 지워야 한다(선점은 `AVAILABLE`만 잡는다). 그 삭제가 C1보다 먼저 커밋됐으면 C1은 0행(FM1 → 404). C1이 먼저면 C1이 홀드 행을 쥐어 배치 DELETE가 기다린다 → 그동안 좌석은 `AVAILABLE`이 될 수 없다. 홀드 id는 BIGSERIAL이라 다시 쓰이지 않아(V1__init.sql:25) Y의 새 홀드가 내 id로 보이는 ABA(값이 A → B → A로 돌아와 변경을 못 알아채는 문제)가 없다. 같은 홀드 이중 확정(FM2)은 뒤 쪽 C1이 앞 쪽 커밋을 기다린 뒤 0행 → 404.
   165	- 배치와(이 모드에서는 A′ 배치 — §3.6): FM3(확정이 먼저)에서 A′의 조건부 DELETE는 홀드 행을 기다린 뒤 0행 → 그 쌍은 감소 0 · 좌석은 되돌림 대상에 들지 않는다 → **틱은 커밋**(정정 — 초안의 '틱 전체 롤백이 남는다'는 A 배치 무변경 전제였다). 배치가 먼저면 C1 0행 → 404(지금 A의 '배치 뒤 확정 = 404'와 같은 응답).
   166	- 문장 수: 성공 3(지금 A2 · A3 · A5 · A6 · A7 = 5 — 추정 `[구현 검증]` #2) · 실패 +1(진단).
   167	- 되돌리기: 손잡이를 `current`로(스키마 없음).
   168	
   169	#### 3.2 ② 비관락 — 홀드 · 좌석 `FOR UPDATE` 뒤 확인 · 전환 (`seat.confirm.mode=pessimistic`)
   170	
   171	- 데이터 모델: 변경 없음.
   172	
   173	```sql
   174	-- P0 홀드 찾기(잠금 없음) — 없음 404 · 남의 것 403(남의 홀드 행을 잠그지 않으려고 잠금 전에 거른다 — LazyConfirmProcess.kt:38-40 K1과 같다)
   175	SELECT seat_id, schedule_id, user_id FROM seat_hold WHERE id = :hold;
   176	-- P1 홀드 행 잠금 + 새 판정 — 행 없음(그 사이 배치 · 다른 확정) → 404 · expires_at <= :now → 409 HOLD_EXPIRED
   177	SELECT expires_at FROM seat_hold WHERE id = :hold FOR UPDATE;
   178	-- P2 좌석 행 잠금 — status <> 'HELD' → 409 SEAT_NOT_HELD
   179	SELECT status FROM product_seat WHERE id = :seat FOR UPDATE;
   180	-- P3~P5 전환 — 두 행을 쥐었으므로 조건 없이 쓴다. P4는 1행이어야 한다(아니면 ERROR + 롤백 — 설계상 생기지 않는다)
   181	UPDATE product_seat SET status = 'RESERVED' WHERE id = :seat;
   182	DELETE FROM seat_hold WHERE id = :hold RETURNING clock_timestamp() > expires_at AS late;
   183	INSERT INTO reservation (…) VALUES (…) RETURNING id;     -- C3과 같다
   184	```
   185	
   186	- **잠금 순서 = 홀드 → 좌석**(초안 '좌석 → 홀드'를 바꾼다 — Q2). 좌석을 먼저 잡으면: ① ②가 좌석 S를 잠금 ② A′ 배치 B3이 내 홀드 h를 DELETE(행 잠금 획득) 뒤 B5 좌석 S UPDATE에서 ②를 기다림 ③ ②의 P1이 h에서 배치를 기다림 → **고리(40P01 — 교착 탐지로 한쪽 롤백)**. A′가 홀드 → 좌석 순서로 쓰기 때문이다(§3.6 · `[구현 검증]` #3). 정정 15-02: JPA 배치(`current`)는 좌석 → 홀드 순이라 '좌석 → 홀드' 판과 고리가 닫히지 않는다 — 대조판은 A′ 배치와 짝지어 보인다. ADR-014 B·C·D 확정(`LazyConfirmProcess` — 좌석 K2 → 홀드 K3)은 좌석 → 홀드지만, 그쪽 배치는 좌석을 `SKIP LOCKED`로 먼저 잡거나(C) 좌석을 쓰지 않아(D) 고리가 없다(ADR-014 §3.2) — A 배치는 그렇지 않다. 재현 테스트에 '좌석 → 홀드' 대조판을 넣어 40P01이 나는 것을 한 번 보인다(§설계-7 #9).
   187	- ①과의 차이: 확인을 문장 조건이 아니라 잠근 뒤 메모리에서 한다. 잠금 읽기 2문장이 늘고(성공 6), 좌석 잠금을 P2부터 커밋까지 쥔다 — 그동안 같은 좌석 선점은 NOWAIT로 진다(어차피 `HELD`라 선조회 409가 먼저다 — UserLimitStrategies.kt:340).
   188	- 배치와(A′): P1이 먼저면 A′ DELETE가 기다린 뒤 0행 → 그 쌍만 건너뛰고 틱 커밋(①과 같다). 배치가 먼저면 P1 행 없음 → 404.
   189	- 되돌리기: 손잡이.

   191	#### 3.3 ③ 낙관락 — 좌석 버전 비교 (`seat.confirm.mode=optimistic`)
   192	
   193	- **지금 버전은 아무도 올리지 않는다**: `product_seat.version`(V3)은 엔티티에 매핑돼 있지 않고(V3__add_seat_version.sql:1-2 — '@Version을 달면 모든 전략에 낙관락 검사가 걸려 기준선이 바뀐다'), 올리는 곳은 ADR-003 낙관락 선점 전략뿐이다(DbLockHoldStrategies.kt:74-93 · ProductSeatRepository.kt:44-51). 기본 조합의 선점 · 배치 · 확정은 버전을 올리지 않는다 → 확정만 버전을 비교하면 FM1(배치 `AVAILABLE` → Y `HELD` — 상태가 `HELD`로 돌아오는 ABA)을 못 본다.
   194	- 버전을 올릴 방법(Q3):
   195	
   196	| 안 | 내용 | 판단 |
   197	|---|---|---|
   198	| (가) `ProductSeat`에 `@Version` 매핑 | JPA가 모든 좌석 UPDATE에 `version = version + 1 … WHERE version = ?`를 붙인다 | **기각** — 손잡이와 무관하게 모든 전략 · 경로의 SQL이 바뀐다(V3 주석). ADR-003 낙관락 선점은 버전을 먼저 읽고 flush 뒤 `bumpVersion(expected)`를 하는데(DbLockHoldStrategies.kt:86-91) JPA가 먼저 올리면 늘 0행 → 늘 진다. 범위(A 확정만) 밖 |
   199	| (나) 상태가 바뀔 때 버전을 올리는 DB 트리거 — 새 **선택 위치** `db/migration-confirm-version`의 **V14**(15-01b에서 V13 → V14 — 기본 위치의 V12 · V13 위에 두어, 나중에 이 위치를 더해도 '적용된 버전보다 낮은 미적용'이 되지 않게 · §설계-4 번호): `BEFORE UPDATE OF status ON product_seat FOR EACH ROW WHEN (OLD.status IS DISTINCT FROM NEW.status)` → `NEW.version := OLD.version + 1` | 선점 · 배치 · 확정(JPA · JDBC 모두) 코드를 고치지 않고 덮는다. ③ 셀에만 위치를 더한다 — 트리거 비용이 곧 ③의 비용이다 | **권장** — 기동 검사로 짝을 맞춘다(§설계-5 · V4·V8과 같은 방식 — HoldStrategyStartupCheck.kt:97-104 · :122-132) |
   200	| (다) 선점(HoldSeatProcess) · 배치(ExpireHoldsService)에 버전 증가 문장 추가 | 손잡이로 켬 | 차선 — 범위 밖 코드 두 곳을 고친다 · 앞으로 새 쓰기 경로가 빠뜨릴 수 있다 |
   201	
   202	```sql
   203	-- O1 한 문장 = 한 스냅숏(잠금 없음) — A 순서로 판정: 없음 404 · 남의 것 403 · expires_at <= :now 409 HOLD_EXPIRED · status <> 'HELD' 409 SEAT_NOT_HELD
   204	SELECT h.seat_id, h.schedule_id, h.user_id, h.expires_at, s.status, s.version
   205	FROM seat_hold h JOIN product_seat s ON s.id = h.seat_id WHERE h.id = :hold;
