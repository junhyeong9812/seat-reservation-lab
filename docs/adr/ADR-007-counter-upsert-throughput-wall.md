# ADR-007: counter-upsert 처리량 벽 — 원인 진단과 기본 전환 판정
> 번호 이동(2026-10-09, 2차): ADR-006 처리량 벽 진단을 새 ADR-007로 넣으며 기존 ADR-007~012를 008~013으로 옮겼다 — 이 문서의 번호 참조는 새 번호다.

- 상태: 가설 (Hypothesis) — 명세 합의(2026-10-09), 구현·하네스 진행 중
- 명세: `docs/plans/2026-10-09/adr-007-throughput-wall/requirement-spec.md`
- 날짜: 2026-10-09
- 선행: **ADR-006(counter-upsert 재비교 — 결정: advisory-try 유지, 벽 원인을 찾아 해결되면 counter-upsert로 전환)**, ADR-005(1인 매수 제어 — advisory-try 기본)
- 후행: ADR-008(홀드 만료 — counter-upsert를 택하면 만료 배치가 카운터를 내리는 주체)

## 1. 문제

ADR-006에서 counter-upsert(트랜잭션 안 한 문장 `INSERT … ON CONFLICT DO UPDATE … WHERE cnt + 1 <= 상한`)는 S2(사용자 100명 × 각자 좌석 10개 동시)·S7-m1(2매 보유자 + 일반 1명)에서 가장 좋았다. 억울한 좌석 0(advisory-try 67), 같은 사용자 지연 p99 230ms(advisory-try 433), CPU도 덜 든다. 그러나 S4(도착률 계단, 요청마다 새 사용자·좌석)에서 **벽**을 만났다.

- 11단계(목표 4,325건/s)를 26~27초 동안 p99 5~17ms로 버티다가, **10회 모두 같은 초**에 무너진다. 누적 선점은 약 37만 건이다.
- L2와 L4(앱·DB CPU 2개·4개)에서 같은 초에 무너진다 → CPU가 아니다.
- Hikari 대기가 1초 안에 0 → 190으로 뛴다. 서서히 늘어나는 압박보다 전역 정지에 가깝다.
- 벽은 시간 기준 체크포인트가 진행 중인 구간에 있다. counter-upsert만 체크포인트 쓰기가 빨라졌다(WAL +21%).
- 그 결과 L4 엄격 한계가 4,300 → 2,866(5회 중 3회)이다.

또 쓰기 비용이 있다.
- 실제 흐름(S3, 이탈 20%)에서 WAL이 2.8배, 디스크 쓰기가 1.55배다. 좌석에서 지는 시도도 upsert 후 롤백한다(추정).
- 쿼터 행은 만료로 지워지지 않는다.

질문: **벽은 무엇에서 오는가, 그리고 설정이나 구조 변경으로 없앨 수 있는가?** 없앨 수 있고 ADR-006 §6 전환 규칙을 만족하면 기본을 counter-upsert로 바꾼다.

## 2. 원인 후보 (ADR-006 §5.3 ②)

| # | 후보 | 맞다면 보일 것 |
|---|------|--------------|
| C1 | 체크포인트 가속·WAL 압박 — WAL이 빨리 쌓여 `max_wal_size`에 맞춰 체크포인트가 쓰기를 당긴다 | 벽 시각이 체크포인트 진행·전체 페이지 쓰기(FPI) 급증과 맞는다. 대기 이벤트 LWLock:WALWrite·IO:WALSync·DataFileWrite. `max_wal_size`를 키우면 벽이 밀린다 |
| C2 | 버퍼 교체 — 누적 데이터가 `shared_buffers`(128MB)를 넘는다 | 백엔드 직접 쓰기·읽기 급증, 대기 이벤트 BufferIO·BufferMapping. `shared_buffers`를 키우면 벽이 밀린다 |
| C3 | 관계 확장 락 — 쿼터 테이블·인덱스가 계속 늘어난다 | 대기 이벤트 Lock:extend |
| C4 | B-tree 오른쪽 끝 페이지 경합 — S4는 사용자 ID가 늘 증가한다 | 대기 이벤트 LWLock:BufferContent, 설정을 바꿔도 남는다 |

- 누적 행 수와 경과 시간이 겹쳐 있다. 도착 계획이 고정이라 ADR-006 설계로는 둘을 가를 수 없다.

## 3. 선택지 (명세 확정 2026-10-09)

| 방식 | 설명 |
|------|------|
| none | 대조군. advisory-try는 처리량이 none과 같고(ADR-005·006) 억울한 좌석도 해결하지 못해 뺐다(사용자 지적) |
| counter-upsert | ADR-006 그대로 |
| **counter-upsert-precheck** (신규) | 아래 순서 |

counter-upsert-precheck의 처리 순서:

1. 좌석 상태를 **잠금 없이** 먼저 읽는다. 팔렸으면 쓰기 없이 `SEAT_NOT_AVAILABLE`이다.
2. upsert를 한다.
3. upsert가 0행이면 좌석을 다시 읽는다. 그 사이 팔렸으면 `SEAT_NOT_AVAILABLE`, 아니면 `HOLD_LIMIT_EXCEEDED`다.
4. 3b 좌석 잠금으로 넘어간다.

설계 의도:
- 에러 순서는 **명세 순서(좌석 먼저)** 다. 사용자는 '팔렸으면 좌석, 아니면 매수 먼저' 혼합안을 거부했다.
- 매수 초과 사용자는 좌석 락을 잡기 전에 거절된다 → 억울한 좌석 0을 유지한다.
- 남는 틈: 다른 트랜잭션이 커밋 전에 쥔 좌석은 잠금 없는 읽기에 AVAILABLE로 보인다. 그래서 매수가 찬 사용자에게 `HOLD_LIMIT_EXCEEDED`가 난다. 잠금 없이는 볼 수 없다.
- 좌석 잠금 뒤 upsert 안은 매수 초과자가 좌석 락을 잡아 억울한 좌석이 되살아나서 제외했다.

## 4. 가설

| # | 가설 | 틀렸다고 판정할 관측 |
|---|------|------------------|
| H1 | 벽은 체크포인트에서 온다(C1) — 체크포인트 없음 조건에서 counter-upsert의 벽이 사라진다 | 체크포인트 없음에서도 counter-upsert가 S4 11단계에서 무너진다 |
| H2 | 벽은 누적 행 수가 아니라 체크포인트 시각을 따라간다 | 고정 4,200/s·2,000/s에서 벽이 누적 약 37만(각 약 88·185초)에 난다 |
| H3 | shared_buffers 512MB는 벽을 없애지 못한다(C2 아님) | 512MB에서 벽이 사라진다(단 체크포인트 시점도 바뀌므로 대기 이벤트와 함께 판정) |
| H4 | 벽 시각의 대기 이벤트는 WAL·데이터 파일 쓰기 계열이 지배한다 | Lock:extend·BufferContent·BufferMapping이 지배한다(C3·C4·C2) |
| H5 | precheck는 S3-a20 WAL을 none 수준으로 낮추고(counter-upsert의 2.8배 → 1.x배), 억울한 좌석 0·매수 정합 0을 유지한다 | S3 WAL이 counter-upsert와 비슷하다 / S7-m1 억울한 좌석 > 0 / 매수 초과 > 0 |
| H6 | precheck의 남는 틈(커밋 전 잠긴 좌석 → LIMIT)은 S2·S7-m1에서 드물다 | 팔린 좌석에 LIMIT 응답이 매 회차 수십 건 이상 |

## 5. 측정 계획 (명세 §9.2)

| 묶음 | 방식 | 설정 | 부하 | 회차 |
|------|------|------|------|------|
| 진단 | none · counter-upsert · counter-upsert-precheck | 기본(`checkpoint_timeout` 5min·`max_wal_size` 1GB·`shared_buffers` 128MB) · 체크포인트 없음(1h·16GB) · 버퍼 512MB | S4 계단 · 고정 4,200/s 6분 · 고정 2,000/s 6분 | 3 |
| 변형 확인 | 같음 | 기본 | S2 · S7-m1 · S3-a20 | 3 |

- 진단 81회 + 변형 확인 27회, 약 15시간(추정). L4(앱·DB CPU 4개)만 잰다.
- 모든 셀에서 `pg_stat_activity` 대기 이벤트를 초 단위로 기록한다. 고정 4,200/s는 누적 37만에 약 88초, 2,000/s는 약 185초에 닿는다. 둘 다 시간 기준 체크포인트(k6 시작 약 +249초) 전이라 누적과 시각을 가른다.
- 판정 기준(명세 §9.4): ① 벽 원인 ② 지속성 ③ 처리량 ④ 변형 쓰기 비용 ⑤ 변형 정합·롤백 피해 ⑥ 변형 에러 순서 ⑦ 실패 모드.

## 5.1 측정 전 검증

- 테스트 173개 green(4bf8d7d9). precheck는 counter-upsert 계약 묶음에 더해 아래를 확인했다.
  - 팔린 좌석은 쓰기 없이 거절한다. 새 사용자는 쿼터 행이 없고, 기존 행은 xmax 0이다.
  - 매수가 찬 사용자 + 팔린 좌석 → 좌석 불가(명세 순서).
  - 커밋 전 잠긴 좌석에서 매수가 찬 사용자는 LIMIT(남는 틈, 좌석 락 시도 없음)이고, 매수가 남은 사용자는 3b에서 좌석 불가다.
  - 없는 좌석 → 좌석 없음.
- 그린 위장 점검: 선조회를 빼면 테스트 2개가 실패한다.

## 6. 전환 판정 (ADR-006 §6 전환 규칙)

- 벽이 **설정으로 사라지거나 계단 상한 밖으로 밀린다**(운영에서 조정 가능). 고정 도착률에서도 지속 처리량이 none과 같다. 실패 시도의 쓰기 비용이 해소되거나 수용 가능한 수준으로 확인된다 → **counter-upsert로 전환**. 쿼터 행 정리 설계를 함께 넣는다.
- 벽이 **쿼터 테이블 구조**에서 오고 설정으로 안 사라진다 → **advisory-try 유지**. counter-upsert는 구조를 바꾼 뒤 다시 잰다.
