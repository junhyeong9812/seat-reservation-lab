# Seat Reservation Lab

좌석 10,000석에 동시 접속 20만 명이 몰리는 공연 예매를 가정하고, 좌석 예약에서 생기는 동시성 문제를 하나씩 부하 테스트로 측정해 방식을 정하는 실험 저장소다. 질문마다 ADR(결정 기록)을 하나씩 쓰고, 가설과 합격 기준을 먼저 적은 뒤 측정하고 결정한다.

- 스택: Kotlin 2.2, Spring Boot 3.5, JPA, PostgreSQL 16, Redis(Redisson), Flyway, k6, Docker
- 진행 상황(2026-11-18): ADR-017까지 결정. 다음은 ADR-018 연석 예약

## 다루는 질문

| # | 질문 | 상태 | 결정 기록 |
|---|---|---|---|
| 1 | 같은 좌석에 1,000명이 동시에 요청하면? | 결정 | ADR-003, 004 |
| 2 | 2연석 중 1석만 선점에 성공하면? | 예정 | ADR-018 |
| 3 | 좌석을 선점해 놓고 결제 없이 떠나면? | 결정 | ADR-014 |
| 4 | 오픈 정각에 20만 명이 동시에 들어오면? | 예정 | ADR-020 |
| 5 | 화면에서는 빈자리였는데 요청하니 이미 팔렸다면? | 예정 | ADR-019 |
| 6 | 결제는 성공했는데 그 사이 선점이 만료됐다면? | 결정 | ADR-015, 016, 017 |
| 7 | 테스트가 끝났을 때 좌석 상태는 정말 정확한가? | 결정 | ADR-001 |

1인 최대 2매 제한(ADR-005~008)과 매수 카운터의 정합성(ADR-009, 012, 013)은 질문 1을 풀다가 이어진 문제다.

## 부하 가정과 근거

| 사례 | 관찰된 수치 | 출처 |
|---|---|---|
| 소형 공연 (1,500석) | 예매 시작 5분 안에 전석 매진 | [뉴스핌](https://www.newspim.com/news/view/20260922000268) |
| 스타디움 3회차 공연 | 순간 동시 접속 21만 명 이상, 일반 예매 22분 만에 매진 | [TV리포트](https://v.daum.net/v/20260626124216017) |
| 초대형 내한 공연 | 최대 동시 접속 약 130만 명, 35분 만에 매진 | [뉴스1](https://m.news.nate.com/view/20260521n29892) |
| 글로벌 최대 사례 | 하루 35억 건 요청, 이전 피크의 4배 | [Ticketmaster](https://business.ticketmaster.com/press-release/taylor-swift-the-eras-tour-onsale-explained/) |

동시 접속 수치는 대기열에서 기다리는 인원을 포함한 접속자 수이고, 초당 요청 수가 아니다. 국내 예매사는 측정 방식을 공개하지 않아 규모를 가늠하는 용도로만 썼다.

이 실험은 스타디움 사례를 모델로 잡았다. 좌석 10,000석, 피크 동시 접속 200,000명, 1인 최대 2매, 홀드(선점 유지) 5분이다.

## 지금 적용된 방식

| 항목 | 방식 | 결정 기록 |
|---|---|---|
| 같은 좌석 선점 | `SELECT ... FOR NO KEY UPDATE NOWAIT`. 이미 잠긴 좌석은 대기 없이 바로 409 | ADR-003 |
| 느린 작업(외부 호출) | 좌석 확인 뒤에 둔다 | ADR-004 |
| 1인 매수 제한 | 카운터 테이블 단일 쿼리 upsert + 사전 조회(`counter-upsert-precheck`) | ADR-007, 008 |
| DB 설정 | 인덱스 5개, 커넥션 풀 10 | ADR-002 |
| 카운터 불일치 | 만료 배치는 실패한 키만 스킵, 증분 보정 1초 + 폴백 스캔(1분마다 DB 시간 2초) | ADR-009, 012 |
| 홀드 만료 | 만료 배치(`sweep`) | ADR-014 |
| 결제 확정 | 결제 시작 시 홀드 연장 + 결제 마감 시각(`conditional-extend` + `payBy`) | ADR-015, 016 |
| 확정 실패 시 | 즉시 환불(`refund`) | ADR-017 |
| 측정용 앱 | 메모리 2g + 세대형 ZGC, k6 버전 고정, 측정 전 k6 PC 점검 | ADR-010, 011 |

## 결정 기록 (ADR)

질문, 결정, 결정 근거 하나만 적었다. 선택지별 측정값, 미리 정한 합격 기준, 탈락 이유는 각 문서에 있다.

| ADR | 질문 | 결정 | 결정 근거 |
|---|---|---|---|
| [000](docs/adr/ADR-000-baseline-domain.md) | 무엇과 비교할 것인가 | 동시성 제어가 없는 평범한 구현을 베이스라인으로 | 이후 ADR이 여기서 문제를 관측하고 하나씩 고친다 |
| [001](docs/adr/ADR-001-consistency-oracle.md) | 결과가 정말 정확한가 | DB 행을 직접 세고 응답과 비교하는 정합성 검증기 | DB만 보면 위반 0, 응답과 비교하니 실패 응답인데 확정된 건 345건(CPU 1개) |
| [002](docs/adr/ADR-002-db-baseline.md) | 비교 기준이 될 DB 설정은 | 인덱스 5개 + 커넥션 풀 10 | 인덱스로 한계 처리량 378 -> 2,867건/s(CPU 2개). 풀 10/20/40은 처리량이 같다 |
| [003](docs/adr/ADR-003-same-seat-contention.md) | 같은 좌석 경합을 어떻게 처리하나 | FOR UPDATE NOWAIT | 대기 없이 바로 실패시키는 방식 중 추가 인프라가 없다. p50/p99 33/288ms(CPU 4개) |
| [004](docs/adr/ADR-004-critical-section-hold-time.md) | 락을 잡은 동안 느린 작업이 끼면 | 느린 작업은 좌석 확인 뒤에 | 외부 호출 20ms에서 블로킹 방식의 경합 없는 요청 처리량 388 -> 322건/s |
| [005](docs/adr/ADR-005-per-user-limit.md) | 1인 2매를 어떻게 막나 | advisory-try (counter는 재측정) | counter가 롤백 피해 0 vs 67석으로 낫지만 처리량 1,911 vs 4,300건/s |
| [006](docs/adr/ADR-006-counter-upsert.md) | counter를 단일 쿼리로 줄이면 | advisory-try 유지 | 4,325건/s에서 26~27초 뒤 10회 모두 같은 초에 처리량 급락, 원인 모름 |
| [007](docs/adr/ADR-007-counter-upsert-throughput-wall.md) | 처리량 급락의 원인은 | precheck로 전환 | 동시성 제어가 없어도 같은 지점에서 급락, DB 없이 fio만으로 재현. 원인은 디스크 flush |
| [008](docs/adr/ADR-008-precheck-default.md) | 코드 기본값으로 넣어도 되나 | precheck 기본 적용 | 13회 전부 합격, 한계 처리량 4,297건/s |
| [009](docs/adr/ADR-009-counter-drift.md) | 카운터가 실제와 달라지면 | 실패한 키만 스킵 + 앱 내 보정 배치 | 주입한 불일치 180/180 복구, 오탐 0, 비용 p99 +1.0% |
| [010](docs/adr/ADR-010-jvm-gc-baseline.md) | 짧은 앱 멈춤은 무엇인가 | 메모리 2g + 세대형 ZGC | GC 정지 3.5 -> 0.2ms, 앱 CPU 170 -> 143% |
| [011](docs/adr/ADR-011-measurement-tail-latency.md) | 남은 테일 레이턴시의 원인은 | 측정 전 k6 PC 점검, k6 버전 고정 | 다른 컨테이너를 내리자 26초 주기 스파이크 16/16 -> 0/20 |
| [012](docs/adr/ADR-012-incremental-reconcile.md) | 보정 배치가 데이터만큼 느려지면 | 증분 보정(1초) + 폴백 스캔 | 30분 부하 후반 스파이크가 보정을 끈 수준으로 줄고, 주입한 불일치 100% 복구 |
| [013](docs/adr/ADR-013-counter-config-cutover.md) | 서비스 중에 보정 방식을 바꾸려면 | 새 앱 롤링 배포 + 보정으로 따라잡기 | 5가지 절차 30회 모두 전환 중 손실 0, 작업 단계가 가장 적다 |
| [014](docs/adr/ADR-014-hold-expiry.md) | 홀드 만료를 어떻게 처리하나 | 만료 배치(sweep) 유지 | 조회 시점 판정 방식은 정합성은 통과했지만 DB CPU 1.19배(허용 1.10배) |
| [015](docs/adr/ADR-015-confirm-atomicity.md) | 결제 뒤 확정이 만료와 겹치면 | 조건부 UPDATE 한 번으로 확정 | 경합 시 확정 5xx 18~26건 -> 0, 확정 p99 1.84~1.99 -> 1.32~1.38ms |
| [016](docs/adr/ADR-016-paid-seat-loss.md) | 결제하고도 좌석을 잃는 사용자는 | 결제 시작 시 홀드 연장 + 결제 마감 시각 | 좌석을 잃은 사용자 11.09% -> 0, 결제 전 거부와 결제 실패 합계 0.36% |
| [017](docs/adr/ADR-017-confirm-failure-compensation.md) | 그래도 확정에 실패하면 | 즉시 환불 | 27회 모두 유효. 승인 후 매입 방식은 확정 p99가 1.22배라 탈락 |
| [018](docs/adr/ADR-018-adjacent-seats.md) | 2연석 중 일부만 선점되면 | 예정 (가설 단계) | 해당 없음 |
| [019](docs/adr/ADR-019-seat-map-query.md) | 좌석 맵 조회와 실제 상태가 다르면 | 예정 (가설 단계) | 해당 없음 |
| [020](docs/adr/ADR-020-open-spike.md) | 오픈 순간 요청이 몰리면 | 예정 (가설 단계) | 해당 없음 |
| [021](docs/adr/ADR-021-kafka-replica-reconcile.md) | 불일치 탐지를 읽기 복제본으로 옮기면 | 보류 | 쓰기량이 더 늘어나는 조건을 측정한 뒤 시작한다 |

## 측정 원칙

- 측정 전에 가설과 합격 기준을 먼저 적는다. 결과를 보고 기준을 바꾸지 않기 위해서다.
- 방식을 비교할 때는 대조군(동시성 제어 없음)을 함께 돌린다.
- 측정하지 않은 것은 "미측정", 추론은 "추정"으로 적는다.
- 결과는 DB에 남은 행을 직접 세어 확인하고, 클라이언트가 받은 응답과 비교한다(ADR-001).

## ADR 본문에서 쓰는 말

ADR 본문은 측정하면서 쓴 기록이라 줄임말이 많다. 본문을 읽을 때 이 표를 참고한다.

| 본문의 말 | 뜻 |
|---|---|
| 기준선 | 베이스라인. 동시성 제어가 없는 구현 또는 비교 기준이 되는 설정 |
| 판정기 | 정합성 검증기. DB 행을 세고 응답과 비교하는 도구 |
| 유령 확정 | 클라이언트는 실패 응답을 받았는데 서버는 확정 처리한 건 |
| 벽 | 처리량 급락. 부하를 올리다가 처리량이 갑자기 떨어지는 지점 |
| 이긴 쪽, 진 쪽 | 경합에서 성공한 요청, 실패한 요청 |
| 억울한 좌석 | 한 요청이 좌석을 잡았다가 롤백하는 동안 다른 사용자가 놓친 좌석 |
| 억울한 사용자 | 결제를 끝냈는데 확정이 거부돼 좌석을 잃은 사용자 |
| 어긋남 | 카운터와 실제 예약 수의 불일치(drift) |
| 쌍 | (회차, 사용자) 키 |
| 대조 | 보정 배치(reconcile). 카운터를 실제 값과 비교해 고치는 작업 |
| 견딤 | 만료 배치가 실패한 키만 스킵하고 계속 실행하는 것 |
| 안전망 | 폴백 스캔. 증분 보정이 놓친 불일치를 찾는 주기적 전체 스캔 |
| 바퀴 | 풀 스캔 1회 |
| 꼬리, 튐 | 테일 레이턴시, 스파이크 |
| 느린 초 | 최대 응답이 50ms를 넘은 1초 구간의 수 |
| 손잡이 | 기본값은 아니지만 설정으로 켤 수 있게 남긴 옵션 |
| 틱 | 배치가 한 번 실행되는 주기 |
| L1, L2, L4 | 앱과 DB에 CPU를 1개, 2개, 4개 준 조건 |
| S2 | 사용자 100명이 각자 좌석 10개를 동시에 요청하는 시나리오 |
| S3 | 입장부터 선점, 확정 또는 이탈까지 전체 예매 흐름 시나리오 |
| S4 | 초당 요청 수를 단계적으로 올리는 시나리오 |
| S7-m1 | 2매 보유자 1명과 일반 사용자 1명이 경합하는 시나리오 |

## 저장소 구조

Gradle 다중 프로젝트다. 루트에는 settings, 플러그인 버전, Gradle wrapper만 둔다.

| 폴더 | 내용 |
|---|---|
| `main-app/` | 업무 앱. 좌석 선점, 확정, 만료, 카운터 보정 |
| `reconcile-core/` | 불일치 탐지와 복구 공통 모듈 (ADR-012) |
| `reconciler-app/` | 별도로 띄우는 보정 앱 (ADR-012) |
| `k6/ADR-NNN/` | ADR별 부하 테스트 스크립트와 결과 |
| `docs/adr/` | 결정 기록 |

- 테스트: `./gradlew test`
- jar: `./gradlew :main-app:bootJar`
