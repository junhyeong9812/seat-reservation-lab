# ADR-014: 운영 중 매수 방식 전환 — 기존 데이터가 있을 때

> 번호 이동(2026-10-15, 6차): 앱 JVM GC·메모리 기준을 새 ADR-010으로 넣으며 기존 ADR-010~016을 011~017로 옮겼다 — 이 문서의 번호 참조는 새 번호다.
> 번호 이동(2026-10-16, 7차): 측정 환경 꼬리 지연 원인을 새 ADR-011로 넣으며 기존 ADR-011~017을 012~018로 옮겼다 — 이 문서의 번호 참조는 새 번호다.
> 번호 이동(2026-10-18, 8차): 카운터 증분 대조·Kafka/복제본 대조를 새 ADR-012·013으로 넣으며 기존 ADR-012~018을 014~020으로 옮겼다 — 이 문서의 번호 참조는 새 번호다.

- 상태: 가설 (Hypothesis) — 미측정. 작업 착수 시 새 명세(인터뷰)부터 시작한다.
- 대응 질문: "advisory-try(또는 none)로 운영 중이던 서비스를 counter 계열로 바꾸려면 — 기존 홀드·예약 데이터와 롤링 배포 중 섞여 도는 옛 버전은 어떻게 처리하나?" (사용자 제기 2026-10-12)
- 선행: ADR-008(V6 백필 — '멈추고 바꾸기'만 지원) · **ADR-009**(대조·복구·트리거 — 이 ADR의 전환 도구)
- 번호: 009 어긋남 → 010 전환(사용자 결정 2026-10-12 — 전환이 ADR-009의 대조·복구·트리거를 그대로 쓰기 때문)

## 문제

ADR-008의 V6 백필은 전환 전제로 "카운터를 유지하지 않는 옛 버전의 쓰기 주체를 모두 멈춘다"를 둔다. 그래서:

- 전환하는 동안 선점이 멈춘다(다운타임).
- 롤링 배포(옛 버전과 새 버전이 함께 도는 구간)에서는 쓸 수 없다. 옛 버전이 카운터를 올리지 않고 홀드를 쓰면 V6 직후부터 다시 어긋난다(ADR-009 §1의 어긋남 — 만료 정지·조용한 한도 초과).

## 선택지 후보

| 선택지 | 순서 | 예상 장단점 |
|---|---|---|
| ① 멈추고 바꾸기 (ADR-008 V6) | 옛 앱 정지 → V6 백필 → 새 앱 기동 → 불일치 0 확인 | 단순·확실 / 다운타임 |
| ② 그림자 모드 = 확장 → 전환 → 정리 (expand/contract) | ⓐ 새 버전을 "카운터는 올리고 내리되 판정은 옛 방식"으로 배포 ⓑ 옛 버전이 다 내려가면 ADR-009 대조(C)로 어긋난 쌍 복구 ⓒ 불일치 0 확인 뒤 설정으로 판정을 counter 계열로 ⓓ 옛 방식 코드 제거 | 다운타임 없음·롤링 배포 안전 / 그림자 모드라는 새 동작, 카운터 쓰기 비용을 먼저 치름 · ADR-009 기동 검사는 C를 counter 계열에서만 허용하므로 그림자 모드를 그 집합에 넣는 조합 규칙 확장이 필요 |
| ③ 대조로 따라잡기 | 새 버전을 바로 배포 + 짧은 주기 대조로 어긋남을 계속 고침 | 단순 / 섞여 도는 동안 한도 초과·부당 거절이 실제로 날 수 있음 |
| ④ 트리거 먼저 (ADR-009 B) | 트리거를 먼저 설치해 옛 버전 쓰기도 DB가 카운터에 반영 → 백필 → 판정 전환 | 앱 버전과 무관하게 정합 / 트리거 쓰기 비용·교착(ADR-009 측정) · **ADR-009 B 그대로는 쓸 수 없다**: V8 트리거는 엄격해 쿼터 행이 없으면 증가도 SR001로 거절하고 행을 만들지 않는다 → 백필 전 옛 버전의 선점·만료가 실패한다. 또 기동 검사가 '트리거 ⇔ counter-trigger'를 강제해 옛 방식 판정 버전이 뜨지 못한다. 행을 만드는(upsert) 비엄격 변형 + 백필 순서 재설계가 필요 |

- 비교할 것(예상): 전환 구간 동안 매수 정합(한도 초과·부당 거절 수) · 다운타임 · 전환 비용(처리량·WAL) · 되돌리기(롤백) 경로 · 운영 절차의 단계 수.
