# ADR-009: 카운터 어긋남 탐지·격리·복구 · 판매 마감 · 쿼터 행 정리

- 상태: 결정됨(Accepted) — 2026-10-14. 매수 카운터는 그대로 쓰고, A(만료 배치 쌍 단위 견딤) + C(앱 안 대조)를 기본으로 켜 어긋나도 스스로 복구되게 한다. 쿼터 행 정리 ①(마감 후 회차 단위)·판매 마감 기본 켬. B(DB 트리거)·F(별도 대조 앱)는 선택지(§8). 본측정 84/84 ok(§7).
- 측정 전 고정: §1~§6은 본측정 전에 커밋했다(63e53775 — 가설을 결과에 맞춰 고치지 않기 위해). §7·§8은 측정 뒤에 썼다.
- 명세: `docs/plans/2026-10-12/adr-009-counter-drift/requirement-spec.md`(§10·§11 재합의 포함) · 설계: 같은 폴더 `design-v2.md`·`design-sql/` · 기록: `log.md`
- 날짜: 2026-10-12 ~
- 선행: **ADR-008 §6**(넘긴 것: R1 카운터 어긋남 · 쿼터 테이블 없는 환경의 기동 검사 · 쿼터 행 정리) · ADR-007(저장 경로 C5 — 처리량 절대값 해석 단서)
- 후행: **ADR-010**(운영 중 매수 방식 전환 — 이 ADR의 대조·복구·트리거를 전환 도구로 쓴다) · ADR-011(홀드 만료 방식 Q3) · ADR-012(확정 원자성 — 확정↔만료 경합, 아래 §6 ③)

## 1. 문제

ADR-008에서 매수 제어 기본값이 counter-upsert-precheck(카운터 = 쿼터 행 `user_hold_quota.cnt`)가 됐다. 정상 경로에서는 카운터가 실제 값(`seat_hold` 행 + CONFIRMED 예약)과 어긋나지 않는다(ADR-008 13회 불일치 0). 그러나 **어긋났을 때 막을 장치가 없다**(ADR-008 §6 ①, R1):

| 어긋남 | 결과 (지금 코드) |
|---|---|
| 쿼터 행 없음 | 만료 배치의 감소 `check(updated == 1)` 실패 → **만료 틱 전체 롤백, 매 틱 반복 → 모든 회차 만료 정지**(좌석이 HELD로 남음) |
| cnt < 감소 수 | `CHECK (cnt >= 0)` 위반 → 같은 전역 정지 |
| cnt가 실제보다 조금 작음 | 감소는 성공, **조용히 한도 초과 허용** |
| cnt가 실제보다 큼 | 감소는 성공, **조용히 정상 사용자 거절** |

어긋남이 생기는 경로: 전환 전제(옛 버전 쓰기 정지) 위반 · DB 직접 수정 · 앞으로의 버그.

함께 다루는 것 (ADR-008이 넘김 + 설계 중 발견):

- **판매 마감 미정의**: 회차 `starts_at`은 저장만 되고 어디서도 검사하지 않는다(ADR-000 설계 누락 — 사용자 확인 2026-10-12). 공연이 시작된 뒤에도 선점이 된다.
- **쿼터 행 정리**: 만료로 쿼터 행이 지워지지 않아 계속 쌓인다.
- **기동 시 검사**: 쿼터 테이블이 없는 DB에서 쿼터를 쓰는 방식으로 뜨면 기동은 되고 요청 때 500이 난다.

질문: **어긋남을 막거나, 생겨도 전역 정지 없이 찾아 고치는 방법 중 무엇이 가장 싸고 확실한가? 그 비용은 부하 처리량을 얼마나 깎는가?**

## 2. 선택지 (명세 §1 · 사용자 결정 2026-10-12)

| 후보 | 하는 일 | 막는 것 | 못 막는 것·비용 |
|---|---|---|---|
| **A** 쌍 단위 견딤 (`counter-drift.expiry-repair`) | 만료 배치의 감소를 가드 감소(`cnt >= n`)로 바꾸고, 실패한 (회차, 사용자) 쌍만 그 자리에서 실제 값으로 다시 세어 덮어쓴다. 나머지 쌍은 정상 만료 | 전역 만료 정지(행 없음·음수) | 조금 작음·큼(감소가 성공하므로 안 보임) |
| **B** DB 트리거 (`limit-strategy: counter-trigger`, `db/migration-trigger` V8) | 홀드·예약 행이 바뀔 때 DB가 같은 트랜잭션에서 cnt를 고친다. 한도 판정은 앱. 트리거는 엄격(행 없음·음수 → 오류), 마감 회차는 기여 쪽별로 건너뜀 | 앱 경로·옛 버전 쓰기의 어긋남(원천 차단) | DB 직접 cnt 조작. 모든 쓰기에 비용 · 확정↔만료 교착(만료가 쿼터 행 선잠금으로 회피) |
| **C** DB 안 청크 대조 (`counter-drift.reconcile`) | 앱 안 전용 스케줄러가 60초마다 열린 회차를 두 갈래로 훑는다: ① 쿼터 행을 키 순서로 읽고 쌍마다 실제 값 탐색 ② 쿼터 행이 없는 쌍은 홀드·예약 쪽에서 찾기. 어긋난 쌍은 잠근 뒤 다시 세어 자동 복구, 맞으면 오탐으로 기록 | 네 갈래 전부(탐지까지 최대 한 주기) | 앱 풀·DB 읽기 비용 |
| **F** 별도 대조 앱 (`reconciler` 프로필) | C와 같은 일을 별도 컨테이너(같은 jar, 포트 8102)에서 | C와 같음 | DB 읽기 비용은 C와 같음, 앱 CPU 간섭만 다름(가정) |

조합 규칙(기동 검사 — 사용자 결정): C·F를 켜면 A 필수(마감 회차는 대조에서 빠지므로 남은 홀드의 감소 실패는 A가 맡음) — 단 B는 예외(트리거가 마감 회차를 건너뛰어 정지 경로가 없음). B + A는 거부. B + 판매 마감 끔은 거부(한도 우회).

함께 넣는 것:

- **판매 마감**: `now(앱 Clock) >= starts_at`이면 선점 거절 `SCHEDULE_CLOSED`(409). 판정 순서 마감 → 좌석 → 매수. 확정은 막지 않는다. 회차 행 `FOR SHARE`로 정리 ①과 직렬화. 끄는 키 `sales-close.enabled`.
- **쿼터 행 정리 2방식**: ① `schedule` — 마감 뒤 회차 행 `FOR UPDATE` → 홀드 0 재확인 → 회차 쿼터 행 전체 삭제 ② `zero` — cnt = 0 행 삭제.
- **판정기 v2**: `v_counter_mismatch`는 열린 회차만 센다(마감 회차는 카운터를 쓰지 않음 — 사용자 결정).
- **기동 검사**: 쿼터 테이블을 쓰는 방식 전부 + 위 조합 규칙.

## 3. 가설 (측정 전 고정)

| # | 가설 | 틀렸다고 판정할 관측 |
|---|------|------------------|
| H1 | **대조군(후보 끔)은 행 없음·음수 주입으로 전역 만료 정지를 재현한다** — 문제의 실재 | control 효과 셀에서 주입 뒤 틱 실패 0 · 끝 오래된 HELD 0 |
| H2 | **A는 행 없음·음수(D·L1) 쌍을 고쳐 전역 정지를 0으로 만들지만, 조용한 어긋남(L2 조금 작음·H 큼)은 고치지 못한다** | A 효과 셀에서 틱 실패 > 0 / 끝 오래된 HELD > 0 / D·L1 복구 수 ≠ 주입 수 / D·L1 끝 cnt ≠ 실제 / L2·H가 고쳐짐 |
| H3 | **A+C·A+F는 주입한 네 갈래를 100% 탐지·복구하고, 주입 안 한 쌍의 오탐 복구는 0이다.** C·F의 탐지 시간은 대조 주기(60초) + 한 바퀴 안 — **L2·H로 판정한다**(D·L1은 대부분 A가 먼저 고쳐 A의 시간이 된다) | 주입 쌍 중 끝에 cnt ≠ 실제 / 오탐 복구 > 0 / L2·H 탐지 시간 > 2주기 |
| H4 | **C·F 대조의 부하 비용은 작다** — S4c4200(고정 도착률 4,200건/s)에서 대조군(A) 대비 처리량·선점 p99 차이가 5% 미만이고, 디스크 벽 시작 시각이 앞당겨지지 않으며, 한 바퀴는 부하 중에도 주기(60초)보다 짧다 | 처리량 또는 p99 차 ≥ 5% / 벽 시작이 앞당겨짐 / 바퀴 ≥ 60초 |
| H5 | **F와 C의 DB 쪽 비용은 같고, 차이는 앱 쪽 간섭(CPU·커넥션 풀 대기)뿐이다**(명세 가정 2) | F와 C의 **DB 쪽 대기 이벤트**(출처별 대기 표본 — C는 문장 표지 근사)가 다르다. 대조 청크 시간은 풀 대기를 포함하므로(C는 앱 풀 공유) 반증 근거로 쓰지 않고, 처리량·p99 차이는 앱 간섭의 크기로 해석한다 |
| H6 | **B는 앱 경로의 어긋남을 원천 차단하지만 쓰기 비용이 크다** — S3-a20(입장→선점→확정 실제 흐름, 이탈 20%) 선점당 WAL이 대조군보다 늘고(설계 단일 세션 근사 +17%), S4c4200 선점 p99가 대조군보다 높거나 디스크 벽이 앞당겨진다. B+C에서 행 없음·작음 주입의 틱 실패는 C 복구 뒤 멈춘다 | B의 선점당 WAL·p99·벽 시각이 대조군과 같다 / B+C에서 복구 뒤에도 틱 실패 · (B 단독의 '직접 조작을 못 고치고 복구 전까지 만료 정지'는 효과 셀이 없어 측정하지 않는다 — 코드에서 끌어낸 추론, §6 ⑨) |
| H7 | **판매 마감의 회차 행 `FOR SHARE` 비용은 10% 미만이다**(사용자 기준 R1 — 넘으면 잠금 방식을 다시 정함, 2026-10-13 관측 보강: 처리량과 함께 p99·벽 시각도 본다). 회차 하나에 요청이 몰리는 구조라 MultiXact가 생긴다 | control 대 control-noclose(S4c4200 디스크)에서 처리량 또는 선점 p99 차 ≥ 10% / 디스크 벽 시작이 앞당겨짐 · 함께 기록: 마감 판정 시간(선점당 평균 ms)·MultiXact 수 |
| H8 | **정리 ①은 홀드가 남은 동안 지우지 않고, 홀드 0이 된 뒤 회차 쿼터 행을 모두 지운다. ②는 cnt 0 행만 지운다. 마감 직전까지 카운터 정합이 유지된다.** 마감 뒤 선점은 전부 `SCHEDULE_CLOSED`, 마감 뒤 확정은 성공 | ①이 홀드 남은 동안 삭제 / ① 끝에 홀드 0인데 쿼터 행 남음 / ② 끝에 cnt 0 행 남음 / 마감 5초 전 표본 불일치 > 0 / 마감 뒤 선점이 `SCHEDULE_CLOSED` 아님 / 마감 뒤 확정 실패 (마감 뒤에는 열린 회차가 없어 판정기 불일치로는 반증할 수 없다 — §6 ⑩) |

## 5. 판정 기준 (명세 §5 — 사용자 기본 안 2026-10-12)

1. 주입한 어긋남에서 **만료 전역 정지 0** (B·B+C는 주입 → 복구 구간의 행 없음·작음 원인 틱 실패를 B의 결과로 기록 — 사용자 결정 'B 엄격'의 결과)
2. 주입한 쌍 **100% 탐지·복구**(조용한 누락 0) + 주입 안 한 쌍의 **오탐 복구 0**
3. **비용**: S4c4200 처리량·선점 p99·디스크 벽 시작 시각, S2 p99, S3-a20 선점당 WAL을 대조군과 비교. **허용선은 측정을 본 뒤 사용자와 함께 정한다.**
4. 판매 마감 `FOR SHARE`: 마감 끔 대비 처리량 또는 p99가 10% 이상 나쁘거나 벽이 앞당겨지면 잠금 방식을 다시 정한다(§11 R1 — 2026-10-13 사용자: 고정 도착률 셀에서 처리량만으로는 둔감하므로 p99·벽 시각 추가).

**고정 도착률 셀의 처리량 한계**: S4c4200은 디스크에서는 ADR-007 벽(약 2,900건/s)에 묶이고, tmpfs에서는 도착률(4,200건/s)과 같아진다. 그래서 처리량만으로는 비용이 보이지 않을 수 있다 — 비용 판정은 p99·벽 시작 시각·선점당 WAL을 함께 본다.

## 6. 받아들이는 한계 (측정 전에 알려진 것)

1. **B의 엄격성 범위는 트리거 경로다.** B 선점 경로는 쿼터 행이 없으면 cnt 0으로 만들고 판정한다(precheck와 같은 기존 의미) — 조용한 '행 없음 → 작음' 변환은 C가 잡는다.
2. **시각 출처**: 앱 경로는 앱 Clock 하나로 통일했다(B 트랜잭션마다 `seatlab.counter_now`를 SET LOCAL). DB 직접 쓰기는 DB `now()`로 폴백한다 — 앱·DB 서버 시계 차만큼 마감 경계가 어긋날 수 있다.
3. **확정↔만료 경합의 정합**(범위 밖 → ADR-012): 확정과 만료 모두 좌석 행을 잠그지 않는다. 지금 정합은 orphanRemoval DELETE의 행 수 확인(StaleState) 하나에 기대는 것으로 보인다(설계 실험 M1 — 실제 Hibernate 동작 확인은 구현 검증 대장 IV-009-1). B의 선잠금은 교착만 없앤다.
4. **C의 DB 세션 구분은 근사다**: C는 앱 풀을 공유해 접속 이름으로 가를 수 없다 — 대기 표본에서 문장 표지로 나눈다(F는 접속 이름 `seatlab-reconciler`로 정확).
5. **S2의 C·F 비용은 대조가 쉬는 상태에 가깝다**: S2 부하는 몇 초라 60초 주기 대조와 거의 겹치지 않는다. C·F 비용 비교는 S4c·S3로 한다.
6. **'제외 쌍'의 두 정의**: 대조 바퀴 기록 `skipped_pairs` = 마감 회차의 쿼터 행 수, 판정기 `counter_excluded_pairs` = 쿼터 ∪ 실제 쌍. 마감 제외(reason=closed)는 복구 실패가 아니다(`skipped_closed`로 따로 센다).
7. **부하 시드의 시한**: 시드 회차 `starts_at` = 2026-12-31 19:00 KST. 그 뒤에는 모든 부하 하네스가 마감으로 거절된다(하네스는 2026-12-31 09:00Z부터 실행 거부).
8. **처리량 절대값은 이 서버 저장 경로에 묶여 있다**(ADR-007 §8). 비교는 같은 조건끼리, 그리고 tmpfs 묶음으로 본다.
9. **B 단독의 효과는 재지 않는다**: 효과 셀에 B 단독이 없다. 'B 단독은 DB 직접 조작을 고치지 못하고, 열린 회차 행 없음·작음이면 복구 전까지 만료가 멈춘다'는 코드(V8 엄격 · 만료 틱 전체 롤백)와 테스트(`TriggerLoop1ImplTest`·`Loop2ImplTest`)에서 끌어낸 것이다.
10. **정리 ②의 '확정 쌍 행은 남긴다'는 마감 뒤 판정기로 반증할 수 없다**: S3 시드 회차는 1개이고 마감되면 열린 회차가 없어 판정기는 늘 0이다. 마감 직전 정합은 마감 5초 전 표본 하나로 본다.
11. **A+C·A+F에서 C·F의 D·L1 탐지는 A에 가려진다**: D·L1은 만료가 가까운 홀드라 대부분 A가 먼저 고친다. C의 D·L1 탐지는 B+C에서만 보이고, F의 D·L1 경로는 C와 같은 코드라는 추론이다.
12. **F와 C의 대조 청크 시간은 직접 비교할 수 없다**: C의 청크 시간에는 앱 커넥션 풀 대기가 들어간다.

## 8. 결정 (2026-10-14, 사용자)

**매수 카운터는 그대로 쓰고, 어긋나도 스스로 복구되게 A(만료 배치 쌍 단위 견딤) + C(앱 안 대조)를 기본으로 켠다. 쿼터 행 정리는 ① 마감 후 회차 단위를 기본으로. 판매 마감(공연 시작 시각에 선점 거절)은 기본으로 켠다. B(DB 트리거)·F(별도 대조 앱)는 기본이 아니다(선택지로 유지).**

- 비용 허용선(사용자): tmpfs 기준 선점 p99·처리량이 대조군 대비 10% 이내. A(만료 배치 쌍 단위 견딤)·C(앱 안 대조)·F(별도 대조 앱)·판매 마감은 통과, **B(DB 트리거)는 초과**(p99 7.5배). 디스크 값은 저장 경로 한계(ADR-007)와 함께 참고.
- **왜 A(만료 배치 쌍 단위 견딤) + C(앱 안 대조)인가**: A(만료 배치 쌍 단위 견딤)만으로는 조용한 어긋남(L2·H — 한도 초과 허용·부당 거절)이 남는다(H2). C(앱 안 대조)를 더하면 네 갈래 모두 100%·오탐 0(H3)이고 tmpfs 비용이 보이지 않는다(H4). A(만료 배치 쌍 단위 견딤)는 C(앱 안 대조)가 마감 회차를 대조하지 않는 동안 남은 홀드의 감소 실패를 맡는다(조합 규칙).
- **왜 F(별도 대조 앱)가 아닌가**: DB 쪽 비용은 C(앱 안 대조)와 같고(H5) tmpfs에서 차이가 없다. 디스크에서 바퀴가 짧은 장점은 있지만 에러율·벽 시작이 오히려 나빠졌고(원인 미확인) 배포 단위가 하나 는다.
- **왜 B(DB 트리거)가 아닌가**: 원천 차단의 장점보다 비용이 크다(H6). 엄격성 때문에 어긋남이 있으면 확정이 실패하고 복구 전까지 만료가 멈춘다. 운영 중 전환(ADR-010)에서 비엄격 변형으로 다시 본다.
- **적용(명세 §12, 2026-10-14)**: 기본값 3개 변경(설정·코드 — `counter-drift.expiry-repair`·`reconcile.enabled` 켬, `cleanup.mode: schedule`) · `reconciler` 프로필은 A(만료 배치 쌍 단위 견딤)·정리 끔 · ADR-001~009 하네스와 옛 기본값을 가정한 테스트에 '끔' 명시(렌더 58변형 실효 차이 0) · 기본값 테스트 14 · 전체 507/0/0 · 서버 스모크(기본값 S2·S3e, control S2 회귀) 모두 ok. 커밋 8e4c92e3·9b0ca984·a601bba5·46f5b04d.
- **운영 제약 — 여러 인스턴스**: 대조(C(앱 안 대조))와 정리 ①은 앱 인스턴스마다 돈다(인스턴스 사이 단일 실행 장치 없음 — 정리의 `@Synchronized`는 JVM 안에서만). N대면 60초마다 대조 부하가 N배, 같은 쌍의 기록이 중복된다(정합은 회차 행 FOR UPDATE 직렬화로 유지). 이번 측정·허용선은 1대 기준이다. 여러 대로 운영하면 대조·정리는 1대(또는 F(별도 대조 앱))에서만 켠다.
- **운영 제약 — 기록 테이블**: 기본 켬이면 `counter_reconcile_run`이 60초마다 1행(하루 약 1,440행) 쌓인다. 보존·정리 정책은 아직 없다(NEXT).
- **F(별도 대조 앱)와 C(앱 안 대조)를 함께 켜지 않는다**: 업무 앱에 `external-reconciler=true`면 C(`reconcile.enabled`)를 꺼야 한다 — 기동 검사가 거부한다(리뷰 반영).
- 기본값에서 새로 기동 실패하는 조합(안내 메시지 있음): 카운터 계열이 아닌 매수 방식(none·quota·advisory 등)은 A(만료 배치 쌍 단위 견딤)·C(앱 안 대조)·정리를 꺼야 하고, counter-trigger는 A(만료 배치 쌍 단위 견딤)를, counter(ADR-005)·판매 마감 끔은 정리를 꺼야 한다.

### 8.1 넘기는 것

- **ADR-010(운영 중 매수 방식 전환)**: 이 ADR의 대조·복구를 전환 도구로 쓴다. B(DB 트리거)의 비엄격 변형·그림자 모드 조합 규칙 확장 필요(ADR-010 문서).
- **디스크 부하에서 C(앱 안 대조) 탐지 지연**: 디스크 벽 구간에 C(앱 안 대조) 한 바퀴가 주기보다 길다(최대 110초) — 탐지가 늦어질 뿐 누락은 없다. 대조 전용 작은 풀이나 F(별도 대조 앱)를 다시 볼 조건 = 운영 저장 장치에서도 바퀴가 주기를 넘을 때.
- **A+F(만료 배치 쌍 단위 견딤 + 별도 대조 앱) 디스크 에러율·벽 시작**: 원인 미확인(F(별도 대조 앱) 컨테이너 호스트 자원 공유 추정).
