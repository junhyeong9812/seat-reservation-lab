# 01. Seat Reservation Lab

## 결정 기록 (ADR)

> **진행 상황(2026-10-18)**: ADR-011까지 완료(PR #8·#9·#10 병합). **ADR-009** 카운터 어긋남 — 기본값 A(만료 배치 쌍 단위 견딤)+C(앱 안 대조) · 판매 마감 · 쿼터 행 정리 ①. **ADR-010** 측정용 앱 JVM 2g + 세대형 ZGC. **ADR-011** 측정 환경 꼬리 원인 — 26초 주기 튐은 k6 PC의 다른 컨테이너(측정 대상 밖), 30분 측정에서 C의 규모 한계 발견. 다음: **ADR-012 카운터 증분 대조**(명세 중 — 바뀐 쌍만 짧은 주기로 대조, 외부 대조 앱 포함) · **ADR-013 Kafka + 읽기 복제본 대조**(CDC·아웃박스 비교) · 기존 ADR-012~018(운영 중 매수 방식 전환~오픈 폭주)은 014~020으로 옮겼다(8차).
>
> **지금 적용된 기본값**: 좌석 선점 = 3b `pessimistic-nowait`(ADR-003) · 느린 작업은 좌석 판정 뒤(ADR-004) · 매수 제어 = `counter-upsert-precheck`(ADR-007 결정 → ADR-008 적용) · 인덱스 5개 + 커넥션 풀 10(ADR-002) · 카운터 어긋남 = A(만료 배치 쌍 단위 견딤) + C(앱 안 대조, 60초) · 판매 마감(공연 시작 시각) · 쿼터 행 정리 ①(마감 후 회차 단위, schedule)(ADR-009). **측정 조건**(ADR-011부터): 측정용 앱 = 2g + 세대형 ZGC(ADR-010 — 하네스 기본값, Dockerfile 무변경) · 주 k6 v2.2.0 고정 · 저율 측정기 두 곳(PC·서버) · 캠페인 전 k6 PC 점검(재시작 반복 컨테이너·부하·다른 실험) · 장시간은 `--seed-schedules 800 --pg-tmpfs-size 12`(ADR-011).
>
> **결정 흐름(매수 제어)**: ADR-005 advisory-try를 기준으로 정함(코드 적용은 확인 전까지 보류 — 코드 값 none) → ADR-006 counter-upsert가 지표는 가장 좋지만 S4(도착률 계단, 요청마다 새 사용자·좌석) 벽 → ADR-007 벽은 방식이 아니라 서버 저장 경로(디스크 flush 반감) → precheck로 전환 결정 → ADR-008 코드 적용·기본값 확정 측정 13회 합격.

## Architecture

```
Client
  ↓
Queue Server (Redis Sorted Set)
  ↓ 입장 토큰 (초당 N명)
Reservation API
 ├── Seat Map Query ── Cache
 └── Seat Hold ─────── Redis SET NX EX / DB Lock
        ↓
      Hold Expiry ── 만료 시 좌석 반환
        ↓
Payment (→ 02. Payment Consistency Lab)
  ↓
Reservation Confirm

Verification Batch → Seat state consistency check
```
