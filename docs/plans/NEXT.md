- **합의된 범위(인터뷰)**: 방식 0~8 전부(락 없음·synchronized·조건부 UPDATE·FOR UPDATE(+NOWAIT)·@Version·유니크·advisory·Redis SET NX·Redis 분산락) · 판정 기준 7개(정합성·공정성·경합 강도·자원 점유·실패 모드·수평 확장(앱 2대)·운영 복잡도(정성)) · 전환 = 전략 인터페이스 + 기동 설정 · S1·S4 L2·L4 ×5 + S3 L4만 이탈 0/20/50 ×5 · 앱 2대는 S1 L4 ×5 · Redis는 compose 내부망·CPU 1 · 대기형 락(FOR UPDATE·advisory·Redis 분산락)만 풀 20 추가 · 약 63시간
- **발생 가능한 문제**: ADR-002 §9 인계 — S4 계단 상한 6,487건/s라 인덱스 있음 L4는 한계 미관측(계단 확장 필요) · 대기형 락은 커넥션을 잡고 기다려 풀과 상호작용 · 측정 중 경로 단절(와이파이·NAT)로 회차 오염 · 캠페인이 로그아웃·배포 단절에 멈춤
- **대처**: 하네스 보강을 명세에 포함(아래 N4) · 같은 캠페인 안에서만 비교 · 에러율은 타임아웃/연결 수립 실패/연결 끊김/5xx로 분리 보고

### N3. L2 S3 붕괴 원인(ADR-002 A3) — 우선순위: 중간 · 후속 ADR(번호 미정)

- **관측**: 2 CPU에서 S3 원본 확정 실패 약 62%(타임아웃 44% + 연결 단계 18%), 인덱스·풀과 무관. 60회 중 2회만 붕괴하지 않음(앱 CPU·메모리 낮게 유지).
- **방법론 비교**: ① 연결 대기열(accept backlog·Tomcat acceptCount/maxConnections) 지표 수집 후 재측정 ② 앱 메모리·GC 로그 ③ 서버 쪽 요청 도착 기록으로 경로 단절과 분리 — ③이 먼저(경로 오염을 배제해야 ①②를 해석 가능).

### N5. 배경 100만에서 인덱스 있음의 처리량 저하(ADR-002 A4) — 우선순위: 낮음 · 사용자 결정: 이후 실험으로 증명

- **비교할 것**: 자원(CPU·DB 메모리) 증설 vs 처리 방식 변경(파티셔닝 등). 선행: DB 대기 이벤트·버퍼 적중률 수집.

### N6. 사용자 검증 단계 추가 시 지연 — 우선순위: 낮음

- **왜 뒤로 미루나**: 앱에 사용자 테이블·인증이 없다(사용자 = `X-User-Id` 숫자). 2026-09-29 사용자 결정 — "이 과정이 추가되면 얼마나 시간 지연이 되는지 후자로 넘기자".
- **측정할 것**: 선점 경로에 사용자 조회·검증을 더했을 때 p99·처리량 변화 — 사용자 수(더미 규모)별.

### N7. 다중 인스턴스·MSA에서의 경합 제어 — 우선순위: 낮음 · ADR-003 결과 이후(사용자 제기 2026-10-03)

- **왜**: 예약 서버가 2대 이상이면 JVM 락은 무의미하다(ADR-003 스모크: 앱 2대 jvm-lock 성공 2). ADR-003의 ⑦은 공유 DB·Redis 방식이 앱 2대에서 정합성을 지키는지만 본다.
- **비교할 것**: ① 공유 DB 원자 연산·락(ADR-003 결과 승계) ② 외부 락 서버(Redis — Redis↔DB 부분 실패) ③ **키 기준 라우팅**(같은 공연·좌석 요청을 같은 인스턴스로 → 로컬 락 재유효, 대신 재배치·핫 키 쏠림) ④ 서비스별 DB가 나뉜 MSA(좌석 서비스 소유 DB, 사가·이벤트) — 락 키 정의(전역 id vs 범위 키 `회사:공연:좌석`)와 키별 락 회수 포함.
