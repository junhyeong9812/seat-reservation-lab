# ADR-002: DB 기준선 보정 — 일반 인덱스와 커넥션 풀

- 상태: 측정 완료 · 결과 작성 — 리뷰 후 확정
- 날짜: 2026-09-29
- 대응: ADR-001의 처리량 한계(C3)·타임아웃·유령 확정(C4)이 **락이 아니라 DB 차원의 기본기**(인덱스 부재·풀 크기)에서 오는지 가른다
- 선행: ADR-000(측정 대상), ADR-001(판정기·하네스·before 수치)
- 후행: ADR-003(락 비교)은 이 ADR이 정한 조합을 기준선으로 쓴다
- 명세: `docs/plans/2026-09-29/adr-002-db-baseline/requirement-spec.md`

## 1. 문제

ADR-001에서 관측한 것:

- **선점 한 번에 `seat_hold` 전체 스캔 2회** — 1인 2매 확인(`countByScheduleIdAndHoldsUserId`)과 좌석의 홀드 목록 로드. 홀드 20만 행에서 각각 9.5~12.5ms·7~8ms(ADR-001 §4.3 실행 계획). 요청당 DB 비용이 누적 홀드 수에 비례한다.
- S4 처리량 한계(L2 378·L4 252건/s)에서 **DB CPU가 포화**(215%·421%). 앱은 한가했다.
- L1·L2 S3 원본에서 **확정 타임아웃 약 1만 건/회차**, 그중 일부가 뒤늦게 처리돼 **유령 확정**(−149~−345).
- 커넥션 풀 10은 전 단계 고정. Hikari 대기 예외는 0건 — 풀이 병목으로 **관측되지는 않았다**. 그러나 S1 같은 좌석 중복 성공이 **정확히 풀 크기(10)**였다.

이 상태에서 락 방식을 비교하면(ADR-003) 모든 방식이 같은 스캔 비용에 묻혀 차이가 안 보인다. 그래서 락보다 먼저 **DB 차원의 기본기를 갖춘 기준선**을 정한다.

## 2. 가설

| # | 가설 | 틀렸다고 판정할 관측 |
|---|------|------------------|
| H1 | 일반 인덱스를 추가하면 선점 경로의 전체 스캔이 인덱스 스캔으로 바뀌고, S4 한계가 오르며 DB CPU 포화가 늦어진다 | 실행 계획이 Seq Scan 그대로 / S4 한계가 ADR-001 범위 안 |
| H2 | 인덱스로 요청이 빨라지면 L2 S3 원본의 확정 타임아웃·유령 확정이 줄어든다 | L2 S3 확정 에러율이 ADR-001(62~66%)과 같음 |
| H3 | 풀을 늘려도 처리량은 거의 늘지 않는다(병목은 DB CPU) — 오히려 느려질 수 있다 | 풀 20·40에서 S4 한계가 풀 10보다 뚜렷이 높음 |
| H4 | 풀을 늘리면 S1 같은 좌석 중복 성공이 풀 크기를 따라 늘어난다 | 풀 20·40에서도 S1 성공이 10 근처 |
| H5 | 일반 인덱스는 **정합성 위반을 막지 않는다** — S1 중복·S2 매수 초과는 그대로 재현된다 | S1 성공 1 / S2 초과 0 (그렇다면 인덱스가 아닌 무언가가 막은 것 — 측정 설계 오류) |
| H6 | 인덱스 없이는 선점 경로 쿼리 비용이 홀드·예약 행 수에 **비례**해 커지고, 인덱스가 있으면 규모와 거의 **무관**하다 | S5에서 인덱스 없음의 지연이 규모에 따라 늘지 않음 / 인덱스 있음이 규모에 따라 크게 늘어남 |
| H7 | 그 차이가 시스템 처리량으로 이어진다 — 인덱스 없음은 배경이 커질수록 S4 한계가 떨어지고, 인덱스 있음은 거의 유지된다 | 배경 10만·100만에서 인덱스 유무의 S4 한계 차이가 배경 0과 같음 |

## 3. 선택지 (조건)

### 3.1 인덱스 (Flyway `V2__add_indexes.sql`, 모두 유니크 아님)

| 인덱스 | 쓰는 곳 |
|--------|--------|
| `seat_hold(seat_id)` | 좌석의 홀드 목록 로드(애그리거트 컬렉션), FK |
| `seat_hold(user_id)` | 1인 2매 확인 — 홀드 수 (처음 설계한 `seat_hold(schedule_id, user_id)`는 쓰이지 않아 교체 — §6.1) |
| `seat_hold(expires_at)` | 만료 배치 조회 |
| `reservation(schedule_id, user_id)` | 1인 2매 확인 — 확정 예약 수 |
| `reservation(seat_id)` | FK |

- **유니크 인덱스·제약은 쓰지 않는다.** 유니크는 중복 자체를 막는 해결책이라 ADR-003의 후보다. 여기서 쓰면 "인덱스 효과"와 "중복 차단 효과"가 섞인다.
- 인덱스 없음 조건은 `spring.flyway.target=1`(V1까지만 적용)로 만든다. 코드·스키마 파일은 같고 설정만 다르다.

### 3.2 커넥션 풀

10(ADR-001) · 20 · 40. Tomcat 스레드 200·대기열 무제한·Hikari 대기 30s는 ADR-001과 같게 둔다. PostgreSQL `max_connections` 기본 100으로 풀 40까지 수용한다.

- 일반론(HikariCP 풀 크기 가이드: 코어 수 × 2 + 디스크 수)으로는 DB 2~4코어에 풀 10 안팎이 적정이다. 이 환경에서 맞는지는 측정으로 본다.

## 4. 측정 계획

| 조건 | 풀 | 시나리오 | 단계 | 회차 |
|------|----|---------|------|------|
| 인덱스 있음 | 10 / 20 / 40 | S1 · S2 · S4 · S3 원본 × 이탈 0/20/50 | L2 · L4 | 5 |
| 인덱스 없음 | 20 / 40 | S1 · S4 | L2 · L4 | 5 |
| **인덱스 없음 (기준선 재측정)** | 10 | S1 · S2 · S4 · S3 원본 × 이탈 0/20/50 | L2 · L4 | 5 |
| ~~인덱스 없음 — ADR-001 결과 재사용~~ | 10 | — | — | 환경 판정 실패로 재사용하지 않음(§6.6) |
| 규모별: 인덱스 없음·있음 × 배경 10만·100만 | 10 | S1 · S4 | L2 · L4 | 5 |
| S5 규모별 쿼리 비용: 인덱스 없음·있음 × 배경 0·1만·10만·100만·500만 | — | 선점 경로 쿼리 4종(DB 직접) | L2 · L4 | 조합당 1회 |

- **배경 데이터**(규모 N): 측정 회차와 다른 배경 회차에 좌석 2N — HELD N(홀드 1개씩) + RESERVED N(CONFIRMED 1건씩). 판정 위반 0에서 시작하고, 측정 동작은 그대로 둔 채 테이블 행 수만 늘린다. 현실 대응: 예약은 지난 공연이 쌓이는 정상 규모, 홀드 수십만~수백만은 만료 배치가 밀린 비정상 규모.
- **S5**: 앱·HTTP 없이 DB 컨테이너에서 `pgbench`로 선점 경로 쿼리(1인 2매 확인 — 홀드·예약, 좌석의 홀드 목록, 만료 배치 조회)를 반복 실행해 지연(평균·분위수)과 동시 10연결 처리량을 잰다 — 인덱스 효과만 분리.
- 합계 약 360회 + S5, 약 61시간(추정). 시나리오·시드·예열·타임아웃은 ADR-001과 같다.
- **환경 동일성 확인 → 실패 → 기준선 재측정**: 인덱스 없음·풀 10 S4를 다시 재서 ADR-001 범위를 벗어나(§6.6) ADR-001 결과를 재사용하지 않고, 기준선을 이 ADR 안에서 전 시나리오로 다시 잰다. 모든 비교는 같은 캠페인 안에서만 한다.
- **타임아웃 빈도의 정의**: 응답 코드 0(클라이언트 30s 포기)·5xx 비율 — S1·S2는 선점, S3는 선점·확정 각각, S4는 단계별. 유령 확정(확정 200 − CONFIRMED)을 함께 본다.

### 6.1 이슈 — 1인 2매 확인용 인덱스가 쓰이지 않았다 (ISSUE-ADR002-1)

**증상**: 인덱스를 추가했는데도 1인 2매 확인의 홀드 수 쿼리(Q1)가 `seat_hold` 전체 스캔 그대로였다. 나머지 세 쿼리는 인덱스로 60~90배 빨라졌다.

S5 스모크 (4 CPU, 배경 10만 행, 커밋 `ad363c8` — 결과 `k6/ADR-002/results/smoke-s5/`):

| 쿼리 | 인덱스 없음 | 인덱스 있음(기존 설계) | 실행 계획(있음) |
|--|--|--|--|
| Q1 1인 2매 — 홀드 수 | 3.9ms | **4.1ms** | **Seq Scan on seat_hold** (10만 행 필터) |
| Q2 1인 2매 — 확정 수 | 4.4ms | 0.055ms | Index Scan `idx_reservation_schedule_user` |
| Q3 좌석의 홀드 목록 | 3.8ms | 0.062ms | Index Scan `idx_seat_hold_seat_id` |
| Q4 만료 배치 조회 | 4.2ms | 0.048ms | Index Scan `idx_seat_hold_expires_at` |

(시간 = `EXPLAIN ANALYZE` 실행 시간, 1회)

**원인**: Q1은 도메인의 `countByScheduleIdAndHoldsUserId`가 만드는 쿼리로, 조건이 **`seat_hold.user_id`와 `product_seat.schedule_id`**다 — 회차 조건은 홀드가 아니라 **조인한 좌석 테이블**에 걸린다.

```sql
SELECT count(ps.id) FROM product_seat ps JOIN seat_hold h ON ps.id = h.seat_id
WHERE ps.schedule_id = ? AND h.user_id = ?
```

처음 설계한 `seat_hold(schedule_id, user_id)`는 앞 열(`seat_hold.schedule_id`)이 조건에 없어 쓰일 수 없다(PostgreSQL 16은 복합 인덱스의 앞 열을 건너뛰는 스캔이 없다). 인덱스 이름만 보고 "1인 2매용"이라고 설계했지, **실제 쿼리의 조건 열을 확인하지 않은** 설계 실수다.

**변경**

| | 기존 | 변경 |
|--|--|--|
| V2 인덱스 | `idx_seat_hold_schedule_user ON seat_hold (schedule_id, user_id)` | `idx_seat_hold_user_id ON seat_hold (user_id)` |
| 근거 | 쿼리 이름("회차·사용자별") | 실제 쿼리의 조건 열(`h.user_id`) — 사용자당 홀드는 몇 개뿐이라 충분히 선택적이고, 회차는 좌석 PK로 확인 |

- 사용자 합의(2026-09-29, 명세 §9.1 변경).
- V2 파일은 **직접 수정**했다: V2가 적용된 DB는 테스트·스모크에서 매번 새로 만들고 지운 것뿐이라, 적용된 마이그레이션을 바꿀 때의 Flyway 체크섬 문제가 없다. 운영 DB였다면 V3로 교체해야 한다.
- 변경 후 확인: §6.4 스모크.

**교훈** (study-note 이슈 후보): 인덱스는 **쿼리 이름이 아니라 실제 SQL의 조건 열**로 설계하고, 조인 쿼리는 조건이 어느 테이블에 걸리는지 본다. 설계한 인덱스는 **실데이터 규모에서 실행 계획으로 확인**한 뒤 측정에 들어간다 — 확인 없이 측정했다면 "인덱스를 넣어도 1인 2매 확인은 그대로"라는 틀린 결론이 38시간 측정에 실렸을 것이다.

### 6.2 코드 리뷰 정리 — 기존 → 변경

리뷰어 A = Opus 워커, B = codex. 두 리뷰어가 같은 결함을 따로 짚은 항목이 많았다(교차 표시). 재점검 판정은 수정 후 codex 타깃 재점검 결과.

| # | 지적 (리뷰어) | 기존 형태 | 변경 | 재점검 |
|---|------|---------|------|-------|
| R1 | 1인 2매 인덱스가 쿼리 조건과 안 맞음 (A·B) | `seat_hold(schedule_id, user_id)` | `seat_hold(user_id)` — §6.1 | 해소 |
| R2 | 배경 행이 응답-DB 대조에 섞임 (A·B) | "201 − 홀드 행"이 배경 N만큼 음수(배경 100만이면 약 −100만) | 요약기가 `meta.bg`를 뺀다 | 해소 |
| R3 | 캠페인 동결이 무력화 (A) | 캠페인 중 작업트리를 고치면 남은 조건이 전부 SHA 불일치로 즉시 종료, 캠페인은 "done"으로 끝남 | 캠페인에서 불리면 작업트리 검사 생략(캠페인이 시작 때 확인) + 하위 실행이 비정상 종료하면 캠페인 중단(ABORT) · 1차 수정의 셸 우선순위 버그(미추적 파일 검사가 생략되지 않음)도 재점검에서 잡아 괄호로 수정 | 해소 |

| R5 | S5 실패·누락이 숨음 (A·B) | 실패 조합도 `DONE` 기록 → 영원히 재측정 안 됨, 재실행 시 원시 결과 덮어씀, 검증은 pgbench 출력만 | 계획 기록(`plan.json`), 조합마다 status(실행 계획·행 수(기대값 대조)·인덱스·지연 로그까지), 끝난 조합 건너뜀, 미완성은 `.incomplete-<시각>`으로 보존, 실패가 있으면 DONE 없음·exit 1, 이어서 실행은 계획과 인자가 다르면 거부 | 해소 |

### 7.3 판단 기준별 분석

각 기준은 결론 → 근거 데이터 → 편향·한계 → 다음 ADR 입력 순서로 쓴다.

#### D1 — 인덱스 효과 (풀 10, 배경 0: c00 vs c01)

**결론**: 일반 인덱스 5개로 선점 경로의 전체 스캔이 모두 인덱스 스캔이 되고, 처리량 한계가 오른다 — L2는 계단 해상도상 약 5~11배(378 → 2,867), L4는 계단 끝(6,487건/s)까지 기준을 지켜 **진짜 한계를 관측하지 못했다**(≥6,294, 즉 ≥7.4배). 부하 구간 CPU 최대로 보면 한도에 붙는 쪽이 **DB → 앱**으로 바뀐다. 그러나 L2 S3 원본의 확정 타임아웃·유령 확정은 **줄지 않는다**(H2 기각) — 그 원인은 쿼리 비용이 아니다.

**근거 1 — S4 처리량 한계와 부하 중 CPU 최대** (`R/COMPARISON.md` S4 표)

| 조건 | 단계 | 엄격 한계 | 회차별 | 포화점 | 앱 CPU% 최대 | DB CPU% 최대 |
|--|--|--|--|--|--|--|
| 인덱스 없음 | L2 | 378 [378–378] (n 4/5 — rep5 제외) | 378, 378, 378, 378 | 459 [378–482] | 104 | **204** |
| 인덱스 없음 | L4 | 567 [567–567] | 567 ×5 | 567 | 55 | **403** |
| 인덱스 있음 | L2 | **2,867** [0–2,867] | 2,867 ×4, 0 | 3,660 [3,577–3,667] | **206** | 165 |
| 인덱스 있음 | L4 | **≥6,294** [50–≥6,313] | ≥6,307, ≥6,313, ≥6,267, ≥6,294, 50 | 6,307 [6,267–6,340] | **374** | 261 |

- CPU는 k6 실행 구간 **전체**(과부하 단계·중단 후 꼬리 포함)의 최대값이다 — 한계 단계만의 CPU는 산출하지 않았다. 그 기준으로 인덱스 없음은 DB가 한도(200%·400%)에 붙고 앱은 절반 이하 — ADR-001 §4.3과 같은 모양. 인덱스 있음은 앱이 한도에 붙고 DB는 여유가 있다.
- **계단 해상도**: S4 단계는 50 × 1.5ⁱ(13단계, 마지막 6,487건/s)라 한계는 1.5배 간격으로만 정해진다. 배수는 구간으로 읽는다 — L2 인덱스 없음 [378, 567) vs 있음 [2,867, 4,325).

**편향·한계**
- **엄격 한계 규칙이 시작 직후의 지연 튐에 약하다**: 인덱스 있음 L2 rep4(한계 0)는 첫 단계(50건/s) p99 26.8s, L4 rep5(한계 50)는 둘째 단계(75건/s) p99 27.0s — 그 뒤 단계는 다른 회차와 같다(2,867·6,340건/s까지 p99 15~51ms). 규칙이 "처음 기준을 넘은 단계의 직전"이라 한 번의 튐이 한계를 0으로 만든다. 중앙값으로 판정했고, 튐의 원인은 §7.5.
- 인덱스 없음 L2 rep5(168)는 측정 중 연결 불가로 정상이 아닌 회차 — 계산에서 제외했다(`compare.py` 포함 규칙). 인덱스 있음 L2 rep4(0)·L4 rep5(50)는 원인이 미확정(§7.5 A2)이라 포함했다 — 중앙값은 그대로고 범위의 최소값만 이 회차다.
- CPU%는 `docker stats` 10초 간격 표본의 최대값 — 짧은 순간 값은 놓칠 수 있다. 병목 판단(한도에 붙었는지)에는 충분하다.
- L2 S3의 **에러 0% 회차**(인덱스 있음 이탈 20% rep3 — 그리고 D2의 풀 20 이탈 0% rep5)는 설정이 같은데 L4처럼 동작했다. 앱 CPU 최대 124~132%·메모리 끝 600MiB로, 무너진 회차(201~216%·790MiB)와 다르다 → L2 S3가 "무너짐/안 무너짐" 두 갈래라는 가설(§7.5).

**다음 ADR 입력**
- ADR-003의 기준선은 **인덱스 있음** — 인덱스 없이는 락 방식 차이가 스캔 비용에 묻힌다(§1).
- 인덱스 있음에서는 부하 구간 최대 기준 **앱 CPU가 먼저 한도에 붙는다**(한계 단계만의 CPU는 산출하지 않았고, L4는 한계를 관측하지 못했다 — 병목 단정은 아니다). ADR-003은 한계 단계의 CPU를 따로 산출해 락 방식의 처리량 효과를 앱 CPU·DB 대기로 나눠 본다.
- L2 S3 확정 타임아웃은 인덱스로 안 풀린다 — ADR-003에서 S3로 락 방식을 비교하기 전에 이 현상의 원인(§7.5)을 먼저 가려야 한다. 그렇지 않으면 락 효과와 붕괴 여부가 섞인다.

#### D2 — 풀 효과 (풀 10/20/40)

**결론**: 풀을 늘려도 처리량은 늘지 않는다. 인덱스 없음은 풀과 무관하게 같은 한계(DB CPU 포화), 인덱스 있음 L4는 **풀 20·40이 풀 10을 넘지 못한다** — 엄격 한계가 계단 한 칸 아래(4,300 vs ≥6,294, 5/5회), 포화점 기준 −26%(풀 20)·−7%(풀 40). 차이는 마지막 단계(6,487건/s)에서만 난다. 풀은 **쿼리가 기다리느라 느릴 때**(락·IO·네트워크) 의미가 있고, CPU를 쓰느라 느릴 때나 쿼리가 빠를 때는 의미가 없다.

- 리틀의 법칙으로 보면 풀 10이 6,300건/s(계단 상한 — 그 이상일 수 있다)를 처리했다는 것은 요청당 커넥션 점유가 약 1.6ms 이하라는 뜻 — 빠른 쿼리에서는 커넥션 10개가 충분하다. 인덱스 없음은 쿼리가 느리지만 그 느림이 DB CPU 사용(전체 스캔)이라 커넥션을 늘려도 같은 CPU를 나눠 쓸 뿐이다.

**편향·한계**
- **크기는 계단 해상도의 산물**이다: 엄격 한계의 차이는 계단 한 칸(1/1.5)이고, 실제 처리량 차이는 포화점 기준 −26%·−7%. 방향(풀 10을 넘지 못함)만 5/5회 일관이다.
- **측정 날짜가 다르다**: 풀 10(c01) 09-30 오후, 풀 20(c06) 10-01 밤, 풀 40(c07) 10-02 새벽. 같은 조건 5회의 좁은 범위는 조건 사이의 드리프트를 제한하지 못한다(§6.6에서 같은 조건 L4가 캠페인 사이에 2배 움직였다) — 풀 10 대조를 같은 시기에 다시 재지 않았다.
- 풀 20 L4는 마지막 단계에서 **서버가 바쁜 채 응답 완료가 24~27초 끊긴** 회차가 3개다(rep1·4·5, 앱 CPU 260~291%, `R/stalls.json` tail 구간) — 풀 20이 그 단계에서 무너진 모습이다. 풀 20이 풀 40보다 포화점이 낮은(4,669 < 5,841) 이유는 이 데이터로 설명하지 못한다.
- 이 측정에는 **락 대기가 없다**. 커넥션이 락을 기다리며 잡혀 있게 되면(ADR-003) 풀 크기가 다시 병목이 될 수 있다 — 이번 결론은 "락 없는 단순 조회"로 한정한다.
- 풀 크기 일반론(DB 코어 × 2 + 디스크 수 — 2~4코어에 4~9)과 같은 방향이지만, 이 환경에서 풀 10 미만은 재지 않았다.

**다음 ADR 입력**
- 기준선 풀은 **10** 유지.
- ADR-003에서 비관적 락(`SELECT … FOR UPDATE`)·advisory lock처럼 커넥션을 잡고 기다리는 방식은 **풀 크기와 상호작용**한다 — 그 방식에 한해 풀 10/20을 함께 재는 것을 검토한다.

#### D3 — 풀과 정합성 (S1 중복 성공, S2 매수 초과)

#### D4 — 인덱스는 중복을 막지 않는다

**결론**: 유니크가 아닌 인덱스는 조회만 빠르게 하고 중복을 막지 않는다 — 측정 설계대로다(막혔다면 다른 무언가가 들어간 것).

**근거**: D3 표 — 인덱스 있음·풀 10에서 S1 성공 10(L4 5회 모두), S2 매수 초과 사용자 15~17. 판정기의 중복 홀드 좌석·초과 홀드 행도 같은 값으로 잡힌다(`R/c01-idx-p10/SUMMARY.md` S1 "좌석당 초과 홀드 행" 9). 테스트로도 확인했다(§6 — V2 위에서 같은 좌석 홀드 2행·CONFIRMED 2건 삽입 성공).

**편향·한계**: 없음(정합성 위반은 DB 사실 기준 판정 — ADR-001 §7의 판정기).

**다음 ADR 입력**: 중복을 막는 것은 유니크 인덱스·제약·락·조건부 쿼리 — ADR-003(같은 좌석)·ADR-004(1인 매수)의 후보.

**다음 ADR 입력**: 만료 배치가 밀려 홀드가 쌓이는 상황(ADR-005 홀드 만료, ADR-010 오픈 스파이크)에서 인덱스가 없으면 선점 경로 전체가 행 수에 비례해 느려진다 — 기준선의 인덱스는 그 시나리오들의 전제다.

#### D7 — 규모별 시스템 처리량 (배경 0·10만·100만)

**결론**: 쿼리 비용의 차이가 그대로 시스템 처리량으로 이어진다. 인덱스가 없으면 배경 10만에서 한계가 약 1/5로, 100만에서 **첫 단계 50건/s도 처리하지 못한다**. 인덱스가 있으면 10만까지 그대로이고 100만에서 떨어지며 흔들린다(L2 계단 한 칸 아래, L4 회차별 567~≥6,329).

**근거 — S4** (`R/COMPARISON.md` S4 표)

| 인덱스 | 단계 | 배경 0 | 배경 10만 | 배경 100만 |
|--|--|--|--|--|
| 없음 | L2 엄격 한계 | 378 [378–378] (n 4/5) | 75 [50–112] | **0** [0–0] (n 5/5 — 결과 회차) |
| 없음 | L4 엄격 한계 | 567 [567–567] | 112 [50–252] | **0** [0–0] (n 5/5 — 결과 회차) |

- 인덱스 있음·배경 100만은 앱 CPU가 한도에 못 미친 채(147%·221%) 한계가 떨어지고 회차별 흔들림이 크다(L4 567~6,329) — 예: L4 rep4는 1,922건/s 단계부터 p99 2.4s로 지연이 커져 성공 RPS가 2,000 근처에 머문다.

| 인덱스 | 단계 | 배경 0 | 10만 | 100만 |
|--|--|--|--|--|
| 없음 | L4 | 359 | 606 | 1,087 |
| 있음 | L4 | 567 | 352 | 236 |

- S1은 요청 1,000개뿐이라 배경 행 수의 효과가 작다. 인덱스 없음만 배경에 따라 지연이 늘어난다.

**편향·한계**
- 인덱스 있음·배경 100만의 처리량 저하 원인은 아직 모른다 — 앱 CPU 여유가 있는데 지연이 커진다. 후보: 큰 테이블의 인덱스·버퍼 캐시(DB 메모리 2GiB 한도), 만료 배치(`expires_at` 인덱스 스캔이 배경 홀드 100만을 건너뛰는지), 측정 홀드 행 위치. 확인은 DB 대기 이벤트·버퍼 적중률이 필요하다 — 이 측정은 그것을 수집하지 않았다(§7.5).
- 인덱스 없음·배경 10만은 L4 5회 중 3회(rep3 한계 75·rep4 252·rep5 252)와 L2 1회(rep3 75)에서 측정 도중 서버 지표 수집이 끊겼다(§7.1 품질 의심) — 한계는 대체로 단절 전 단계에서 정해졌으나 품질을 보장하지 못한다. L4 중앙값 112는 단절 없는 rep2이고, 범위 [50–252]는 단절 회차가 넓힌 것이다.
- 인덱스 없음·배경 100만 L2 3회는 판정 요청이 HTTP 500으로 실패해 DB 사실 판정이 없다 — 부하 결과(한계 < 50건/s)만 쓴다.
- 배경 행은 측정과 다른 회차에 있고 만료되지 않는다(먼 미래). 현실의 "같은 회차에 홀드가 쌓이는" 상황은 아니다 — 행 수 효과만 분리했다.
- c04의 "한계 0"은 한계 규칙상의 값이다. 실제로는 "50건/s 미만"이며 정확한 값은 재지 않았다(계단이 50건/s부터 시작).

**다음 ADR 입력**: 배경 규모에 따른 처리량 저하(인덱스 있음 100만에서 L2 계단 한 칸 아래 — L4는 기준값이 계단 상한이라 저하 폭은 하한만 안다)는 ADR-005(홀드 만료)·ADR-010(오픈 스파이크)의 입력 — 홀드 행이 쌓이는 시나리오에서 같은 저하가 나는지 본다.

### 7.4 공통 편향·측정 조건의 한계

- **같은 캠페인 안 비교만 유효 — 그러나 조건 사이 드리프트는 분리되지 않는다**: 환경 동일성 확인이 실패했다(§6.6). 모든 비교는 이 캠페인(09-29 ~ 10-02) 안에서 했지만 조건은 순서대로 돌아 날짜·시간대가 다르다. 같은 조건 5회는 시간상 연속이라 그 범위가 좁아도 조건 사이의 드리프트를 제한하지 못한다(§6.6에서 같은 조건이 캠페인 사이에 2배 움직였다). 큰 차이(인덱스 효과 5배+, 배경 100만의 붕괴)는 드리프트로 설명되기 어렵지만, 계단 한 칸 수준의 차이(풀 효과 D2, 배경 100만 인덱스 있음 D7)는 드리프트와 구분되지 않는다.
- **S4 계단 해상도와 상한**: 한계는 1.5배 간격으로만 정해지고, 인덱스 있음 L4는 계단 끝(6,487건/s)까지 통과해 진짜 한계를 관측하지 못했다(`≥` 표시).
- **k6 PC 네트워크**: k6 PC가 와이파이 + 공유기 NAT를 거쳐 서버에 닿는다. 측정 중 단절 1회(c00 L2 S4 rep5)가 결과에 섞였다(정상 아닌 회차로 제외). 최고 부하(6,000건/s대)에서 네트워크가 상한을 만들었는지는 확인하지 않았다 — 인덱스 있음 L4의 다음 단계(9,731건/s)는 계단 설계상 재지 않았다.
- **서버의 다른 부하**: 서버의 `metrics-agent` 서비스가 파일 누락으로 5초마다 재시작에 실패하고 있었다(재시작 56만 회+, seatlab과 무관). 배경 CPU 잡음 — 크기는 측정하지 않았다.
- **에러율은 응답 코드 0(타임아웃·연결 실패)의 합**이다 — 5xx는 전 조건 0. 종류별 분리는 §7.5 A1.
- 요청별 원시 기록(`k6-requests.csv.gz`, 7.7GB)은 커밋하지 않는다 — 로컬·백업 보관, 커밋에는 파일별 sha256 목록과 그것에서 산출한 요약만(명세 §9.2, 사용자 결정 2026-10-02). ADR-001(전부 커밋)과 다른 점.

### 7.5 추가 분석

#### A1 — 응답 코드 0 vs 5xx (명세의 "타임아웃 빈도")

**결론**: 캠페인 전체에서 **5xx는 0건**이다 — 실패는 전부 응답 코드 0(응답을 못 받음)이다. L2 S3 확정 실패(약 62%)는 세 가지로 나뉜다 — **30초 요청 타임아웃 약 44%**, **연결 수립 실패 약 12%**(dial i/o timeout — TCP 연결을 맺지 못함), **맺어진 연결이 도중에 끊김 약 6%**(reset by peer·EOF). ADR-001부터 "확정 타임아웃"이라 부른 것에는 타임아웃이 아닌 연결 단계 실패가 섞여 있었다. 연결 단계 실패가 **서버 쪽 대기열에서 났는지 경로(와이파이·NAT)에서 났는지는 이 데이터로 가를 수 없다**. L4 S3와 인덱스 있음 L4 S4는 0 근처.

**근거** (`R/COMPARISON.md` "응답 코드 분류 — S1·S2·S3", 비율도 스크립트 산출 — 확정 요청, 포함 규칙상 회차 5개 합계)

| 인덱스 있음·풀 10 | L2 S3-a0 | 86,670 | 33,127 | 37,842 (43.7%) | 10,474 (12.1%) | 3,544 (4.1%) | 1,671 (1.9%) | 0 |

- **S4는 단계별**(`R/COMPARISON.md` "S4 단계별"): 실패는 한계를 넘은 단계에서만 난다. 인덱스 없음은 그 단계의 실패가 전부 타임아웃(DB가 느려 30초를 넘김 — 예: L4 1,281건/s 단계 99.8% — 그 앞 854건/s 단계는 23.3%), 인덱스 있음 L2는 마지막 단계(6,487건/s)에서 타임아웃 2.2% + 연결 수립 실패 0.8%, 인덱스 있음 L4는 전 단계 0 근처.
- 오류 코드는 k6 `error_code`(1050 request timeout · 1211 dial i/o timeout · 1220 connection reset by peer · 1000 EOF 등) — 회차 하나에서 k6 경고 로그의 메시지 수와 정확히 일치함을 확인했다(c01 L2 S3-a0 rep1: 확정 타임아웃 7,710 · dial 2,077 · reset 737 · EOF 326).

**편향·한계**
- **처음 산출은 틀렸다**: 지연 ≥ 29.9초를 타임아웃으로 셌는데, k6는 타임아웃 난 요청의 지연을 0 근처로 기록한다 — 그 결과 타임아웃이 "연결 실패"로 잘못 분류됐다. 오류 코드 기준으로 고쳐 다시 산출했다(이 표).
- **연결 단계 실패의 위치를 모른다**: 서버의 연결 대기열(커널 accept 대기열·Tomcat `acceptCount`·`maxConnections`)이 넘쳐도, k6 PC~서버 경로(와이파이·NAT 연결 추적)가 끊겨도 같은 오류가 난다. 서버 커널의 `Possible SYN flooding on port 8101`(10-01 09:34, S4 중)은 서버 쪽 대기열 포화의 간접 증거일 뿐이다. L4 S3가 0인 것은 경로 쪽 설명을 약하게 하지만 배제하지는 못한다.
- **끊김(1220·1000)은 처리됐을 수 있다**: 연결 수립 실패(1211)와 달리 요청을 보낸 뒤 끊긴 확정은 서버가 처리했을 수 있다 — 유령 확정(확정200 − CONFIRMED가 음수)의 후보다.
- 요청별 원시 기록은 커밋하지 않는다 — 이 표는 `R/errsplit.json`(커밋)과 `R/requests-sha256.txt`(원본 대조)로 재현 근거를 남긴다.

**다음 ADR 입력**: 락 비교(ADR-003)의 에러율은 이 분류(타임아웃 · 연결 수립 실패 · 연결 끊김 · 5xx)로 나눠 보고한다. L2 S3 실패 원인 후속(A3)은 앱 CPU·메모리와 함께 연결 대기열과 경로를 함께 본다.

#### A2 — S4 부하 중 응답이 끊긴 구간: 원인 미확정, 서버 CPU가 낮은 멈춤과 수집까지 끊긴 멈춤이 있다

**결론**: 인덱스 있음 S4의 "한계 0·50" 회차는 부하 초반(50·75건/s)에 응답 완료가 11초간 0이었고, 그동안 서버 CPU는 낮았다. 원인은 **확정하지 못했다** — k6 PC~서버 경로 단절이 가장 그럴듯하지만(같은 캠페인에서 경로 단절이 확인된 회차가 있다), 서버 쪽 IO 정체·연결 생성 지연처럼 CPU를 쓰지 않는 정체도 같은 모양이라 배제하지 못한다(서버 쪽 요청 도착 기록은 수집하지 않았다). 엄격 한계 규칙은 이런 한 번의 멈춤에 한계를 0으로 만든다.

**근거** (`scripts/stalls.py` → `R/stalls.json` — 부하 중 응답 완료가 5초 이상 0인 구간, k6 시작 기준 시각, 같은 시각 ±6초의 서버 CPU 최대와 표본 수)

**편향·한계**: CPU는 10초 간격 표본(멈춤 ±6초 안에 2개)이라 짧은 정체(GC 등)를 놓칠 수 있고, docker stats CPU%는 IO 대기를 보여 주지 않는다. 같은 단계의 정상 회차 CPU와 비교하지 않았다. 엄격 한계 규칙의 취약성(한 번의 멈춤이 한계를 0으로)과 회차 판정이 측정 중 경로 단절을 거르지 못하는 것은 하네스 인계(§9)로 넘긴다.

#### A3 — L2 S3 두 갈래(무너짐/안 무너짐): 이 ADR에서는 관측까지, 원인은 후속

L2 S3 60회(인덱스 없음 풀 10 15회 + 인덱스 있음 풀 10·20·40 각 15회) 중 2회(모두 인덱스 있음 — 풀 10 이탈 20% rep3, 풀 20 이탈 0% rep5)가 확정 에러 0%로 끝났다(D1 편향). 원인 규명은 이 ADR의 범위(인덱스·풀)를 넘는다 — **사용자 결정(2026-10-02): ADR-003은 S3를 L4에서만 비교**하고, L2 S3 붕괴 원인은 별도 후속으로 넘긴다(§9).

#### A4 — 인덱스 있음·배경 100만의 처리량 저하: 후속 실험

앱 CPU 여유가 있는데 지연이 커진다(D7). 이 측정은 DB 대기 이벤트·버퍼 적중률을 수집하지 않아 원인을 가를 수 없다. **사용자 결정(2026-10-02)**: 자원(CPU·메모리) 증설과 처리 방식 변경(파티셔닝 등) 중 무엇이 맞는지는 이후 실험으로 증명한다(§9).

## 8. 결정

**결정(2026-10-02 사용자 확정)**: ADR-003 이후의 기준선 = **일반 인덱스 5개(V2) + 커넥션 풀 10**. before 수치는 §7.3 D5. 단 커넥션을 잡고 기다리는 락 방식은 ADR-003에서 풀 20을 함께 잰다(사용자 "풀 10과 20 재검토는 맞는 거 같아").

- 인덱스: 처리량 L2 약 5~11배(계단 해상도), L4 ≥7.4배(계단 상한 — 한계 미관측), 규모에 무관한 쿼리 비용(D1·D6·D7). 유니크가 아니라 정합성 문제는 그대로 남는다 — ADR-003·ADR-004가 풀 문제(D4).
- 풀 10: 처리량이 가장 높고 경쟁 구간이 가장 좁다(D2·D3). 락 대기가 생기는 ADR-003에서는 풀과의 상호작용을 다시 본다.
