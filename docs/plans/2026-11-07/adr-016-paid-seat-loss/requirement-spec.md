## 1. 목표·대상 (필수)

`k6/ADR-015/` 하네스에서 **반복 사이 유휴 연결 재사용으로 생기는 선점 · 재선점 EOF**를 재현으로 확인하고, 정상 종료 끝 요청의 `Connection: close`(서버가 닫음) + k6 옵션 `noVUConnectionReuse: true`(반복이 끝나면 남은 연결을 닫음 — 조기 종료)로 없앤다. 재현 시나리오에서 처방 전 EOF > 0 → 처방 뒤 0이면 끝.

## 2. 경계·불변식 (필수)

- 측정 대상(앱 코드 · 앱 설정 · DB · 판정 규칙 · 요약기 판정식 · plan15 고정값)은 **무변경**. 바뀌는 것은 k6 연결 재사용 범위(반복 사이)와 끝 요청의 `Connection` 머리뿐.

- 기존 k6 결과 폴더 · ADR-015 결과 문서는 무변경.

## 5. 검증 방법 (필수)

- **재현(로컬)**: 06c처럼 유휴 한도를 짧게 둔 서버(예: keep-alive 2초) + 반복 사이 유휴 > 한도인 작은 k6 시나리오 → 처방 전 EOF(status 0) > 0 · 처방 뒤 0. 같은 시나리오 · 같은 VU 수로 비교.
- **TIME_WAIT 위치**: 재현에서 서버 쪽 · PC 쪽 TIME_WAIT 최댓값을 변형마다 기록 — (가)+(나)에서 PC 쪽이 (나)만보다 작아야 한다. .164 스모크에서 cost 셀 PC 쪽 최댓값도 잰다.
- **반복 경계 · 반복 안**: 재현 시나리오에서 반복 첫 요청이 전부 새 연결(`timings.connecting > 0`)이고 반복 안 둘째 요청은 재사용(처방이 반복 안을 바꾸지 않음).
- **하네스 셀프테스트** 전부 통과 · plan15/요약기 diff 0.
- **통합 스모크**: .164에서 ④ race 1회(사용자 합의 '한다' — 코드 0 = 0 · 회차 status ok). 처음 적은 '로컬 스모크'는 이 하네스가 .164 원격 기동 전용(run.sh)이라 이 스모크로 대신한다(2026-11-07 — 사용자 보고).

## 8. load-bearing 가정

1. EOF의 원인은 **반복 사이** 유휴 연결 재사용이다(반복 안 긴 생각 시간은 이미 close 처방됨). → task 01 재현으로 먼저 실증. 재현이 안 되면 멈추고 보고(처방을 추측으로 넣지 않는다).
2. 처방은 다음 반복의 첫 요청을 새 연결로 만들고 반복 안 재사용은 남긴다 — 재현에서 `timings.connecting`으로 확인(첫 요청 18000/18000 새 연결 · 반복 안 4501/4501 재사용).
