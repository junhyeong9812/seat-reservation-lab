# ADR-002: DB 기준선 보정 — 일반 인덱스와 커넥션 풀

- 상태: 가설 (Hypothesis) — 측정 준비 중
- 날짜: 2026-09-29
- 대응: ADR-001의 처리량 한계(C3)·타임아웃·유령 확정(C4)이 **락이 아니라 DB 차원의 기본기**(인덱스 부재·풀 크기)에서 오는지 가른다
- 선행: ADR-000(측정 대상), ADR-001(판정기·하네스·before 수치)
- 후행: ADR-003(락 비교)은 이 ADR이 정한 조합을 기준선으로 쓴다
- 명세: `docs/plans/2026-09-29/adr-002-db-baseline/requirement-spec.md`

## 1. 문제

ADR-001에서 관측한 것:

- **선점 한 번에 `seat_hold` 전체 스캔 2회** — 1인 2매 확인(`countByScheduleIdAndHoldsUserId`)과 좌석의 홀드 목록 로드. 홀드 20만 행에서 각각 9.5~12.5ms·7~8ms(ADR-001 §4.3 실행 계획). 요청당 DB 비용이 누적 홀드 수에 비례한다.
- S4 처리량 한계(L2 378·L4 252건/s)에서 **DB CPU가 포화**(215%·421%). 앱은 한가했다.
- L1·L2 S3 원본에서 **확정 타임아웃 약 1만 건/회차**, 그중 일부가 뒤늦게 처리돼 **유령 확정**(−149~−345).
- 커넥션 풀 10은 전 단계 고정. Hikari 대기 예외는 0건 — 풀이 병목으로 **관측되지는 않았다**. 그러나 S1 같은 좌석 중복 성공이 **정확히 풀 크기(10)**였다.

이 상태에서 락 방식을 비교하면(ADR-003) 모든 방식이 같은 스캔 비용에 묻혀 차이가 안 보인다. 그래서 락보다 먼저 **DB 차원의 기본기를 갖춘 기준선**을 정한다.

## 2. 가설

| # | 가설 | 틀렸다고 판정할 관측 |
|---|------|------------------|
| H1 | 일반 인덱스를 추가하면 선점 경로의 전체 스캔이 인덱스 스캔으로 바뀌고, S4 한계가 오르며 DB CPU 포화가 늦어진다 | 실행 계획이 Seq Scan 그대로 / S4 한계가 ADR-001 범위 안 |
| H2 | 인덱스로 요청이 빨라지면 L2 S3 원본의 확정 타임아웃·유령 확정이 줄어든다 | L2 S3 확정 에러율이 ADR-001(62~66%)과 같음 |
| H3 | 풀을 늘려도 처리량은 거의 늘지 않는다(병목은 DB CPU) — 오히려 느려질 수 있다 | 풀 20·40에서 S4 한계가 풀 10보다 뚜렷이 높음 |
| H4 | 풀을 늘리면 S1 같은 좌석 중복 성공이 풀 크기를 따라 늘어난다 | 풀 20·40에서도 S1 성공이 10 근처 |
| H5 | 일반 인덱스는 **정합성 위반을 막지 않는다** — S1 중복·S2 매수 초과는 그대로 재현된다 | S1 성공 1 / S2 초과 0 (그렇다면 인덱스가 아닌 무언가가 막은 것 — 측정 설계 오류) |
| H6 | 인덱스 없이는 선점 경로 쿼리 비용이 홀드·예약 행 수에 **비례**해 커지고, 인덱스가 있으면 규모와 거의 **무관**하다 | S5에서 인덱스 없음의 지연이 규모에 따라 늘지 않음 / 인덱스 있음이 규모에 따라 크게 늘어남 |
| H7 | 그 차이가 시스템 처리량으로 이어진다 — 인덱스 없음은 배경이 커질수록 S4 한계가 떨어지고, 인덱스 있음은 거의 유지된다 | 배경 10만·100만에서 인덱스 유무의 S4 한계 차이가 배경 0과 같음 |

## 3. 선택지 (조건)

### 3.1 인덱스 (Flyway `V2__add_indexes.sql`, 모두 유니크 아님)

| 인덱스 | 쓰는 곳 |
|--------|--------|
| `seat_hold(seat_id)` | 좌석의 홀드 목록 로드(애그리거트 컬렉션), FK |
| `seat_hold(schedule_id, user_id)` | 1인 2매 확인 — 홀드 수 |
| `seat_hold(expires_at)` | 만료 배치 조회 |
| `reservation(schedule_id, user_id)` | 1인 2매 확인 — 확정 예약 수 |
| `reservation(seat_id)` | FK |

- **유니크 인덱스·제약은 쓰지 않는다.** 유니크는 중복 자체를 막는 해결책이라 ADR-003의 후보다. 여기서 쓰면 "인덱스 효과"와 "중복 차단 효과"가 섞인다.
- 인덱스 없음 조건은 `spring.flyway.target=1`(V1까지만 적용)로 만든다. 코드·스키마 파일은 같고 설정만 다르다.

### 3.2 커넥션 풀

10(ADR-001) · 20 · 40. Tomcat 스레드 200·대기열 무제한·Hikari 대기 30s는 ADR-001과 같게 둔다. PostgreSQL `max_connections` 기본 100으로 풀 40까지 수용한다.

- 일반론(HikariCP 풀 크기 가이드: 코어 수 × 2 + 디스크 수)으로는 DB 2~4코어에 풀 10 안팎이 적정이다. 이 환경에서 맞는지는 측정으로 본다.

## 4. 측정 계획

| 조건 | 풀 | 시나리오 | 단계 | 회차 |
|------|----|---------|------|------|
| 인덱스 있음 | 10 / 20 / 40 | S1 · S2 · S4 · S3 원본 × 이탈 0/20/50 | L2 · L4 | 5 |
| 인덱스 없음 | 20 / 40 | S1 · S4 | L2 · L4 | 5 |
| 인덱스 없음 (환경 동일성 확인) | 10 | S4 | L2 · L4 | 2 |
| 인덱스 없음 | 10 | 전 시나리오 | L1 · L2 · L4 | ADR-001 결과 재사용 |
| 규모별: 인덱스 없음·있음 × 배경 10만·100만 | 10 | S1 · S4 | L2 · L4 | 5 |
| S5 규모별 쿼리 비용: 인덱스 없음·있음 × 배경 0·1만·10만·100만·500만 | — | 선점 경로 쿼리 4종(DB 직접) | L2 · L4 | 조합당 1회 |

- **배경 데이터**(규모 N): 측정 회차와 다른 배경 회차에 좌석 2N — HELD N(홀드 1개씩) + RESERVED N(CONFIRMED 1건씩). 판정 위반 0에서 시작하고, 측정 동작은 그대로 둔 채 테이블 행 수만 늘린다. 현실 대응: 예약은 지난 공연이 쌓이는 정상 규모, 홀드 수십만~수백만은 만료 배치가 밀린 비정상 규모.
- **S5**: 앱·HTTP 없이 DB 컨테이너에서 `pgbench`로 선점 경로 쿼리(1인 2매 확인 — 홀드·예약, 좌석의 홀드 목록, 만료 배치 조회)를 반복 실행해 지연(평균·분위수)과 동시 10연결 처리량을 잰다 — 인덱스 효과만 분리.
- 합계 304회 + S5, 약 49시간(추정). 시나리오·시드·예열·타임아웃은 ADR-001과 같다.
- **환경 동일성 확인**: 인덱스 없음·풀 10 S4를 다시 재서 ADR-001 범위에 드는지 본다. 벗어나면 ADR-001 결과를 재사용하지 않는다.
- **타임아웃 빈도의 정의**: 응답 코드 0(클라이언트 30s 포기)·5xx 비율 — S1·S2는 선점, S3는 선점·확정 각각, S4는 단계별. 유령 확정(확정 200 − CONFIRMED)을 함께 본다.

## 5. 판정 기준 (결과 작성 시)

각 기준마다 ADR-001과 같은 형식(결론 → 근거 데이터 → 편향·한계 → 다음 ADR 입력)으로 쓴다.

| 기준 | 비교 |
|------|------|
| D1 인덱스 효과 | 인덱스 없음 vs 있음(풀 10) — S4 한계·DB CPU, S3 타임아웃·유령 확정, 실행 계획 |
| D2 풀 효과 | 풀 10/20/40 — 인덱스 있음·없음 각각의 S4 한계·p99 |
| D3 풀과 정합성 | 풀 10/20/40별 S1 중복 성공 수, S2 매수 초과 |
| D4 인덱스는 중복을 막지 않는다 | 인덱스 있음에서도 S1 > 1, S2 초과 > 0 |
| D5 새 기준선 선택 | ADR-003이 쓸 (인덱스, 풀) 조합과 그 before 수치 |
| D6 규모별 쿼리 비용 | S5 — 행 수 0~500만 × 인덱스 유무의 쿼리 지연·처리량 곡선 |
| D7 규모별 시스템 처리량 | 배경 0·10만·100만 × 인덱스 유무의 S4 한계, S1 지연 |
