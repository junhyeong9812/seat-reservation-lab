# 01. Seat Reservation Lab

## 결정 기록 (ADR)

> **현재 진행: ADR-007** counter-upsert(매수 카운터 한 문장 upsert)의 S4(도착률 계단) 처리량 벽 원인 진단 — 해결되면 매수 제어 기본을 advisory-try에서 counter-upsert로 전환(ADR-006 결정).

| ADR | 결정 (확정일은 각 행) | 이유 | 문서 |
|-----|----------------------|------|------|
| **ADR-003** 같은 좌석 동시 선점 — 락 방식 | **3b `pessimistic-nowait`**(`SELECT … FOR NO KEY UPDATE NOWAIT`)를 선점 기본 방식으로 한다. 이미 잠긴 좌석은 기다리지 않고 바로 409 | 기다리는 동안 사용자가 다른 좌석을 고를 기회를 잃으면 안 된다는 것이 우선이다(즉시 실패형). 즉시 실패형은 3b(FOR UPDATE NOWAIT)와 7 `redis-nx` 둘인데, redis-nx는 Redis 운영, Redis↔DB 부분 실패(키만 남는 경우 — 미측정), 홀드 TTL 동안 남는 키 관리가 따른다. 그래서 **아직 Redis는 쓰지 않고** DB만으로 끝나는 3b를 고른다. 대가: 이긴 쪽이 롤백하거나(1인 2매 초과 등) 만료 배치·확정이 좌석 행 락을 쥔 동안 들어온 요청도 409 — 사용자가 다시 눌러야 한다 | [ADR-003](docs/adr/ADR-003-same-seat-contention.md) §8 |
| **ADR-004** 임계 구역 길이와 락 보유 시간 | **느린 작업(외부 호출)은 좌석 판정 뒤에 둔다.** 진 쪽이 느린 작업을 하지 않게, 기다리는 동안 커넥션을 쥐지 않게 한다. 느린 작업을 트랜잭션 밖으로 빼는 것(선점 커밋 → 외부 호출 → 실패 시 보상)은 ADR-009·010에서 판정 | 지연 20ms에서 즉시 실패형(3b·7(nowait·redis-nx))과 커넥션 밖 대기형(1a·8(jvm-lock·redis-lock))만 경합 영향 최저점(K=100)을 지켰다. 진 쪽도 지연을 다 쓰는 방식(2·5·4(conditional·unique·optimistic))은 최저점보다 약 35~42% 낮았다 | [ADR-004](docs/adr/ADR-004-critical-section-hold-time.md) §6 |
| **ADR-005** 1인 최대 2매 — 같은 사용자 동시 요청 | **L2 `advisory-try`**(`pg_try_advisory_xact_lock(회차, 사용자)`)를 매수 제어 기본으로 한다. 같은 사용자의 다른 선점이 진행 중이면 기다리지 않고 409(`HOLD_LIMIT_EXCEEDED`), 매수 판정은 좌석 확인 뒤(에러 우선순위 보존) — 2026-10-09 확정 | 매수 정합 0(9방식 공통), 처리량이 제어 없음과 같음(S4(도착률 계단) L2·L4(앱·DB CPU 2·4개) 2,866 / 4,300), 스키마 추가 없음. counter는 롤백 피해(S7-m1(2매 보유자 + 일반 1명) 0석 vs 67석)·같은 사용자 지연에서 낫지만 이번 구현은 요청당 커넥션 3회로 S4 L4 −56% → **ADR-006에서 한 문장 upsert로 재측정**. serializable은 가짜 거절 69/100명으로 제외 | [ADR-005](docs/adr/ADR-005-per-user-limit.md) §8 |
| **ADR-006** 매수 카운터 한 문장 upsert 재비교 | **매수 제어 기본은 advisory-try 유지.** counter-upsert(트랜잭션 안 `INSERT … ON CONFLICT DO UPDATE … WHERE cnt + 1 <= 상한`, 커넥션 빌림 1회)의 처리량 벽 원인을 ADR-007에서 찾고, 해결되면 counter-upsert로 전환 — 2026-10-09 확정 | counter-upsert는 억울한 좌석 0(S7-m1(2매 보유자 + 일반 1명), advisory-try 67)·같은 사용자 p99 230ms(S2(사용자 100명 × 각자 좌석 10개 동시) L4(앱·DB CPU 4개), advisory-try 433)·CPU 약 150%(206%)로 가장 좋다. 그러나 S4(도착률 계단) 4,325건/s에서 26~27초 뒤 같은 초에 무너진다(10/10, CPU 무관, 원인 미확정 — L4 엄격 한계 2,866 vs 4,300). 실제 흐름(S3) WAL 2.8배, 쿼터 행은 만료로 안 지워진다 | [ADR-006](docs/adr/ADR-006-counter-upsert.md) |

## Architecture

```
Client
  ↓
Queue Server (Redis Sorted Set)
  ↓ 입장 토큰 (초당 N명)
Reservation API
 ├── Seat Map Query ── Cache
 └── Seat Hold ─────── Redis SET NX EX / DB Lock
        ↓
      Hold Expiry ── 만료 시 좌석 반환
        ↓
Payment (→ 02. Payment Consistency Lab)
  ↓
Reservation Confirm

Verification Batch → Seat state consistency check
```
