## 1. 목표·대상 (필수)

`seat-reservation-lab`에 ADR-001 관측 하네스를 만들고 **ADR-000 기준선의 부하·정합성 기준값(before)을 실측**해 ADR-001 문서에 기록하면 끝.
하네스 = loadtest 프로필(시드 초기화·정합성 판정 엔드포인트 + actuator) · Dockerfile · compose(자원 제한 변수화) · k6 시나리오 S1~S4 · 원격 실행/수집 스크립트 — 전부 `k6/ADR-001/`(앱 코드 제외).

## 2. 경계·불변식 (필수)

- **측정 대상 불변**: ADR-000의 도메인·API·서비스 동작은 바꾸지 않는다 — loadtest 프로필 밖에서 앱 동작 diff 0. 기존 테스트 22개 green 유지.
- **판정은 DB 사실 기준**: `/internal/consistency`는 DB 행을 직접 센다(애그리거트 로직 재사용 금지 — 측정 대상이 스스로를 채점하지 않게). 항목: 좌석당 홀드 행 >1 인 좌석 수 · 좌석당 CONFIRMED >1 · RESERVED 수 vs CONFIRMED 수 · HELD 수 vs 홀드 보유 좌석 수 · 만료됐는데 HELD(배치 주기 경과 후) · (사용자,회차)당 홀드+확정 >2 인 사용자 수 · k6 성공 응답 수 대비 DB 소유 수.
- **loadtest 전용 코드는 프로필 밖에서 로드되지 않는다** (`@Profile("loadtest")`) — 기본 실행·테스트 컨텍스트에서 `/internal/**` 404.
- **매 회 초기 상태 동일**: 회차마다 `/internal/reset`으로 같은 시드(결정적) 재생성 후 측정.
- **근거 전부 보존**: 회차마다 k6 요약 JSON · 시계열 원시(CSV gzip) · 판정 결과 JSON · 적용 설정(actuator configprops·env 중 비밀 아닌 것) · 서버·k6 PC 자원 스냅샷(전·후) · 실행 커밋 SHA · compose 자원 설정 — `k6/ADR-001/results/<run-id>/`에 저장·커밋. 요약 표는 원시 파일에서 스크립트로 산출(손 계산 금지).
- **측정값은 실측만**: 미실행 셀은 "미측정", 추정 금지.

## 5. 검증 방법 (필수)

- 하네스 자체: 기존 테스트 22개 green + loadtest 프로필 통합 테스트(reset이 결정적 시드를 만든다, consistency가 **일부러 만든 불일치**(중복 홀드·RESERVED/CONFIRMED 불일치·매수 초과)를 각각 검출한다 — 판정기의 그린 위장 방지) + 프로필 없을 때 `/internal/**` 404
- 스모크: .164에서 compose 기동 → k6 PC에서 S1을 1회(소규모) 실행 → 결과 폴더에 전 산출물이 생기는지, 판정 JSON이 채워지는지 확인
- 본 측정: 매트릭스 전 셀 실행, 셀별 5회 원시 파일 존재 확인(누락 0 — 실패 회차는 실패로 기록, 무음 스킵 금지)
- ADR-001 요약 표 = 원시 결과에서 스크립트로 재산출 가능

## 8. load-bearing 가정

1. .164에서 `git clone` + `docker compose build`(Gradle 빌드 포함)가 되고, compose `cpus`/`mem_limit`가 컨테이너에 실제 적용된다(JVM이 제한 CPU 수를 인식) — 착수 직후 스모크로 실증.
2. k6 PC가 S1(1,000 VU)·S4 상한까지 병목이 되지 않고, 회차당 원시 결과 크기가 git에 커밋 가능한 수준이다 — 스모크 1회의 k6 PC CPU와 결과 크기로 실증. 넘으면 멈추고 보고(Git LFS 등 선택지 제시).

## 9. 설계 (합의 대상)

### 9.1 파일 배치

```
seat-reservation-lab/
├── Dockerfile                          앱 이미지 (멀티스테이지: JDK로 bootJar → JRE 실행)
├── src/main/.../loadtest/              @Profile("loadtest") — 앱 코드이므로 src 아래
│     InternalResetController · InternalConsistencyController (+ JdbcTemplate SQL — 도메인 밖)
└── k6/ADR-001/
    ├── README.md                       실행 방법·매트릭스·결과 읽는 법
    ├── compose.yml                     app + postgres, 자원 제한·풀 크기 = 환경변수
    ├── scenarios/ s1-same-seat.js · s2-same-user.js · s3-full-flow.js · s4-throughput.js · lib/
    ├── scripts/  run.sh(매트릭스·회차 실행·수집·검증) · lib.sh(원격·HTTP 공통) · summarize.py(계획 기준 표 산출)   ← 리뷰 후 구현 기준으로 동기화
    └── results/<run-id>/               회차별 원시 결과 전부 (커밋)
```

- `@Query` 금지는 도메인 규칙이다. loadtest 판정·시드는 측정 도구라 JdbcTemplate SQL을 쓴다(도메인 패키지 밖).

### 9.2 시나리오

| # | 내용 | 시드 | 부하 |
|---|------|------|------|
| S1 | 같은 좌석 1개에 동시 선점 | 1회차 × 10,000석 | 1,000 VU × 1회, 사용자 모두 다름 |
| S2 | 같은 사용자가 서로 다른 좌석 동시 선점 | 1회차 × 10,000석 | 사용자 100명 × 동시 10요청(1,000 VU) |
| S3 | 선점 → (대기) → 확정/이탈 전체 흐름 | 1회차 × 10,000석 | 입장 300명/s, 좌석 선택 = 앞 20%에 70% 핫스팟, 409면 다른 좌석 최대 3회 재시도, 확정자는 TTL 안에서 대기 후 확정 · 이탈률 0/20/50% · **원본**: TTL 5분·대기 30s~4m·상한 30분 / **축소**: 전부 1/10(TTL 30s·대기 3~24s·상한 3분) |
| S4 | 처리량 한계 (성공 경로) | 100회차 × 10,000석 = 100만 석 | 도착률 계단 상승(요청마다 새 사용자·새 좌석) → 단계별 달성 RPS·p99·에러율, 세 기준 한계 산출 |

- 409(비즈니스 거절)는 에러율에서 제외, 5xx·타임아웃·연결 실패만 에러.
- S3 원본/축소 비교 = 시간축을 TTL로 나눈 곡선(누적 확정 수·재선점 수)이 겹치는지.
- **S3 축소판 2종 (2026-09-28 사용자 결정 "둘 다")** — 모양을 좌우하는 것은 비율(대기/TTL, TTL당 입장 수, 입장/좌석)이다.
  - 축소 A: 시간(TTL·대기·입장 창·배치 주기)만 1/10, 입장 300/s 유지 → TTL당 입장 수 1/10 (다른 조건의 측정)
  - 축소 B: 시간 1/10 + 입장 ×10(3,000/s) → 모든 비율이 원본과 같음. 포화되면 그 자체를 결과로 기록
  - 원본: 입장 300/s × 200,000명(20:1) → 입장 창 약 667s, 상한 = 입장 창 + TTL + 여유

### 9.3 매트릭스·예상 시간 (추정 — 실측으로 갱신)

- 자원 단계 L1/L2/L4 = 앱·DB 각각 CPU 1/2/4 (메모리 고정: 앱 1GB · DB 2GB), 커넥션 풀 기본 10
- 단계당 셀: S1(5) · S2(5) · S3 축소 A(3×5) · S3 축소 B(3×5) · S3 원본(3×5) · S4(5) = 60회 → 전체 180회
- 단계당 약 9~10시간(S3 원본이 약 7.5시간) → **전체 약 30시간**, 무인 연속 실행
- 매트릭스 순서: 단계별로 S1→S2→S4→S3 축소→S3 원본 (짧은 것부터 — 초기 실패를 빨리 발견)

### 9.4 원격 실행 (2026-09-28 사용자 지시로 변경: GitHub 경유 → 직접 전송)

- 원문: "k6관련 코드는 너가 직접 복사해서 처리하고 결과들도 복사해서 가져와서 최종본만 커밋해서 아카이브"
- k6 PC가 오케스트레이터. 측정 대상 = **로컬 커밋 1개**: `git archive <SHA> | ssh jun@192.168.55.164 'tar -x -C ~/labs/seat-reservation-lab/<SHA>'` → 서버에서 `docker compose -p seatlab up -d --build`(자원 변수 주입) → 헬스 대기 → k6 로컬 실행 → 판정·설정·자원 스냅샷 수집 → 결과를 k6 PC로 회수(`k6/ADR-001/results/<run-id>/`)
- **push 없음** — 측정 중 GitHub 경유 금지. 하네스 코드는 로컬 커밋, **결과는 전 매트릭스 종료 후 한 번에 커밋**, push는 ADR-001 문서까지 끝난 최종본 1회만 사용자 확인
- **회차마다** compose down → up (JVM·풀·DB 캐시를 회차 사이에 넘기지 않음 — 리뷰 R17), 볼륨 삭제는 seatlab 프로젝트 볼륨만. 서버의 `~/labs/seat-reservation-lab/` 외 경로는 쓰지 않는다
- k6 시나리오도 측정 SHA에서 `git archive`로 꺼내 실행 (리뷰 감사 A1)
- 장시간 매트릭스는 k6 PC의 백그라운드 프로세스 1개(`run-matrix.sh`)로 실행하고 진행 로그를 파일로 남긴다
