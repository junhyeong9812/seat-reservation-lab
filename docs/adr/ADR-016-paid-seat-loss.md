## 문제

ADR-015 ① `conditional`은 늦은 확정을 **명확한 거부**로 바꿨다(500 · 틱 전체 롤백 → 409 `HOLD_EXPIRED` 또는 404 `HOLD_NOT_FOUND`). 거부가 확실하니 환불도 확실해졌지만, **거부되는 사람의 수는 그대로다**. 결제(외부 — 이 랩 범위 밖)가 홀드 만료보다 늦게 끝나면 그 사용자는 돈을 낸 뒤 좌석을 잃는다.

- **억울한 사용자(정의 — 초안)**: 결제를 끝낸 뒤 보낸 확정이 거부된 세션. 거부 코드 = 409 `HOLD_EXPIRED`(만료 · 배치 전) · 404 `HOLD_NOT_FOUND`(배치가 지운 뒤) · 409 `SEAT_NOT_HELD`(V12 위반 매핑 — 같은 좌석 남의 확정).
- **억울하지 않은 실패(구분)**: 결제를 **시작하기 전에** 거부된 세션. 좌석은 못 얻지만 돈이 빠지지 않는다. 예방책은 대개 억울한 실패를 이 쪽으로 옮기는 것이다. 그래서 두 수를 함께 잰다.

## 가설

- 억울한 실패는 '결제 시작 시점의 남은 TTL'과 '결제에 걸린 시간'의 경주다. 결제 시작 때 남은 시간을 보장하거나(ⓐ), 모자라면 시작을 막으면(ⓑ) 수가 줄어든다.
- ⓐ는 홀드를 늘리므로 좌석 회전이 느려지고 DB 쓰기가 늘어난다(ADR-015 cost DB CPU ④/① 1.119 — 비겹침). ⓑ는 읽기 하나라 싸지만, 결제 시작 거부(억울하지 않은 실패)를 늘린다.

## 설계-2 용어 · 실패 모양

| 용어 | 뜻 |
|---|---|
| `e` | 홀드 만료 시각(`seat_hold.expires_at` — 선점 응답 `expiresAt`) |
| `t_p` | 결제 시작 시각(사용자가 결제창으로 넘어가는 순간 — 서버는 ①에서 모른다) |
| `R = e − t_p` | 결제 시작 때 남은 시간 |
| `D` | 결제 시간(결제 시작 → 결제 성공 응답 · 외부 · 분포는 Q3) |
| `t_c ≈ t_p + D` | 확정 송신 시각(결제 성공 직후) |
| 억울한 실패(paid-loss) | 결제 성공 뒤 확정이 409 `HOLD_EXPIRED` · 404 `HOLD_NOT_FOUND` · 409 `SEAT_NOT_HELD`(Q1) |
| 결제 전 거부(pre-pay refusal) | 결제 시작이 서버에서 거부돼 결제를 하지 않음 — 좌석은 못 얻지만 돈은 안 빠짐 |
| 결제 실패(pay timeout) | ⓒ 상한에 걸려 결제 자체가 실패 — 돈은 안 빠짐 |

- **①(지금 기본)의 억울한 실패 조건**: `D > R`(확정이 만료 뒤 도착). 경합(재선점 · 배치)은 결과 코드만 가른다(배치 전 409 · 뒤 404 · 남이 확정 409 SEAT_NOT_HELD). 따라서 **억울한 비율 ≈ P(D > R)** — 생각 시간 분포(`R`을 정함)와 결제 시간 분포 `D`가 정한다.
- **ⓑ 확인(문턱 θ)**: `R < θ`면 결제 전 거부 · 억울 = P(D > R ∧ R ≥ θ) — θ가 `D`의 상위 분위면 꼬리만 남는다.
- **ⓐ ④ 연장(창 W · 최소 θ)**: `R ≥ θ`면 만료가 `t_p + W`로(R ≥ W면 그대로) → 억울 = P(D > max(R, W) ∧ R ≥ θ). 대가: 홀드 수명 최대 `TTL + W`(좌석 회전 · 동시 홀드 수).
- **ⓒ 상한(C = payBy − t_p)**: 결제를 `C` 안에 못 끝내면 결제 실패 — 억울 = 0에 가까움(상한 강제가 결제 쪽에 있을 때만). 대가: 결제 실패율 P(D > C).
- **ⓓ 승인 → 확정 → 매입**: 확정 실패면 승인 취소 — 돈이 빠지는 억울함 0(좌석 못 얻음은 남음). 결제 쪽 2단계 API 필요(ADR-017 · 02 랩).
- **판정 지표가 분포 계산으로 거의 정해진다는 점**: 억울 · 결제 전 거부 · 결제 실패 비율은 위 식에 분포를 넣으면 나온다(모형 계산). 부하 측정이 따로 답해야 하는 것은 ① 서버가 식대로 동작하는가(경합 · 배치 · 연장 창 FM5 아래) ② 비용(DB CPU · p99 · 동시 홀드 수)이다 — Q7.

## 설계-3 선택지 상세 (서로 배타가 아니다)

### 3.1 ⓑ ①의 결제 시작 확인 — `POST /api/holds/{holdId}/payment-start`를 ①에도 연다 (Q2 결정)

- 같은 경로 · 같은 응답 모양 `200 {holdId, expiresAt, payBy}`(payBy = Q4 · 3.3). 모드가 연장 여부만 가른다: `conditional` = **확인만(쓰기 0)** · `conditional-extend` = 지금 ④ E1(첫 연장).
- ① 문장(초안): `SELECT user_id, expires_at FROM seat_hold WHERE id = ?`(잠금 없음 — 판정은 확정 C1이 다시 한다). 갈래: 없음 404 · 남의 것 403 · 만료(`expires_at ≤ :now`) 409 `HOLD_EXPIRED` · **`expires_at − :now < θ` → 409 새 코드(Q8)** · 그 밖 200.
- 문턱 손잡이: `seat.confirm.payment-min-remaining`(θ) — ④의 `extend-min-remaining`과 같은 뜻이라 하나로 합칠지 Q9.
- 확인은 상태를 바꾸지 않는다 — 200 뒤에도 홀드는 `e`에 만료된다(확인 ≠ 보장). 그래서 ⓑ 단독은 꼬리 `D > R ≥ θ`를 못 막는다.
- 지금 `current` · ② · ③에는 열지 않는다(결정 범위 — 기본 ①과 ④만).

### 3.2 ⓐ ④ 연장 — 지금 코드 그대로 · 값만 정한다

- E1 · 진단 · 지표(`seat.confirm.extend{result}`)는 ADR-015 §3.4 그대로. 이 ADR이 정하는 것: **W(payment-window) · θ 기본값**(지금 앱 기본 0 — 규칙 4가 ④ 기동 때 명시를 요구) · 비용을 감수할지(ADR-015 cost DB CPU ④/① 1.119 — EOF 수정 하네스로 다시 잰다).
- 마감 회차 연장(ADR-015 §설계-11 — '받아들이고 기록')은 그대로.

### 3.3 ⓒ 결제 마감 시각 `payBy` — 서버는 알려 주고, 강제는 결제 쪽 (Q4)

- `payBy = expiresAt − M`(M = 확정 요청 왕복 · 시계 차 여유 — 손잡이 `seat.confirm.pay-by-margin` · 값 Q9). 선점 201 · payment-start 200 응답에 더한다(필드 추가 — 기존 클라이언트는 무시해도 된다).
- 클라이언트 몫(이 랩 밖 — 계약만 적는다): 남은 시간 표시 · 결제창 · PG 결제 제한 시간 ≤ `payBy − now`.
- 측정에서는 흉내 결제가 `D > payBy − t_p`면 결제를 실패로 끝내고 확정을 보내지 않는다(결제 실패로 센다).

### 3.4 ⓓ 승인 → 확정 → 매입 — 설계만(측정 안 함 · Q5)

- 순서: 결제 승인(한도 묶음) → 확정 → 성공이면 매입 · 실패면 승인 취소. 확정 실패가 '돈이 빠짐'이 아니라 '승인 취소'가 된다.
- 이 랩에는 결제가 없다(확정은 `paymentUid`를 받기만 함) → 흉내 결제 어댑터와 함께 ADR-017이 구현 · 비교한다. 이 ADR은 외부 근거(PG 승인 · 매입 분리 지원 · 매입 기한)만 남긴다(설계-7).

## 설계-8 측정 설계 — 뼈대 (고정값 · 문턱은 측정 전 고정 커밋에서 확정)

### 8.1 두 부분 (Q7)

- **A. 모형 계산**(스크립트 · 서버 없음): 생각 시간 `T` · 결제 시간 `D` 분포에서 표본을 뽑아 정책마다 억울 · 결제 전 거부 · 결제 실패 비율과 홀드 수명을 계산한다 → θ · W · M 후보를 고른다.
- **B. 부하 측정**(.164 · 하네스 `k6/ADR-016/` 새로): A가 고른 값으로 ① 서버가 식대로 동작하는가(경합 · 배치 · 연장 창 아래) ② 비용을 잰다. 모형과 부하의 비율이 어긋나면 서버 쪽 결함(또는 모형 가정 결함)이다.

### 8.2 분포 가정 (Q3 결정 '외부 근거 + 꼬리 긴 분포' · Q11)

- `D` ~ 로그정규 · 중앙값 `m` ∈ {30, **45**, 60}초(E5 · E6 — 추정) · σ ∈ {0.7, **0.94**, 1.2}(σ 0.94 = p90 150초 — 추정) · **10분에서 절단**(E2 · E3 · E4 — 넘으면 결제 실패 · 억울 아님).

### 8.5 고르는 규칙 (초안 — 문턱 Q14 결정: 억울 ≤ 0.1% · 결제 전 거부 + 결제 실패 ≤ 5%)

- **모형 예시로 본 함의**(8.3 · 기준 분포): ① · ①+ⓑ · ①+ⓒ는 목표를 못 넘는다(억울 11.5% · 4.6% · 또는 실패 13.6%) — 계산상 통과 후보는 **④ W ≈ 10분**뿐이다. 측정의 실질 질문은 'W 10분 연장의 비용(홀드 수명 최대 15분 · DB CPU)을 감수하는가'가 된다.


1. **G-정합**: 모든 셀 판정기 0 · N16-1(① payment-start 쓰기 0 — `pg_stat_user_tables` `seat_hold` n_tup_upd 증분) · N16-5(`seat.confirm.rejected` = 확정 비2xx).

3. **G-목표**: 억울 ≤ 목표(Q14) **그리고** 결제 전 거부 + 결제 실패 ≤ 상한(Q14) — 기준 분포(m 45 · σ 0.94)에서. 민감도(σ 0.7 · 1.2)는 설명.

5. 통과 후보가 여럿이면 단순성 순서 ① + ⓒ > ① + ⓑ + ⓒ > ④ + ⓒ · 없으면 판정 불가 → 사용자 보고.

## 설계-9 설계 리뷰가 바꾼 것 (루프 1 — 2026-11-07 · **위 절보다 우선**)

> codex ∥ Opus 설계 선검증 + 듀얼 1패스(ledger = 작업 폴더 log RD16-*). 사용자 재확인 3건(2026-11-07): 목표 0.1% 유지 + 비용 보고 · 거부 코드 HOLD_EXPIRED 유지 · payment-start 호출은 **권고**(확정이 검사하지 않음 — 강제하려면 ①에 쓰기가 필요해 N16-1과 충돌).

### 9.1 실패 모양 · 세는 단위
- **세는 단위 = 세션(paymentUid)**: 억울 = 결제 성공한 세션이 끝 상태에 그 세션의 확정 예약을 갖지 않음. 같은 홀드 이중 확정의 둘째 404는 억울이 아니다(ADR-015 confirm-contention이 이미 구분). k6 집계를 끝 상태 `reservation`(CONFIRMED · payment_uid)과 record-level로 대조한다(RD16-4 · RD16-19).
- **서버 판정 시각**: C1은 연결을 얻은 뒤의 `:now`로 판정한다(AtomicConfirmProcess.kt:41) → 억울 조건은 `D + δ > R`(δ = 확정 송신 → `:now` 채취 · 풀 대기 포함). 모형에 δ 분포를 넣고(부하 회차의 실측 δ로 보정), 부하 회차마다 δ를 기록한다(RD16-1).
- **409 `SEAT_NOT_HELD`의 뜻**: ① · ④에서 '남이 먼저 확정'은 생기지 않는다 — 재선점은 배치가 내 홀드를 지운 뒤에만 가능하고 그러면 내 C1은 404다. SEAT_NOT_HELD = 최후 방어선(V12) 위반 · C2 0행 — **기대 0**. Q1의 억울 정의에는 남기되 '남의 확정' 뜻을 싣지 않는다(RD16-15).

### 9.2 ⓑ ① payment-start 계약
- **별도 읽기 전용 경로**: ① 갈래는 E1을 거치지 않는 함수 · `@Transactional(readOnly = true)`(쓰기가 오류로 드러남 — [구현 검증]) · 테스트에서 홀드 · 좌석 · 쿼터 행 전후 대조(N16-1 증거 — RD16-8).
- **θ 경계 통일**: `expires_at − :now ≤ θ`면 거부 — 지금 ④(`expires_at > :now + min`이어야 연장 · PaymentStartService.kt:44 · :75)와 같은 쪽(RD16-6).
- **응답에 보장 여부**: `200 {holdId, expiresAt, payBy, extended}` — ①은 `extended = false`(확인만 · 200 ≠ 보장) · ④는 연장했거나 이미 연장이면 true(RD16-11).
- **① 결과 지표**: `seat.confirm.pay_start{result = ok | insufficient | expired | not_found | not_owned}` — 결제 전 거부의 서버 교차 확인(RD16-13).
- **바뀌는 기존 계약**: `Adr015RaceScenarios.kt:228-235`('conditional-extend가 아니면 404')는 ①에서 200으로 바뀐다 — 구현 task가 이 테스트를 ADR-016 계약으로 옮긴다. ADR-015 요약기 `summarize.py:42` CONTRACT_PAIRS는 새 코드를 모른다 — race 셀 재사용 때 하네스가 함께 고친다(RD16-5).
- **거부 코드(Q8 — 사용자 재확인 2026-11-07: 'HOLD_EXPIRED 유지')**: ① θ 미만 거부도 409 `HOLD_EXPIRED` — ADR-015 인터뷰 결정('새 에러 코드를 두지 않는다' — ADR-015 :27 · :221)을 지킨다. 클라이언트는 둘을 구분하지 않아도 된다(어느 쪽이든 '결제를 시작하지 않는다' — 같은 행동) · 구분은 서버 지표 `pay_start{result=insufficient | expired}`로만 한다(오류 본문 필드 추가 없음 — post-fix RD16-post-1) · ④ too_late · ADR-015 요약기 CONTRACT_PAIRS 무변경(RD16-5).
- 재시도: ④ `already`(이미 연장 — θ 검사 없음 · :71-74)는 그대로 200 — 연장된 만료 안의 재결제는 허용. 모형은 1회 시도를 가정한다(설명 · RD16-OQ1).

### 9.3 ⓒ payBy
- 기동 검사: `M ≥ 0` · ~~`M < θ`(①) · `M < W`(④)~~ → **`M ≤ θ`(① · ④)**(구현 명세 2026-11-07 — ① 200 · ④ 연장 · not_needed 200은 남은 시간 > θ일 때만 나가므로 `M ≤ θ`면 이 응답들의 `payBy > :now`가 보장된다(보장 밖: ④ `already` 200은 θ 검사가 없어 payBy가 이미 지났을 수 있고 · 선점 201은 TTL ≤ M이면 payBy가 처음부터 지나 있다 — 지난 경우에는 `payWithinSeconds = 0`(1초 미만 남아도 내림으로 0) · TTL 쪽 기동 검사는 다음 명세의 θ < TTL 질문에 합침) · `M < θ`면 기본 θ = M = 0으로 기동 불가 · ④는 규칙 4의 θ < W와 합쳐 M < W도 성립) — 어기면 거부(RD16-7).
- 붙이는 곳: ① · ④ 모드의 선점 201 · payment-start 200(둘 다 A sweep · 앱 Clock — B · C · D는 current 명시가 강제돼 이 기능 밖 · RD16-OQ3).
- 클라이언트 시계 차: 절대 시각만 주면 클라이언트 시계로 계산된다 → **상대값 `payWithinSeconds`(= payBy − 서버 :now)를 함께 준다**(RD16-OQ3).
- ⓒ 셀의 억울 ≈ 0은 하네스가 확정을 보내지 않아 생기는 값이라 서버 증거가 아니다 — ⓒ 셀이 검증하는 것은 'M이 δ + 시계 차를 덮는가'뿐(RD16-19).

### 9.6 측정 설계 고침
- **결제 상한 CAP 다시 읽기**: E2 '10분'은 *인증 뒤 승인 호출* 창이고 같은 원문의 '결제 유효 시간 30분'이 결제 전체 쪽이다(메인 원문 대조 — 두 문장 모두 확인). E3 · E4도 하위 단계 → CAP ∈ {10, 30}분을 **판정에 넣는 민감도**로 둔다(RD16-14).
- **W 고르는 규칙**: 'G-목표를 넘는 최소 W'(비용이 W에 단조) — 모형 계산(T U[30,240] · m 45초 · 표본 30만 · 시드 3):

  | 목표 억울 | σ 0.7 | σ 0.94 | σ 1.2 |
  |---|---|---|---|
  | ≤ 0.1% (Q14) · CAP 10 / 30분 | 6.5 / 6.5분 | **9.5 / 13.5분** | 10.0(실패 1.52%) / 23.5분 |
  | ≤ 0.5% · CAP 10 / 30분 | 5.0 / 5.0분 | 7.5 / 8.5분 | 9.0 / 15.5분 |
  | ≤ 1% · CAP 10 / 30분 | 4.0 / 4.0분 | 6.5 / 7.0분 | 8.0 / 12.0분 |

  → 기준 분포에서 Q14(0.1%)는 홀드 수명 최대 **약 15~19분**(TTL 5 + W 9.5~13.5)을 요구한다. **사용자 재확인(2026-11-07): '0.1% 유지 + 비용 보고'** — 측정 뒤 좌석 점유 · 다른 사용자 거부 비용을 보고하고 그때 정한다(G-비용 보고 조건 · RD16-14 · RD16-16).
- **판정은 관측으로**: G-목표 = **실제 눈금 paid-flow 셀의 관측** 억울 비율의 한쪽 95% 상한 ≤ 목표(0건이면 상한 ≈ 3/n → 0.1%에는 셀당 n ≥ 3,000 세션). 모형은 후보 · W 선택 · 민감도에만 쓴다. 관측이 모형 구간 밖이면 원인 조사 → 재측정 1회 → 그래도 밖이면 판정 불가 → 사용자 보고(RD16-2 · RD16-17).

## 구현 (2단계 — 2026-11-07 · 작업 폴더 `docs/plans/2026-11-07/adr-016-payment-start/`)

- 범위: 앱 코드 + ADR-015 하네스 키 맞춤(측정 · k6/ADR-016 하네스는 다음 명세). 커밋 ea020de4(기능) · a7b2aacb(계약 테스트) · 7e3f046e · 1c2d8d5b · a271bb92(리뷰 반영).
- 계약(설계-9를 구현한 그대로):
  - 손잡이 `seat.confirm.payment-min-remaining`(θ · ① 확인과 ④ too_late 공통 · 기본 0) · `seat.confirm.pay-by-margin`(M · 기본 0). 옛 키 `extend-min-remaining`은 프로퍼티 · 환경 변수 어느 형태든 기동 거부(Flyway 앞). θ · M 음수 거부(모드 무관) · `M ≤ θ`(① · ④ — `ConfirmMode.paymentStartEnabled` 한 곳).
  - ① payment-start = 읽기 전용 트랜잭션의 잠금 없는 SELECT 한 번(`PaymentStartService.check`) · 404 → 403 → 409 expired → 409 insufficient(둘 다 HOLD_EXPIRED) → 200 · 지표 `seat.confirm.pay_start{result}`(200은 커밋 뒤).
  - 응답: payment-start 200 `{holdId, expiresAt, payBy, payWithinSeconds, extended}` · ① · ④ 선점 201에 `payBy · payWithinSeconds`(current · ② · ③은 키 3개 그대로). `payWithinSeconds = max(0, ⌊(payBy − 응답 시각)/1초⌋)`.
  - 확정 지표: `seat.confirm.rejected{code}`(처리기가 고른 상태 그대로 나간 도메인 거부) · `seat.confirm.failed{status}`(그 밖 비2xx · 미처리 예외 500 · 오류 본문을 못 쓴 거부 포함) — 확정 핸들러가 선택된 요청만(핸들러 매핑 전 405 · 컨테이너 파싱 400은 앱 밖).
- `:now`(① 판정 시각)는 요청당 한 번, 트랜잭션에 들어가 연결을 얻은 뒤의 앱 Clock — 확정 C1(설계-9.1의 δ 정의) · ④ E1과 같은 규칙이라 ① 200이 C1 판정을 더 잘 예측하고, 풀 대기만큼 보수적이다(명세 정정 2026-11-08 · 사용자 확인).
- 검증: 기존 전체 테스트(최종 코드 fb6e79dbc · 1,161 · 실패 0 · 건너뜀 24) · blind 계약 테스트 40 + fix 테스트 · 변이 3건(θ 경계 · rejected 증가 제거 · 거부 판정 옛 식)이 모두 테스트에 잡힘 · 로컬 기동 스모크(① · ④ · current · 옛 키). 리뷰 ledger = 작업 폴더 log.
- 측정 전 정할 것(이 단계 밖): θ < TTL 기동 검사 여부(θ ≥ TTL이면 ①은 모두 insufficient · ④는 모두 too_late — RC16-OQ1) · k6 대조에서 핸들러 매핑 전 비2xx를 어떻게 셀지(RC16-OQ2).
