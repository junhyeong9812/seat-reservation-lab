## 0. 요구사항 원문 (인터뷰 기록)

- 인터뷰 1차:

## 1. 목표·대상 (필수)

`seat-reservation-lab` 선점 경로의 **1인 최대 2매 규칙**에 사용자 단위 제어 방식 8개(아래 표)를 기동 설정으로 고를 수 있게 넣고, 좌석 선점은 ADR-003 결정(3b)으로 고정한 채 같은 캠페인으로 실측해 **매수 정합성·가짜 거절·처리량 회귀·이긴 쪽 롤백·매수 확인 지연**의 비교와 선택 근거를 `docs/adr/ADR-005-…md`에 기록하면 끝.

| # | 방식(설정 키 `seat.hold.limit-strategy`) | 같은 사용자 동시 요청을 막는 수단 | 진 쪽 |
|---|------|------|------|
| L0 | `none` | 지금 그대로(COUNT 후 비교) — 대조군 | 통과(초과 발생 예상) |
| L1 | `advisory` | `pg_advisory_xact_lock(회차, 사용자)`(두 정수 키) → COUNT | 기다림 |
| L2 | `advisory-try` | `pg_try_advisory_xact_lock(회차, 사용자)` — 못 잡으면 거절 | 즉시 `HOLD_LIMIT_EXCEEDED` |
| L3 | `quota-lock` | (회차, 사용자) 쿼터 행 `INSERT … ON CONFLICT DO NOTHING` → `SELECT … FOR UPDATE` → COUNT | 기다림 |
| L4 | `quota-nowait` | 같은 쿼터 행 `FOR UPDATE NOWAIT` | 즉시 `HOLD_LIMIT_EXCEEDED` |
| L5 | `counter` | 쿼터 행의 매수 카운터 `UPDATE … SET cnt = cnt + 1 WHERE cnt + 1 <= 2` — 영향 행 0이면 거절. COUNT 없음 | 행 락 대기 후 재평가 |
| L6 | `serializable` | 트랜잭션 격리 수준 SERIALIZABLE — 충돌(40001)은 거절 | 즉시 `HOLD_LIMIT_EXCEEDED` |
| L7 | `serializable-retry` | 같고, 40001이면 트랜잭션 전체를 최대 3회 다시 | 재시도 후 거절 |

## 2. 경계·불변식 (필수)

- **좌석 선점 방식은 3b `pessimistic-nowait`로 고정**하고 앱 기본값도 3b로 바꾼다(ADR-003 결정 반영). 좌석 전략 11개 코드는 그대로 두고 기본값만 바꾼다. 기본 매수 방식 = `none`.
- **락 순서는 사용자 → 좌석**: 사용자 단위 락(L1~L4)은 트랜잭션 시작 직후·좌석 읽기 전에 잡는다. **에러 우선순위는 보존** — 락만 먼저 잡고, 판정 순서는 지금처럼 좌석 불가(`SEAT_NOT_AVAILABLE`) → 매수 초과(`HOLD_LIMIT_EXCEEDED`). **예외 = L5 counter**: 카운터 갱신 자체가 매수 판정이라 좌석보다 먼저 판정된다(사용자 허용 — ADR에 기록).
- **응답 계약 불변**: 새 에러 코드 없음. 즉시 실패형의 거절은 `HOLD_LIMIT_EXCEEDED`(409) 재사용.
- **같은 사용자만 직렬화**: 다른 사용자끼리는 서로 막지 않아야 한다(S4 처리량으로 확인). advisory 키는 두 정수 형태 `(회차, 사용자)`로 ADR-003 advisory 전략의 한 정수 키(좌석 id)와 공간을 나눈다.
- **매수 정의는 그대로**: 홀드 수 + 확정 예약 수 < 2. 카운터(L5)는 같은 값을 유지해야 한다 — 선점 +1, 만료 −1(만료 배치, **counter 전략일 때만**), 확정은 홀드 → 예약이라 변화 없음, 선점 실패(좌석 NOWAIT 등)는 같은 트랜잭션 롤백으로 원복.
- **만료·확정 경로는 counter 전략일 때만 바뀐다** — 다른 방식에서 만료·확정 동작은 지금 그대로.
- **스키마 추가는 다른 방식에 무해하게**: 쿼터 테이블(`user_hold_quota(schedule_id, user_id, cnt)`, PK (schedule_id, user_id)) 추가 — L3·L4·L5만 쓴다. 기존 테이블·인덱스 변경 없음.
- **측정 조건은 ADR-003과 같게**: 같은 서버·k6 PC(유선)·시드·예열·타임아웃(30s)·Tomcat·인덱스 V2·풀 10. 달라지는 변수는 매수 방식뿐. 비교는 같은 캠페인 안에서만, 대조군도 이 캠페인에서 다시 잰다.
- **판정·근거 보존 규칙은 ADR-001~003 그대로**: DB 사실 기준 판정, 응답-DB 대조, 표는 스크립트 산출(errsplit 뒤 compare), 미측정은 '미측정', 요청별 원시 CSV는 sha256만.

## 5. 검증 방법 (필수)

- **방식 단위 테스트(Testcontainers)**: 같은 사용자가 서로 다른 좌석 N개를 동시 선점 → `none`은 초과가 나야 정상(양성 대조, 라운드 안에서), 나머지 7개는 사용자당 성공 ≤ 2 · 판정기 `v_over_limit_users` 0. 다른 사용자끼리 동시 선점이 서로 막히지 않음(대기형 포함). counter: 선점·만료·확정·좌석 실패 롤백 뒤 카운터 = 홀드 + 확정 예약. 에러 우선순위(L5만 바뀜) 테스트.
- 기본 좌석 전략 3b·기본 매수 방식 none에서 기존 테스트 전부 green(기본값에 기대던 테스트는 명시 설정으로).
- 하네스 스모크: 매수 방식 대조(`limit-strategy-mismatch`), S2 L4 1회(none 초과 재현 = 가정 1), 롤백 시나리오 1회, DB 벤치 1조합.
- 본측정: 계획 대비 누락 0, 비정상 회차 재측정 — ADR-003 캠페인 규칙 그대로.
- ADR-005 표는 원시 결과에서 스크립트로 재산출. 판정기 전수 절로 '위반 0' 근거.

## 8. load-bearing 가정 (1~2개)

1. **좌석 전략을 3b로 둔 채 S2에서 none(대조군)이 매수 초과를 재현한다** — ADR-002 S2는 좌석 전략 none에서 15~17명이었다. 3b가 좌석 경합만 막고 매수 경합은 그대로 두는지 착수 직후 테스트·S2 스모크로 실증. 재현 안 되면 사용자 보고(시나리오 재설계).
2. **사용자 단위 제어를 좌석 전략이 연 같은 트랜잭션 안에 끼울 수 있다**(락 → 좌석 NOWAIT → 매수 판정 → 저장이 한 트랜잭션, SERIALIZABLE은 그 트랜잭션의 격리 수준) — 3b의 S1 결과(성공 1)가 바뀌지 않는지 테스트로 실증.

## 9. 설계

### 9.1 구조

- `UserLimitStrategy` 인터페이스 + 구현 8개, `seat.hold.limit-strategy`(기본 `none`)로 하나 선택. `HoldSeatProcess`에 갈래점 둘: 트랜잭션 시작 직후 `acquire(회차, 사용자)`(L1~L4 락, L5 카운터 갱신), 매수 판정 자리 `check(…)`(L0·L1~L4·L6·L7은 지금의 COUNT, L5는 이미 판정됨).
- SERIALIZABLE(L6·L7): 좌석 전략의 `TransactionTemplate` 격리 수준을 매수 방식이 정한다. L7 재시도는 트랜잭션 바깥(선점 유스케이스)에서 최대 3회.
- 매수 확인 구간 타이머(Micrometer `seat.hold.limit.check`) — 실 락 획득부터 판정까지. 하네스가 k6 전후 차분으로 수집.

### 9.2 측정 매트릭스 (좌석 3b, 풀 10, 인덱스 V2, 배경 0)

| 대상 | 시나리오 | 단계 | 회차 |
|------|---------|------|------|
| 매수 방식 8개 | S2(사용자 100 × 좌석 10 동시) · S4(16단계) | L2 · L4 | 5 |
| 매수 방식 8개 | S3 원본 × 이탈 0/20/50 | L4 | 3 |
| 매수 방식 8개 | **S7 이긴 쪽 롤백**(새): 이미 2매인 사용자 1명 + 일반 사용자 M명이 같은 좌석을 동시에 — 좌석이 끝내 비었는데 진 일반 사용자 수. **M=20(`S7`)과 M=1(`S7-m1`, 재합의)** | L4 | 5 |
| 매수 확인 쿼리 2개 | DB 직접 벤치(pgbench): 배경 홀드·예약 0 / 10만 / 100만 — 지연·실행 계획 | L4 | 조합당 1 |

→ 약 40~45시간(추정 — ADR-003 실측 비례).

### 9.3 판정 기준

| 기준 | 지표 |
|------|------|
| ① 매수 정합성 | 사용자당 성공 ≤ 2, `v_over_limit_users` 0 — 전 회차 |
| ② 가짜 거절 | S2에서 끝 상태 매수 < 2인데 거절된 사용자 수(즉시 실패형·SERIALIZABLE) |
| ③ 처리량 회귀 | S4 엄격 한계·커넥션 획득 대기 — 대조군 대비 |
| ④ 이긴 쪽 롤백 | S7에서 좌석이 비어 끝났는데 409를 받은 일반 사용자 수 |
| ⑤ 매수 확인 지연 | 앱 타이머(구간 시간) · DB 벤치(배경 규모별) |
| ⑥ 실패 모드 | 응답 분류, 데드락, 40001 비율, 재시도 횟수 |
| ⑦ 카운터 정합 | S3 끝 상태에서 카운터 = 홀드 + 확정 예약(counter만) |
