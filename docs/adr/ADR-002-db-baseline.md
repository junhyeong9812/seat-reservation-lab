# ADR-002: DB 기준선 보정 — 일반 인덱스와 커넥션 풀

- 상태: 가설 (Hypothesis) — 측정 준비 완료(측정 전 검증에서 결함 발견·수정, §6)
- 날짜: 2026-09-29
- 대응: ADR-001의 처리량 한계(C3)·타임아웃·유령 확정(C4)이 **락이 아니라 DB 차원의 기본기**(인덱스 부재·풀 크기)에서 오는지 가른다
- 선행: ADR-000(측정 대상), ADR-001(판정기·하네스·before 수치)
- 후행: ADR-003(락 비교)은 이 ADR이 정한 조합을 기준선으로 쓴다
- 명세: `docs/plans/2026-09-29/adr-002-db-baseline/requirement-spec.md`

## 1. 문제

ADR-001에서 관측한 것:

- **선점 한 번에 `seat_hold` 전체 스캔 2회** — 1인 2매 확인(`countByScheduleIdAndHoldsUserId`)과 좌석의 홀드 목록 로드. 홀드 20만 행에서 각각 9.5~12.5ms·7~8ms(ADR-001 §4.3 실행 계획). 요청당 DB 비용이 누적 홀드 수에 비례한다.
- S4 처리량 한계(L2 378·L4 252건/s)에서 **DB CPU가 포화**(215%·421%). 앱은 한가했다.
- L1·L2 S3 원본에서 **확정 타임아웃 약 1만 건/회차**, 그중 일부가 뒤늦게 처리돼 **유령 확정**(−149~−345).
- 커넥션 풀 10은 전 단계 고정. Hikari 대기 예외는 0건 — 풀이 병목으로 **관측되지는 않았다**. 그러나 S1 같은 좌석 중복 성공이 **정확히 풀 크기(10)**였다.

이 상태에서 락 방식을 비교하면(ADR-003) 모든 방식이 같은 스캔 비용에 묻혀 차이가 안 보인다. 그래서 락보다 먼저 **DB 차원의 기본기를 갖춘 기준선**을 정한다.

## 2. 가설

| # | 가설 | 틀렸다고 판정할 관측 |
|---|------|------------------|
| H1 | 일반 인덱스를 추가하면 선점 경로의 전체 스캔이 인덱스 스캔으로 바뀌고, S4 한계가 오르며 DB CPU 포화가 늦어진다 | 실행 계획이 Seq Scan 그대로 / S4 한계가 ADR-001 범위 안 |
| H2 | 인덱스로 요청이 빨라지면 L2 S3 원본의 확정 타임아웃·유령 확정이 줄어든다 | L2 S3 확정 에러율이 ADR-001(62~66%)과 같음 |
| H3 | 풀을 늘려도 처리량은 거의 늘지 않는다(병목은 DB CPU) — 오히려 느려질 수 있다 | 풀 20·40에서 S4 한계가 풀 10보다 뚜렷이 높음 |
| H4 | 풀을 늘리면 S1 같은 좌석 중복 성공이 풀 크기를 따라 늘어난다 | 풀 20·40에서도 S1 성공이 10 근처 |
| H5 | 일반 인덱스는 **정합성 위반을 막지 않는다** — S1 중복·S2 매수 초과는 그대로 재현된다 | S1 성공 1 / S2 초과 0 (그렇다면 인덱스가 아닌 무언가가 막은 것 — 측정 설계 오류) |
| H6 | 인덱스 없이는 선점 경로 쿼리 비용이 홀드·예약 행 수에 **비례**해 커지고, 인덱스가 있으면 규모와 거의 **무관**하다 | S5에서 인덱스 없음의 지연이 규모에 따라 늘지 않음 / 인덱스 있음이 규모에 따라 크게 늘어남 |
| H7 | 그 차이가 시스템 처리량으로 이어진다 — 인덱스 없음은 배경이 커질수록 S4 한계가 떨어지고, 인덱스 있음은 거의 유지된다 | 배경 10만·100만에서 인덱스 유무의 S4 한계 차이가 배경 0과 같음 |

## 3. 선택지 (조건)

### 3.1 인덱스 (Flyway `V2__add_indexes.sql`, 모두 유니크 아님)

| 인덱스 | 쓰는 곳 |
|--------|--------|
| `seat_hold(seat_id)` | 좌석의 홀드 목록 로드(애그리거트 컬렉션), FK |
| `seat_hold(user_id)` | 1인 2매 확인 — 홀드 수 (처음 설계한 `seat_hold(schedule_id, user_id)`는 쓰이지 않아 교체 — §6.1) |
| `seat_hold(expires_at)` | 만료 배치 조회 |
| `reservation(schedule_id, user_id)` | 1인 2매 확인 — 확정 예약 수 |
| `reservation(seat_id)` | FK |

- **유니크 인덱스·제약은 쓰지 않는다.** 유니크는 중복 자체를 막는 해결책이라 ADR-003의 후보다. 여기서 쓰면 "인덱스 효과"와 "중복 차단 효과"가 섞인다.
- 인덱스 없음 조건은 `spring.flyway.target=1`(V1까지만 적용)로 만든다. 코드·스키마 파일은 같고 설정만 다르다.

### 3.2 커넥션 풀

10(ADR-001) · 20 · 40. Tomcat 스레드 200·대기열 무제한·Hikari 대기 30s는 ADR-001과 같게 둔다. PostgreSQL `max_connections` 기본 100으로 풀 40까지 수용한다.

- 일반론(HikariCP 풀 크기 가이드: 코어 수 × 2 + 디스크 수)으로는 DB 2~4코어에 풀 10 안팎이 적정이다. 이 환경에서 맞는지는 측정으로 본다.

## 4. 측정 계획

| 조건 | 풀 | 시나리오 | 단계 | 회차 |
|------|----|---------|------|------|
| 인덱스 있음 | 10 / 20 / 40 | S1 · S2 · S4 · S3 원본 × 이탈 0/20/50 | L2 · L4 | 5 |
| 인덱스 없음 | 20 / 40 | S1 · S4 | L2 · L4 | 5 |
| **인덱스 없음 (기준선 재측정)** | 10 | S1 · S2 · S4 · S3 원본 × 이탈 0/20/50 | L2 · L4 | 5 |
| ~~인덱스 없음 — ADR-001 결과 재사용~~ | 10 | — | — | 환경 판정 실패로 재사용하지 않음(§6.6) |
| 규모별: 인덱스 없음·있음 × 배경 10만·100만 | 10 | S1 · S4 | L2 · L4 | 5 |
| S5 규모별 쿼리 비용: 인덱스 없음·있음 × 배경 0·1만·10만·100만·500만 | — | 선점 경로 쿼리 4종(DB 직접) | L2 · L4 | 조합당 1회 |

- **배경 데이터**(규모 N): 측정 회차와 다른 배경 회차에 좌석 2N — HELD N(홀드 1개씩) + RESERVED N(CONFIRMED 1건씩). 판정 위반 0에서 시작하고, 측정 동작은 그대로 둔 채 테이블 행 수만 늘린다. 현실 대응: 예약은 지난 공연이 쌓이는 정상 규모, 홀드 수십만~수백만은 만료 배치가 밀린 비정상 규모.
- **S5**: 앱·HTTP 없이 DB 컨테이너에서 `pgbench`로 선점 경로 쿼리(1인 2매 확인 — 홀드·예약, 좌석의 홀드 목록, 만료 배치 조회)를 반복 실행해 지연(평균·분위수)과 동시 10연결 처리량을 잰다 — 인덱스 효과만 분리.
- 합계 약 360회 + S5, 약 61시간(추정). 시나리오·시드·예열·타임아웃은 ADR-001과 같다.
- **환경 동일성 확인 → 실패 → 기준선 재측정**: 인덱스 없음·풀 10 S4를 다시 재서 ADR-001 범위를 벗어나(§6.6) ADR-001 결과를 재사용하지 않고, 기준선을 이 ADR 안에서 전 시나리오로 다시 잰다. 모든 비교는 같은 캠페인 안에서만 한다.
- **타임아웃 빈도의 정의**: 응답 코드 0(클라이언트 30s 포기)·5xx 비율 — S1·S2는 선점, S3는 선점·확정 각각, S4는 단계별. 유령 확정(확정 200 − CONFIRMED)을 함께 본다.

### 6.1 이슈 — 1인 2매 확인용 인덱스가 쓰이지 않았다 (ISSUE-ADR002-1)

**증상**: 인덱스를 추가했는데도 1인 2매 확인의 홀드 수 쿼리(Q1)가 `seat_hold` 전체 스캔 그대로였다. 나머지 세 쿼리는 인덱스로 60~90배 빨라졌다.

S5 스모크 (4 CPU, 배경 10만 행, 커밋 `ad363c8` — 결과 `k6/ADR-002/results/smoke-s5/`):

| 쿼리 | 인덱스 없음 | 인덱스 있음(기존 설계) | 실행 계획(있음) |
|--|--|--|--|
| Q1 1인 2매 — 홀드 수 | 3.9ms | **4.1ms** | **Seq Scan on seat_hold** (10만 행 필터) |
| Q2 1인 2매 — 확정 수 | 4.4ms | 0.055ms | Index Scan `idx_reservation_schedule_user` |
| Q3 좌석의 홀드 목록 | 3.8ms | 0.062ms | Index Scan `idx_seat_hold_seat_id` |
| Q4 만료 배치 조회 | 4.2ms | 0.048ms | Index Scan `idx_seat_hold_expires_at` |

(시간 = `EXPLAIN ANALYZE` 실행 시간, 1회)

**원인**: Q1은 도메인의 `countByScheduleIdAndHoldsUserId`가 만드는 쿼리로, 조건이 **`seat_hold.user_id`와 `product_seat.schedule_id`**다 — 회차 조건은 홀드가 아니라 **조인한 좌석 테이블**에 걸린다.

```sql
SELECT count(ps.id) FROM product_seat ps JOIN seat_hold h ON ps.id = h.seat_id
WHERE ps.schedule_id = ? AND h.user_id = ?
```

처음 설계한 `seat_hold(schedule_id, user_id)`는 앞 열(`seat_hold.schedule_id`)이 조건에 없어 쓰일 수 없다(PostgreSQL 16은 복합 인덱스의 앞 열을 건너뛰는 스캔이 없다). 인덱스 이름만 보고 "1인 2매용"이라고 설계했지, **실제 쿼리의 조건 열을 확인하지 않은** 설계 실수다.

**변경**

| | 기존 | 변경 |
|--|--|--|
| V2 인덱스 | `idx_seat_hold_schedule_user ON seat_hold (schedule_id, user_id)` | `idx_seat_hold_user_id ON seat_hold (user_id)` |
| 근거 | 쿼리 이름("회차·사용자별") | 실제 쿼리의 조건 열(`h.user_id`) — 사용자당 홀드는 몇 개뿐이라 충분히 선택적이고, 회차는 좌석 PK로 확인 |

- 사용자 합의(2026-09-29, 명세 §9.1 변경).
- V2 파일은 **직접 수정**했다: V2가 적용된 DB는 테스트·스모크에서 매번 새로 만들고 지운 것뿐이라, 적용된 마이그레이션을 바꿀 때의 Flyway 체크섬 문제가 없다. 운영 DB였다면 V3로 교체해야 한다.
- 변경 후 확인: §6.4 스모크.

**교훈** (study-note 이슈 후보): 인덱스는 **쿼리 이름이 아니라 실제 SQL의 조건 열**로 설계하고, 조인 쿼리는 조건이 어느 테이블에 걸리는지 본다. 설계한 인덱스는 **실데이터 규모에서 실행 계획으로 확인**한 뒤 측정에 들어간다 — 확인 없이 측정했다면 "인덱스를 넣어도 1인 2매 확인은 그대로"라는 틀린 결론이 38시간 측정에 실렸을 것이다.

### 6.2 코드 리뷰 정리 — 기존 → 변경

리뷰어 A = Opus 워커, B = codex. 두 리뷰어가 같은 결함을 따로 짚은 항목이 많았다(교차 표시). 재점검 판정은 수정 후 codex 타깃 재점검 결과.

| # | 지적 (리뷰어) | 기존 형태 | 변경 | 재점검 |
|---|------|---------|------|-------|
| R1 | 1인 2매 인덱스가 쿼리 조건과 안 맞음 (A·B) | `seat_hold(schedule_id, user_id)` | `seat_hold(user_id)` — §6.1 | 해소 |
| R2 | 배경 행이 응답-DB 대조에 섞임 (A·B) | "201 − 홀드 행"이 배경 N만큼 음수(배경 100만이면 약 −100만) | 요약기가 `meta.bg`를 뺀다 | 해소 |
| R3 | 캠페인 동결이 무력화 (A) | 캠페인 중 작업트리를 고치면 남은 조건이 전부 SHA 불일치로 즉시 종료, 캠페인은 "done"으로 끝남 | 캠페인에서 불리면 작업트리 검사 생략(캠페인이 시작 때 확인) + 하위 실행이 비정상 종료하면 캠페인 중단(ABORT) · 1차 수정의 셸 우선순위 버그(미추적 파일 검사가 생략되지 않음)도 재점검에서 잡아 괄호로 수정 | 해소 |
| R4 | 요약기가 명세 약속을 다 못 함 (A·B) | S2 에러율 열 없음, ADR-001 비교표·S5 표·0/5xx 분리 없음 | S2 에러율 추가 · 나머지(비교표·S5 표·0/5xx 분리)는 **측정 중 분석 도구로 구현** — 원시 데이터(요청 CSV·pgbench 로그)로 사후 산출 가능, 측정에 영향 없음 | 이연 타당 |
| R5 | S5 실패·누락이 숨음 (A·B) | 실패 조합도 `DONE` 기록 → 영원히 재측정 안 됨, 재실행 시 원시 결과 덮어씀, 검증은 pgbench 출력만 | 계획 기록(`plan.json`), 조합마다 status(실행 계획·행 수(기대값 대조)·인덱스·지연 로그까지), 끝난 조합 건너뜀, 미완성은 `.incomplete-<시각>`으로 보존, 실패가 있으면 DONE 없음·exit 1, 이어서 실행은 계획과 인자가 다르면 거부 | 해소 |
