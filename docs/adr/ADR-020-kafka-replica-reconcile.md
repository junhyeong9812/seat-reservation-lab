# ADR-020: Kafka + 읽기 복제본 대조 — 탐지를 원본 DB 밖으로 옮긴다

> 번호 이동(2026-10-23, 9차): Kafka·읽기 복제본 대조(옛 ADR-013)를 착수 조건이 생기는 오픈 폭주 뒤로 보내 ADR-020으로 옮기고, 기존 ADR-014~020을 013~019로 당겼다 — 이 문서의 번호 참조는 새 번호다.

- 상태: **보류 — 착수 조건: 쓰기 속도 증가(바뀐 쌍 대조 비용이 초당 선점에 비례) 또는 데이터 증가로 안전망 한 바퀴 시간이 길어짐(ADR-012 §8.5-5·§8.8) — 여러 회차 동시 예매·오픈 폭주(새 ADR-019) 측정 뒤 판단(사용자 결정 2026-10-23)**. 설계·가설·측정 계획은 ADR-012 결과 뒤 별도 작업 폴더의 명세로 정하고, 측정 전에 이 문서에 고정한다.
- 선택지 기록 원문: `docs/plans/2026-10-18/adr-012-incremental-reconcile/requirement-spec.md` §0
- 선행: **ADR-012**(증분 대조 M0~M3 — 이 ADR의 기준선) · ADR-009(`PairRepair` 복구 규칙) · ADR-011(C의 규모 한계) · ADR-014(홀드 만료) · ADR-019(오픈 폭주 — 착수 조건을 재는 측정) · 여러 회차 동시 예매(번호 미정)
- 후행: 없음(9차 이동 전에는 ADR-014·019의 선행이었다)

## 1. 왜 따로 두나

ADR-012의 증분 대조(M2·M3)는 바퀴당 일을 '바뀐 쌍 수'로 줄인다. 그래도 **탐지 쿼리는 원본 DB에서** 돈다. 외부 앱(M3)으로 옮겨도 나뉘는 것은 앱 CPU와 커넥션 풀이지 DB CPU가 아니다. 원본에 가는 부하를 '어긋난 쌍의 복구'만 남기려면, 탐지를 원본 밖(읽기 복제본)으로 옮기고 바뀐 쌍을 원본 밖으로 전달해야 한다(사용자 제안 2026-10-17 — "DB를 조회용과 커밋용으로 분리하고, 선점한 좌석을 카프카로 쌓고, 쌓인 데이터를 앱에서 비교해 대조").

## 2. 모델 M4

```
.164                                   .158
본 앱 ──쓰기──▶ 원본 DB ──WAL 스트리밍──▶ 읽기 복제본
   │               │                        ▲ 탐지(cnt 대 실제)
   │ (아웃박스)     │ (CDC — 논리 복제 슬롯)   │
   └──────────────▶ Kafka ──바뀐 (회차, 사용자)──▶ 외부 대조 앱
                                                 │ 어긋난 쌍만
원본 DB ◀──────────── 잠근 뒤 다시 세어 복구(PairRepair) ──┘
```

- 복제본의 한 문장 안에서는 카운터와 실제 값이 같은 시점이라 비교가 일관된다. 복제 지연으로 생기는 오탐은 원본에서 잠근 뒤 다시 세는 복구 단계가 거른다(지금 코드 그대로).
- 키를 (회차, 사용자)로 두면 쌍별 순서가 지켜지고, 대조 소비자를 파티션별로 나눌 수 있다.

## 3. 고른 것과 고르지 않은 것 (인터뷰 2026-10-18)

| 질문 | 고른 것 | 고르지 않은 것 | 이유·대가 |
|---|---|---|---|
| ADR 나누기 | **ADR-012 증분 / ADR-020 Kafka·복제본** | 한 ADR-012로 전부 | 인프라가 커서 결정 주기를 나눴다 |
| 배치 | **.158에 복제본 + Kafka + 대조 앱**(원본 DB·본 앱은 .164) | .158 복제본·대조 앱 + .9 Kafka · .164 안에 모두 | 복제본은 원본과 다른 CPU여야 부하가 나뉜다. .164 안에 모두 두면 기능 검증만 된다 |
| 바뀐 쌍을 쌓는 방식 | **둘 다 비교** — CDC(Debezium — 원본 WAL) · 앱 발행 + 아웃박스 | CDC만 · 아웃박스만 | CDC: 앱 코드 변경 없음 · 앱 밖 변경·주입까지 잡음 · 논리 복제 슬롯이 원본 WAL을 붙잡는 비용. 아웃박스: 같은 트랜잭션에 기록 — 선점 경로에 쓰기 1개 추가 · 앱 밖 변경은 못 봄 |

## 4. 미리 알려진 위험 (설계 때 다룬다)

1. **복제본의 긴 쿼리와 원본 VACUUM의 충돌**: 복제본 쿼리가 원본의 정리와 부딪혀 취소될 수 있다(`max_standby_streaming_delay`). 막으려고 `hot_standby_feedback`를 켜면 원본 테이블이 부푼다(간접 부하). 증분은 짧은 쿼리라 위험이 작지만, 안전망 전체 훑기는 복제본에서 길다.
2. **복제 반영 지연**: 원본이 초당 4,200건을 쓰는 동안 복제본 반영은 단일 프로세스다. 복제본 CPU가 대조와 경합하면 지연이 커진다 — 탐지 시간 = 복제 지연 + 메시지 지연 + 주기.
3. **이중 쓰기(아웃박스 아닌 직접 발행)**: DB 커밋과 Kafka 발행은 원자적이지 않다 — 직접 발행은 비교 대상에서 뺐다.
4. **.158 자원**: CPU 6 · 메모리 15GiB(가용 약 9GiB, 2026-10-18 읽기 전용 확인) · 다른 서비스 컨테이너 7개가 함께 돈다. 복제본 + Kafka + 대조 앱이 들어갈지, 다른 서비스에 영향이 없는지 명세 때 다시 본다.
5. **메시지 유실·보존 기간**: Kafka 보존을 넘긴 유실이나 CDC 재시작에 대비해 드문 전체 훑기 안전망은 남긴다(ADR-012와 같은 원리).
