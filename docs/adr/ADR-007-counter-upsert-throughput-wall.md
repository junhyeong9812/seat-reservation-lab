## 1. 문제

ADR-006에서 counter-upsert(트랜잭션 안 한 문장 `INSERT … ON CONFLICT DO UPDATE … WHERE cnt + 1 <= 상한`)는 S2(사용자 100명 × 각자 좌석 10개 동시)·S7-m1(2매 보유자 + 일반 1명)에서 가장 좋았다. 억울한 좌석 0(advisory-try 67), 같은 사용자 지연 p99 230ms(advisory-try 433), CPU도 덜 든다. 그러나 S4(도착률 계단, 요청마다 새 사용자·좌석)에서 **벽**을 만났다.

- 11단계(목표 4,325건/s)를 26~27초 동안 p99 5~17ms로 버티다가, **10회 모두 같은 초**에 무너진다. 누적 선점은 약 37만 건이다.
- L2와 L4(앱·DB CPU 2개·4개)에서 같은 초에 무너진다 → CPU가 아니다.
- Hikari 대기가 1초 안에 0 → 190으로 뛴다. 서서히 늘어나는 압박보다 전역 정지에 가깝다.
- 벽은 시간 기준 체크포인트가 진행 중인 구간에 있다. counter-upsert만 체크포인트 쓰기가 빨라졌다(WAL +21%).
- 그 결과 L4 엄격 한계가 4,300 → 2,866(5회 중 3회)이다.

또 쓰기 비용이 있다.
- 실제 흐름(S3, 이탈 20%)에서 WAL이 2.8배, 디스크 쓰기가 1.55배다. 좌석에서 지는 시도도 upsert 후 롤백한다(추정).
- 쿼터 행은 만료로 지워지지 않는다.

질문: **벽은 무엇에서 오는가, 그리고 설정이나 구조 변경으로 없앨 수 있는가?** 없앨 수 있고 ADR-006 §6 전환 규칙을 만족하면 기본을 counter-upsert로 바꾼다.

## 2. 원인 후보 (ADR-006 §5.3 ②)

| # | 후보 | 맞다면 보일 것 |
|---|------|--------------|
| C1 | 체크포인트 가속·WAL 압박 — WAL이 빨리 쌓여 `max_wal_size`에 맞춰 체크포인트가 쓰기를 당긴다 | 벽 시각이 체크포인트 진행·전체 페이지 쓰기(FPI) 급증과 맞는다. 대기 이벤트 LWLock:WALWrite·IO:WALSync·DataFileWrite. `max_wal_size`를 키우면 벽이 밀린다 |
| C2 | 버퍼 교체 — 누적 데이터가 `shared_buffers`(128MB)를 넘는다 | 백엔드 직접 쓰기·읽기 급증, 대기 이벤트 BufferIO·BufferMapping. `shared_buffers`를 키우면 벽이 밀린다 |
| C3 | 관계 확장 락 — 쿼터 테이블·인덱스가 계속 늘어난다 | 대기 이벤트 Lock:extend |
| C4 | B-tree 오른쪽 끝 페이지 경합 — S4는 사용자 ID가 늘 증가한다 | 대기 이벤트 LWLock:BufferContent, 설정을 바꿔도 남는다 |
| C5 | (본측정 결과로 추가, §7.1) 저장장치·호스트 쓰기 경로 지연 — 방식·PG 설정과 무관하게 DB가 일정량을 쓰면 장치 쓰기가 느려진다 — **확인(2026-10-11, §7.2)** | 벽이 누적 선점·경과 시간이 아니라 DB 컨테이너의 누적 쓰기량에 맞는다. 모든 방식·설정에서 같은 지점. 호스트 디스크 지연이 함께 뛰고, PG 없이(fio) 재현되며, DB를 메모리에 두면 사라진다(§7.2 후속) |

- 누적 행 수와 경과 시간이 겹쳐 있다. 도착 계획이 고정이라 ADR-006 설계로는 둘을 가를 수 없다.

## 3. 선택지 (명세 확정 2026-10-09)

| 방식 | 설명 |
|------|------|
| none | 대조군. advisory-try는 처리량이 none과 같고(ADR-005·006) 억울한 좌석도 해결하지 못해 뺐다(사용자 지적) |
| counter-upsert | ADR-006 그대로 |
| **counter-upsert-precheck** (신규) | 아래 순서 |

counter-upsert-precheck의 처리 순서:

1. 좌석 상태를 **잠금 없이** 먼저 읽는다. 팔렸으면 쓰기 없이 `SEAT_NOT_AVAILABLE`이다.
2. upsert를 한다.
3. upsert가 0행이면 좌석을 다시 읽는다. 그 사이 팔렸으면 `SEAT_NOT_AVAILABLE`, 아니면 `HOLD_LIMIT_EXCEEDED`다.
4. 3b 좌석 잠금으로 넘어간다.

설계 의도:
- 에러 순서는 **명세 순서(좌석 먼저)** 다. 사용자는 '팔렸으면 좌석, 아니면 매수 먼저' 혼합안을 거부했다.
- 매수 초과 사용자는 좌석 락을 잡기 전에 거절된다 → 억울한 좌석 0을 유지한다.
- 남는 틈: 다른 트랜잭션이 커밋 전에 쥔 좌석은 잠금 없는 읽기에 AVAILABLE로 보인다. 그래서 매수가 찬 사용자에게 `HOLD_LIMIT_EXCEEDED`가 난다. 잠금 없이는 볼 수 없다.
- 좌석 잠금 뒤 upsert 안은 매수 초과자가 좌석 락을 잡아 억울한 좌석이 되살아나서 제외했다.

### 3.1 코드 변화 — ADR-006 `counter-upsert` → ADR-007 `counter-upsert-precheck`

선점 요청의 실행 흐름(컨트롤러 → `HoldSeatService` → 좌석 3b 트랜잭션 → `HoldSeatProcess`)과 매수 방식이 끼어드는 자리 ⓐ~ⓓ는 ADR-006 §2.1 (1)과 같다. precheck가 바꾸는 것은 ⓒ `acquire` 하나다. 그 자리는 트랜잭션 안이고 좌석 `for no key update nowait`보다 앞이다. 코드는 `service/impl/limit/UserLimitStrategies.kt`에서 옮겼다. upsert 문(`upsertQuota`)과 만료 감소(`decrementCounters`)는 counter-upsert와 같은 함수를 공유한다. **바뀐 것은 upsert 앞뒤의 잠금 없는 좌석 조회뿐이다.**

```kotlin
// ADR-006 CounterUpsertUserLimit
override fun acquire(command: HoldSeatCommand): Boolean {
    if (!upsertQuota(jdbc, command, properties.maxPerUser)) limitExceeded()
    return true
}

// ADR-007 CounterUpsertPrecheckUserLimit
override fun acquire(command: HoldSeatCommand): Boolean {
    assertSeatAvailable(command)
    if (!upsertQuota(jdbc, command, properties.maxPerUser)) {
        assertSeatAvailable(command) // 선조회 뒤 팔렸으면 좌석 불가가 먼저
        limitExceeded()
    }
    return true
}

private fun assertSeatAvailable(command: HoldSeatCommand) {
    val status = jdbc.queryForList(
        "SELECT status FROM product_seat WHERE id = ? AND schedule_id = ?", String::class.java,
        command.seatId, command.scheduleId,
    ).singleOrNull() ?: throw SeatReservationException(ErrorCode.SEAT_NOT_FOUND)
    if (status != SeatStatus.AVAILABLE.name) throw SeatReservationException(ErrorCode.SEAT_NOT_AVAILABLE)
}
```

| 상황 | counter-upsert | counter-upsert-precheck |
|------|----------------|-------------------------|
| 팔린 좌석, 매수 남음 | upsert(+1) → 3b에서 좌석 불가 → 롤백(WAL 남김) | 선조회에서 `SEAT_NOT_AVAILABLE` — **쓰기 없음** |
| 팔린 좌석, 매수 참 | upsert 0행 → `HOLD_LIMIT_EXCEEDED`(명세 순서 위반) | 선조회에서 `SEAT_NOT_AVAILABLE`(명세 순서) |
| 빈 좌석, 매수 참 | upsert 0행 → `HOLD_LIMIT_EXCEEDED`, 좌석 락 없음 | 같다(재조회도 AVAILABLE) |
| 빈 좌석, 매수 남음 | upsert(+1) → 3b 좌석 잠금 | 같다(선조회 1문장 추가) |
| 다른 트랜잭션이 커밋 전에 쥔 좌석, 매수 참 | `HOLD_LIMIT_EXCEEDED` | 같다 — 잠금 없는 읽기에 AVAILABLE로 보인다(남는 틈) |

- 선조회는 같은 트랜잭션 안의 일반 `SELECT`라 커넥션 빌림은 그대로 1회다. 좌석 행 잠금도 잡지 않는다.
- 판정 위치는 ADR-006과 같다(`HoldSeatProcess.hold`의 `limit.acquire`, 좌석 로드 전). 그 뒤 `findByIdAndScheduleId` → `assertHoldable`의 3b 좌석 확인은 그대로다.

## 4. 가설

| # | 가설 | 틀렸다고 판정할 관측 |
|---|------|------------------|
| H1 | 벽은 체크포인트에서 온다(C1) — 체크포인트 없음 조건에서 counter-upsert의 벽이 사라진다 | 체크포인트 없음에서도 counter-upsert가 S4 11단계에서 무너진다 |
| H2 | 벽은 누적 행 수가 아니라 체크포인트 시각을 따라간다 | 고정 4,200/s·2,000/s에서 벽이 회차별 실제 누적 약 37만에 난다(계획 도착량 기준 k6 약 118·214초 — 판정은 실제 누적으로) |
| H3 | shared_buffers 512MB는 벽을 없애지 못한다(C2 아님) | 512MB에서 벽이 사라진다(단 체크포인트 시점도 바뀌므로 대기 이벤트와 함께 판정) |
| H4 | 벽 시각의 대기 이벤트는 WAL·데이터 파일 쓰기 계열이 지배한다 | Lock:extend·BufferContent·BufferMapping이 지배한다(C3·C4·C2) |
| H5 | precheck는 S3-a20 WAL을 none 수준으로 낮추고(counter-upsert의 2.8배 → 1.x배), 억울한 좌석 0·매수 정합 0을 유지한다 | S3 WAL이 counter-upsert와 비슷하다 / S7-m1 억울한 좌석 > 0 / 매수 초과 > 0 |
| H6 | precheck는 팔린 좌석에 LIMIT를 주지 않고(명세 순서), 남는 틈(커밋 전 잠긴 좌석 → LIMIT)은 드물다 | S7-m1-late에서 기회 대비 위반 > 0(counter-upsert는 양성 대조로 위반이 나야 한다) / S2·S7-m1 틈 포함 지표가 매 회차 수십 건 이상 |

## 5. 측정 계획 (명세 §9.2)

| 묶음 | 방식 | 설정 | 부하 | 회차 |
|------|------|------|------|------|
| 진단 | none · counter-upsert · counter-upsert-precheck | 기본(`checkpoint_timeout` 5min·`max_wal_size` 1GB·`shared_buffers` 128MB) · 체크포인트 없음(1h·16GB) · 버퍼 512MB | S4 계단 · 고정 4,200/s 6분 · 고정 2,000/s 6분 | 3 |
| 변형 확인 | 같음 | 기본 | S2 · S7-m1 · S7-m1-late · S3-a20 | 3 |

- 진단 81회 + 변형 확인 36회 = 117회, 약 15시간(추정). L4(앱·DB CPU 4개)만 잰다.
- S7-m1-late(2026-10-09 재합의): S7-m1은 U를 R보다 먼저 보내 '팔린 좌석에 U'가 생기지 않는다(기회 0 — 스모크와 ADR-006 10회 전부). late는 같은 좌석 R의 응답을 받은 뒤 U를 보낸다.
- 모든 셀에서 `pg_stat_activity` 대기 이벤트를 초 단위로 기록한다.
- 고정 셀은 60초 램프 뒤 6분 유지한다. 계획 도착량 기준 누적 37만은 4,200/s에서 k6 약 118초, 2,000/s에서 약 214초다. 판정은 회차별 실제 누적으로 한다.
- 판정 기준(명세 §9.4): ① 벽 원인 ② 지속성 ③ 처리량 ④ 변형 쓰기 비용 ⑤ 변형 정합·롤백 피해 ⑥ 변형 에러 순서 ⑦ 실패 모드.

## 5.1 측정 전 검증

- 테스트 173개 green(4bf8d7d9). precheck는 counter-upsert 계약 묶음에 더해 아래를 확인했다.
  - 팔린 좌석은 쓰기 없이 거절한다. 새 사용자는 쿼터 행이 없고, 기존 행은 xmax 0이다.
  - 매수가 찬 사용자 + 팔린 좌석 → 좌석 불가(명세 순서).
  - 커밋 전 잠긴 좌석에서 매수가 찬 사용자는 LIMIT(남는 틈, 좌석 락 시도 없음)이고, 매수가 남은 사용자는 3b에서 좌석 불가다.
  - 없는 좌석 → 좌석 없음.
- 그린 위장 점검: 선조회를 빼면 테스트 2개가 실패한다.
- 하네스(c402e12b~a8494242) 오프라인 확인:
  - 캠페인 계획 108회(조건 36 × 3, S7-m1-late 추가 전). 회차 상태 판정식을 양방향으로 32/32 확인했다.
  - ADR-006 counter-upsert 결과를 새 스크립트로 다시 내면 SUMMARY·S4-WALL과 같다.
- 서버 스모크 4종(모두 status ok):

  | 스모크 | 결과 |
  |--------|------|
  | (a) counter-upsert·기본·S4 | 벽 356초(11단계 시작 +25초). ADR-006 356~358초와 같다. 벽 전 성공 선점 362,309건, 시간 기준 체크포인트 진행 중 |

- 고정 셀의 벽은 **기동 과도 뒤 벽**(요청 시작 초 기준, p99 ≤ 200ms가 5초 연속된 뒤 첫 p99 > 200ms)으로 판정한다. 명세 문자 그대로의 정의는 0번 구간의 기동 과도(p99 11.8초)에 걸려 1초가 나와 판정에 쓸 수 없다.

  - **표본 끊김의 원인은 받는 쪽 awk(mawk)의 입력 블록 버퍼링**이었다. 회차 끝에 마지막 덩어리가 버려졌다. bash 줄 읽기로 바꾼 뒤 흘려받은 줄과 서버 사본이 1줄 차이로 맞는다.
  - k6는 응답 코드 0(타임아웃·연결 실패)의 지연을 거의 0ms로 기록한다. 그래서 초별 p99에서 빼고, 그 초 완료의 1% 이상이면 무너진 초로 본다.

## 6. 전환 판정 (ADR-006 §6 전환 규칙)

- 벽이 **설정으로 사라지거나 계단 상한 밖으로 밀린다**(운영에서 조정 가능). 고정 도착률에서도 지속 처리량이 none과 같다. 실패 시도의 쓰기 비용이 해소되거나 수용 가능한 수준으로 확인된다 → **counter-upsert로 전환**. 쿼터 행 정리 설계를 함께 넣는다.
- 벽이 **쿼터 테이블 구조**에서 오고 설정으로 안 사라진다 → **advisory-try 유지**. counter-upsert는 구조를 바꾼 뒤 다시 잰다.

**한계**

- **꺾이는 누적량이 다르다.** fio pgwal은 장치 누적 5.2GB(채우기 포함 6.3GB), DB 회차는 호스트 기준 3.26~3.74GB다. 왜 다른지는 확인하지 않았다(쓰기 구성 — 체크포인트 데이터 쓰기·세그먼트 생성 등 — 차이로 추정).
- **pgwal에서는 시간과 누적량이 겹친다.** 속도가 고정이라 +179초와 5.2GB를 가를 수 없다. 옛 append(flush 약 900회/s, 총 약 65MB/s)는 +119초·7.81GB에서 꺾였다 — 초당 flush가 절반 아래인데도 꺾였다는 점은 "초당 약 2,000회" 자체가 조건은 아님을 뜻한다.
- **디스크 이력에 거의 매이지 않는다.** 휴식 뒤 S4(fio-3 끝 72.7초 뒤)·30분 휴식 뒤 fio-3가 같은 자리에서 꺾였고, pgwal은 40.5초 쉰 뒤 정상 기준선에서 다시 같은 자리에서 꺾였다. 예외: 옛 패턴 fio-2(23초 뒤)만 일찍(60초 · 3.79GB) 꺾였다. 아주 짧은 쉼의 효과는 패턴에 따라 다를 수 있다.
- **SSD 내부는 보지 못했다.** "DRAM 없는 SSD(Samsung 980)의 캐시·매핑 동작"은 해석이다. sudo가 없어 `smartctl`·`nvme-cli`도 쓰지 못했다. 볼 수 있는 것은 커널이 보는 요청 시간까지다.
- w_await는 대기열 시간이 섞인 합의 평균이다(분포 아님). 그래서 flush 평균을 함께 본다.
- tmpfs 조건은 저장 층 전체를 뺄 뿐 아니라 DB 메모리 한도도 2g → 8g로 바꾼다(교란 변수 — 명세 §2). 그래서 (c)는 "저장 경로를 빼면"이지 "SSD를 빼면"이 아니다.
- log.md 10-11 04:3x 행의 `docker 반감 디스크 16/16`은 스모크 회차를 포함한 수다(같은 log 11:0x 정정 행). 이 문서는 캠페인의 12/12만 적는다.

- **억울한 좌석 0**(§7.1 H5 · S7-m1). advisory-try는 67(ADR-006 §5.3 ④).
- **WAL이 가장 적다**: S3-a20 precheck 24.6MB(none 86.5 · counter-upsert 243.2MB, §7.1 H5).
- **에러 순서가 명세대로다**: 팔린 좌석에는 LIMIT를 주지 않는다(S7-m1-late 위반 0/100, §7.1 H6).
- 판정기 위반 0, 매수 초과 0, 카운터 불일치 0(§7.1 ⑤ · H5).

받아들이는 한계 — **H6 남는 틈**: 동시 경합에서 매수가 찬 사용자는 '좌석 불가' 대신 `HOLD_LIMIT_EXCEEDED`를 받는다. 다른 트랜잭션이 커밋 전에 쥔 좌석이 잠금 없는 읽기에 AVAILABLE로 보이기 때문이다. S7-m1에서 매 회차 100/100 났다(§7.1 H6). 정합·억울한 좌석에는 영향이 없다.

확인한 사실(이 결정의 적용 범위):

- **지금 코드 기본값은 advisory-try가 아니라 `none`이다**: `src/main/resources/application.yml:36` `limit-strategy: none` · `src/main/kotlin/com/jun/labs/seatreservation/service/SeatHoldProperties.kt:14` `UserLimitStrategyType.NONE`. ADR-005는 advisory-try를 기준으로 정했지만, 코드 적용은 제대로 확인할 때까지 미뤄 두었다(ADR-006·007이 그 확인 과정). 그래서 결정은 advisory-try → precheck, 코드 값은 none → precheck로 바뀐다(정정 2026-10-12 — 처음엔 '반영된 적이 없다'로 적어 누락처럼 읽혔다).
- 그래서 이 결정의 적용은 **새 후속 ADR-008(counter-upsert-precheck 기본 적용·검증)** (2026-10-11 번호 이동 — 홀드 만료는 ADR-010)에서 한다. **아직 하지 않았다.** 범위(`docs/plans/NEXT.md` N1과 같다):
  - 설정·코드 기본값을 `counter-upsert-precheck`로
  - Flyway 백필: **`seat_hold` 행 전체(만료 전·후 구분 없음) + 확정 예약**으로 `user_hold_quota.cnt`를 채운다 (정정 2026-10-12 — 처음 적은 "유효(만료 전 HELD) 홀드"는 틀렸다. 만료 배치가 실제로 지운 홀드만큼 내리므로 판정기 `v_counter_mismatch`와 같은 정의여야 한다, ADR-008 §3)
  - 기존 테스트 전체 + 기본값 테스트
  - 서버 스모크(기본값으로 기동)
  - 부하 하네스 무영향 확인 — counter 계열은 배경 행 시드를 거부한다(`src/main/kotlin/com/jun/labs/seatreservation/loadtest/LoadtestDataService.kt:38`). 방식을 명시하지 않는 기존 하네스(배경 행을 쓰는 ADR-002 등)가 기본값 변경으로 깨질 수 있다
  - 기본값으로 기능 셀 재측정: S2·S3-a20·S7-m1·S7-m1-late × 3, S4 × 1
- **이 서버 디스크에서 잰 처리량은 낮게 나올 수 있다.** 호스트 쓰기가 약 3.5GB(반감 지점 3.26~3.74GB)에 닿는 셀의 처리량 절대값은 이 저장 경로의 flush 반감에 묶여 있다. ADR별로 확인하지는 않았다 — 예: ADR-003은 L4 S4 약 4,300건/s 상한을 유선 측정 경로 탓으로 두었다(원인 미확정, ADR-003 측정 경로 항목). 이후 ADR의 처리량 비교는 이 점을 감안해 읽고, 처리량 자체를 볼 때는 tmpfs나 다른 디스크에서 잰다.
