## 4. 판단 기준별 분석

각 기준마다 **결론 → 근거 데이터 → 데이터의 편향·한계 → 다음 ADR로 넘기는 것** 순서로 적는다.

### 4.1 C1 — 같은 좌석 동시 선점 (Q1, S1)

**결론**: 기준선은 같은 좌석을 **최대 10명**에게 동시에 준다. 10은 CPU와 무관하고 **커넥션 풀 크기(10)와 같다.** check-then-act의 경쟁 구간에 동시에 들어갈 수 있는 트랜잭션 수가 풀 크기로 제한되기 때문으로 해석한다 — 풀의 10개 트랜잭션이 모두 `AVAILABLE`을 읽고 각자 `HELD`와 홀드를 저장한다. 좌석 테이블에는 `HELD` 하나만 보이고 홀드 행이 10개 생긴다.

**근거 데이터**

|--|--|--|--|--|--|--|
| L1(앱·DB CPU 1개) | 1, 10, 10, 10, 10 | 990 [990–999] | 3.8s | 6.7s | 9 [0–9] | 0 |
| L2(앱·DB CPU 2개) | 10, 10, 10, 10, 10 | 990 | 1.5s | 3.1s | 9 | 0 |
| L4(앱·DB CPU 4개) | 10, 10, 10, 10, 5 | 990 [990–995] | 250ms | 597ms [328ms–3.8s] | 9 [4–9] | 0 |

- 출처: `L*/S1/rep*/k6-summary.json`(201·지연), `consistency.json`(`v_excess_hold_rows`), `k6-requests.csv.gz`(요청마다 좌석·사용자 태그).
- **201 − 홀드 행 = 0**: 성공 응답마다 DB 홀드가 정확히 하나 있다 — 응답이 거짓이 아니라 **실제로 10명이 같은 좌석을 소유**했다.

**편향·한계**

- **"10"은 풀 크기에 묶인 값이다.** 풀 10으로 고정해 쟀으므로 "최대 10명"은 이 설정의 산물이다. 풀을 키우면 중복도 커질 것으로 예상하지만 **실측하지 않았다**.
- 표본은 셀당 5회뿐이다. L1(앱·DB CPU 1개) rep1(1건)과 L4(앱·DB CPU 4개) rep5(5건)는 경쟁 구간이 우연히 겹치지 않은 경우로 보이며, 분포의 꼬리를 말하기에는 표본이 적다.
- S1(좌석 1개에 1,000명 동시)은 1,000 VU가 "동시에" 출발하지만, k6 VU 기동과 네트워크 도착은 완전한 동시가 아니다. 경쟁 구간은 서버 처리 속도에 따라 달라진다. L4(앱·DB CPU 4개)에서 p50이 250ms로 짧아졌는데도 중복이 10인 것은, 도착 분산보다 트랜잭션 동시성이 지배한다는 방증이다.
- S1(좌석 1개에 1,000명 동시)은 수 초 만에 끝나 5초 간격 k6 PC 시계열이 비어 있는 회차가 있다(전체 15회 — S1·S2(같은 좌석 1,000명·같은 사용자 10좌석)). 이 셀의 k6 PC 부하는 미측정이다.

**ADR-003로 넘기는 것**

- **판별력 있는 before**: 성공 10(정합 1) · 초과 홀드 행 9. S1(좌석 1개에 1,000명 동시)이 락 방식 비교의 주 시나리오다.
- **비교 축**: 성공 수(=1 여부), 409 응답의 p99(진 사람이 얼마나 빨리 알게 되나 — before: L4(앱·DB CPU 4개) p99 597ms), DB 초과 홀드 행.
- **풀 크기를 고정 변수로 유지**한다(10). 락이 없는 기준선의 중복 수가 풀에 비례한다는 가설은 ADR-003의 대조군(락 없음)에서 풀 크기를 바꿔 확인할 수 있다.
- 주 측정 단계는 **L4**(포화 없음)를 권장. L1·L2(앱·DB CPU 1·2개)는 앱 CPU 포화(§5)가 지연을 지배한다.

**ADR-003로 넘기는 것**

- 좌석 락(ADR-003)은 **이 위반을 고치지 못해야 정상**이다 — 1인 2매는 여러 좌석에 걸친 규칙이라 좌석 애그리거트의 락 범위 밖이다(ADR-000 §2.1). ADR-003 실험에서 S2(사용자 100명 × 각자 좌석 10개 동시)를 **대조군**으로 함께 돌려 "좌석 락과 매수 규칙은 별개"임을 수치로 보인다. 해결은 ADR-005.

| 1인 2매 확인 `countByScheduleIdAndHoldsUserId` | `seat_hold` Seq Scan (20만 행 필터) | 9.5ms / 12.5ms |
| 좌석의 홀드 목록 로드(`seat_id`) | `seat_hold` Seq Scan | 7.0ms / 8.0ms |

- 출처: `L*/S4/rep*/k6-summary.json`(단계별 서브메트릭), `timeline-server.jsonl`(컨테이너 CPU), `timeline-db.jsonl`(누적 홀드), 실행 계획은 이 문서 작성 중 로컬 임시 컨테이너에서 V1 스키마로 재현(저장소·서버 무변경).
- 선점 한 번에 두 쿼리가 모두 `seat_hold`를 전부 훑는다(V1에 `seat_hold(user_id)`·`seat_hold(seat_id)` 인덱스 없음 — ADR-000이 의도적으로 뺐다). 요청당 DB 비용이 누적 홀드 수에 비례하므로 전체 비용은 누적의 제곱으로 커진다.

**편향·한계**

- **누적 편향이 가장 크다.** S4(도착률 계단, 요청마다 새 사용자·좌석)는 요청마다 새 좌석이라 홀드가 줄지 않고 쌓인다(TTL 60m로 만료도 배제). 실제 예매에서 살아 있는 홀드는 좌석 수(1만)를 넘지 않는다. 그래서 S4(도착률 계단, 요청마다 새 사용자·좌석)의 한계값은 **실제 운영보다 비관적**이고, 단계가 뒤로 갈수록 "도착률"과 "누적 행 수"가 함께 커져 둘의 효과가 분리되지 않는다.
- **단계 해상도가 거칠다.** 도착률이 ×1.5 계단(169 → 253 → 380 → 570)이라 한계는 계단 값으로만 나온다(252, 378). 실제 한계는 계단 사이 어딘가다.
- **L4(앱·DB CPU 4개) < L2(앱·DB CPU 2개)는 설명하지 못했다.** L4(앱·DB CPU 4개)는 부하가 낮은 169건/s에서부터 p99가 L2(앱·DB CPU 2개)보다 10배 이상 크다. 실행 계획상 병렬 스캔은 쓰이지 않았고(가설 기각), 운영 컨테이너 간섭도 최대 4.6%로 무시할 수준이다. 측정 시간대(L4(앱·DB CPU 4개)는 새벽)·Docker CPU 제한 방식(CFS 쿼터)·Postgres가 cgroup 제한을 모르는 점 등이 후보지만 **확인하지 않았다**.
- 에러율 기준 한계는 클라이언트 타임아웃(30s)에 좌우된다. p99 기준과 포화점은 타임아웃과 거의 무관하다.
- 한계를 넘은 뒤의 수치(30s 타임아웃, 적체)는 **대기열이 없는 조건의 과부하 동작**이다. 실제 아키텍처는 대기열이 입장 속도를 조절하므로(README), 이 구간은 ADR-020의 before로 넘긴다.

**ADR-003로 넘기는 것**

- **처리량 비교는 이 벽 아래에서만 의미가 있다.** 락 방식별 처리량을 S4(도착률 계단, 요청마다 새 사용자·좌석)로 비교하면 누적 스캔 비용이 모든 방식에 같이 걸려 차이가 묻힌다. ADR-003의 처리량 비교는 누적이 없는 조건(S1·S3(같은 좌석 1,000명·전체 흐름) L4(앱·DB CPU 4개))으로 하거나, 인덱스 문제를 별도 ADR로 먼저 해결한 뒤에 한다.
- **주의 — 선택지가 인덱스를 몰래 추가한다.** ADR-003 후보 중 "유니크 제약"(`seat_hold(seat_id)` 유니크)은 인덱스를 함께 만든다. 그러면 성능이 좋아진 이유가 락이 아니라 인덱스일 수 있다. 비교할 때 인덱스 효과를 분리해야 한다(예: 대조군에 같은 인덱스를 추가한 조건).
- 대기열 입장 속도(ADR-020)는 이 한계보다 낮아야 한다. 판매 속도 기준(1만 석 / 20분 ≈ 8석/s)으로는 지속 처리량은 문제가 아니고, **입장 직후의 순간 경합**이 본질이다(2026-09-28 논의).

### 4.4 C4 — 전체 흐름 정합성과 응답-DB 대조 (Q7, S3 원본)

**결론**: 회차가 끝난 뒤 DB 상태만 보면 S3(입장→선점→확정/이탈 전체 흐름) 원본은 **전 단계에서 판정 위반 0**이다. 그러나 **응답과 DB를 대조하면** L1·L2(앱·DB CPU 1·2개)에서 **유령 확정**이 보인다 — 클라이언트는 확정 실패(타임아웃)를 받았는데 서버는 그 확정을 나중에 처리해 좌석을 `RESERVED`로 만들었다.

**근거 데이터** (S3(입장→선점→확정/이탈 전체 흐름) 원본, 입장 300/s × 20만 명)

| | 확정 200 − DB CONFIRMED (a0 / a20 / a50(이탈 0·20·50%)) | 확정 응답 코드 (a0(이탈 0%) rep1) | 확정 에러율 | 중복 선점(경쟁 중 동시 소유) |
|--|--|--|--|--|
| L1(앱·DB CPU 1개) | −345 / −258 / −232 | 200=6,625 · 0=10,472 · 409=10 | 61~63% | 50 / 48 / 51 |
| L2(앱·DB CPU 2개) | −265 / −208 / −149 | 200=6,672 · 0=10,715 · 409=5 | 62~66% | 24 / 22 / 23 |
| L4(앱·DB CPU 4개) | 0 / 0 / 0 | 200=10,000 · 409=1 | 0% | 0 / 1 / 1 |

- 출처: `L*/S3-a*/rep*/consistency.json`, `k6-summary.json`(confirm 카운터), `k6-requests.csv.gz`(응답 코드), `curves/L*-S3-a*-rehold.csv`(중복 선점).
- 응답 코드 0 = k6가 30초 후 포기. 서버는 Tomcat 무제한 대기열에 쌓인 확정을 뒤늦게 처리했다.
- **중복 선점**은 같은 좌석에 앞 홀드가 살아 있는 동안 또 성공한 선점(서버 만료 시각 기준)이다. 부하가 클수록(L1(앱·DB CPU 1개) 50 > L2(앱·DB CPU 2개) 24 > L4(앱·DB CPU 4개) 0~1) 많다 — 응답이 느릴수록 check-then-act의 경쟁 구간이 길어진다.

**편향·한계**

- **L1·L2(앱·DB CPU 1·2개)의 S3(입장→선점→확정/이탈 전체 흐름) 원본은 과부하 측정이다.** 입장 300/s에 재시도(최대 4요청/입장)가 더해져, 매진 뒤에는 409 요청만 최대 초당 약 1,200건(계산값 — 실측 아님)이 된다. L1·L2(앱·DB CPU 1·2개) 앱 CPU가 포화(§5)였다. 대기열이 입장 속도를 조절하는 실제 아키텍처라면 이 조건은 오지 않는다. **정합성 결론은 L4(앱·DB CPU 4개)를 기준으로 읽는다.**
- 유령 확정의 **크기**(−345 등)는 클라이언트 타임아웃 30s와 과부하 정도에 좌우된다. 현상의 존재는 판별되지만 크기를 실제 운영에 옮기면 안 된다.
- "회차 끝 판정 위반 0"은 **최종 상태**의 정합이다. 중복 선점처럼 도중에 생겼다가 만료·확정으로 사라지는 불일치는 최종 판정에 안 잡힌다 — 그래서 CSV 기반 곡선(재선점·중복 선점)을 따로 둔다.
- 판정 폴링(부하 중 DB 직접 조회)의 소요 시간이 L1(앱·DB CPU 1개) S3(입장→선점→확정/이탈 전체 흐름) 원본에서 최대 3.5~4.5s, L4(앱·DB CPU 4개) S3B(S3 축소판, 시간 1/10·입장 ×10)에서 최대 14s였다 — DB가 바쁠 때 폴링 곡선의 시각 해상도가 떨어진다. 폴링 자체의 부하는 좌석 1만 행 집계 3개로 작다.

**ADR-003로 넘기는 것**

- **S3(입장→선점→확정/이탈 전체 흐름)는 L4(앱·DB CPU 4개)에서 락 방식을 비교해도 차이가 안 보인다** — 기준선도 중복 선점 0~1이다. 판별력은 S1(좌석 1개에 1,000명 동시)에 있다. S3(입장→선점→확정/이탈 전체 흐름)는 ADR-003에서 "락이 정상 흐름을 망가뜨리지 않는가(확정 수·p99 회귀 없음)"의 회귀 검사로 쓴다(before: L4(앱·DB CPU 4개) a0(이탈 0%) 확정 10,000, 선점 p99 35ms).
- 유령 확정은 락과 무관한 과부하·응답 경계 문제다 → ADR-016(확정 원자성)·ADR-017(결제 성공 후 확정 실패 보상)·ADR-020(대기열)의 before.

### 4.5 C5 — 선점 후 이탈과 만료 (Q3, S3 원본·축소)

**결론**: L4(앱·DB CPU 4개) S3(입장→선점→확정/이탈 전체 흐름) 원본에서 이탈한 사람의 좌석은 만료 후 다른 사람에게 다시 팔린다(재선점 a20(이탈 20%) 2,217 / a50(이탈 50%) 6,115). 이탈률이 높을수록 **최종 매진율이 낮아진다**(확정 10,000 → 9,739 → 8,080). 과부하(L1(앱·DB CPU 1개) S3B(S3 축소판, 시간 1/10·입장 ×10))에서는 **만료 배치가 따라가지 못해 만료됐는데 HELD인 좌석**이 남는다.

**근거 데이터**

| | 확정 (a0 / a20 / a50(이탈 0·20·50%)) | 재선점 | 오래된 HELD (회차 끝) |
|--|--|--|--|
| L4(앱·DB CPU 4개) S3(입장→선점→확정/이탈 전체 흐름) 원본 | 10,000 / 9,739 / 8,080 | 0 / 2,217 / 6,115 | 0 / 0 / 0 |
| L1(앱·DB CPU 1개) S3B(S3 축소판, 시간 1/10·입장 ×10) | 1 / 1 / 0 | 1 / 2 / 1 | **2,549 / 2,835 / 2,890** |

- 출처: `curves/L*-S3*-rehold.csv`, `curves/L*-S3*-db.csv`, `consistency.json`(`v_stale_held_seats`, 유예 = 배치 주기 × 2).
- 오래된 HELD는 L1(앱·DB CPU 1개) S3B(입장 3,000/s, 선점 에러 88%)에서만 나왔다 — 앱이 포화돼 1초 주기 배치도 밀렸다.

**편향·한계**

- 이탈 모델이 단순하다: 이탈자는 **선점 직후** 떠나고, 확정자는 반드시 TTL 안에 확정한다. "결제 도중 TTL 만료"(Q6(결제 성공 + 선점 만료))는 이 시나리오에 없다.
- 매진율 하락(a50(이탈 50%) 8,080)은 **입장 종료(약 11분) 이후 새 사용자가 없어서** 만료된 좌석을 다시 사 갈 사람이 없기 때문이기도 하다. 실제 잔여석 구간(README 20~30분 롱테일)의 재방문은 모델링하지 않았다.

**ADR-005로 넘기는 것**: 재선점 곡선과 매진율이 만료 방식(sweep vs lazy) 비교의 before. 오래된 HELD는 sweep 지연의 직접 증거(과부하 한정).

### 4.6 C6 — S3 축소판이 원본의 모양을 유지하는가

**결론**: **유지하지 않는다.** 포화가 없는 L4(앱·DB CPU 4개)에서도 t50·t90(좌석의 50%·90%가 확정되는 시각 ÷ TTL)이 원본과 다르다. **Q3(선점 후 결제 이탈) 결론은 원본 TTL(5분) 측정으로만 낸다.**

**근거 데이터** (L4(앱·DB CPU 4개), 이탈 0%)

| 변형 | TTL당 입장 | 실제 입장 (계획) | k6 미시작 | t50/TTL | t90/TTL | 선점 p99 |
|--|--|--|--|--|--|--|
| 원본 | 90,000 | 194,094 (200,000) | 6,006 | **0.58** | **0.88** | 35ms |
| A (시간 1/10) | 9,000 | 19,336 (20,000) | 764 | 1.27 | 2.73 | 8.5ms |
| B (시간 1/10 + 입장 ×10) | 90,000 | **87,251** (200,000) | 113,751 | 1.27 | 1.97 | **8.6s** |

- 출처: `curves/L4-S3*-a0-db.csv`(시간축 = (시각 − k6 시작) / TTL), `k6-summary.json`(iterations·dropped).
- **A가 다른 이유**: TTL 동안 들어오는 경쟁자가 1/10(2:1 경쟁)이라 좌석이 늦게 찬다 — 설계상 예상된 차이(다른 조건의 측정).
- **B가 다른 이유**: 비율은 원본과 같게 설계했지만, 입장 3,000/s가 L4(앱·DB CPU 4개)에서도 서버를 포화시켜(선점 p99 8.6s) k6 VU가 대기에 묶였고, **계획한 20만 명 중 8.7만 명만 실제로 들어왔다.** 비율이 같다는 전제 자체가 깨졌다.

**편향·한계**

- 비교는 L4(앱·DB CPU 4개)만 유효하다(L1·L2(앱·DB CPU 1·2개)는 원본도 과부하).
- B의 실패는 "축소 원리가 틀렸다"가 아니라 "압축된 부하(10배 도착률)를 서버·k6가 감당하지 못했다"는 뜻이다. 용량이 압축 부하의 10배 이상인 조건이라면 B가 원본을 재현할 가능성은 남아 있다 — **확인하지 않았다**.
- t50·t90은 5초 간격 DB 폴링에서 산출한다. 축소판은 TTL이 30s라 5초 = 0.17 TTL로 해상도가 거칠다.

**다음 ADR로 넘기는 것**: ADR-003 이후의 S3(입장→선점→확정/이탈 전체 흐름) 회귀 검사는 **원본 TTL**로 하거나, 축소판을 쓰려면 "축소판끼리의 before/after 비교"로만 쓴다(원본과의 교차 비교 금지). S3B(S3 축소판, 시간 1/10·입장 ×10)는 쓰지 않는다.

## 6. 이 측정 중 정정한 판단

- "1 CPU S4(도착률 계단, 요청마다 새 사용자·좌석) 붕괴 때 CPU가 포화되지 않았다"(스모크 판단) → **틀림.** 스모크의 10초 평균 샘플을 잘못 읽었다. 전 회차 최대값으로 보면 L1(앱·DB CPU 1개) 앱 100%·S4(도착률 계단, 요청마다 새 사용자·좌석) DB 108%로 포화였다.
- "30초 = 쿼리 30초 이상 또는 커넥션 풀 대기" → **둘 다 아님.** 500 응답·Hikari 대기 예외가 0건. Tomcat 대기열 적체였다.
- "L4(앱·DB CPU 4개)에서 병렬 스캔 때문에 느려졌다" → **근거 없음.** 실행 계획에 병렬 노드가 없다. L4(앱·DB CPU 4개) < L2(앱·DB CPU 2개)는 미해명으로 남긴다.

## 7. 판정기(oracle) 자체의 검증

- 위반 유형 8종을 테스트에서 **일부러 하나씩 만들고**, 결과 맵 전체를 비교해 해당 항목만 0이 아님을 확인(거짓 양성까지 검출) — `LoadtestEndpointsTest`.
- 측정에서 실제로 위반을 잡았다: S1(좌석 1개에 1,000명 동시) 초과 홀드 행 9, S2(사용자 100명 × 각자 좌석 10개 동시) 초과 사용자 11~19, L1(앱·DB CPU 1개) S3B(S3 축소판, 시간 1/10·입장 ×10) 오래된 HELD 2,500~2,900, L1 S3A(S3 축소판, 시간 1/10) 중복 홀드 좌석 최대 3.
- 판정기가 **못 보는 것**: 도중에 생겼다 사라지는 불일치(→ CSV 곡선으로 보완), 응답과 DB의 어긋남(→ 요약기의 대조 열로 보완).

## 9. 미해명 · 후속

- L4(앱·DB CPU 4개) S4(도착률 계단, 요청마다 새 사용자·좌석)의 한계·저부하 지연이 L2(앱·DB CPU 2개)보다 나쁜 이유 (§4.3). → **2026-09-29 재현 안 됨**: ADR-002의 같은 조건 재측정(인덱스 없음·풀 10, 2회)에서 4 CPU는 570건/s까지 p99 10ms(엄격 한계 567)로, 이 문서의 4 CPU 값(252~378)보다 크게 좋았다. 이 문서의 4 CPU 결과는 측정 당시 환경의 이상값이었을 가능성이 크다 — ADR-002 §6.6. 이후 비교는 ADR-002의 재측정 기준선을 쓴다.
- 풀 크기와 S1(좌석 1개에 1,000명 동시) 중복 수의 비례 여부 (§4.1) — ADR-003 대조군에서 확인 가능.
- 축소판 B가 용량이 충분한 조건에서 원본을 재현하는지 (§4.6).
