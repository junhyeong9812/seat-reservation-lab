## 0. 요구사항 원문 (인터뷰 기록)

- 원문(2026-10-15): "위 설명은 별도 문서로 간단하게 작성해주고, 정리하면 현재 애플리케이션 램할당이 적어서 시리얼라이즈 jvm으로 설정되어서 처리량의 문제가 생겼고 G1을 할당하는 최소 자원으로 재구동 후 간단하게 1회씩만 테스트 해보면 이를 확정지을 수 있다는거면 ADR10으로 위 설명을 위에 적고 그렇게 간단하게 실험 한번만 돌려보자. 이건 1회면 충분할 꺼 같고, G1 JVM 최소 할당 자원의 기준을 잡아서 해당 기준으로 서버를 띄우는 기준으로 만들면 좋겠네. 이 기준을 잡는 ADR 10 진행하자"
- 메인 정정(사용자에게 보고): 처리량은 줄지 않았다(tmpfs 4,200건/s = 도착률). 문제는 **꼬리 지연** — 약 47초마다 Full GC 72~108ms 정지로 그 초의 최대 응답 150~300ms.
- Q/A(2026-10-15):
  - 번호 → **새 ADR-010**, 기존 ADR-010~016은 011~017로 한 칸씩 민다.
  - 조건 → **4조건 사다리** 각 1회: ① 1g 기본(Serial) ② 1g + `-XX:+UseG1GC` ③ 1792m 기본(JVM 자동 G1 경계 기대) ④ 2g 기본.
  - 기준 정의 → **G1 명시 + 꼬리 지연 기준**: 자동 선택에 기대지 않고 `-XX:+UseG1GC`를 명시, 그 위에서 정상 구간 Full GC 0 · 가장 나쁜 1초 p99가 평소 수준인 최소 메모리.

## 1. 목표·대상 (필수)

seat-reservation-lab에서 ① GC 설명을 머리에 둔 `docs/adr/ADR-010-jvm-gc-baseline.md`를 쓰고(기존 010~016 → 011~017), ② ADR-009 하네스에 앱 메모리·JVM 옵션 손잡이를 더해 S4c4200 tmpfs(고정 도착률 4,200건/s, DB 메모리) × 4조건 × 1회를 서버(.164)에서 재고, ③ 결과로 "앱 JVM 기준(수집기·메모리)"을 정해 ADR-010 결정과 Dockerfile 기본 실행 옵션에 반영하면 끝.

## 2. 경계·불변식 (필수)

- **손잡이 기본값은 기존 동작과 같다**: 새 손잡이를 주지 않으면 compose 렌더 결과(JAVA_TOOL_OPTIONS·mem_limit)가 지금과 바이트 단위로 같다 — ADR-009 재실행 재현성.
- 회차는 앱 기본값 조건(`--cond default` — A+C·정리 ①·판매 마감 켬, ADR-009 결정)으로 잰다.
- 실험 조건마다 실제 수집기·힙 최대치를 결과에 기록하고(`gc.json` collector, `-Xlog:gc,init`), 기대와 다르면(예: ③이 G1이 아님) 그대로 결과로 적는다 — 덮어쓰거나 재해석하지 않는다.
- 1회 측정임을 문서에 명시(반복 없음 — 사용자 결정). 판정은 Full GC 수·GC 정지 최대·가장 나쁜 1초 p99처럼 회차 하나로 뚜렷이 갈리는 지표 위주.
- ADR-001~009 compose·결과는 바꾸지 않는다(번호 변경에 따른 문서 참조 갱신은 예외).

## 10. 재합의 (2026-10-15, 측정 뒤)

- **적용 위치**: '앱 기본 실행 설정(Dockerfile)에도 반영'을 철회 — Dockerfile을 바꾸면 ADR-001~009 하네스도 같은 이미지로 떠 지난 결과의 재현(수집기)이 깨져 §2 불변식과 충돌한다. 사용자 선택 "하네스 기본값으로": Dockerfile 무변경, ADR-011부터 새 하네스 앱 기본값 = 1g + `-XX:+UseG1GC`, ADR-010 문서에 측정용 앱 기준으로 기록. → task 05의 Dockerfile 항목 삭제(코드 변경 없음).
- **GC 아닌 약 26.5초 주기 튐**: 사용자 선택 "후속 후보로 넘김" — ADR-010은 GC 기준에서 닫고 NEXT에 원인 조사 후보로.

## 11. 확장 재합의 — 2차 측정: G1·ZGC × 메모리 (2026-10-15)

- 원문: "저 zgc도 확인해보고 자원도 늘려보면서 기준점을 잡아볼까" · "이걸 10으로 확장해서 이부분을 10으로 정해서 우리에게 맞는 gc 및 동작가능성도 있지만 안정성도 확인하는게 중요할 꺼 같아"
- Q/A: 조건 = **G1·ZGC(세대형 `-XX:+UseZGC -XX:+ZGenerational`) × 1g·2g·4g** · 반복 **3회**(18회, 약 3.3시간) · 기준 원칙 = **꼬리 충족 후 최소 자원** · 문서 = **ADR-010 확장**(2차 측정 절 — 가설·계획 측정 전 고정, 결과로 §8 갱신 · PR #9에 이어서).
- **목표**: 측정용 앱 수집기·메모리 기준을 '동작함'이 아니라 '안정적으로 동작함'으로 정한다.
- **판정(안정성 포함 — 메인 제안, 측정 전 고정)**: 조건이 기준 후보가 되려면 3회 모두
  1. 정상 구간 Full GC 0 · 앱 스레드의 할당 멈춤(Allocation Stall)·재배치 멈춤 0(GC 작업자 스레드 재배치 멈춤은 기록만 — 하네스 리뷰로 측정 전 정정)
  2. GC 정지 최대 < 10ms(정상 구간)
  3. 에러율 0 · 코드 0 비율 0 · 성공 RPS = 도착률(차 < 0.5%)
  4. 회차 안 메모리 추세: 앱 메모리(docker stats) 램프 뒤 첫 1분(k6 60~120초) 대비 마지막 1분 증가 < 10%(누수·힙 계속 커짐 없음 — 램프 중 힙 성장은 빼려고 창을 램프 뒤로 둠, 1차 결과 5.3~7.8%)
  - 통과 조건들 중 p99·1초 p99 최대(3회 중앙값)가 가장 좋은 것과 **범위가 겹치는**(흔들림 안) 조건 가운데 메모리 → 앱 CPU 순으로 가장 적은 것을 기준으로 한다. 3회 범위(최대 − 최소)도 함께 보고 흔들림이 큰 조건은 낮춘다.
- **불변식 추가**: 새 손잡이(`--app-gc zgc`)도 지정하지 않으면 렌더·계획이 이전과 같다 · ZGC 회차는 수집기 = Z, 세대형 표시(Minor Collection) 확인 — 아니면 `gc-collector-mismatch`.
- **한계(측정 전)**: 셀 길이 7분(램프 1분 + 6분) — 30분 이상 장시간(soak)은 현재 시드(200만 석)로 불가(4,200건/s × 30분 ≈ 756만 건) → 후속. 남은 GC 아닌 주기 튐(51~149ms)이 모든 조건 꼬리에 섞인다.
- **task**: 06 하네스(`--app-gc zgc` · ZGC 로그 파서 — Z 정지·할당 멈춤·세대형 · 메모리 추세 · `--set jvm-ladder` · compare 다회차) → 리뷰 → 스모크(4g ZGC 1회) · 07 측정 18회 · 08 결과·§8 갱신·리뷰.
