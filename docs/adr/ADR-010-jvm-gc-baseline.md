# ADR-010: 앱 JVM GC·메모리 기준 — 측정용 앱을 무엇으로 띄우나

- 상태: **결정**(2026-10-16) — 측정용 앱 기준 = **메모리 2g + 세대형 ZGC**(`-XX:+UseZGC -XX:+ZGenerational`, ADR-011부터 하네스 기본값 `--app-mem 2g --app-gc zgc`). 1차(1g + G1, §8)는 2차(§9·§10 — G1·ZGC × 1g·2g·4g × 3회, 안정성 판정)로 대체했다. §9는 2차 측정 전에 고정했다(ef2c3b87 · 판정 ① 정정 93f35059 = 캠페인 하네스 SHA). §1~§5는 측정 전에 고정했다(9e18c807 · 꼬리 지표 정정 17afdecc). §6~§8은 측정 뒤에 썼다.
- 명세: `docs/plans/2026-10-15/adr-010-jvm-gc-baseline/requirement-spec.md` · 기록: 같은 폴더 `log.md`
- 선행: **ADR-009 §7.7**(비용 재측정에서 짧은 앱 멈춤 = Serial Full GC와 시각 일치)
- 후행: ADR-011(운영 중 매수 방식 전환) 이후의 모든 측정 — 이 ADR이 정한 기준으로 앱을 띄운다.

## 1. 왜 응답이 잠깐씩 멈추나 — 쉬운 설명

**GC는 앱을 세우고 쓰레기를 치운다.** 요청 하나를 처리할 때마다 JVM 안에 객체(요청 내용, SQL 결과, JSON 문자열 등)가 많이 생기고, 대부분 요청이 끝나면 필요 없어진다. 이 쓰레기를 치우는 일이 GC(가비지 컬렉션)다. 지금 앱이 쓰는 **Serial 수집기는 치우는 동안 앱의 모든 스레드를 멈추고, 스레드 하나로 혼자 치운다**(stop-the-world).

**힙은 두 칸이다.**

| 칸 | 들어가는 것 | 치우는 GC | 정지 (ADR-009 재측정 실측) |
|---|---|---|---|
| Young(새 객체) | 막 생긴 객체 | Young GC — 1초에 약 5번 | 1회 2~3ms(거의 티 안 남) |
| Old(오래 산 객체) | Young GC를 몇 번 버틴 객체(커넥션 풀·캐시·처리 중 요청 등) | old가 가득 차면 **Full GC**(표시 → 주소 계산 → 포인터 조정 → 이동·압축) | **1회 72~108ms, 약 47초마다** |

**100ms 정지가 응답 지연이 되는 과정.** 부하는 1초에 4,200건씩 일정하게 들어온다. 앱이 100ms 멈추면 약 420건이 쌓이고, 풀리는 순간 몰려 처리되며 뒤 요청까지 줄을 선다. 그래서 평소 p99 4ms인데 그 1초의 최대 응답이 150~300ms로 튄다(ADR-009 §7.7 — tmpfs 4조건 모두 같은 패턴). **처리량은 줄지 않았다**(4,200건/s 그대로) — 문제는 꼬리 지연이다.

**왜 이렇게 자주 Full GC가 나나 — 이번 설정의 문제.**

1. **수집기가 Serial로 골라졌다.** JVM은 CPU 2개 이상·메모리 약 1792MB 이상이면 '서버급 기계'로 보고 G1을 기본으로 쓴다. 앱 컨테이너 메모리 한도가 1 GiB라 그 아래여서 Serial이 골라졌다(CPU는 4개).
2. **힙이 작게 유지된다.** 최대 힙은 768MB(`MaxRAMPercentage=75`)까지 허락돼 있지만 실제로 잡은 힙은 약 190~200MB에 머물렀다. Serial은 Full GC 뒤 살아남은 양(약 80MB)에 맞춰 힙을 작게 유지하므로 old 칸에 여유가 거의 없고, 금방 다시 차서 Full GC가 반복된다.
3. 비유하면 — 방은 큰데 작은 쓰레기통만 두고, 꽉 찰 때마다 모두를 세워 대청소를 하는 상태다.

**G1은 무엇이 다른가(일반 지식 — 이 ADR이 실측으로 확인).** G1은 힙을 작은 구역(region)으로 나눠 여러 스레드로 치우고, old 영역 표시를 앱과 함께 돌린다(concurrent marking). 그래서 정상 상태에서는 Full GC 없이 짧은 Young·Mixed 정지만 나는 것이 기대 동작이다. 다만 메모리가 너무 작으면 G1도 Full GC로 떨어질 수 있다 — 그래서 '최소 메모리'를 재야 한다.

**왜 지금 정하나.** 이 꼬리 지연은 ADR-001~009 모든 측정의 p99 꼬리에 들어 있었을 것이다(같은 앱 설정 — ADR-009 §8.1, 추정). 조건끼리 비교하는 판정은 같은 조건에서 쟀으므로 유지되지만, 앞으로의 측정(꼬리 지연을 다루는 ADR-012 홀드 만료·ADR-017 오픈 폭주 등)에서는 GC 꼬리가 조건 차이를 가릴 수 있다. 측정용 앱의 실행 기준을 먼저 고정한다.

## 2. 선택지

| 후보 | 설정 | 장점 | 우려 |
|---|---|---|---|
| ① 지금 그대로 | 메모리 1g, 수집기 미지정(→ Serial) | 바꿀 것 없음 | 약 47초마다 72~108ms 정지 |
| ② G1 명시 | 메모리 1g, `-XX:+UseG1GC` | 자원 그대로 | 1g에서 G1이 Full GC 없이 버티는지 모름 |
| ③ 자동 G1 경계 | 메모리 1792m, 수집기 미지정 | 옵션 없이 G1 | JVM 버전마다 경계가 바뀔 수 있음 — 자동 선택에 기댄다 |
| ④ 넉넉한 메모리 | 메모리 2g, 수집기 미지정 | 여유 | 자원이 두 배 |

**기준 정의(사용자 결정 2026-10-15)**: 자동 선택에 기대지 않는다 — 기준은 **`-XX:+UseG1GC`를 명시**하고, 그 위에서 아래 §4 판정을 통과하는 **가장 작은 메모리**로 정한다. ③·④는 '메모리를 늘리면 자동으로 G1이 되는가, 그리고 그때 꼬리가 사라지는가'를 확인하는 비교 조건이다.

## 3. 가설 (측정 전 고정)

| # | 가설 | 틀렸다고 판정할 관측 |
|---|------|------------------|
| J1 | ①(1g 미지정)은 Serial이고 정상 구간(k6 60초 이후)에 Full GC가 반복된다 — ADR-009 재측정의 재현 | ① collector ≠ Serial 또는 정상 구간 Full GC 0 |
| J2 | ②(1g + G1 명시)는 정상 구간 Full GC 0이고, GC 정지 최대가 ①보다 작으며(< 50ms), 1초 p99 최대가 ①보다 낮다 | ② 정상 구간 Full GC > 0 / 정지 최대 ≥ 50ms / 1초 p99 최대 ≥ ① |
| J3 | ③(1792m 미지정)에서 JVM이 G1을 자동으로 고른다 | ③ collector ≠ G1 |
| J4 | ④(2g 미지정)는 G1이고 ②와 꼬리 지연이 같은 수준이다 — 1g에서 G1이면 메모리를 늘릴 이득이 꼬리에는 없다 | ④ 1초 p99 최대가 ②보다 25% 넘게 낮다 / ④ collector ≠ G1 |
| J5 | 수집기를 바꿔도 처리량(성공 RPS)·평균적 지연(p50)은 같다 — 차이는 꼬리뿐이다 | 성공 RPS 차 ≥ 1% / p50 차 ≥ 10%(①과 비교) |

## 4. 측정 계획 · 판정 기준

- 셀: **S4c4200 tmpfs**(고정 도착률 4,200건/s, DB 저장소를 메모리에 — 디스크 벽 제거, ADR-007). 앱 조건 `default`(ADR-009 결정 — A(만료 배치 쌍 단위 견딤)+C(앱 안 대조)·정리 ①·판매 마감 켬). L4(앱·DB CPU 4개).
- 조건 4개 × **1회**(사용자 결정 — Full GC 수·정지 최대처럼 회차 하나로 뚜렷이 갈리는 지표로 판정). 같은 하네스 SHA로 ①도 다시 잰다.
- 하네스: ADR-009 하네스(`k6/ADR-009`)에 앱 메모리·JVM 옵션 손잡이를 더해 쓴다(손잡이를 안 주면 ADR-009와 같은 렌더). 결과는 `k6/ADR-009/results/<id>`.
- 기록·지표: 수집기(`gc.json` collector) · 최대 힙 · 실제 잡은 힙 · 정상 구간(k6 60초 뒤) Full GC 수 · GC 정지 수·합·최대(safepoint 기준) · 선점 p99·p50 · **1초 p99 최대**·최대 응답 > 50ms인 초 수·최대 응답(램프 밖, 1초 = k6 행 타임스탬프) · 가장 나쁜 30초 구간 p99(참고) · 램프 p99 · 성공 RPS · 앱 CPU·메모리 사용.
- **꼬리 지표를 1초로 둔 이유**(측정 전 정정 2026-10-15): 하네스의 '가장 나쁜 구간 p99'는 30초 구간이라 0.1초짜리 Full GC 멈춤이 묻힌다 — ADR-009 재측정 control tmpfs 1회차에서 30초 구간 최대 4.2ms인데 1초 p99 최대 283ms, 최대 응답 > 50ms인 초 8개(= 정상 구간 Full GC 8회).
- **기준 판정**: G1 명시 조건 중 '정상 구간 Full GC 0 · GC 정지 최대 < 50ms · 1초 p99 최대가 ①보다 낮음'을 통과하는 가장 작은 메모리. 1g(②)가 통과하면 기준 = **1g + G1 명시**. 통과하지 못하면 G1 명시 + 1.5g·2g를 추가로 재서 정한다(그때 사용자에게 먼저 묻는다).

## 5. 받아들이는 한계 (측정 전에 알려진 것)

1. **1회 측정이다** — 회차 사이 흔들림은 재지 않는다. 판정은 크게 갈리는 지표만 쓰고, 경계에 걸리면 반복을 다시 정한다.
2. **tmpfs 한 셀이다** — 디스크 벽 부하·다른 시나리오(S2·S3)의 할당 패턴은 재지 않는다.
3. **기준은 측정용 앱의 기준이다** — 운영 배포의 힙 크기·수집기 튜닝(일시정지 목표 `MaxGCPauseMillis` 등)은 범위 밖이다.
4. 자동 G1 경계(약 1792MB)는 JDK 21(eclipse-temurin:21-jre) 동작이다 — 다른 JDK에서는 다를 수 있다(그래서 기준은 명시 옵션으로 둔다).

## 7. 가설 판정

| 가설 | 판정 | 근거 |
|---|---|---|
| J1 ①은 Serial이고 정상 구간 Full GC가 반복된다 | **성립** | Serial, Full GC 8회(ADR-009 재측정과 같은 수) |
| J2 ②는 Full GC 0 · 정지 최대 < 50ms · 1초 p99 최대 < ① | **성립** | Full GC 0, 정지 최대 3.4ms, 1초 p99 최대 97 < 301ms. **반증 쪽 관측**: ②의 p99는 ①보다 +12%(5.13 대 4.58ms), 가장 나쁜 30초 구간 p99는 26.1 대 15.7ms로 나쁘고, 느린 초 수는 줄지 않았다(13 대 12) |

### 1차 결정 (2026-10-15 — 대체됨, 기록으로 남김)

**측정용 앱 기준 = 메모리 1g + `-XX:+UseG1GC` 명시**(`MaxRAMPercentage=75`는 그대로). 측정 전 판정 규칙(§4 — '1g + G1(②)가 Full GC 0 · 정지 최대 < 50ms · 1초 p99 최대 < ①을 통과하면 기준 = 1g + G1')에 따른 결정이다.

- **무엇을 얻고 무엇은 아직 모르나**: Serial Full GC(약 47초마다 0.1초 정지 · 1초 p99 최대 300ms)가 없어진다 — 이것이 기준을 바꾼 이유다. 반면 전체 p99·30초 구간 p99는 ②가 ①·③·④보다 나빴고, 메모리를 늘린 ③·④가 가장 좋았다(J4). 1회라 확정하지 못한다 — 메모리를 늘리는 것이 p99에 이득인지는 반복 측정으로 다시 본다(§8.1).
- **적용 위치(사용자 재합의 2026-10-15)**: Dockerfile은 바꾸지 않는다. 바꾸면 ADR-001~009 하네스도 같은 이미지로 떠서 다시 돌릴 때 지난 결과와 수집기가 달라진다. 대신 **ADR-011부터 새 하네스의 앱 기본값을 '1g + `-XX:+UseG1GC`'로** 잡는다(새 하네스 compose `JAVA_TOOL_OPTIONS`, 또는 ADR-009 하네스를 이어 쓰면 `--app-gc g1`). ADR-001~009 하네스 기본값(1g · 자동 = Serial)은 그대로다.
- **왜 G1인가 — ZGC·Parallel이 아닌 이유**(측정 뒤 정리 2026-10-15 — 수집기 종류는 부록 A):
  - **실측 근거**: G1로 Full GC가 0이 됐고 정상 구간 GC 정지가 최대 2.6~4.8ms다. 남은 꼬리(51~149ms 튐)는 GC 정지로 설명되지 않는다(§6). 그래서 정지를 1ms 미만으로 줄이는 ZGC·Shenandoah로 바꿔도 **지금 꼬리에서 줄어들 몫은 G1의 몇 ms뿐**이라고 본다 — **추론이다, ZGC는 재지 않았다**.
  - **요청 하나가 만드는 객체의 성질**: 선점 요청 하나는 짧게 사는 객체(요청·SQL 결과·JSON 등)를 많이 만들고, 오래 사는 것은 적다(실측 — Young GC 초당 약 5~10회, Full GC 뒤 살아남는 양 약 80MB). 이런 '대부분 금방 죽는' 할당은 세대 구분 수집기(Serial·Parallel·G1·세대형 ZGC 모두)가 잘 다룬다 — **이 성질 자체는 G1만의 근거가 아니다**. G1을 고른 근거는 '세대 구분 + Old 영역을 앱과 동시에 표시해 Full GC를 피함 + 작은 힙에서 오버헤드가 적당함'이다.
  - **Parallel이 아닌 이유**: 처리량은 가장 좋지만 Old가 차면 앱 전체를 세우는 Full GC가 그대로 남는다 — 이 ADR이 없애려던 것이 바로 그 정지다(재지 않음 — 수집기 설계에서 끌어낸 판단).
  - **ZGC를 다시 볼 때**: 남은 GC 아닌 튐을 없앤 뒤에도 G1의 몇 ms 정지가 꼬리를 좌우할 때(예: 오픈 폭주 ADR-017), 또는 힙이 수 GB 이상으로 커질 때. 그때는 CPU·메모리 여유(ZGC는 동시 작업과 할당 속도 대비 여유 힙이 더 필요하다)와 함께 잰다.
- **기준과 함께 지키는 것**: 회차마다 수집기·메모리 한도·`JAVA_TOOL_OPTIONS`를 기록·대조한다(`gc.json` collector · `app-jvm.json` — `gc-collector-mismatch`·`app-jvm-mismatch`). 꼬리 지연은 1초 단위로 본다(30초 구간 p99는 0.1초 멈춤을 가린다 — §4).
- **대가**: 앱 CPU +19~25%(L4 — 앱 CPU 4개 중 약 1.75개 사용). 앱 CPU가 병목인 셀에서는 처리량에 영향이 있을 수 있다 — 그때 다시 본다.
- **운영 배포 기준은 아니다**(§5 ③) — 운영 힙·일시정지 목표는 범위 밖.

## 9. 2차 측정 — G1·ZGC × 1g·2g·4g × 3회 (명세 §11 — 측정 전 고정 2026-10-15)

1차 결정(1g + G1)은 '동작함'을 확인했다. 2차는 ZGC와 메모리를 늘린 조건까지 넓혀 **안정적으로 동작하는 최소 자원**을 정한다(사용자 2026-10-15: "동작가능성도 있지만 안정성도 확인하는게 중요"). 결과로 §8을 갱신한다.

**조건**: 앱 기본값 조건(default) · S4c4200 tmpfs · L4 · {G1(`-XX:+UseG1GC`), ZGC 세대형(`-XX:+UseZGC -XX:+ZGenerational`)} × {1g, 2g, 4g} × **3회** = 18회(회차 우선, 조건 순서를 회차마다 2칸 회전). 하네스 `--set jvm-ladder`.

**안정성 판정** — 기준 후보가 되려면 **3회 모두**:

1. 정상 구간 Full GC 0 · **앱 스레드의** 할당·재배치 멈춤(ZGC가 할당을 못 따라가 앱 스레드가 기다림) 0 — GC 작업자 스레드의 재배치 멈춤(`ZWorker…`)은 앱이 기다린 것이 아니라 기록만 한다(측정 전 정정 — 하네스 리뷰). ZGC에는 Full GC가 없으므로 ZGC 회차는 사실상 멈춤 수로 판정된다
2. GC 정지 최대 < 10ms(정상 구간)
3. 에러율 0 · 코드 0 비율 0 · 성공 RPS ÷ 4,200 > 0.995
4. 앱 메모리(docker stats) 램프 뒤 첫 1분 → 마지막 1분 증가 < 10%(1차 4회 5.3~7.8%)

**기준 고르기**: 통과 조건 중 p99·1초 p99 최대(3회 중앙값)가 가장 좋은 조건과 **3회 범위가 겹치는** 조건들 가운데, 메모리 → 앱 CPU 순으로 가장 적은 것. 3회 범위가 다른 조건보다 눈에 띄게 넓으면(흔들림) 순위를 낮춘다.

**ZGC가 실제로 잡은 힙**(GC 로그 `gc,heap` Capacity — 하네스 요약에는 없어 원시 로그에서 직접 셈): 1g 678~700MB(최대 768 · 소프트 최대 691) · 2g 1,314~1,316MB · 4g 2,632MB. ZGC는 힙을 소프트 최대(최대의 90%) 근처까지 잡는다 — 1g는 힙 약 690MB에 나머지 약 330MB(컨테이너 사용량 − 힙 — 힙 밖 메모리·공유 메모리·페이지 캐시가 섞인 값이라 힙 밖 사용량으로 확정할 수는 없다)가 더해져 한도에 닿았고, 수집 원인도 대부분 '힙 사용률 높음'(Minor (High Usage) — 1g 약 500회 · 2g 약 195회 · 4g 약 87회)이었다.

- G1의 ④ 실패는 경계 근처다(1g 10.1%). 늘어난 몫(약 48MiB)이 힙 안인지 밖인지는 나눠 재지 않아 원인 미상이다 — 하네스 요약에는 잡은 힙의 최대(152~174MB)만 있고 시간 추이가 없다. **측정 전 예상과 반대로 `/dev/shm` GC 로그는 G1이 더 컸다**(§9 한계의 'ZGC에 불리'는 틀린 예상 — G1 4.0~5.7MB 대 ZGC 0.9~2.5MB). 1g G1 rep3의 10.1%는 로그 증가분(약 0.5~1%p, 추정) 안의 경계값일 수 있다. 판정은 측정 전 기준대로 ✕로 둔다.
- **④는 수집기 사이에 비대칭이다**: ZGC는 힙을 처음부터 거의 다 잡아 추세가 구조적으로 작게(−1.3~4.0%) 나오고, G1은 작은 힙이 자라는 몫이 그대로 잡힌다 — ④는 ZGC의 힙 안 변화를 거의 보지 못하고 G1에 엄격하다.
- **1g ZGC는 판정은 통과했지만 앱 메모리가 3회 모두 컨테이너 한도(1,024.0MiB)에 닿았다**(OOM 종료는 없었다). 잡은 힙 678~700MB + 나머지 약 330MB다(위 — 나머지의 구성은 나눠 재지 않음). 한도에 닿은 상태는 커널이 캐시를 회수하며 버티는 것일 수 있고, 회수할 수 없는 몫이 얼마인지는 재지 않았다. 정상 구간 정지도 7.8ms로 다른 ZGC(0.2ms)보다 길다(원시 gc.log의 `ZMarkStartYoung` safepoint 7.7ms — 메모리 여유 부족 때문인지는 추정). 부하가 조금만 달라져도 OOM 종료·할당 멈춤으로 넘어갈 위험이 크다(크기는 미측정) — **안정성 여유 없음**.
- **4g ZGC의 꼬리가 2g보다 나빴다**(1초 p99 최대 107.0 [71.1–292.3]ms · rep3 느린 초 20 · p99 5.75ms). 힙은 램프 중(k6 52초 안)에 2.6GB까지 다 커져 정상 구간의 힙 확장 탓은 아니다. 약 8초마다 끝나는 Major 수집과의 일치는 뚜렷하지 않다(rep3 20개 중 약 9개가 ±1초 — 우연 기대 약 36%). 2g ZGC에는 약 25~26초 주기 튐만 있고, 4g에는 그 위에 주기 없는 튐이 더 있다. 앱 메모리가 회차 중에도 늘어(평균 3,004 → 최대 3,201MiB) 잡아 둔 큰 힙의 첫 접근 페이지 폴트가 흩어져 생겼을 가능성이 있다 — **원인 미상(추정 후보)**, `-XX:+AlwaysPreTouch` 비교로 가릴 수 있다(§8.1).

**기준 고르기(§9 규칙)**: 통과 = {2g G1, 1g ZGC, 2g ZGC, 4g ZGC}. 규칙의 '메모리'는 **컨테이너 한도로 해석했다**(측정 전에는 정하지 않았다 — 사용자 확인 2026-10-16).

- 1초 p99 최대가 가장 좋은 것 = **2g ZGC 47.5 [44.6–55.1]** — 범위가 겹치는 것: 2g G1 [37.5–123.1]. (1g ZGC [61.1–75.5]·4g ZGC [71.1–292.3]는 겹치지 않음)
- p99가 가장 좋은 것 = 1g ZGC 3.58 [3.45–4.08] — 겹치는 것: 2g ZGC·2g G1·4g ZGC.
- 두 지표 모두 최고와 겹치는 조건 = {2g ZGC, 2g G1} → 메모리 한도 같음(2g) → 앱 CPU 143% 대 168% → **2g ZGC**. 2g G1은 1초 p99 최대 범위가 넓다(폭 85.6 대 10.5ms — 흔들림)는 점에서도 뒤진다.
- **실사용 메모리로 해석했다면**: 2g G1 535MiB 대 2g ZGC 1,744MiB라 메모리 단계에서 **2g G1**이 뽑힌다. 다만 흔들림 조항(범위가 눈에 띄게 넓으면 순위를 낮춘다)을 적용하면 2g ZGC가 될 수 있고, 그때 결정 근거는 CPU가 아니라 흔들림 조항이다.

**가설 판정(§9)**

| 가설 | 판정 | 근거 |
|---|---|---|
| K1 G1은 1g·2g·4g 모두 안정성 통과 | **반증** | 1g·4g가 ④ 메모리 추세에서 실패(경계 근처 — 늘어난 몫이 힙 안인지 밖인지는 원인 미상) |
| K2 G1에서 메모리를 늘리면 p99가 낮아진다 | **반증** | p99 1g 4.14 [3.87–4.90] · 2g 4.32 [3.99–4.62] · 4g 3.87 [3.64–4.55] — 범위가 모두 겹쳐 2차에서는 개선을 확인하지 못했다(1차의 '2g G1 p99 −26%'는 1회 값이라 재현되지 않았다) |
| K3 ZGC 2g·4g는 통과하고 정지 최대 < 1ms | **성립** | 0.2 [0.1–0.4]ms |
| K4 ZGC 1g는 할당 멈춤이 생긴다 | **반증** | 3회 모두 0. 다만 메모리 100%·정지 7.8ms로 여유가 없다 |
| K5 ZGC는 같은 메모리의 G1보다 앱 CPU가 높다 | **반증 — 반대** | ZGC 142~145% 대 G1 163~174%(범위 비겹침, −15%). 원인은 추정이다: G1은 잡은 힙을 150~175MB로 작게 유지해 GC를 자주 돌리고(k6 GC 정지 중앙값 2,816~3,254회), ZGC는 힙을 크게 잡아 덜 돈다(ZGC 정지는 한 주기에 여러 번 생기는 짧은 정지라 횟수를 G1과 '몇 번 돌았나'로 직접 비교할 수는 없다 — 347~963회). 일반 지식의 'ZGC가 CPU를 더 쓴다'는 **이 부하(S4c4200 tmpfs)·이 힙 크기·3회**에서는 맞지 않았다 — 다른 부하로 일반화하지 않는다 |
| K6 ZGC의 1초 p99 최대는 G1과 흔들림 안 | **성립** | 같은 메모리끼리 범위가 겹친다(1g 64 대 97 · 2g 47.5 대 73.2 · 4g 107 대 84). 범위 겹침만으로 원인을 가르지는 못한다 — '남은 꼬리는 GC 정지로 설명되지 않는다'는 §6(Full GC 시각 대조)의 관측이고, 이 측정은 그와 모순되지 않는다는 데까지다 |

**결론(규칙 적용 결과 — §8 최종 결정)**: 측정용 앱 기준 = **메모리 2g + 세대형 ZGC**(`-XX:+UseZGC -XX:+ZGenerational`). 1차 기준(1g + G1)보다 **확실히 좋아진 것은 GC 정지(3.5 → 0.2ms)와 앱 CPU(170 → 143%)** — 둘 다 범위 비겹침. 1초 p99 최대는 중앙값이 낮고(96.8 → 47.5ms) 3회 흔들림이 가장 작지만 G1(1g·2g)과 범위가 겹쳐 개선이라고 단정하지 않는다. 대가는 메모리 한도 2배와 실제 메모리 사용 약 3.4배(506 → 평균 1,744 · 최대 1,817MiB — 최대 기준 여유 약 11%)다.

## 부록 A. JDK 21(HotSpot) 수집기 종류 — 일반 지식 요약(측정 뒤 추가 2026-10-15)

> 이 ADR에서 잰 것은 Serial과 G1뿐이다. 나머지 칸은 수집기 설계에서 알려진 일반적 특성이다(이 서버에서 재지 않음).

| 수집기 | 옵션 | 방식 | 멈춤 | 처리량 | CPU·메모리 추가 부담 | 맞는 곳 |
|---|---|---|---|---|---|---|

| Parallel | `-XX:+UseParallelGC` | Serial과 같은 방식을 여러 스레드로 | Serial보다 짧지만 Full GC 때 앱 전체 정지 | **가장 높음** | 적음 | 처리량이 중요하고 정지는 견딜 수 있는 배치 |
