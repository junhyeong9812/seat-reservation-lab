# ADR-011: 측정 환경 꼬리 지연의 원인 — 주기 튐 · 큰 힙 ZGC 튐 · 장시간 안정성

- 상태: **결정**(2026-10-17). ① 26초 주기 튐의 원인 = **k6 PC의 다른 컨테이너(text-es — Elasticsearch)가 약 24초마다 기동 실패를 되풀이한 것**(없애기 실험으로 강하게 지지 — **되돌리기는 하지 않아 명세 §2의 '확정'에는 못 미친다**, §10 ① · 측정 대상 밖의 오염) · ② 4g ZGC 추가 튐은 **오염이 없으면 재현되지 않음**(T4 기각 — 전제 소실, ADR-010의 관측은 ①의 오염과 함께 나타남) · ③ 2g ZGC는 30분에서 **안정**(T5 성립) · 새로 찾은 것: 30분 측정 후반의 서버형 튐 = **앱 안 대조 C의 바퀴**(켜고 끄기로 확정 — ADR-009가 고른 C의 규모 한계). §1~§5는 측정 전에 고정했다(8fddcba9 · 측정 전 정정 6b2ef3de·3af80c99·ddfbe6c3). §6 이후는 측정 뒤에 썼다.
- 명세: `docs/plans/2026-10-16/adr-011-tail-latency/requirement-spec.md` · 기록·읽기 전용 분석 원문: 같은 폴더 `log.md`
- 선행: **ADR-010**(측정용 앱 기준 2g + 세대형 ZGC · §8.1이 넘긴 것)
- 후행: ADR-013(홀드 만료) · ADR-018(오픈 폭주) 등 꼬리 지연을 다루는 모든 측정 — 이 ADR이 정한 측정 조건(부하 생성기 버전·측정기)으로 잰다.

## 1. 문제

ADR-010 측정에서 GC 정지로 설명되지 않는 꼬리가 남았다.

1. **약 26초 간격 튐**: 램프 밖에서 1초 단위 최대 응답이 50~150ms로 튀는 초가 회차당 7~20개 있었다. 수집기(Serial·G1·ZGC)와 무관했다.
2. **4g ZGC의 추가 튐**: 4g ZGC는 1초 p99 최대가 2g보다 나빴다(107 [71–292] 대 47.5 [45–55]ms). 주기 없는 튐이 더해졌다.
3. **장시간 미확인**: 회차가 7분(램프 1분 + 6분)뿐이라 2g ZGC가 메모리를 한도의 최대 89%까지 쓰는 상태로 오래 버티는지 모른다.

꼬리 지연을 다룰 다음 ADR들(홀드 만료·오픈 폭주) 전에 원인을 가려야 한다. 측정 장치 쪽 원인이면 조건 비교가 엉뚱한 차이를 잴 수 있다.

## 2. 읽기 전용 분석으로 좁힌 것 (측정 전 — 원문 `log.md` '읽기 전용 분석')

- **시점**: 26초 주기 튐은 **k6 v2.3.0 회차 24회 전부**에 있고 **v2.2.0 회차 20회에는 없다**. 둘 사이에 PC 재부팅(2026-10-15 12:43 — 커널 7.0.0-34 → 38, k6 v2.2.0(go1.26.5) → v2.3.0(go1.26.8), 패키지 약 120개 갱신)이 있었다. 같은 날 앱 조건(control 계열 → default)과 하네스도 바뀌어 이 자료만으로는 서로 갈라지지 않는다.
- **지연의 모양**: 서버가 실제로 멈춘 초(Serial Full GC)는 늦어진 시간이 전부 '서버 응답 대기'(k6 `http_req_waiting`)에 있다. 26초 주기 초는 클라이언트 안 구간(연결 대기 `blocked`·보내기 `sending`·받기 `receiving`)이 30~57ms(중앙값)로 크다 — 142바이트 요청을 보내는 데 수십 ms가 걸린 셈이라 서버·네트워크보다 **k6 프로세스가 잠깐 멈춘 모양**에 가깝다.
- **서버 신호와 불일치**: safepoint·DB 대기·잠금·autovacuum·checkpoint·대조 바퀴·디스크·하네스 표본 수집기와의 시각 일치가 우연 수준이다(배수 0.5~1.07). 26초 근처 주기의 수집기·예약 작업도 없다.
- **4g ZGC 추가 튐**은 '서버 응답 대기' 쪽 모양이 많다 — 서버 쪽 원인(첫 접근 페이지 폴트 후보 — ADR-010 §10)과 모순되지 않는다.

이것들은 **후보**다. 원인 확정은 아래 켜고 끄는 실험으로 한다(명세 §2 — 원인을 없애면 튐이 사라지고 되돌리면 돌아와야 확정).

## 3. 실험

모든 실험은 측정용 앱 기준(**2g + 세대형 ZGC**, 앱 기본값 조건 default)·S4c4200(고정 도착률 4,200건/s) tmpfs·L4. 같은 캠페인 안에서 조건을 번갈아(ABAB) 잰다.

**측정기 3곳(모든 회차)**: 주 부하 k6와 함께, 상태를 바꾸지 않는 `GET /actuator`(actuator 링크 목록 — 200, DB를 거치지 않음 — 앱 웹 서버·JVM만)를 초당 50건 부르는 저율 측정기를 두 곳에 더 띄운다. (측정 전 정정 2026-10-16: 처음 정한 `/actuator/health/ping`은 이 앱에서 404 — 서버 스모크 실측, `/actuator/health`는 DB 검사를 부른다.) 측정기 바이너리 = k6 v2.2.0(공식 빌드 — sha256 기록·대조).

| 측정기 | 어디서 | 무엇을 가르나 |
|---|---|---|
| 주 k6 | PC | (지금까지의 측정) |
| PC 측정기 | PC — 주 k6와 다른 프로세스 | 주 k6만 튀면 **k6 프로세스 안**, PC 측정기도 같이 튀면 **PC 전체**(커널·CPU 스케줄) |
| 서버 측정기 | 서버 — seatlab compose 안 컨테이너, 앱에 직접 | 서버 측정기까지 튀면 **서버** |

**E1 — 부하 생성기 버전**: 주 k6 {v2.2.0, v2.3.0, v2.3.0 + Go GC 기록(`GODEBUG=gctrace=1` — PC 시각으로 남긴다)} × 3회(9회, 조건 순서 번갈아). (측정 전 정정 2026-10-16: 처음엔 두 버전 모두 Go GC 기록을 켜기로 했으나, 기록을 켠 스모크(v2.3.0)에서 느린 초가 72개로 늘고(ADR-010 같은 조건 9~11개) 26초 성분이 사라졌으며 느린 초 70/72가 긴 Go GC와 겹쳤다 — **기록 자체가 주 k6를 흔든 정황**. 그래서 버전 비교(T1·T2)는 기록 없는 두 조건으로, Go GC 대조(T3)는 기록을 켠 셋째 조건으로 나눈다.)

**E2 — 큰 힙 ZGC 첫 접근 비용**: 4g ZGC × {없음 · 초기 힙 = 최대(`-XX:InitialRAMPercentage=75`) · 초기 힙 = 최대 + 미리 건드림(`+ -XX:+AlwaysPreTouch`)} × 3회(9회, 조건 순서 번갈아). (측정 전 정정 2026-10-16 — `AlwaysPreTouch`는 기동 때 잡힌 힙만 건드린다: 4g 컨테이너에서 초기 힙이 64MB라 `AlwaysPreTouch`만으로는 힙의 2%만 건드린다(로컬 실측 `-Xlog:gc+init` — Initial Capacity 64M, `InitialRAMPercentage=75`면 3,072M). 초기 힙 효과와 미리 건드림 효과를 가르려고 중간 조건을 둔다.) k6 버전은 E1 결과로 26초 튐이 없는 쪽을 쓴다(둘 다 튀면 v2.2.0).

**E3 — 장시간**: 2g ZGC × 30분 이상 × 2회. 시드를 늘린다(4,200건/s × 1,800초 ≈ 756만 건 → 회차 800 × 1만 석). k6 버전은 E1 결과대로.

## 4. 가설 (측정 전 고정)

| # | 가설 | 틀렸다고 판정할 관측 |
|---|------|------------------|
| T1 | 26초 주기 튐은 **k6 v2.3.0에서만** 나온다(v2.2.0 회차에는 없다) — Go GC 기록 없는 두 조건으로 판정 | v2.2.0 3회 중 하나라도 26초 성분 유의 / v2.3.0 3회 중 하나라도 없음. 26초 성분 = '10ms 넘는 요청 수'(log1p) 1초 계열 주기도의 24~31초 대역 최대, 귀무 = **AR(4) 스펙트럼 대리 계열 1000개**(진폭·위상 모두 무작위 — 고정 시드), p ≤ 0.05면 유의. (측정 전 정정: 무작위 재배열 귀무는 자기상관 계열에서 거짓 양성이 크다 — AR(1) φ=0.5에서 13/40. AR 귀무는 기존 v2.2.0 20회(Full GC 초 가림) 0/20 · v2.3.0 24회 23/24 · AR(1) 합성 4.5~4.8%로 확인) |

Go GC 사건 = gctrace 바퀴 중 STW(a+c) ≥ 5ms 또는 wall(a+b+c) ≥ 100ms, 구간 = [줄 시각 − wall, 줄 시각](줄은 GC가 끝난 시각). 겹침·우연 비율·최대 배수·판정 불가는 T2와 같다. (측정 전 정정: 모든 바퀴를 세면 4,200건/s에서 GC가 약 1.2초마다라 우연 비율 1.0 — 가설이 참이어도 기각만 나온다. 임계값은 스모크 gctrace의 분포로 최대 배수가 2를 넘게 정했다.) **기록 조건의 느린 초 모양이 기록 없는 v2.3.0과 다르면(26초 성분 소실 등) T3는 '기록이 측정을 바꿈'으로 판정 불가** |

## 5. 받아들이는 한계 (측정 전)

1. 측정기를 더하면 부하가 조금 늘어난다(초당 50건 × 2 — 주 부하의 2.4%). 측정기 요청은 DB를 거치지 않는다. 측정기 프로세스(PC)가 주 k6와 CPU를 나눠 쓰는 영향은 v2.3.0(기록 없음)의 26초 성분이 ADR-010(측정기 없음)처럼 남는지로 본다.
6. Go GC 기록은 주 k6를 흔들 수 있다(스모크 정황) — 그래서 T3는 따로 둔 조건에서만 보고, 그 조건은 T1·T2에 쓰지 않는다.
2. k6 버전 비교는 PC 재부팅 뒤 상태(커널 등)에서 한다 — v2.2.0에서도 튀면 'k6 버전'이 아니라 'PC 상태'가 원인 후보가 되고, 커널을 되돌리는 실험은 이 ADR 범위 밖이다(사용자 결정 필요).
3. k6 요청 기록 시각은 정수 초다 — 시각 대조는 ±1초.
4. 장시간(E3)은 2회뿐이고 셀 하나다.
5. 서버 측정기 컨테이너용 이미지를 서버에 하나 내려받는다(seatlab compose 프로젝트 안에서만 쓰고 회차 끝에 내린다).

### 6.1 측정 도중 찾은 오염 — k6 PC의 text-es

E1이 끝난 뒤(2026-10-16 20:00) k6 PC(노트북 — HP Victus 16 · 24스레드)를 읽기 전용으로 점검했다. **다른 프로젝트의 Elasticsearch 컨테이너 `text-es`(compose `text-server` · 재시작 정책 unless-stopped)가 PC 재부팅 뒤(10-15 — 재부팅 기록 12:43·12:56 두 번, §2의 12:43은 첫 번째 · text-es 기동 실패 반복은 12:56 부팅 뒤부터) 약 24초마다 기동에 실패하고 다시 뜨기를 되풀이하고 있었다.**

- 재시작 횟수 4,635 ≈ 재부팅 뒤 31시간 ÷ 약 24초. 기동 간격 실측 23.4~27.9초.
- 기동할 때마다 JVM이 `AlwaysPreTouch`로 약 9GB를 건드리고 CPU를 400% 넘게 썼다.
- 실패 원인: 바인드 경로(`~/markCloud/squatting-project/text-server` 아래)가 compose 파일 없이 빈 root 소유 폴더로 남아 있었다. 재부팅 때 Docker가 없는 바인드 경로를 root로 새로 만들어, ES가 데이터 경로 잠금을 얻지 못했다.
- 재부팅 시각·주기·'PC 전체' 영향(T2의 PC 측정기 동반 튐)이 모두 맞았다. 사용자 결정으로 20:06:51에 컨테이너를 지웠다(이미지는 그대로).

그래서 E1·E2는 text-es가 켜진 상태(E1 9회 · E2 7회)와 꺼진 상태(E1 재측정 9회 · E2 재측정 9회)로 나뉜다.

- 18회 모두 안정성 4항목 ○ · 앱 메모리 최대 ÷ 한도 85.8~91.7%.

### 6.4 E3 — 장시간 30분 (`20261017-adr011-soak-c5117f4b` → `20261017-adr011-soakrc-52cde2a9`)

**첫 시도(`soak`, default 조건 2회 계획)**: 회차 6개(끝까지 돈 5 + 도중에 멈춘 1)가 모두 같은 사유로 `re-measure`됐다 — 회차 800 × 1만 석(800만 행) + 30분 선점이 DB tmpfs 6g를 채워, **k6가 끝난 약 25초 뒤** 끝 정합성 검사 쿼리의 임시 파일이 `No space left on device`로 실패했다. 부하 구간(k6 창)은 오류 전에 끝났으므로 꼬리 지표는 쓸 수 있다(정합성 판정 없음 · 안정성·메모리 요약은 rep1만). 하네스에 `--pg-tmpfs-size <GiB>`(지정 안 하면 6g · DB 메모리 8g 그대로)를 더하고 12g(DB 14g)로 다시 쟀다.

**새 관측**: 6회 모두 느린 초가 12~15개(합 81)였고, 그중 약 76개가 **k6 시작 약 17~20분 뒤에 몰렸다**(앞쪽 5개 — 2.4·8.9·13.3·16.7분 등). 거의 전부 서버형(`waiting` 중앙 57~71ms · 클라이언트 구간 0.1ms) · 최대 135~206ms · 26초 성분 없음 · ZGC 정지 최대 0.05ms · 할당 정지 0 — JVM이 아니다.

- 읽기 전용 분석(워커): 후반 느린 초 76개 중 72개가 **앱 안 대조 C(`CounterReconciler`)의 바퀴 진행 중**이었다(우연 기대 23.2 · ×3.1 · 6/6 회차). 바퀴는 `scheduleWithFixedDelay` 60초 + 바퀴 시간(후반 14~27초)이라 약 80초 주기다. 바퀴 일은 `seat_hold` 행 수에 비례하고(매 바퀴 전체 훑기 — 쌍 395만 → 526만에 바퀴 14.0 → 20.6초), 약 460만 쌍에서 행 없음 갈래의 청크당 시간이 약 12 → 15.3ms로 끊기며 병렬 쿼리 대기가 처음 나타났다. 대조 중 DB 컨테이너 CPU는 한도 400% 중 338~384%였다.
- 기각한 후보: 체크포인트(×0.92) · autovacuum(×0.73) · DB 메모리·tmpfs(부하 중 4.1/8GiB) · JVM · 호스트 CPU 포화.

**켜고 끄기(`soakrc` — task 07)**: C만 다르게 1회씩, 끔 → 켬 순서.

| 조건 | 대조 바퀴 | 느린 초 | 서버형 | 바퀴 안 느린 초 | 1초 p99 최대 | 마지막 5분 p99 | 정합성 | 안정성 4항목 | 앱 메모리 최대 ÷ 한도 |
|---|---|---|---|---|---|---|---|---|---|
| noc(`--cond A --cleanup schedule` = default − C) | 0 | **1** | 1 | — | 50.6ms | 1.33ms | 위반 0 | ○ | 1,874MiB · 91.5% |
| c(default) | 28(마지막 766만 쌍) | **12** | 10 | 9/12(기대 2.7 · ×3.4) | 97.6ms | 1.49ms | 위반 0 | ○ | 1,894MiB · 92.5% |

- C를 끄면 후반 튐이 1개로 줄고, 켜면 12개로 돌아온다. 앞선 default 6회(켬 — 12~15) → noc(끔) → c(켬)가 '있음 → 없앰 → 되돌림'이다 — **후반 서버형 튐 = C의 바퀴로 확정**(명세 §2). 앞선 6회는 tmpfs 6g·DB 8g로 조건이 달라 모양 비교로만 쓴다.
- c의 C 바퀴는 400만 쌍 이상에서 14.7~25.5초였다(마지막 766만 쌍 25.4초). 마지막 5분 p99는 noc 1.33 대 c 1.49ms(+12%)지만 1회씩이라 판정하지 않는다.
- 두 회차 모두 약 19.7분(정상 구간 약 1,180초)에 느린 초가 하나씩 있다(최대 응답 noc 94.2 · c 167.2ms). noc는 체크포인트 끝(1,183초)과 겹친다 — C가 없는 회차라 **체크포인트 경계가 별도 후보**다(켜고 끄기 없음). c는 다음 체크포인트 시작(1,180.7초)과 C 바퀴(#20)가 함께 걸쳐 있어 원인을 가를 수 없다(위 '바퀴 안 9/12'에 이 초도 들어 있다). 같은 부하라 WAL 양이 같아 같은 시점에 체크포인트가 온다.
- 끝 정합성 쿼리 뒤 tmpfs 남은 공간 8.8GB(12g 중) — 12g면 충분하다.

## 8. 결정

1. **26초 주기 튐은 측정 대상 밖의 오염으로 본다**(되돌리기 없음 — §10 ①). 하네스·앱·k6 버전은 바꾸지 않는다. 대신 **측정 전 k6 PC 점검**을 측정 조건으로 둔다: 캠페인 시작 전 `docker ps`(재시작 중·재시작 횟수가 늘어나는 컨테이너가 없는지) · 부하 평균(load average) · 다른 실험 프로세스를 확인하고 log에 1행 남긴다. 하네스 자동 점검(PC 쪽 컨테이너 재시작 횟수를 회차 앞뒤로 기록·대조)은 후보로 넘긴다(§9).
2. **측정기 두 곳(PC·서버 `GET /actuator` 50건/s)은 꼬리를 다루는 측정에서 계속 켠다.** 이번 원인을 '주 k6 밖·PC 전체'로 좁힌 것이 측정기였다(비용 = 주 부하의 2.4%). 주 k6는 공식 v2.2.0 바이너리(sha256 대조)로 고정한다 — 버전은 무관했지만 E2·E3를 이것으로 쟀다.
3. **4g ZGC의 '추가 튐'은 거둬들인다** — 오염이 없으면 2g와 범위가 겹친다(오염이 있을 때 더 나빴던 이유는 미확인 — §6.3). `AlwaysPreTouch`·초기 힙 = 최대는 기준에 넣지 않는다(줄일 튐이 없었고 메모리만 +10%p).
4. **2g ZGC 기준(ADR-010)은 30분에서도 유지된다.** 장시간 측정은 `--seed-schedules 800 --pg-tmpfs-size 12`로 잰다 — tmpfs 6g는 800만 행 시드 + 30분에서 끝 정합성 검사가 넘친다.
5. **C(앱 안 대조)는 쌓인 행 수에 비례해 비용이 커진다 — ADR-009가 고른 C의 규모 한계다.** 7분 회차(ADR-009 §7.7 — p99 +2.2%)에서는 보이지 않았고, 약 400~460만 쌍을 넘는 30분 측정에서 바퀴가 14~26초(마지막 766만 쌍 25.4초)로 길어지고, 그동안 DB CPU 사용률이 높았으며(338~384% / 400%), 1초 p99 최대가 50.6 → 97.6ms로 올랐다(1회씩). 이후 측정에서:
   - **15분이 넘거나 홀드 행이 수백만인 측정**은 C 바퀴가 꼬리에 섞인다는 것을 전제로 읽는다. 카운터가 주제가 아닌 측정이면 대조 바퀴 시각을 함께 기록·대조한다(`drift-db.json` reconcile_runs — 이미 남는다).
   - C를 고치는 것은 이 ADR 범위가 아니다 — 대처 후보는 §9.
6. **ADR-010 1차·2차 결과의 꼬리 지표는 오염된 것으로 본다.** 1차(10-15 13:48~)·2차(10-15 18:58~) 모두 PC 재부팅(12:56) 뒤, text-es가 기동 실패를 되풀이하던 동안에 쟀다. 1초 p99 최대·느린 초 수는 text-es 튐을 담고 있다(원인 판정의 한계는 §10 ①). ADR-010의 결정(2g + 세대형 ZGC)은 GC 정지(0.2ms — 범위 비겹침)·앱 CPU(143 대 168% — 범위 비겹침)·안정성 4항목이 받치고, 이 셋은 꼬리 지표가 아니다. 다만 §10 기준 고르기 규칙의 첫 단계('1초 p99 최대가 가장 좋은 것과 범위가 겹치는 것')는 오염된 지표를 썼다 — 그 단계를 다시 재지는 않았다(§9). 이 ADR의 꺼짐 측정에서 2g ZGC의 1초 p99 최대는 4.6~23.0ms(E1 재측정 9회)였다.

## 9. 넘기는 것

- **C의 규모 한계 대처**(새 ADR 후보 — 근거 §6.4). 대조 중 DB CPU 사용률이 높았다(338~384% / 400%) — 병목이 DB CPU인지 앱 풀 대기인지는 아래 1로 가른다. 후보를 작은 것부터:
  1. **F(별도 대조 앱)를 30분으로 재기** — 하네스에 이미 있다(`--cond A+F`). ADR-009 디스크 측정에서 F는 자기 커넥션 풀이라 바퀴 최대 약 4초(C는 앱 풀 대기 포함 94초 — §7.7)였다. 이번 tmpfs 30분에서 C 바퀴를 늘린 것이 풀 대기인지 DB CPU인지는 가르지 않았다 — F로 가른다.
  2. **증분 대조** — 매 바퀴 전체 훑기 대신 최근 바뀐 쌍만 짧은 주기로 대조하고, 전체 훑기는 드문 안전망으로 남긴다(바뀌지 않은 쌍의 어긋남 — DB 직접 수정·정리 작업 — 은 증분이 못 본다). 바뀐 쌍을 아는 방법(앱 메모리 집합 · `seat_hold.id` 기준점 · 쿼터 행 `updated_at`)과 커밋 순서·창 겹침은 설계 때 정한다.
  3. **읽기 복제본에서 탐지** — 탐지 쿼리를 복제본으로, 복구(`PairRepair` — 원본에서 잠근 뒤 다시 셈)만 원본으로. 복제 지연으로 생기는 오탐은 기존 다시 세기가 거른다. 주의: 복제본의 긴 쿼리와 원본 VACUUM의 충돌(`hot_standby_feedback`를 켜면 원본이 부푼다) · 복제본은 원본과 다른 CPU에 있어야 부하가 나뉜다(서버 2대 필요).
  4. **메시지(Kafka 등) · CDC로 바뀐 쌍 전달** — 앱 재시작·여러 앱·앱 밖 DB 변경까지 담는다. 이중 쓰기 문제(아웃박스 또는 CDC)와 인프라 비용이 크다 — 1~3의 측정으로 필요가 보일 때.
- **체크포인트 경계 튐**(30분 측정 약 19.7분 · noc 최대 응답 94.2ms — c의 같은 초는 C 바퀴와 겹쳐 가를 수 없음) — 후보. 켜고 끄기(체크포인트 간격·`max_wal_size` 변경)는 하지 않았다.
- **ADR-010 기준 고르기 첫 단계 재확인** — 오염 없는 상태에서 1g·2g × G1·ZGC 1초 p99 최대를 다시 잴지(결정은 GC 정지·CPU가 받쳐 유지 — 사용자 판단).
- **측정 전 PC 점검 자동화** — PC 쪽 `docker ps` 재시작 횟수·부하 평균을 회차 앞뒤로 기록·대조하는 하네스 손잡이.

## 10. 한계 (측정 뒤)

1. **text-es의 '되돌리기'는 하지 않았다 — 명세 §2의 '확정'에 못 미친다.** 근거는 '끄면 사라짐'(E1 9/9 · E2 9/9) + 끈 시점 앞뒤 대조(E2 rep3) + 기동 주기 일치(실측 기동 간격 23.4~27.9초 대 26초 성분 최대 주기 25.85~28.35초 — 켜짐 16회 `tail.json`, ADR-010 자료 24회는 25.2~30.4초 — §2 분석) + PC 측정기 동반 튐이다. 켜짐·꺼짐 캠페인이 시간 순서로 나뉘어 그사이 다른 변화는 배제되지 않는다. 확정이 필요하면 같은 증상을 일부러 재현하는 실험(예: PC에서 약 24초마다 CPU·메모리를 크게 쓰는 프로세스를 띄움)을 따로 한다.
2. **soakrc는 조건마다 1회 · 끔 → 켬 순서 고정이다**(리뷰 HT-17). 켬 쪽은 앞선 default 6회가 같은 모양(12~15)이라 기준선이 되고, 끔 → 켬이 '없앰 → 되돌림'이 된다. 그 6회는 tmpfs 6g·DB 8g이고 끝 정합성 검사가 실패한 회차라, 기준선은 모양 비교로만 쓴다. 순서 효과(먼저 돈 회차의 서버 상태)는 가르지 않았다. noc는 C가 꺼져 어긋남이 생기면 끝 정합성 검사에 걸릴 수 있었으나 위반 0이었다(이 부하는 어긋남을 넣지 않는다).
3. C 바퀴가 DB를 채우는 기전(병렬 쿼리 계획 전환 이유 · CPU 스로틀 — `nr_throttled` 미수집)은 확인하지 않았다.
4. E2 켜짐 캠페인(`20261016-adr011-pretouch-088f722a`)은 text-es 켜짐·꺼짐과 사용자의 다른 실험(로컬 postgres 부하)이 섞여 판정에 쓰지 않았다.
5. 모든 결과는 S4c4200 tmpfs 한 부하 · .164 한 서버 · 이 노트북 한 PC에서다.
