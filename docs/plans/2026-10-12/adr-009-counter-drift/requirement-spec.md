## 0. 요구사항 원문 (인터뷰 기록)

- 원문: "이 역할만 하는 애플리케이션을 별도로 분리하고 DB 자체에는 조회만 … 파티셔닝으로 가져와서 블록단위 비교 … 아니면 순수 DB에서 처리 … 방법들을 리스트업해서 다 비교" · "진행하자" · "공연 시작 시간으로 진행하자"
- Q/A (2026-10-12):
  - 범위 = **카운터 어긋남 먼저**. 지금 만료 방식(좌석에 HELD 저장 + 배치 sweep)은 그대로 둔다. Q3 만료 방식 비교는 다음 ADR로 넘긴다.
  - 번호 = **새 ADR-009(카운터 어긋남 탐지·격리·복구)**를 만들고, 기존 ADR-009~014는 010~015로 옮긴다.
  - 구현·비교 후보 = **A 쌍 단위 견딤 · B DB 트리거 · C DB 안 청크 대조 · F 별도 대조 앱**
  - 함께 넣을 것 = **기동 시 검사(fail-fast) · 쿼터 행 정리**
  - 쿼터 행 정리 = **둘 다 비교**: ① 회차 시작 후 회차 단위 삭제 ② cnt = 0 행 정리
  - 회차 시작 후 선점 = **거절 추가**. 판매 마감 = **공연 시작 시각(`starts_at`)**
  - 어긋남 만드는 법 = **부하 중 DB 직접 조작**(쿼터 행 삭제 · cnt 줄이기 · cnt 늘리기)
  - 복구 정책(C·F) = **자동 복구 + 기록**. 다시 세어 맞으면 청크 사이 시점 차이로 생긴 오탐으로 보고 고치지 않는다.
  - 측정 = **디스크 + tmpfs 둘 다**
  - 결정 기준 = **기본 안**(§5)
  - 브랜치 = **PR #7(ADR-007·008)이 병합된 뒤 main에서**. 그 전까지는 명세·설계만 한다.
- 메인이 실코드에서 확인한 사실(명세 근거):
  - 만료 배치는 `@Transactional` 하나로 만료된 홀드 전체를 다시 조회한다(`ExpireHoldsService.kt:20-27`). 감소는 `decrementCounters`가 쌍마다 `UPDATE … SET cnt = cnt - n`이고, 행이 없으면 `check(updated == 1)`이 실패한다(`UserLimitStrategies.kt:213-224`). 음수는 `CHECK (cnt >= 0)`(`V5__user_hold_quota.sql:6`)에 걸린다. → 어긋난 쌍 하나가 매 틱 배치 전체를 롤백한다.
  - **회차 시작 시각을 읽는 코드가 없다.** `ProductSchedule.startsAt`(`ProductSchedule.kt:14`)은 저장만 되고, 선점·확정 어디에서도 검사하지 않는다. ADR-000에도 판매 기간 정의가 없다(설계 누락 — 사용자 확인 2026-10-12).
  - 부하 시드의 회차 시작 시각은 `2026-12-31 19:00+09`(`LoadtestDataService.kt:50-52,80`)이고, 테스트 픽스처는 지금 + 1~2일(`IntegrationTest.kt:55` · `V6BackfillMigrationTest.kt:41`)이다. → 마감 규칙을 넣어도 지금 하네스·테스트는 영향이 없다. **단 2026-12-31 19:00 이후에는 모든 부하 하네스가 거절된다**(시드 시각을 바꿔야 함 — 이 작업에서 기록만).
  - `V6FlywayUpgradeTest.kt:51`은 회차를 `now()`로 넣는다(SQL 직접 삽입이라 선점 API를 거치지 않으면 영향 없음 — 구현 때 확인).
  - 에러 코드는 7개다(`ErrorCode.kt:3-11`). 새 코드를 추가하면 공개 계약이 바뀐다.

## 1. 목표·대상 (필수)

`seat-reservation-lab`에서 매수 카운터(`user_hold_quota.cnt`)가 실제 값(`seat_hold` 행 + CONFIRMED 예약)과 어긋났을 때를 다룬다.

1. **어긋남 처리 후보 4개 구현**(모두 설정으로 켜고 끈다. 기본값은 비교 뒤 결정한다):
   - **A 쌍 단위 견딤**: 만료 배치에서 감소가 실패한 쌍(행 없음·음수)만 그 자리에서 실제 값으로 다시 세어 덮어쓰고, 나머지 쌍의 만료는 계속 진행한다. 고친 쌍은 로그·지표·기록 테이블에 남긴다.
   - **B DB 트리거**: 홀드·예약 행이 바뀔 때 DB가 같은 트랜잭션에서 cnt를 고친다. 앱의 증감과 중복되지 않게 별도 매수 방식(또는 모드)으로 둔다. 한도 판정 방식은 설계 선검증에서 정한다.
   - **C DB 안 청크 대조**: 회차 단위로(또는 (회차, 사용자) 키 범위로) 짧은 대조 쿼리를 반복한다. 어긋난 쌍은 자동 복구하고 기록한다.
   - **F 별도 대조 앱**: C와 같은 대조·복구를 앱과 분리된 프로세스로 돌린다(같은 jar의 다른 프로필, .164의 별도 컨테이너).
2. **판매 마감**: 회차의 `starts_at`이 지나면 선점을 거절한다. 새 에러 코드(가칭 `SCHEDULE_CLOSED`)를 쓴다.
3. **쿼터 행 정리 2방식 구현·비교**: ① 마감 후 회차 단위 삭제 ② cnt = 0 행 정리.
4. **기동 시 검사**: counter 계열인데 쿼터 테이블이 없으면 기동할 때 실패시킨다.
5. **측정**: 후보별 효과(주입한 어긋남 탐지·복구, 만료 정지 여부)와 비용(처리량·p99·WAL)을 잰다.
6. **기록**: 새 ADR-009 결정, 번호 이동(009~014 → 010~015), ADR-000 정정 메모(판매 기간 미정의 → ADR-009에서 추가).

## 2. 경계·불변식 (필수)

- **복구 불변식**: 복구는 주 DB에서 그 쌍의 쿼터 행을 `FOR UPDATE`로 잠근 뒤, 같은 트랜잭션에서 실제 값을 세어 덮어쓴다. 복구가 끝나면 그 쌍은 cnt = 실제 값이다. 복구는 홀드·예약 행을 바꾸지 않는다. 쿼터 테이블만 쓴다.
- **무음 금지**: 고친 쌍, 건너뛴 쌍, 오탐으로 판정한 쌍은 모두 기록(로그 + 지표 + 기록 테이블)에 남는다. A가 쌍을 고치고 계속 진행할 때도 "조용히 넘김"이 되면 안 된다.
- **A의 범위**: A는 실패한 쌍만 다룬다. 나머지 쌍의 만료 결과(좌석 AVAILABLE 전환, 감소)는 지금과 같다. 한 쌍이 실패해 배치 전체가 롤백되는 일은 없어야 한다(전역 만료 정지 0).
- **대조 오탐 처리**: 청크로 읽는 사이에 쓰기가 계속되므로, 대조에서 어긋나 보인 쌍은 잠금 후 다시 세어 맞으면 고치지 않는다(오탐으로 기록).
- **판매 마감**: `now >= starts_at`이면 선점을 거절한다. 시각의 출처는 지금 선점 경로가 쓰는 앱 `Clock`이다. **확정은 막지 않는다** — 시작 전에 잡은 홀드의 결제 결과는 반영한다. 에러 판정 순서는 마감 → 좌석 → 매수 순이다(팔 수 없는 회차는 좌석·매수 판정 전에 거절).
- **쿼터 행 정리 안전 조건**:
  - ① 회차 단위 삭제: 마감 뒤에만 지우고, **그 회차에 `seat_hold` 행이 하나도 없을 때만** 지운다. 남은 홀드가 만료될 때 감소할 행이 있어야 하기 때문이다.
  - ② cnt = 0 정리: 동시에 진행 중인 upsert가 같은 행을 1로 올리는 중이면 지우지 않는다(행 잠금 뒤 다시 확인).
- **기본값 외 동작 불변**: 후보를 끈 설정은 지금과 같다(ADR-008 기본값의 동작·응답 그대로). 마감은 기본으로 켠다(도메인 규칙).
- **서버(.164) 경계**: `~/labs/seat-reservation-lab` · compose project seatlab · 포트 8101/15432(+ F 대조 앱 포트 1개 추가 — 설계에서 정함). sudo 없음. tmpfs는 ADR-007 방식 그대로.

## 5. 검증 방법 (필수)

- **테스트**(blind 테스트 워커 — 구현 diff를 보지 않고 이 명세에서 출발):
  - 어긋남 세 갈래(행 없음 · cnt 작음(음수 경로·조용한 경로) · cnt 큼) × 후보 A·B·C·F:
    - A는 전역 정지 0, 실패 쌍 복구·기록, 나머지 쌍 정상 만료.
    - C·F는 주입 쌍 100% 복구·기록, 주입 안 한 쌍 변경 0.
    - B는 트리거 경로에서 어긋남이 생기지 않고(앱 증감 없이 cnt = 실제), DB를 직접 조작한 어긋남은 C·F와 조합할 때만 복구되는지 기록.
  - 대조 오탐: 대조 도중 쓰기가 들어와 어긋나 보였다가 다시 세면 맞는 쌍은 고치지 않는다.
  - 판매 마감: `starts_at` 직전 성공 · 이후 `SCHEDULE_CLOSED` · 마감된 회차의 확정은 성공 · 에러 순서(마감 → 좌석 → 매수).
  - 쿼터 행 정리: ① 홀드가 남은 회차는 지우지 않음 ② 진행 중 upsert와 겹치면 지우지 않음 · 둘 다 정리 뒤 `v_counter_mismatch` 0.
  - 기동 검사: 쿼터 테이블 없음 + counter 계열 → 기동 실패 · none → 기동.
  - 기존 테스트 전체 green.
- **부하 측정**(새 `k6/ADR-009` 하네스 — ADR-008 하네스 기반):
  - **비용**: 조건 {대조군(후보 끔), A, B, C, F} × 셀 {S4c4200(고정 도착률 4,200건/s) — 디스크·tmpfs, S2(사용자 100명 × 각자 좌석 10개 동시 — 같은 사용자 동시 요청 셀) — 디스크, S3-a20(입장→선점→확정 실제 흐름, 이탈 20%) — 디스크} × 3회. C·F는 부하 중 대조 주기를 켠 상태로 잰다.
  - **효과**: 어긋남 주입 셀 — S3-a20 부하 중(만료가 일어나는 셀) 정해진 시각에 쿼터 행 삭제·cnt 줄이기·cnt 늘리기를 정해진 수만큼 주입. 조건 {대조군, A, C, F, B + C} × 3회.
  - 지표: 주입 쌍 탐지·복구 수와 걸린 시간 · 오탐 수 · 만료 정지(틱 롤백 수, 끝에 남은 만료 HELD 좌석) · 처리량·p99 · WAL · 대조 쿼리 시간·횟수 · 판정기 위반 0.
- **결정 기준(기본 안, 사용자 2026-10-12)**:
  - ① 주입한 어긋남에서 만료 전역 정지 0
  - ② 주입한 쌍 100% 탐지·복구(조용한 누락 0) + 주입 안 한 쌍의 오탐 복구 0
  - ③ 비용: S4c4200 처리량·p99, S2 p99, S3-a20 WAL을 대조군과 비교. 허용선은 측정을 본 뒤 사용자와 함께 정한다.
- **리뷰**: stakes 높음 → 설계 선검증(복구 불변식·트리거·마감·정리 안전 조건) + 듀얼 리뷰 루프(≤3) + blind 테스트 워커. 결과 문서(ADR-009)는 듀얼 1패스.

## 8. load-bearing 가정 (1~2개)

1. **쌍 단위 복구(쿼터 행 `FOR UPDATE` → 실제 값 집계 → 덮어쓰기)가 동시 선점·만료와 경합해도 복구 직후 그 쌍의 cnt = 실제 값이다** — counter-upsert-precheck는 홀드를 만들 때 같은 쿼터 행을 잡기 때문. 착수 직후 동시성 테스트로 실증한다.
2. **F(별도 프로세스)와 C(앱 안)는 DB 읽기 부하가 같고, 차이는 앱 프로세스 자원 간섭뿐이다** — 측정에서 대조 쿼리 시간과 앱 CPU를 따로 기록해 확인한다.

## 10. 재합의 (2026-10-12, 설계 선검증 뒤 — 사용자 답변)

설계 선검증(Opus)과 codex 교차 검증에서 나온 명세 충돌·누락에 대한 사용자 결정. 위 본문보다 이 절이 우선한다.

- **마감 회차의 카운터**(codex C1·C3): 마감된 회차는 카운터를 쓰지 않는다. 대조(C·F)와 판정기 `v_counter_mismatch`에서 제외하고, 제외한 회차·쌍 수는 기록에 남긴다. 남은 홀드의 만료 감소 실패는 A가 맡는다. 정리 ①은 그 회차의 홀드가 0이 되면 확정 예약이 있는 쌍까지 회차 단위로 모두 지운다(§2 '정리 안전 조건 ①'을 이 문장으로 바꾼다).
- **정리 ①과 마감 직전 선점의 경합**(codex C2): 회차 행 잠금으로 직렬화한다. 선점은 마감 판정 때 회차 행을 `FOR SHARE`로 읽고, 정리는 회차 행을 `FOR UPDATE`로 잡은 뒤 홀드 0을 다시 확인한다. 선점당 공유 잠금 비용을 측정에 넣는다.
- **마감 비용 분리**(D2): 마감을 끄는 설정 키를 두고, 대조군을 마감 끔 상태로 S4c4200(고정 도착률 4,200건/s) 디스크 3회 더 잰다.
- **정리 2방식 비교**(D6): 마감 임박 전용 셀을 더한다. S3-a20(입장→선점→확정 실제 흐름, 이탈 20%)과 같은 흐름이고, 시드 회차 `starts_at` = 부하 시작 + 10분이다. ①·② 각 3회.
- **B 설계**(D3): 한도 판정은 앱에서 한다(트리거 거절은 억울한 좌석을 되살림). 트리거는 엄격하게 둔다(행 없음·음수 → 오류, 0으로 자르지 않음). B 방식에서만 만료가 쿼터 행을 먼저 잠근다(확정↔만료 교착 실측 회피). 카운터 기여가 바뀌지 않는 UPDATE는 건너뛴다(codex B1).
- **기동 시 검사 범위**(D4): 쿼터 테이블을 쓰는 방식 전부(counter 계열 + quota 계열). 함께 확인: 트리거 ⇔ B, 후보와 매수 방식 조합, 대조 앱 프로필이면 만료 스케줄러 끔. `IndexMigrationTest`(인덱스 없는 기동)에 `limit-strategy=none`을 명시한다(기존 테스트 수정 1곳).
- **C 커넥션**(D8): 앱 풀을 공유한다. 하네스의 '요청당 빌림 1.0' 판정은 대조가 빌린 횟수를 빼고 계산한다.
- **오탐 테스트**(D1): 탐지와 잠금 사이에 테스트 전용 이음새(훅)를 둔다. 운영 설정에서는 비어 있다.
- **측정 시간**: 약 19시간(설계 실측 기반 16.1시간 + 마감 끔 세트 약 0.5시간 + 마감 임박 셀 약 2.2시간). §9 task 06의 예상 12~15시간을 이 값으로 바꾼다.
- **범위 밖으로 기록**(메인 발견, codex E2와 같은 지점): 확정(`findByHoldsId`)과 만료(`findDistinctByHoldsExpiresAtLessThanEqual`)는 둘 다 좌석 행을 잠그지 않는다. 엔티티에 `version`도 매핑되어 있지 않다. 그래서 만료 경계에서 같은 홀드를 두고 확정과 만료가 겹치면, 확정 예약은 있는데 좌석이 AVAILABLE인 상태가 될 수 있다(설계 실험 B2 끝 상태). 이건 B 이전부터 있던 위험이므로 ADR-013(확정 원자성)로 넘긴다. B의 선잠금은 교착만 해결하고 이 정합 문제는 해결하지 않는다고 ADR-009에 적는다.
- **문구 정정**(D15): §2 '복구는 쿼터 테이블만 쓴다' → 쿼터 테이블 + 기록 테이블만 쓴다.

## 11. 재합의 2 (2026-10-12, 설계 v2 뒤 — 사용자 답변)

- 마감 판정 잠금 = **회차 행 `FOR SHARE`**. 마감 끔 대조 세트와 비교해 처리량이 10% 넘게 떨어지면 다시 정한다(R1).
- 청크 대조 = **두 갈래**(① 쿼터 행을 키 순서로 읽고 쌍마다 실제 값 탐색 ② 쿼터 행이 없는 쌍은 홀드·예약 쪽에서 찾기). 첫 설계(회차·사용자 범위 한 문장)는 162만 쌍에서 한 바퀴 155초로 기각했다(R2).
- 대조 주기 = 비용·효과 셀 모두 **60초**(R3).
- 측정 조건 갱신(리뷰 루프 1 — 사용자 'C·F 켜면 A 필수', counter-trigger 예외): 비용·효과 셀의 C·F 조건은 **A+C · A+F**다(F는 업무 앱에 `external-reconciler=true` + A). B+C는 A 없이 돈다(트리거가 마감 회차를 건너뜀). B 단독·B+C에서 열린 회차 행 없음 주입 시 복구 전까지의 틱 실패는 B의 결과로 판정한다(합격 기준 ①의 B 예외로 기록).
- 구현 합격 항목에 더한다(codex 재점검 N1~N3): 행 없음 쌍 SQL 두 갈래 모두 열린 회차만 보기 + 예약 쪽 갈래 실측 · 마감 판정 순서(마감 → 좌석 → 매수)를 모든 좌석 전략·매수 방식의 실제 호출 경로에서 통합 테스트로 보장 · 하네스는 부하 대상 회차가 전부 판정에서 빠지면 미판정(실패)으로 표시.

## 12. 결정·적용 범위 (2026-10-14, 본측정 뒤 — 사용자 답변)

- 기본값: **A(`counter-drift.expiry-repair`) 켬 + C(`counter-drift.reconcile.enabled`) 켬 · 정리 ① `cleanup.mode: schedule`** · B는 기본 아님(선택지로 유지) · F는 기본 아님.
- 비용 허용선: tmpfs 기준 선점 p99·처리량이 대조군 대비 10% 이내(A·C·F·마감 통과, B 초과). 디스크 값은 저장 경로 한계(ADR-007)와 함께 참고.
- 적용은 ADR-009 안에서(task 07a): 기본값 3개 변경(설정·코드) · ADR-001~009 하네스와 기본값을 가정한 테스트에 '끔' 명시(측정 의미 보존 — ADR-008 방식) · 기본값 테스트 · 서버 스모크(기본값 기동 S2·S3e 1회씩).

## 13. 재합의 3 (2026-10-14, 결과 문서 리뷰·원인 분석 뒤 — 사용자 답변)

- 발견: 대조 조건(A+C·A+F)만 k6 시작 전 첫 대조 바퀴를 약 30초 더 기다렸다(하네스 `wait_reconcile_run`). 그 결과 k6 시작이 DB autovacuum 시점과 다르게 겹쳐, tmpfs의 control·A·B에만 k6 26~36초 '램프 붕괴'(p99 최대 약 4.2초)가 났다. A·control·B 대 A+C·A+F의 비용 비교(H4·H5)는 교란으로 무효. 정합 결과(H1~H3·H8)와 같은 시작 방식끼리의 비교(B 대 control — H6, 마감 켬 대 끔 — H7)는 유효.
- 결정: **교란을 고치고 비용 셀을 다시 잰다.**
  - 하네스: 모든 조건이 k6 전에 같은 대기를 거친다(대조 조건과 같은 길이 — 또는 시드 직후 ANALYZE로 시작 상태를 같게). 앱 JVM에 GC 로그(`-Xlog:gc`)를 켠다(짧은 벽의 원인 확인용).
  - 재측정: control · A · A+C · A+F × {S4c4200 디스크, S4c4200 tmpfs, S2, S3-a20} × 3회 = 48회(약 9~10시간). 효과 셀(S3e)·정리 셀(S3c)·B·control-noclose는 다시 재지 않는다.
  - 판정은 새 캠페인의 같은 하네스 회차끼리만 한다(옛 캠페인과 섞지 않음).
