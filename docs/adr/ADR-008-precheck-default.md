## 1. 문제

ADR-007 §8은 매수 제어 기본을 advisory-try에서 counter-upsert-precheck로 바꾸기로 정했지만, 코드에는 적용하지 않았다. 코드 기본값은 지금도 **`none`**이다(`application.yml:36` · `SeatHoldProperties.kt:14`). ADR-005가 advisory-try를 기준으로 정했지만, 그 적용은 제대로 확인할 때까지 일부러 미뤄 두었기 때문이다(ADR-006·007이 그 확인 과정이었다). 그래서 결정으로는 advisory-try → counter-upsert-precheck이고, 코드에서 실제로 바뀌는 값은 **none → counter-upsert-precheck**다.

전환에는 걸리는 점이 셋 있다.

1. **기존 데이터**: counter 계열은 `user_hold_quota.cnt`가 실제 값과 같다는 전제로 동작한다. none 시절에 만든 홀드·예약은 카운터에 들어 있지 않다.
2. **기동 검사**: 매수 방식이 none이 아니면 좌석 전략은 `PESSIMISTIC_NOWAIT`이어야 한다(`HoldStrategyStartupCheck.kt:36`). 좌석 전략만 바꾸는 기존 하네스(ADR-001~003)와 테스트는 기본값이 바뀌면 기동에 실패한다.
3. **"기본값으로" 쟀다는 증거**: ADR-005~007 하네스는 매수 방식을 앱 설정에 늘 주입한다. 기본값 경로를 재려면 키를 빼고 띄워야 하고, 정말 기본값으로 떴는지를 결과에 남겨야 한다.

## 3. V6 백필

**카운터 정의**: 판정기(`LoadtestDataService.kt` `v_counter_mismatch`)와 같다. `cnt` = 그 (회차, 사용자)의 `seat_hold` **행 전체 수**(만료 전·후 구분 없음) + `reservation` CONFIRMED 수.

- 만료 전·후를 나누지 않는 이유가 있다. 만료 배치는 실제로 지운 홀드 수만큼 카운터를 내린다(`UserLimitStrategies.kt` `decrementCounters`). 그래서 만료가 지났어도 아직 지워지지 않은 홀드는 카운터에 남아 있어야 한다.
- ADR-007 §8과 NEXT N1에는 "유효(만료 전 HELD) 홀드"라고 적혀 있었다. 이 표현은 틀렸고, 이 작업에서 정정했다.

**SQL** (한 트랜잭션 — Flyway 기본):

1. `LOCK TABLE seat_hold, reservation, user_hold_quota IN SHARE ROW EXCLUSIVE MODE` — 실행 중의 쓰기를 막아 ①·②가 같은 사실을 보게 한다.
2. 실제 값이 1 이상인 쌍: `INSERT … ON CONFLICT DO UPDATE SET cnt = EXCLUDED.cnt WHERE cnt <> EXCLUDED.cnt`. 없으면 만들고, 다르면 덮어쓰고, 같으면 쓰지 않는다.
3. 실제 값이 0인데 cnt가 0이 아닌 기존 행: `cnt = 0`. 행은 지우지 않는다. 쿼터 행 락 방식과 counter의 prepare 단계가 트랜잭션 밖에서 만든 행을 그대로 두기 위해서다.

**성질**

| 성질 | 내용 |
|---|---|
| 빈 DB | 아무 행도 만들지 않는다 |
| 멱등 | 두 번째 실행은 아무 행도 쓰지 않는다 |
| 쓰는 테이블 | 쿼터 테이블 하나. 홀드·예약은 바꾸지 않는다 |
| 상한(2) 초과 | none 시절 초과분도 실제 값 그대로 둔다. 다음 요청부터 upsert의 `cnt + 1 <= 최대`가 막는다 |
| 범위 가정 | 쌍당 합이 int 범위 안이어야 한다. 넘으면 `sum()::int`가 오류로 실패한다(값을 조용히 자르지 않음) |

**전환 전제(cutover)**: V6 실행 **전에** 카운터를 유지하지 않는 옛 버전(none 등)의 쓰기 주체를 모두 멈춘다.

- LOCK은 실행 중의 쓰기만 막는다. 커밋 뒤 옛 버전이 쓴 홀드·예약은 카운터에 반영되지 않는다. V6는 한 번만 돈다.
- 적용 직후 `v_counter_mismatch = 0`을 확인한다.
- 이 전제를 어기면 옛 쓰기 주체와 V6의 잠금 순서가 엇갈려 교착이 날 수 있다. 전제를 지키면 생기지 않는다.

- **S2(사용자 100명 × 각자 좌석 10개 동시 — 같은 사용자 동시 요청 셀) p99 1.75배는 원인을 확인하지 못했다.** 1회차(212ms)는 기준 범위(218~279ms)보다 약간 낮고, 2·3회차(434·448ms)는 높다. 실행 순서로는 설명되지 않는다 — 1회차는 캠페인 첫 순서였지만 기준(ADR-007)의 S2(사용자 100명 × 각자 좌석 10개 동시 — 같은 사용자 동시 요청 셀)도 매 회차 S4(도착률 계단, 요청마다 새 사용자·좌석 — 처리량 한계 셀) 셀들 뒤에 돌고 218~279ms였다(`20261009-adr007-ea8b85cc/order.txt`). 디스크 반감도 아니다: 측정 창의 호스트 `nvme1n1`은 거의 쉬었다(회차별 `timeline-host.jsonl` 처음·끝 표본 차이로 메인 계산 — flush 6~7회/s · 쓰기 0.3~0.4MB/s · flush 평균 0.59·0.91·0.63ms, `default-s2/SUMMARY.md` 디스크 flush 평균 0.624 [0.529–0.887]과 맞음). 짧은 버스트 셀의 꼬리 분산으로 기록한다. 판정 항목이 아니고 0.5~2배 안이다.
- **S4(도착률 계단, 요청마다 새 사용자·좌석 — 처리량 한계 셀) 벽은 ADR-007 §7.2의 디스크 반감과 같은 현상으로 본다(수치는 근접 — 일부는 그 범위를 조금 벗어난다).** 벽은 12단계 379초(`wall-check.json` wall_s)이고, 같은 초에 호스트 flush 반감이 났다(호스트 누적 쓰기 3.76GB). docker BlockIO 반감은 386초다(`WDROP.md`). 아래는 ADR-007 §7.2 표와 같은 정의(반감 시각 전 30초 → 뒤 30초)다.

## 6. 받아들이는 한계·넘기는 것

1. **R1(설계 선검증에서 찾은 위험 1번) — 카운터가 어긋나면 만료 배치가 막히거나 조용히 틀린다** → **ADR-009로 넘긴다**(사용자 결정 2026-10-11). `decrementCounters`는 지운 홀드 수만큼 cnt를 내린다(`UserLimitStrategies.kt` `decrementCounters`). 어긋난 카운터는 세 갈래로 드러난다.
   - 쿼터 행이 없으면 `check(updated == 1)`이 실패한다.
   - cnt가 지운 수보다 작으면 결과가 음수가 된다. `CHECK (cnt >= 0)`(V5)에 걸린다.
   - 이 두 경우는 한 틱의 손실로 끝나지 않는다. 만료 배치는 트랜잭션 하나로 만료된 홀드 전체를 다시 조회한다(`ExpireHoldsService.kt` `expire`). 어긋난 쌍의 홀드가 매 틱 다시 잡혀, 사람이 고칠 때까지 모든 틱이 롤백된다. 결과는 전 회차의 만료가 멈추고 좌석이 HELD로 남는 것이다.
   - 덜 어긋난 경우는 조용히 남는다. 행이 있고 cnt가 실제보다 작지만 지운 수 이상이면 감소는 성공한다. 실제보다 큰 경우도 마찬가지다. 앞쪽은 사용자가 한도를 넘게 받고, 뒤쪽은 사용자가 조용히 거절당한다.
   - 그래서 배치 실패로 잡히는 것은 일부일 뿐이다. 나머지는 판정기 `v_counter_mismatch` 같은 별도 점검으로만 보인다. V6와 전환 전제가 정상 경로의 어긋남은 막지만, 어긋났을 때의 탐지·복구는 없다. 코드에 위험 주석 1줄을 남겼다(`UserLimitStrategies.kt` `decrementCounters`).
2. **부하시험 정합 응답이 바뀐다**(P5 — 설계 교차 검증 지적 5번). `LoadtestDataService` consistency 응답은 counter 계열일 때만 `v_counter_mismatch`를 낸다. 기본값이 counter 계열이 됐으므로 방식을 명시하지 않은 앱은 이제 이 필드를 낸다. 부하시험 전용 엔드포인트라 공개 API가 아니다. 기존 하네스(ADR-001~003)는 none을 명시하므로 응답이 같다.
3. **쿼터 테이블이 없는 환경**: 쿼터 테이블이 없으면(예: ADR-002의 `FLYWAY_TARGET=1`) 기본값 앱은 기동 시점에 실패하지 않고 요청 시점에 500을 낸다. 기존 하네스는 none을 명시해 피했다. 기동 시 검사(fail-fast)는 ADR-009에서 쿼터 행 정리와 함께 본다.
4. **H6 남는 틈**(ADR-007 가설 6 — precheck도 동시 경합에서는 좌석 불가 대신 매수 초과를 줄 수 있음, ADR-007 §8 그대로): 동시 경합에서 매수가 찬 사용자는 '좌석 불가' 대신 `HOLD_LIMIT_EXCEEDED`를 받는다. 정합에는 영향이 없다.
5. **쿼터 행 정리**: 만료로 행이 지워지지 않는다 → ADR-009.
